## 0. 이 문서와 사양서 · 아트 정본의 경계

이 문서는 **아직 확인되지 않은 계획**을 든다 — 결정 순서, 게이트, 채워야 할 값의 자리, 트랙별 진행 상태. [아트 정본](../design/spec/art-direction.md)과 [사양서](../design/spec/art-asset-spec.md)는 **실측하거나 코드 · 씬에 넣어 확인된 것**만 든다. 둘을 가르는 이유는 하나다. 시험되지 않은 계획이 확인된 정본에 섞이면 다음 사람이 가설을 사실로 읽고, 그 위에 구현을 세운 뒤에야 틀렸다는 것을 안다.

그래서 값은 트랙이 게이트를 지나 확인한 뒤에만 정본으로 올라가고(§7), 그 전까지는 여기 있다. 여기 적힌 순서 · 구조 · 후보값은 진행하면서 바뀔 수 있고, 바뀌면 이 문서를 고친다. 왜 이렇게 정했는지의 경위와 검토 · 검증 기록은 2026-10-11 · 2026-10-12 세션 문서가 든다.

## 2. 트랙 다섯과 현재 상태

「방향(무엇을 어떻게)」 · 「경로(실제로 만드는 방법)」 · 「검증(해 봤나)」으로 나눠 본다. 상태 열은 트랙이 움직일 때마다 고친다.

| 트랙 | 방향 | 경로 | 검증 | 비어 있는 것 | 상태 |
|---|---|---|---|---|---|
| UI 줄기(§3) | 반쯤 — 기능 범위 · 와이어프레임 · 목업 둘 | 없음 | 목업 둘은 구현됨 | 스타일(색 · 폰트 · 형태), UI 그림을 무엇으로 뽑는지 | 시작 전 — 다음은 1층 세부 계획(§9) |
| 마법 이펙트(§4.1) | 섰음 | 문서상 섰음(AI 정지 텍스처 한 장 + 엔진 파티클) | **없음** — `ParticleSystem2D` 사용 0건 | 텍스처 한 장으로 프리팹 하나 실측 | 시작 전 |
| 사운드(§4.2) | **없음** — 「BGM 1~2 + 효과음 15~20, 로열티 프리 또는 AI 생성」 한 줄 | 없음 | 없음 — 코드 0, 파일 0 | 전부. 톤, 도구, 라이선스, 재생 코드 | 시작 전 |
| 적 로스터(§4.3) | 섰음 | 섰음(ChatGPT 웹 생성 + 후처리 도구) | 후처리 도구는 다른 서비스의 출력으로 검증됨. ChatGPT 웹 생성 자체는 미실측(사양서 §12) | 12종 원전 도상 시트, 3~4종 변별 게이트, 2D 생성의 미실측 둘(세트 일관성 · 배경 제거 도구) | 시작 전 |
| 맵 아트(§4.4) | 섰음(아트 정본 §7) | 반쯤 — 2D 생성이지만 큰 배경은 처음 | 없음 | 규격(사양서에 절이 없다), 큰 배경 한 장의 분할 · 용량 실측 | 시작 전 |

트랙은 서로 독립이라 병행하고(§8.4), 게임 코드 슬라이스와 번갈아 한다. 아트 정본 §9의 작업 순서는 이 다섯 중 UI를 6번 단계로 든다.

## 3. UI 줄기 — 층 구조

### 3.1 층과 순서

UI 스타일은 한 번에 정하지 않고 네 층으로 나눠 아래층부터 정한다. 색과 글자는 같은 층이고 둘 다 컴포넌트보다 앞이다 — 버튼 · 패널 · 카드의 치수는 글자 너비와 팔레트가 정해진 뒤에만 선다. 폰트는 최우선이 아니다. 그보다 앞에 최소 글자 크기와 예산이 있어야 후보를 같은 조건에서 비교할 수 있다.

| 층 | 결정 | 산출물 |
|---|---|---|
| 0 | 컨셉 · 코드 계약(§1) | 끝남 |
| 1 | 선행 조건 — 무드 브리프 · 화면 맞춤 정책 · 배경 띠 · 최소 글자 크기 · 길이 확장 규칙 · 정보 위계 · 입력 방식 · 접근성 | 원칙 · 최소값 · 대표 샘플 검증까지(§3.2) |
| 2 | 예산 → 폰트 체계 → 팔레트 · 간격 단위 | `ui/Theme.ts` 토큰 교체(§3.3) |
| 3 | 형태 언어 · 컴포넌트 치수와 상태 표 · UI 그림 제작 경로 | 요소 목록 표 · 컴포넌트 상태 표(§3.4) |
| 4 | 아이콘 · 화면별 적용과 상태 표 · 모션 정책 | 전체 위계 표 · 화면 × 상태 표(§3.5) |

**1층의 깊이.** 1층은 「다음 층이 결정을 시작하는 데 필요한 최소 입력」까지만 정한다 — 원칙, 최소값, 대표 샘플 검증까지다. 요소 하나하나의 표와 화면별 전체 표는 그것을 쓰는 층(3 · 4층)이 만든다. 그래야 1층이 검증 묶음 하나 · 사용자 검토 하나에 들어가고, 서로 기대는 여덟 결정이 한 문서 안에 남는다. 1층 안의 확정 순서는 무드 브리프 → 화면 맞춤 정책 → 배경 띠 → 최소 글자 크기 → 길이 확장 규칙 → 정보 위계 → 입력 방식 → 접근성이다.

### 3.2 1층 — 선행 조건

| 결정 | 무엇을 정하나 | 정하는 방법 · 통과 조건 | 지금 |
|---|---|---|---|
| **UI 무드 · 레퍼런스 브리프** | UI가 아트 정본 §1의 세 축(한국 민속 공포 · 판타지 영웅 · 현대 서울) 중 어느 축을 주로 나르고 어느 축을 액센트로 두는지를 정하는 한 장. 담는 것 넷 — 가. 나르는 축, 나. 참고 그림 3~5장과 장마다 가져올 것 · 가져오지 않을 것, 다. 쓰지 않을 것 목록, 라. 분위기 형용사 다섯. 쓰지 않을 것 목록이 없으면 지금 목업 둘의 무채색 범용 패널이 그대로 스타일이 된다 | 입력은 아트 정본 §1의 「기억에 남길 한 장면」과 §4.3 현대 액센트. 취향 결정이라 **사용자가 판정**한다 — AI는 후보를 늘어놓고, GPT 2차 검증은 네 항목이 다 있는지만 본다. 2층 전부와 3층 형태 언어 · 4층 아이콘이 이 브리프를 입력으로 쓴다 | 없음 |
| **배경의 명도 · 채도 띠(수치)** | 배경 규약 「어둡고 낮은 채도」를 수치 띠로 박는다. 띠가 있으면 UI 패널색(2층)과 맵 최종 아트(F41)가 서로를 기다리지 않고 각자 띠에 맞춘다 | **첫 결정은 측정 단위**다 — HSL 명도 · 채도인지, Lab L*인지, sRGB 상대 휘도인지에 따라 같은 그림의 값이 달라진다. 출발값은 지금 placeholder 배경과 목업을 재서 얻는다(§8.6) | 규약 있음, 수치 없음 |
| **최소 글자 크기** | 폰트 후보 비교의 공통 조건. 값은 논리 해상도 1280×720 기준 px이고, 문자 체계별로 둔다(한글 · 한자 · 가나는 라틴보다 큰 px가 필요하다). 1층은 출하 언어 둘(라틴 · 키릴 / 한글)만 정하고 한자 · 가나 값은 2층 폰트 조사가 일본어 후보를 볼 때 측정값으로 더한다 | 실제 화소 크기는 `fitHeight`라 창 높이에 따라 변하므로 **화면 맞춤 정책의 최소 지원 뷰포트 높이에서의 화소 크기로 확인한다** — 비율만으로는 같은 16:9에서 높이 360과 1080이 둘 다 통과해 버린다. 판정은 폰트 비교판(§5.4)을 그 배율로 렌더해 **사용자가 실제 모니터에서 읽히는지**로 하고, 판정한 조건(모니터 인치 · 해상도 · 거리)을 값 옆에 적는다. 출발값은 `ui/Theme.ts`의 지금 글자 크기 토큰 중 보조 라벨 · 기본 HUD 라벨 둘이다. 재검토 조건: 2층에서 폰트가 확정되면 그 폰트로 다시 판정한다 | 없음 |
| **다국어 길이 확장 규칙** | 컨테이너가 글자에 맞춰 늘어난다는 원칙과 넘칠 때의 정책. 컴포넌트 치수(3층) 전에 있어야 하고, 나중에 바꾸면 컴포넌트를 다 다시 잰다. 원칙은 셋 — 컨테이너가 글자에 맞춰 늘어난다, HUD는 Widget으로 모서리에 고정된 요소라 늘어날 자리가 없으므로(타이머가 길어지면 HP 바를 밀 수 없다) 「못 늘어남 + 자릿수 · 넘침 모드」로 다룬다, 주 행동 버튼 · 선택지처럼 중요한 요소는 잘림(CLAMP)을 쓰지 않는다 | 합격 기준은 「영어 × 1.3」 자리 확보가 아니라 **가짜 언어 카탈로그 통과**다(§5.2). 1층은 원칙 · 합격 기준 · 대표 요소 셋(고정 폭 버튼 · 늘어나는 패널 · HUD 모서리 고정 라벨)의 탐침까지 하고, 화면 다섯의 요소 목록 표는 3층이 치수를 재면서 만든다. **통과 조건:** Cocos의 Label 넘침 처리와 Layout 컨테이너 크기 조정이 Widget 앵커 배치와 함께 쓰일 때의 제약을 공식 문서로 확인한 뒤에만 확정한다. 확인 전에는 원칙이다 | §5.2에 초안 |
| **입력 방식 — 키보드 조작 범위** | 「레벨업 카드 · 일시정지 · 결과 · 메뉴를 키보드만으로 조작할 수 있게 하는가」. 지금 코드는 키보드 이동 · ESC와 버튼의 마우스 클릭만 다루고 포커스 이동이 없다. 레벨업 카드는 한 런에 여러 번 뜨는 가장 잦은 상호작용이라 양손이 WASD에 있는 채로 매번 마우스로 손을 옮기는지가 여기서 갈린다. **최소 클릭 크기의 원칙**도 이 행이 든다 — 입력 · 접근성의 계약이라서다 | 「예」면 3층 컴포넌트 상태 표에 focused 열이 들어가고(Cocos `Button`에 focused 상태가 없다) 포커스 이동과 마우스가 섞일 때의 규칙은 코드 슬라이스가 된다. 포커스 이동은 나중의 터치와 공존하는 방식으로 정한다. 최소 클릭 크기는 v1 마우스 기준으로 정하되 손가락 기준(통상 44px 안팎)을 참고값으로 함께 적고, 토큰 값은 2층 간격 행이 든다 | 코드는 키보드 + 마우스, 포커스 이동 없음 |
| **화면 맞춤 정책** | 셋 — 허용하는 화면 비율 범위, 잘리면 안 되는 안전 영역, **최소 지원 뷰포트 높이**. 허용 범위는 v1 데스크톱으로 정하되 세로 · 좁은 비율을 원리적으로 막는 구조(가로 폭을 전제한 고정 배치)는 피한다. 길이 확장 규칙 · 최소 글자 크기 · 3층 치수가 이 범위 안에서만 성립한다 | 비율 · 높이 몇 조합으로 지금 HUD를 띄워 보는 화면 탐침(§8.6)으로 정한다. 백로그 F9(UICanvas 정렬 정책 변경 + HUD 스케일링 회귀 검증)는 정책을 구현하는 후속 코드 슬라이스이지 선행 조건이 아니다. 정책이 서면 ops-build §7의 열린 질문(임베드 방식)이 닫힌다(§7) | 사실만 있음(§1 화면) |
| **화면별 정보 위계 표** | **최소 표** — 화면 다섯(HUD · 레벨업 카드 · 일시정지 · 결과 · 메뉴)마다 여섯 열: 화면 / 1순위 요소와 역할 / 2순위 있음 / 3순위 있음 / 숫자 강조 여부 / 필요한 크기 단계 수. 2층이 폰트 역할과 타입 스케일을 정하는 데 필요한 것이 이 여섯이다 | 1 · 2 · 3순위 전부와 근거를 적는 전체 표는 4층이 채운다. 지금 위계(타이머가 가장 크고 HP는 작은 바)는 레이아웃 슬라이스가 암묵적으로 정한 것이라 검토된 결정이 아니다. 호드 전투 중 시선은 화면 중앙에 묶이므로 HUD는 「흘깃 봐서 읽히는가」로 판정한다 | 없음 |
| **접근성 규칙** | UI 요소를 색만으로 구분하지 않는다는 원칙과 글자 · 배경의 대비 기준. 분류색이 셋이라 색을 못 가리는 플레이어는 색만 다른 아이콘을 구분하지 못한다 | 대비는 WCAG 대비비로 재고 후보값은 본문 4.5:1, 큰 글자 · UI 요소 3:1 — 강제 기준이 아니라 어두운 연출과 부딪히면 값을 내리되 근거를 적는다. 색각 통과 조건: 분류 3색이 1형 · 2형 색각 시뮬레이션에서 구분되거나, 안 되면 4층 아이콘이 형태로 갈라 준다(§8.6). 측정 대상 둘 — 패널 위 글자는 패널색 위에서, 전투 화면 위 HUD 글자는 배경 띠의 가장 밝은 값 위에서 잰다. 못 미치면 외곽선 · 반투명 판이 3층 형태 언어의 결정으로 넘어간다. 예외를 둘 때는 이유와 실측 화면을 함께 적는다 | 없음 |

### 3.3 2층 — 예산 · 폰트 · 팔레트 · 간격

2층 안의 순서는 **예산 → 폰트 → 팔레트 · 간격**이다. 예산이 폰트 선택의 입력이라서다. 결정값은 전부 `ui/Theme.ts`의 토큰(`COLORS` · `FONT` · `SIZES`)을 교체하고, 그 머리 주석도 이 층 구조로 고친다.

| 결정 | 산출물 | 정하는 방법 | 지금 |
|---|---|---|---|
| **UI 성능 · 용량 예산** | 실측할 수 있는 항목 넷 — 폰트 파일 용량, UI와 폰트의 초기 다운로드 용량, 대표 화면에서 UI가 쓰는 프레임 시간, UI 텍스처(아틀라스) 총 용량. 드로 콜은 관찰값으로 적는다 | 대표 화면에서 잰다. 아틀라스 묶음 수와 동시에 뜨는 Label 수는 예산이 아니라 예산을 지킨 구현 결과로 기록한다 — 기기 · 브라우저 · 배칭에 따라 병목이 달라 개수 상한은 성능 계약이 못 된다. 이 자리가 없으면 CJK 폰트를 골라 놓고 빌드에서 용량을 알게 된다. 값이 재어지면 사양서 §8에 절을 만든다(§7) | 없음 |
| **폰트 체계** | 가족 · 굵기 · 역할(본문 · 제목 · 숫자)과 타입 스케일(단계 수 · 비율 · 줄 높이 · 굵기), 폴백 정책 | §5.4. 같은 층의 예산 안에서 고른다. 고른 폰트에 없는 글자가 나오면 Cocos Label이 어떻게 그리는지 공식 문서로 확인한 뒤 폴백 정책을 적는다 | 없음 |
| **UI 팔레트** | **의미색 표** — 색마다 이름 · 토큰명 · 역할 · 글자색인지 배경색인지 · 값 · 쓰는 화면 · 상태 변형(hover · pressed · disabled) · 색 말고 무엇으로 구분되는지 · 대비비(1층 접근성)를 한 줄로 적고, 마지막 열에서 예약된 색(§1)과 부딪히는지 검사한다 | §1의 충돌 셋(HP ↔ 화염, XP ↔ 번개, 승리 ↔ 개별 티어)은 이 표가 푼다 — UI 쪽을 비켜 가는지, 티어색 · 상태바색을 바꾸는지를 행마다 적는다. 중립 패널색은 1층 배경 띠 위에서 읽히는 색으로. **강조색은 하나이고 주 행동 버튼 전용**이다. 포커스 · 선택 표시는 강조색을 그대로 쓰지 않고 「포커스 · 선택」 행을 따로 둔다. **support 분류색도 이 표에서 정한다** — 넷째 색을 비워 두면 나중에 팔레트와 부딪힌다. 값을 코드와 아트 정본 §4.2 · 사양서 §7.2에 반영하는 일은 코드 슬라이스다(§9) | 없음 |
| **간격 · 격자 단위** | 여백을 쌓는 배수 단위와 클릭할 수 있는 최소 크기의 토큰 값 | 최소 크기의 원칙과 손가락 참고값은 1층 입력 방식 행이 들고, 이 행은 그 원칙을 지키는 값을 정한다. HUD 모서리 간격은 값 하나가 아니라 토큰 · 정책으로 두어 나중에 안전 영역(모바일 노치 등)을 더할 수 있게 한다. 단위가 없으면 화면마다 여백이 제각각이 되고, 통일하려면 사용자가 에디터에서 노드를 다시 배치한다 | 없음 |

### 3.4 3층 — 형태 · 치수 · 제작 경로

| 결정 | 산출물 | 정하는 방법 | 지금 |
|---|---|---|---|
| UI 형태 언어 · 컴포넌트 치수 | **요소 목록 표**(화면 다섯의 글자 요소마다 컨테이너 종류 · 늘어나는 방향 · 최대 · 넘침 모드)와 **컴포넌트 상태 표**(버튼 · 카드 · 마법 슬롯 × normal · hover · pressed · disabled, 상태마다 색 · 스프라이트 · 크기 중 무엇이 얼마나 바뀌나) | 글자 너비 · 팔레트 · 간격 단위가 정해진 뒤 버튼 · 패널 · 카드 크기를 잡는다. 목업 둘은 이 층에서 스타일을 입는다. 치수는 보이는 크기와 누르는 영역을 분리할 수 있게 잡고, hover만으로 뜻을 전하는 상태를 두지 않는다. Cocos `Button`의 전환은 NONE · COLOR · SPRITE · SCALE 넷, 상태는 Normal · Pressed · Hover · Disabled 넷이라 결정은 「어느 전환을 쓰고 값은 무엇인가」로 좁혀진다. focused는 엔진에 없어 1층 입력 방식이 「예」일 때만 열을 더하고 그 표시는 코드 슬라이스다 | 레이아웃만 있음 |
| **UI 그림 제작 경로** | 아이콘 · 프레임 · 버튼 그림을 무엇으로 어느 도구에서 만드는가 — AI 생성(ChatGPT 웹 · Gemini), 벡터 도형(코드나 SVG), 9-slice 프레임 텍스처 | 형태 언어가 「그린 프레임」인지 「늘어나는 9-slice」인지에 따라 경로가 갈리므로 형태 언어와 같은 층이고, 4층 아이콘은 이 경로가 선 뒤에만 간다. 후보 비교는 §6.2의 조사 행으로 미리 걸고, **첫 게이트**로 형태 언어를 닫기 전에 대표 부품 하나(기본 버튼 또는 레벨업 카드)를 9-slice · 벡터 · AI 래스터 후보로 실제로 만들어 본다 — 조사표만으로는 「만들 수 있는가」가 안 드러난다 | 없음 |

### 3.5 4층 — 아이콘 · 화면별 적용 · 모션

| 결정 | 산출물 | 정하는 방법 | 지금 |
|---|---|---|---|
| 아이콘 · 화면별 적용 | 마법 아이콘, 카드, 결과 화면 폴리시, 타이틀 · 메뉴 · 설정 · 도감 · 일시정지, 인트로(J5) · 위치 카드(F57). **전체 위계 표**(1층 최소 표를 받아 1 · 2 · 3순위 전부와 근거)와 **화면 × 상태 표**(화면 다섯 × 기본 · 빈 · 부분 · 오류 · 성공 · 비활성) | 타이틀 · 인트로 · 도감은 플레이어가 여유 있게 보는 자리라 무드 브리프가 가장 강하게 적용되는 화면이고, HUD는 전투 중 흘깃 읽기가 우선이라 컨셉을 약하게 싣는다. 인트로 · 위치 카드는 아직 없는 화면이라 J5 · F57이 만들 때 행을 더한다. 화면 × 상태 표는 칸마다 플레이어가 보는 것과 그 칸을 정하는 주인을 적고, 없는 상태는 「해당 없음」과 이유 한 줄로 둔다. 로딩 상태는 지금 코드에 없어 J3(메뉴 · 세이브)가 로딩을 만들 때 채운다. 결과 화면 헤더의 첫 읽기는 「승리 · 패배」여야 하는데 지금 카탈로그에 패배라는 단어가 없다 — 문자열 추가는 코드 슬라이스(§9) | 없음 |
| 모션 정책 | 화면 전환 · 페이드 · 카드 등장 같은 움직임의 시간 상한과 모션을 쓰는 자리 | 입력은 감정 전환 아홉 — 타이틀 진입 · 전투 시작 · 레벨업 진입 · 카드 선택 · 전투 복귀 · 사망 · 승리 · 결과 공개 · 재시작. 피격 · 회복 · 웨이브 전환은 전투 피드백의 몫이라 정책 밖이다. 기준값은 `ui/DeathSequence.ts`의 사망 페이드 길이이고 다른 전환은 이 값에 상대적으로 정한다. **요구 하나:** 승리와 사망의 연출은 달라야 한다 — 지금 승리는 연출 없이 결과 씬에 바로 간다. 구현은 백로그 F28의 몫 | 없음 |

### 3.6 배경과 UI의 순서

배경 **규약**이 먼저고 배경 **그림**은 나중이다. 1층의 띠를 수치로 정하면 UI 색(2층)은 그 띠 위에서 읽히는 색으로 고르고, 최종 맵 아트(F41)는 그 띠 안에서 그린다. 둘이 서로를 기다리지 않는다.

## 4. 독립 트랙 — 접점과 첫 게이트

아래 트랙은 0층 또는 1층의 배경 띠에만 걸리고 UI 줄기와는 독립이라 병행할 수 있다.

### 4.1 마법 이펙트

접점은 분류색(0층)만이다. 제작 방법(AI 정지 텍스처 한 장 + 엔진 내장 `ParticleSystem2D`)은 아트 정본 §3.1이 「미검증 계획」으로 들고 있고 코드 · 프리팹에 사용이 0건이다. 그래서 첫 게이트는 **텍스처 한 장으로 프리팹 하나를 만들어 실측**하는 것이다.

- **측정 환경:** 에디터 미리보기가 아니라 웹 빌드를 브라우저에서(ops-build §4의 임베드 조건).
- **통과 판정의 수:** 웹 빌드에서 실측한 **종료 웨이브의 동시 적 peak**에서 판정한다. 예상값은 사양서 §8.1이 씬 값으로 계산해 든다. 아트 정본 §3.1이 목표로 든 수백 마리 밀도에서의 값도 같이 기록한다 — 출하 기준 통과 여부와 스트레스 결과(참고)를 한 표에 가른다.
- **통과 기준**(적 몇 마리 × 이펙트 몇 개에서 프레임 시간 얼마)은 세부 계획의 첫 결정이다.
- **기록 항목:** PC · GPU · 브라우저, 해상도 · 창 크기, 실측 동시 적 peak, 동시 이펙트 · 파티클 수, 평균 프레임 시간, 1% low(가장 느린 1% 구간), 출하 기준 통과 여부, 스트레스 결과. fps 대신 프레임 시간으로 적는다.
- **통과하면** 분류 3색 × 발사 · 명중 · 폭발 · CC 텍스처로 간다(support 색이 정해지면 더한다). 아트 정본 §3.1의 「미검증」을 지운다(§7).
- **실패하면** 대체 경로는 프레임 시트 스프라이트(정지 텍스처 여러 장을 순서대로 보여 주는 방식)이고, 아트 정본 §3.1 · 사양서 §7.2를 그 트랙이 다시 쓴다(§7).

### 4.2 사운드

접점은 컨셉(0층)만이다. 코드 0 · 파일 0이라 전부 비어 있다. 순서는 다음과 같다.

1. **톤 결정** — 1층 무드 브리프와 같은 틀(나르는 축 · 참고 · 쓰지 않을 것 · 형용사)로 사운드 트랙 세부 계획이 쓰고 사용자가 판정한다.
2. **도구 · 라이선스 조사**(§6) — Gemini · CC0 라이브러리 · AI 음악 서비스. 결과는 라이선스 정본 §2의 행으로 간다(§7).
3. **재생 쪽 확인**(§6.3) — 브라우저 자동 재생 제한, 포맷 호환, 오디오 용량 예산.
4. 샘플 몇 개로 시험.
5. 재생 코드 — `pnpm wf` 슬라이스.

백로그 J6이 이 트랙의 항목이다.

### 4.3 적 로스터

접점은 배경 띠(1층)와의 대비다. 12종 원전 도상 시트(사양서 §11) → 3~4종을 실제 표시 크기로 여러 마리 늘어놓고 구분되는지 본다(변별 게이트, 검수 기준은 사양서 §4.4) → 나머지 생산. 2D 생성의 미실측 둘(세트 일관성, 배경 제거 도구 선정)을 이 트랙의 첫 슬라이스가 닫고 사양서 §6.5 · §12를 고친다(§7). 백로그 F60이 이 트랙의 항목이다.

### 4.4 맵 아트

접점은 배경 띠(1층) 그대로다. 띠가 서면 사양서에 맵 규격 절부터 쓴다(§7) → 큰 배경 한 장을 ChatGPT 웹에서 뽑아 분할 · 용량을 잰다 → 생산. 충돌 제약(볼록 박스 크기 상한, 방 · 복도 금지)을 알고 그린다. 백로그 F41이 이 트랙의 항목이다.

## 5. 다국어가 UI에 거는 조건

### 5.1 언어 후보와 묶음

출하는 한 · 영이지만 나중에 더할 언어 후보로 15개를 둔다 — 한국어 · 영어 · 중국어 간체 · 번체 · 일본어 · 프랑스어 · 독일어 · 스페인어 · 이탈리아어 · 폴란드어 · 포르투갈어 둘 · 러시아어 · 우크라이나어 · 튀르키예어. 아랍어 · 태국어는 후보가 아니다 — 글자 모양이 앞뒤에 따라 바뀌는 처리와 오른쪽에서 왼쪽 배치가 필요해서다.

| 묶음 | 언어 | 걸리는 것 | 지금 결정 |
|---|---|---|---|
| 1 | 한국어 · 영어 | — | 출하 |
| 2 | 프랑스어 · 독일어 · 스페인어 · 이탈리아어 · 폴란드어 · 포르투갈어 둘 · 러시아어 · 우크라이나어 · 튀르키예어 | 길이 확장이 주 시험 대상. 글리프는 라틴 + 키릴 확장 | 길이 확장 규칙(§5.2)으로 지금부터 대비. 글리프 커버는 열 언어 전부 자동 검사 |
| 3 | 일본어 · 중국어 간체 · 번체 | 폰트 파일 크기, 서브셋, 띄어쓰기 없는 줄바꿈 | 글리프 커버는 셋 전부 자동 검사(번체는 글리프가 달라 따로). 줄바꿈 · 파일 크기 · 라이선스는 대표 언어 일본어로 수동 확인하고 번체 샘플 몇 줄을 더한다 |

요약하면 **길이 확장 규칙은 지금 세우고, 글리프는 1묶음만 지금 고른다.** 묶음 2 · 3의 조사는 두 겹이다 — 글리프 커버는 후보 15개 전부를 자동 검사하고(폰트 파일의 글자표를 언어별 필요 글자 목록과 대조하는 스크립트, §8.6), 파일 크기 · 엔진 지원 · 라이선스와 수동 레이아웃 확인은 대표 언어 셋(독일어 · 러시아어 · 일본어)으로 한다. 그 결과 시간과 공수가 크면 한 · 영만 우선 출하한다.

### 5.2 길이 확장 규칙

같은 뜻이 언어마다 길이가 다르다. 업계 경험칙으로 독일어 · 러시아어 · 프랑스어는 영어보다 30% 안팎 길고, 한 · 중 · 일은 짧은 대신 글자가 커서 줄 높이를 더 먹는다. 이 축은 폰트와 무관하고 컴포넌트 치수(3층) 전에 규칙으로 세운다.

- **컨테이너가 글자에 맞춰 늘어난다.** 버튼 · 패널 폭을 고정값으로 박지 않고 내용 크기 + 여백으로 정하며 최소 · 최대만 둔다.
- **합격 기준은 가짜 언어 시험이다.** 영어 길이 × 1.3은 자리를 잡는 출발값이지 합격 기준이 아니다 — 짧은 라벨은 2배도 흔하다. 모든 문자열을 40% 안팎 늘리고 악센트 글자를 섞은 가짜 언어 카탈로그로 UI를 돌리고, 한두 단어짜리 라벨에는 별도의 가장 긴 경우 문자열을 둔다. 1층은 대표 요소 셋으로 먼저 돌리고 전체는 3층 요소 목록 표가 서면 돌린다.
- **넘칠 때의 정책을 요소마다 미리 정한다.** Cocos Label의 넘침 모드는 넷(NONE · CLAMP 잘림 · SHRINK 축소 · RESIZE_HEIGHT 줄바꿈)이고 말줄임 모드는 없다 — 말줄임을 고르면 코드가 필요하다. 축소는 가독성을 깎으므로 마지막 수단이고, 주 행동 버튼 · 선택지는 잘림을 쓰지 않는다.
- **글자를 그림에 굽지 않는다.** 아이콘 · 버튼 그림에 글자를 넣지 않는다.

Label 넘침 처리와 Layout 컨테이너의 크기 조정 방식은 세부 단계에서 공식 문서로 확인하고 적는다. 그 확인이 1층 규칙의 통과 조건이다(§3.2).

### 5.3 폰트도 레이아웃도 아닌 것 — 아직 적힌 곳이 없는 셋

- **띄어쓰기 없는 줄바꿈** — 일본어 · 중국어(묶음 3)에 걸린다. Cocos Label이 어떻게 줄을 바꾸는지 대표 언어 일본어로 확인한다.
- **복수형** — 치환과 어순은 코드 규약 § 다국어와 `logic/I18nLogic.ts`가 다루지만 복수형 처리는 적힌 곳이 없다. 묶음 2 언어(러시아어 · 폴란드어 등)는 복수형 규칙이 둘 이상이다. 코드 슬라이스(§9).
- **데이터 파일 안의 표시 문자열** — 마법 · 카드는 카탈로그 키로 해석하는데 적만 `resources/data/enemies.json`의 이름이 한국어 고정 문자열이다. 카탈로그 키로 옮기는 일은 코드 슬라이스(§9)이고 J3 도감 전에 한다.

### 5.4 폰트 체계

폰트는 역할로 가른다.

| 역할 | 쓰는 곳 | 우선하는 것 |
|---|---|---|
| UI 본문 | 메뉴 · 설명 · 통계 · 카드 텍스트 | 가독성, 다국어 커버 |
| 제목 · 표시 | 타이틀, 승리 · 패배, 섹션 제목 | 개성. 본문과 같은 가족의 굵은 굵기로 대신할 수도 있다. **대문자에 기대는 효과를 쓰지 않는다** — 한 · 중 · 일에는 대문자가 없어 번역하면 사라진다 |
| 숫자 | 데미지 숫자, 카운터 | 성능, 외곽선 · 그림자 |

데미지 숫자를 비트맵 폰트로 따로 만드는 경우가 흔하지만 미리 정하지 않는다 — 웹 빌드의 Cocos에서 실제로 성능 문제가 있는지 2층 예산을 재면서 본다. 다국어 라벨은 TTF다(§1).

**타입 스케일**은 2층 산출물이다 — 단계 수, 단계 사이 비율, 단계별 줄 높이와 굵기. 입력은 1층 최소 글자 크기(가장 작은 단계의 하한)와 1층 정보 위계 표(한 화면에서 1 · 2 · 3순위를 크기로 가르는 데 몇 단계가 필요한가)다.

**다국어 확장과 파일 크기.** 한 · 영 · 일 · 중을 한 가족으로 덮는 무료 폰트는 있다(Noto Sans CJK 계열, OFL). 대가는 파일 크기다 — 한 굵기 파일이 2층 용량 예산을 넘으면 웹 빌드에서는 쓰는 글자만 추리는 서브셋이 필요하다. 「필수」가 아니라 예산이 정한다. 한 · 영만이면 선택지가 넓고 파일이 가볍다(Pretendard · Noto Sans KR · 나눔 계열, 모두 OFL). 미리 한 · 영으로 좁히지 않는다 — §5.1의 결정 방식을 따른다.

**후보를 고르는 방법.** 후보 3~4개를 최소 글자 크기 조건에서 어두운 배경 띠 위에 나란히 렌더한 비교판(한 페이지 HTML)으로 둘로 줄이고, **최종 둘은 Cocos 에디터에서 실제 Label로 넣어 보고** 사용자가 하나를 정한다 — 출하 렌더는 Cocos라 굵기 · 힌팅이 HTML과 다를 수 있다. 비교 조건은 같은 크기 · 같은 문장(한 · 영 · 숫자 · 가짜 언어 · 카탈로그가 쓰는 기호).

## 6. 생성 도구 · 라이선스 — 조사할 것

아래는 조사 후보이지 결정이 아니다. 판정이 나면 [라이선스 정본](../development/spec/ops-licensing.md) §2의 판정 표에 도구 행으로 적는다(ChatGPT 웹 · VRoid가 같은 형식으로 들어 있다). 판정이 없는 도구는 그 표에 올리지 않는다.

### 6.1 Gemini

사용자가 Gemini Pro 구독을 갖고 있고, 배경 · 음악 · 효과음 생성이 된다고 한다. 지금 확인된 것은 없다. 확인할 것은 다음과 같다.

1. 배경(이미지) · 음악 · 효과음을 각각 어느 모델 · 어느 화면에서 만들어 주는지, 셋 중 안 되는 것이 있는지. 음악 · 효과음이 정식 제품인지 실험 제품인지, 실험 제품이면 그 약관이 상업 이용을 따로 막는지.
2. Pro 구독에서 만든 생성물의 상업 이용 조건과 AI 생성물 신고 의무. 신고 의무의 정본은 라이선스 정본 §6이고, Valve 원문을 같은 확인일에 다시 본다.
3. 출력 형식과 품질 한도 — 이미지 해상도 · 배경 투명 여부, 음악 길이 · 반복 재생 가능 여부, 효과음 길이 · 포맷.
4. 생성 당시의 플랜 · 약관 버전 · 확인일, 해지 뒤 권리, 입력물 학습 조건.

### 6.2 후보와 확인할 것

| 종류 | 후보 | 확인할 것 |
|---|---|---|
| 효과음 | CC0 라이브러리(Kenney 등), 공개 효과음 저장소(CC0 · CC-BY 섞임), 절차 생성 도구(sfxr 계열), AI 생성 서비스 | 상업 이용, 출처 표기 의무, AI 생성물이면 Steam · itch.io 신고 의무, 레트로 톤이 애니 셀 화풍과 맞는지 |
| 음악 | AI 생성 서비스(Suno · Udio 등 — 상업권은 유료 플랜에서만 붙는 경우가 많다), CC 라이브러리(OpenGameArt · 출처 표기형) | 상업권이 어느 플랜에 붙는지, 신고 의무, 반복 재생용 편집 가능 여부 |
| 폰트 | Google Fonts의 OFL 폰트, 국내 무료 폰트(나눔 · Pretendard 등) | OFL 여부, 게임 내장 허용, **서브셋(파일 수정) 허용 여부와 OFL의 Reserved Font Name 조항**, 상호 표기 의무, 카탈로그가 화면에 쓰는 기호의 글리프 보유와 어울림(§8.6 기호 뽑기) |
| UI 그림 | AI 생성(ChatGPT 웹 · Gemini — 아이콘 · 프레임 한 장씩), 런타임 벡터(Cocos `Graphics` 컴포넌트), 제작 도구 벡터(SVG로 그려 PNG로 내보낸 뒤 Sprite — Cocos는 SVG를 직접 읽지 않는다), 9-slice 프레임 텍스처(Sprite의 Sliced 모드) | 같은 화풍으로 아이콘 여러 장이 묶이는지, 투명 배경, 늘어나는 프레임이 되는지(§3.4 첫 게이트) |
| 배경 제거 도구(적 · 맵 · UI 그림 공통) | 사양서 §6.5의 빈 자리. 후보를 원본 출력에 대고 §6.5 수치로 견줘 고른다 | 기본 모델의 상업 조건 — 배경 제거 도구가 기본 모델을 상업 유료 계약이 붙는 것으로 바꾼 실제 사례가 있다(라이선스 정본 §7). 후보마다 이 함정부터 본다 |

### 6.3 사운드 재생 쪽

도구와 별개로 재생 코드 쪽에 확인할 것이 셋이다 — 웹 브라우저는 사용자 입력 전의 자동 재생을 막으므로 BGM을 언제 시작하는지, 브라우저별 포맷 호환(ogg · mp3 · m4a), 오디오 파일의 용량 예산. 용량 값이 정해지면 사양서 §8에 오디오 예산 절을 만든다(§7).

## 8. 진행 방식

### 8.1 착수할 때 현재 상태를 보고하고 확인을 받는다

§2에서 「경로가 섰다」고 적은 항목도 그 트랙에 착수할 때는 먼저 현재 상태를 사용자에게 보고하고 확인을 받은 뒤 진행한다. 보고에 넣는 것은 정본 · 코드 · 백로그가 지금 그 항목에 대해 적고 있는 것과, 실제 코드 · 파일이 그것과 맞는지다. 문서에 적힌 것이 낡았거나 잘못 이해한 채로 적혔을 수 있어서다.

### 8.2 두 단계 검증 — Claude 1차, GPT 2차

결정마다 같은 틀로 적어 GPT에 넘긴다. **결정문 · 근거 · 증거 수준 · 버린 대안과 그 이유 · 우리가 틀릴 수 있는 지점 · 재검토 조건 · 검증 질문.** 증거 수준은 근거가 어디서 왔는지(공식 문서 · 실측 · 코드 · 업계 경험칙 · 취향)이고, 재검토 조건은 어떤 사실이 바뀌면 이 결정을 다시 여는지다. 검증 질문에는 「반대 근거를 하나 적어라」 대신 「이 결정을 뒤집을 조건을 적어라」를 묻는다. 라이선스가 걸린 결정은 「확인한 약관 조항과 확인일」 칸을 더한다. 결정마다 번호와 꼬리표(제안 중 · 확정 · 뒤집힘)를 달되, 꼬리표는 결정 기록(세션 문서 · 세부 계획 · 검증 기록)에만 달고 정본 본문에는 달지 않는다.

**넘기는 단위는 층과 트랙이다.** UI 줄기는 1층 전체 · 2층 전체처럼 같은 층의 결정을 한 묶음으로 넘긴다 — 같은 층의 결정은 서로 기대므로 따로 보면 검증이 안 된다(폰트는 예산 없이 검증할 수 없다). 독립 트랙은 트랙마다 한 묶음이다.

GPT가 반대하면 **최종 결정은 사용자가 한다.** 의견이 갈린 채로 넘어가지 않는다. 확정된 결정은 전부 세션 문서로 옮기고, GPT가 반대했던 결정에는 반대 요지와 사용자가 택한 이유를 함께 적는다. GPT가 답을 주지 못하면 Claude 1차 검토만으로 사용자가 결정하고 기록에 「GPT 미검증」을 남긴다. 취향 결정(무드 브리프 · 톤 · 최소 글자 판정)은 사용자가 직접 판정하고 GPT는 틀만 본다.

### 8.3 문서 분할과 「받은 입력」 절

트랙별 세부 계획은 **문서 하나씩**이다(마법 이펙트 · 사운드 · 적 로스터 · 맵). **UI 줄기만은 개요 하나 + 층별 문서 넷**이다 — 2층 값(예산 · 폰트)은 1층 실측 뒤에만 쓸 수 있어 문서 하나를 한 번에 완성할 수 없고, 층 문서 하나가 §8.2의 검증 묶음 하나와 같다.

층 · 트랙 세부 계획은 **머리에 「앞 슬라이스에서 받은 입력」 절**을 둔다 — 값 / 출처 결정(번호 · 날짜) / 이 값을 쓰는 결정 세 열이면 필요한 입력이 다 왔는지 검사할 수 있다. AI는 세션 사이를 기억하지 않으므로 앞 슬라이스의 결과는 이 절과 재검토 조건, 착수 보고로만 이어진다.

### 8.4 여러 폴더 병행

트랙은 서로 독립이라 조사 · 계획 세션은 작업 폴더를 나눠 병행해도 된다. 폴더를 나누는 방법은 worktree가 낫다 — 저장소 하나를 같이 쓰므로 브랜치 · 커밋이 모든 폴더에서 바로 보이고 fetch · push를 따로 하지 않는다. 새 폴더에서 테스트가 안 도는 문제(백로그 F118 — Cocos가 만들고 git이 무시하는 `game/temp/tsconfig.cocos.json` 파일이 없어서)는 그 폴더의 `game` 폴더를 Cocos로 한 번 열거나 원래 폴더의 파일을 복사하면 풀린다. 백로그 세 파일은 여러 트랙이 함께 고치므로 머지할 때 충돌을 예상한다.

### 8.5 산출물 자리

초안과 GPT 검증 기록은 `docs/temp/` 폴더에 둔다(git 밖이라 폴더마다 따로 있다). 합의된 결정은 세션 문서(`docs/development/sessions/`)로 옮기고, 「지금 어떻게 되어 있나」는 이 문서 · 정본 절 · 백로그에 적는다. 코드가 붙는 트랙(가짜 언어 카탈로그의 로더 · 키 정합 가드 변경, F9, 복수형 처리, 재생 코드)은 `pnpm wf start`로 시작해 테스트 RED 게이트를 지키고, 문서와 실측만인 트랙은 문서 경로로 간다. 트랙 폴더를 지우기 전에 `gpt-review` 기록이 세션 문서에 옮겨졌는지 확인한다.

**시각 목업.** gstack 디자이너는 OpenAI 키가 있어야 그림을 뽑는데 키가 없다. 후보 PNG는 사용자가 ChatGPT 웹이나 Gemini에서 뽑고, AI는 비교판만 띄운다.

### 8.6 보조 도구 후보

결정이 아니라 후보 목록이다. 각 트랙의 세부 계획이 여기서 시작해 필요한 것만 고른다. 전부 30분 안팎의 일이다.

- **가짜 언어 카탈로그 생성 스크립트** — `en.json`을 읽어 문자열을 40% 안팎 늘리고 악센트 글자를 섞은 카탈로그를 만들고, 한두 단어 라벨에는 가장 긴 경우 문자열을 넣는다. 카탈로그를 어디에 두고 어떻게 켜며(`systems/I18n.ts`가 언어를 고정 배열로 든다) 키 정합 가드가 그것을 어떻게 다룰지가 걸리면 코드 슬라이스다.
- **폰트 비교판 HTML** — 후보 3~4개를 최소 글자 크기 · 어두운 배경 띠 위에 나란히 렌더한다(§5.4).
- **글리프 커버 자동 검사 스크립트** — 후보 폰트 파일의 글자표를 언어 15개의 필요 글자 목록과 대조해 빠진 글자를 언어별로 뽑는다. 글자 목록은 한자 쪽이 크다(일본 상용한자 · 중국 통용규범 1급 · 대만 상용국자 같은 표준 목록 중 고른다). `py -3`에 fonttools 패키지가 필요해 설치 전에 확인을 받는다.
- **카탈로그 기호 뽑기** — `ko.json` · `en.json`을 읽어 글자 · 숫자가 아닌 기호 목록을 뽑는다. 폰트 후보 확인과 서브셋 보존 목록, 비교판 표본 문장의 입력이다.
- **배경 띠 실측 스크립트** — 지금 placeholder 배경과 목업의 명도 · 채도 분포를 재서 1층 띠의 출발값을 얻는다.
- **분류색 색각 시뮬레이션 페이지** — 분류 3색과 UI 강조색 후보를 색각 이상 조건으로 바꿔 보여 준다(1층 접근성).
- **화면 탐침** — 비율 · 높이 몇 조합(예: 16:9 · 16:10 · 21:9 × 높이 480 · 720 · 1080)으로 지금 HUD를 띄워 모서리 · 중앙 요소의 간격과 글자 화소 크기를 본다(1층 화면 맞춤).
