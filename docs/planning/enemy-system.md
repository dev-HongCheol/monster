# 적 시스템 디자인 (Enemy System)

> **작성일:** 2026-06-04
> **상태:** 게임 디자인 초안. 구현은 별도 사이클 (enemy-variety 슬라이스부터).
> **범위:** 전체 적 taxonomy를 정의하되, **v1은 추격+접촉 서브셋만 구현**한다. 능동 공격 패턴·텔레그래프·엘리트·보스는 v2 설계-보류(스키마 자리만 확보).
> **관련 문서:**
> - [로드맵 v0.2](roadmap.md) — §7 v1 MVP(적 5종, 추격+충돌만), §8 v2(능동 공격 패턴 도입)
> - [마법 시스템 디자인](magic-system-mage.md) — taxonomy 전체정의 + 일부배선 패턴의 선례
> - [용어 사전 § 9 적 시스템](../development/glossary.md#9-적-시스템-enemy-system) — 이동 알고리즘·스탯 프로필·텔레그래프·스폰 디렉터 등

## 0. 이 문서의 역할

적의 **분류 축**(이동/역할·스탯/공격/변종), **이동 알고리즘**, **역할·스탯 프로필**, **공격 타입**, **텔레그래프**, **위협·시각 언어**, **스폰 구성**, **데이터 스키마**를 게임 디자인 관점에서 확정한다.

마법은 `magic-system-mage.md`라는 설계 토대 위에서 코드 enum(`SpellCategory`/`SpellPattern`/`UpgradeOption`)이 taxonomy를 그대로 반영했고, "전체 정의 → 일부만 배선" 패턴으로 v2 확장 시 갈아엎지 않는다. **적은 지금까지 이 토대가 없었다** (`enemies.json`이 평평한 스탯 6개). 이 문서가 그 토대를 만든다.

> **핵심 원칙:** 설계는 전체(v1+v2), 구현은 v1 서브셋. 데이터 스키마는 v2 공격 패턴이 들어올 자리를 미리 비워둔다(forward-compatible).

---

## 1. 설계 원칙

| 원칙 | 내용 |
|------|------|
| **데이터 주도** | 적 추가 = 데이터 한 블록. 코드 분기 없이 `enemies.json` + 스폰 테이블로 새 적 정의 (로드맵 §9). |
| **v1 = 추격 + 접촉만** | 로드맵 §7 확정: v1 적은 플레이어 단순 추격 + 접촉 대미지뿐. 능동 공격(발사체/돌진/폭발)은 v2 위임(§8). |
| **forward-compatible 스키마** | v2 공격 패턴·텔레그래프·엘리트 필드를 스키마에 미리 정의하되 v1 구현은 무시. 마법 `UpgradeOption` 5종 정의·2종 배선과 동일. |
| **placeholder 시각 언어** | 최종 픽셀 아트는 로드맵 7-9주차 일괄 생성. 지금은 색·크기·플래시 같은 **구분 가능한 임시 규칙**만. 최종 에셋 약속 아님. |
| **단일 컨트롤러 + 데이터** | `EnemyController` 하나가 모든 적 데이터를 읽음. 아키타입별 별도 클래스 만들지 않음 (로드맵 §9). |

## 2. 적 분류 축 (Taxonomy Axes)

적은 **4개의 독립 축**으로 정의한다. 한 적(`enemies.json` 한 항목)은 각 축에서 한 값을 가지며, **적 = 이동 × 역할·스탯 × 공격 × 변종**의 조합이다.

| 축 | 의미 | 질문 | v1 |
|----|------|------|----|
| **이동 알고리즘** (§3) | 플레이어 기준으로 어떻게 경로를 잡는가 | *어떻게 움직이나* | 직진 추격만 |
| **역할·스탯 프로필** (§4) | HP·속도·크기 조합이 만드는 전술 역할 | *얼마나 빠르고 튼튼한가* | ✅ 3종 |
| **공격 타입** (§5) | 어떻게 피해를 주는가 | *어떻게 때리나* | 접촉만 |
| **변종 모디파이어** (§9) | 같은 베이스에 붙는 버프 접두사 | *정예 변형인가* | ❌ v2 |

> **이동과 역할·스탯을 분리한 이유:** v1의 추격/스워머/탱크는 셋 다 "플레이어로 직진"이라 **이동 알고리즘은 동일**하고 HP·속도·크기(=스탯)만 다르다. 즉 이들은 *이동 종류*가 아니라 *역할·스탯 프로필*이다. 진짜로 이동이 다른 것(지그재그·플랭커·돌진)은 v2다. 두 축을 섞으면 v2에서 "빠른 탱크" 같은 조합이 애매해지므로 처음부터 나눈다.
>
> 예: `도깨비 = (이동:직진) × (역할:탱크) × (공격:접촉)`.

---

## 3. 이동 알고리즘 (Movement) — 어떻게 움직이나

플레이어를 기준으로 적이 경로를 잡는 방식. **v1은 직진 추격 하나만.** 코드 경로가 생기는 축이라(새 알고리즘 = 새 코드) 신중히 확장한다.

| 이동 | 동작 | 버전 |
|---|---|---|
| **직진 추격 (Chase)** | 플레이어 위치로 직선 이동 (현재 skeleton) | **v1** |
| 지그재그 (Zigzag) | 좌우로 흔들며 접근 — 조준 방해 | v2 |
| 플랭커 (Flank) | 정면이 아닌 측면·후방으로 우회 — 포위 | v2 |
| 돌진형 (Lunge) | 평소 추격 → 일정 거리에서 짧은 윈드업 후 **미끄러지듯 전방 가속 돌진**, 경로상 대미지 | v2 |

> **돌진형은 cross-cutting이다** — 이동이면서 동시에 능동 공격(§5)이다. 이동 알고리즘으로 분류하되 그 대미지·텔레그래프는 공격 축에서 다룬다.

---

## 4. 역할·스탯 프로필 (Role / Stat Profile) — 얼마나 빠르고 튼튼한가

HP·속도·크기의 조합이 만드는 전술 역할. **v1 다양성의 핵심이 여기서 나온다** (이동은 v1 내내 직진 추격뿐이므로). 실제 수치는 `enemies.json`이 직접 들고, 아래 프로필은 그 수치 패턴에 붙는 라벨이다.

| 프로필 | HP | 속도 | 크기 | 전술 역할 | 버전 |
|---|---|---|---|---|---|
| **표준 (Standard)** | 중 | 중 | 중 | 기본 군집 | **v1** |
| **스워머 (Swarmer)** | 낮음 | 빠름 | 작음 | 다수 포위·압박 | **v1** |
| **탱크 (Tank)** | 높음 | 느림 | 큼 | 벽·우선 처리 강제 | **v1** |

> 프로필 라벨(`role`)은 스폰 테이블 그룹화·도감 표시·placeholder 시각 기본값(§7)에 쓰인다. 실제 밸런스는 라벨이 아니라 개별 적의 HP/속도/반경 수치로 결정한다.

## 5. 공격 타입 (Attack Type) — 어떻게 때리나

| 공격 타입 | 설명 | 텔레그래프 필요 | 버전 |
|---|---|---|---|
| **접촉 (Contact)** | 접촉 거리 내 초당 대미지 (현재 구현) | 불필요 | **v1** |
| 단발 발사체 (Projectile · Single) | 플레이어 방향 1발 발사 | 필요 | v2 |
| 부채꼴 발사체 (Projectile · Fan) | 전방 부채꼴 N발 (예: 3발) | 필요 | v2 |
| 확산 발사체 (Projectile · Spread) | 사방/무작위 다발 (탄막) | 필요 | v2 |
| 돌진 공격 (Lunge) | §3 돌진형의 대미지부 — 윈드업 후 전방 가속, 경로상 대미지 | 필요 (강함) | v2 |
| 사망 폭발 (Death AOE) | 사망 시 주변 폭발 | 사망 모션 | v2 |
| 사망 분열 (Death Split) | 사망 시 소형 적 N마리로 쪼개짐 — 군집 폭증 | 사망 모션 | v2 |
| 소환 (Summoner) | 주기적으로 소형 적 스폰 | 약함 | v2 |

> **사망 폭발·사망 분열은 "사망 행동"이다** — 능동 공격은 아니지만 같은 공격 축에 둔다(피해/위협을 만드는 행동이므로). 사망 분열은 변종 모디파이어(§9)로도 부여될 수 있다.

### 사용자가 든 예시 매핑 (전부 v2)

| 네가 말한 것 | 이 문서의 분류 | 버전 |
|---|---|---|
| "발사체 공격" | 단발 발사체 (Projectile · Single) | v2 |
| "발사체 3개 전방 부채꼴" | 부채꼴 발사체 (Projectile · Fan, count=3) | v2 |
| "공격 시작 후 미끄러지듯 전방 특정 거리 돌진" | 돌진형 이동(§3) + 돌진 공격(§5) | v2 |

> 이 세 가지는 **승인된 로드맵에서 명시적으로 v2**다 (§7 "v1은 추격+충돌만 / 능동 공격 패턴은 v2 위임", §8 "적 투사체 패턴(개수/속도/방향)"). **지금 구현하지 않는다.** 다만 §11 데이터 스키마에 `attack` 블록 자리를 비워둬 v2에서 데이터만 채우면 되도록 한다.

> **재사용 검토(v2):** 부채꼴 발사체는 마법의 `SpellPatternLogic`(directional 부채꼴 엔진)과 기하적으로 동일하다. v2에서 적 발사 로직을 마법 패턴 엔진과 공유할지/분리할지는 그때 결정(Open Item §14).

## 6. 텔레그래프 (Telegraph) — v2 공정성 장치

서바이벌물에서 능동 공격은 **예고 없이 맞으면 불공정**하다. v2 공격 타입의 전제 조건.

| 텔레그래프 방식 | 설명 |
|---|---|
| 윈드업 모션 | 공격 전 적이 멈칫·자세 잡음 (애니메이션) |
| 색 깜빡임 | 공격 직전 적이 빨갛게 점멸 |
| 바닥 마커 | 돌진 경로·폭발 범위를 바닥에 미리 표시 |

> v1엔 능동 공격이 없어 텔레그래프도 불필요. 하지만 데이터 스키마에 `attack.telegraphTime`(초) 자리를 잡아둔다. v2 밸런싱의 핵심 노브가 된다.

## 7. 위협 · 시각 언어 (Threat & Visual Language)

플레이어가 **에셋 없이도 적을 구분하고 위협을 읽을 수 있게** 하는 placeholder 규칙. 최종 픽셀 아트(7-9주차)가 이 자리를 대체한다.

| 신호 | 의미 | v1 |
|---|---|---|
| **색 (tint)** | 역할 프로필 구분 (표준=기본 / 스워머=밝은색 / 탱크=어두운색) | ✅ |
| **크기 (scale)** | HP·위협도 (클수록 위협, 탱크가 큼) | ✅ |
| **피격 플래시 (Hit Flash)** | 명중 시 흰색 점멸 — 타격감 | ✅ |
| **사망 연출** | 팝(스케일 튐) + 페이드아웃 | ✅ |
| 외곽선 / 글로우 | 엘리트·정예 표시 | ❌ v2 |
| 원소 색 | 적 원소 약점·저항 (§12) | ❌ v2+ |

> **색 팔레트는 placeholder다.** 역할 프로필을 구분하는 게 목적이지 최종 색 결정이 아니다. 정확한 색·크기 수치는 구현·밸런싱 단계 Open Item.

## 8. 스폰 구성 (Spawn Composition)

### 8.1 가중 스폰 테이블

웨이브마다 "어떤 적이 어떤 비율로 나오는가"를 **데이터로 정의한 가중 테이블**로 결정한다. 마법 덱의 "가중치 있는 무작위 추첨"과 대칭.

```
웨이브 W에서 스폰할 적 선택:
  스폰 테이블[W] = { chivnyeo: 가중치, kumiho: 가중치, dokkaebi: 가중치, ... }
  가중치 비례 무작위 추출 → enemyId
```

### 8.2 웨이브 게이팅

- 초반 웨이브: 표준 추격 위주, 탱크 가중치 낮음.
- 후반 웨이브: 탱크·스워머 가중치 ↑, (v2) 엘리트 주입.
- 마법의 "등급 게이팅"(후반에 고등급 ↑)과 동일한 난이도 곡선 도구.

### 8.3 v2 확장

- **엘리트 주입:** 특정 웨이브에 변종 모디파이어(§9)가 붙은 적을 섞음.
- **웨이브 테마:** 특정 웨이브를 한 프로필로 도배 (예: "스워머 러시").
- **보스:** 일정 웨이브에 단일 강적. 로드맵상 v2 또는 v1.1.

## 9. 변종 모디파이어 (Elite Modifier) — v2

같은 베이스 적에 **버프 접두사**를 붙여 싸게 다양성을 곱한다. (Diablo 접두사 / 뱀서 엘리트 모델)

| 접두사 | 효과 |
|---|---|
| 빠른 (Swift) | 속도 +% |
| 거대 (Giant) | HP·크기·접촉 대미지 +% |
| 분열 (Splitting) | 사망 시 소형 분열 (§5 사망 분열 부여) |
| 방어 (Armored) | 받는 피해 감소 |

> v1엔 없음. v2에서 `eliteModifiers` 배열로 데이터화. 베이스 5종 × 접두사 4종 = 적은 콘텐츠로 큰 체감 다양성.

## 10. v1 적 종류 (구현 대상 초안)

로드맵 §7은 v1 콘텐츠로 **한국 요괴 5종**(도깨비·처녀귀신·구미호·그슨대·야차)을 든다. 단, **최종 스프라이트는 7-9주차** 작업이므로 v1 구현 시점엔 placeholder(색·크기)로만 존재하고, IP 외형은 아트 단계에서 입힌다.

아래는 **IP ↔ (이동 × 역할) 매핑 초안** (확정 아님 — §14 Open Item):

| 적 (IP) | 이동 | 역할·스탯 | 공격 | placeholder 시각 | v1 |
|---|---|---|---|---|---|
| 처녀귀신 | 직진 추격 | 표준 | 접촉 | 기본색·중간 | ✅ |
| 도깨비 | 직진 추격 | 탱크 | 접촉 | 어두운색·큼 | ✅ |
| 구미호 | 직진 추격 | 스워머 | 접촉 | 밝은색·작음 | ✅ |
| 그슨대 | 직진 추격 | 탱크 변형 | 접촉 | 어두운색·중간 | △ |
| 야차 | (v2: 돌진형) | 표준 | (v2: 돌진) | — | v2 |

> **v1 최소 구현은 역할 3종(표준/스워머/탱크)이면 충분하다** (이동은 직진 추격 고정). 5종을 다 넣을지(같은 역할의 스탯 변형 포함) 3종으로 시작할지는 슬라이스 스코핑에서 결정(§13, §14).

## 11. 데이터 스키마 (forward-compatible)

현재 `IEnemyData`(`GameTypes.ts`)를 확장한다. **v1 필드는 구현, v2 필드는 정의만.**

```jsonc
{
  "id": "dokkaebi",
  "name": "도깨비",

  // --- 기존 (v1, 구현됨) ---
  "maxHp": 300,
  "speed": 80,
  "contactDamagePerSec": 30,
  "collisionRadius": 35,
  "xpDrop": 25,

  // --- 신규 (v1, 이번 설계에서 추가) ---
  "movement": "chase",         // 이동 알고리즘 (§3) — v1은 "chase" 고정
  "role": "tank",              // 역할·스탯 프로필 라벨 (§4) — standard|swarmer|tank
  "tint": "#5a3a8a",           // placeholder 색 (§7)
  "threatScale": 1.4,          // 시각 크기 배율 (§7)

  // --- v2 자리만 (구현 안 함) ---
  "attack": null,              // §5 공격 블록. 예: { "type":"projectile_fan", "count":3,
                               //   "spreadAngleDeg":45, "projectileSpeed":300,
                               //   "telegraphTime":0.5, "lungeDistance":0 }
  "eliteModifiers": []         // §9 변종 접두사 (v2)
}
```

- **`movement`** = enum. v1은 `"chase"` 하나뿐이지만 enum으로 둬서 v2 이동(`zigzag`/`flank`/`lunge`)이 case 추가로 들어온다 (마법 `SpellPattern`과 동형).
- **`role`** = 역할 라벨. 스폰 테이블 그룹화·도감·시각 기본값용. 실제 스탯은 위 HP/속도/반경 숫자가 결정.

**스폰 테이블** — `enemies.json`과 분리한 별도 데이터(`spawn-table.json` 등) 권장:

```jsonc
// 웨이브 구간별 가중치 (정확한 수치는 밸런싱 단계)
[
  { "fromWave": 1, "weights": { "chivnyeo": 70, "kumiho": 30 } },
  { "fromWave": 3, "weights": { "chivnyeo": 50, "kumiho": 30, "dokkaebi": 20 } },
  { "fromWave": 6, "weights": { "chivnyeo": 30, "kumiho": 35, "dokkaebi": 35 } }
]
```

> **`movement`(enum)·`attack`·`eliteModifiers`를 지금 스키마에 넣는 이유:** v2에서 적 이동·공격을 추가할 때 데이터만 채우면 되고, `IEnemyData` 타입·로더·세이브 포맷을 바꾸지 않아도 된다. 마법이 `SpellPattern`을 미리 enum화한 것과 같은 이유.

## 12. 마법 시스템과의 관계

| 항목 | v1 | v2+ |
|---|---|---|
| 적 원소 약점·저항 | 없음 — 모든 적이 모든 마법에 동일 피해 | 적 원소 태그 + 마법 분류별 배율 (선택적) |
| 적 발사체 로직 | 없음 (접촉만) | 마법 `SpellPatternLogic` 공유 vs 적 전용 분리 결정 (§14) |
| 적 → 플레이어 CC | 없음 | 슬로우/넉백 등 (v2+) |

> 적 원소 시스템은 강력하지만 v1 스코프 밖이다. 도입 시 마법 분류(화염/얼음/번개)와 적 원소를 매칭하는 큰 밸런싱 작업이라 v2+로 명시 보류.

## 13. v1 구현 슬라이스 정의 (enemy-variety)

이 설계에서 도출되는 **첫 구현 슬라이스**의 범위. (별도 계획 문서로 확정)

**포함 (구현):**
- `enemies.json`에 역할 3종(표준/스워머/탱크) 이상 정의 + 신규 v1 필드(`movement`/`role`/`tint`/`threatScale`).
- **`SpawnDirectorLogic`** — 가중 스폰 테이블에서 웨이브별 enemyId 선택. **순수 로직 → TDD(RED→GREEN) 대상.**
- `EnemySpawner` — 단일 프리팹 유지, 디렉터가 고른 `enemyId`를 인스턴스에 주입(현재 프리팹 하드코딩 제거).
- `EnemyController` — 데이터에서 `tint`/`threatScale` 적용, `takeDamage` 피격 플래시, 사망 팝/페이드.

**제외 (스키마 자리만, 구현 X):**
- v2 이동(지그재그/플랭커/돌진), 능동 공격(발사체/부채꼴/돌진), 텔레그래프, 변종 모디파이어, 엘리트 주입, 보스, 적 원소.
