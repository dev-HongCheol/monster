## 씬 변경 사항 (확정 — 구현된 코드 기준, 2026-07-25)

`main.scene`을 읽어 확인한 현재 상태다(2026-07-25). **새 노드를 만들지 않는다.**

```
Canvas (레이어 DEFAULT 0x40000000)
 ↳ Player                       ← 자식 없음. 아래 네 컴포넌트가 이 노드에 직접 붙어 있다
     · cc.UITransform           Content Size 50×64, Anchor (0.5, 0.5)
     · cc.Sprite                흰색 255, Size Mode CUSTOM, Trimmed, 브릿지 스프라이트가 물려 있음
     · PlayerController         현재 @property 없음 → 이 슬라이스가 프레임 슬롯을 추가
     · SpellCaster              무변경
 ↳ BulletParent
```

> **계획 §9 감사표의 `Player>Sprite` 표기는 부정확했다.** `Sprite`는 `Player`의 자식 노드가 아니라 `Player` 노드 자신에 붙은 컴포넌트다. 그래서 코드가 `@property`로 받지 않고 `getComponent(Sprite)`로 집는다(같은 노드의 Sprite를 이렇게 집는 것은 `EnemyController.onLoad`의 기존 방식과 같다). 연결을 잊어서 방향 전환이 조용히 죽는 실패 모드가 하나 줄어든다.

바뀌는 값은 둘이다.

| 대상 | 현재 | 바꿀 값 | 왜 |
|------|------|---------|-----|
| `Player > UITransform` Content Size | 50×64 | **72×96 (확정)** | 세로는 계획 §6의 90~96px 결정 중 96, 가로는 플레이스홀더 캔버스 종횡비 0.75를 곱한 값이다(384×512). 가로를 종횡비로 얻어야 하는 이유는 CUSTOM 사이즈모드에서 종횡비가 어긋나면 그림이 눌리거나 늘어나기 때문이다 |
| `player.json` `hurtboxHalfWidth`/`hurtboxHalfHeight` | 18 / 30 | **18 / 44 (확정, 코드에 반영됨)** | 반높이만 올린다. 그림이 64→96px로 커졌으므로 30(=박스 높이 60)을 그대로 두면 박스가 그림의 62%만 덮어 **머리·발 높이 피격이 안 잡힌다.** 44는 박스 높이 88 = 그림의 92%로, 브릿지에서의 비율(94%)을 유지한 값이다. 반너비 18은 그대로 둔다 — 박스 폭 36이 72px 그림의 50%이고 플레이스홀더 인물의 양팔 포함 폭(53%)에 맞는다. **최종 마법사 아트가 오면 그 실루엣의 몸통 코어 기준으로 다시 잡는다**(지팡이·불꽃 오버행은 박스 밖 장식) |

**바꾸지 않는 것:** Anchor (0.5, 0.5) — 네 프레임이 같은 피벗을 공유하는 근거다. `Sprite`의 Size Mode **CUSTOM** — Cocos 3.8 공식 문서상 CUSTOM만 노드 크기를 수동 관리로 두고, TRIMMED·RAW는 노드 크기를 스프라이트 프레임에서 가져온다. 바꾸면 노드가 소스 픽셀(수백 px) 크기로 리사이즈돼 플레이어가 화면을 덮는다. 반대로 CUSTOM이면 프레임을 갈아끼워도 크기가 그대로라, 네 방향이 같은 contentSize로 렌더된다. 노드 Scale (1, 1, 1) — 스케일에 크기를 실으면 리깅 때 같은 노드의 스켈레탈 디스플레이로 이월돼 숨은 재작업이 된다.

## 에셋 — 이번 슬라이스는 플레이스홀더다 (확정, 2026-07-25)

**최종 마법사 4방향 아트는 별도 슬라이스로 분리했다**(계획 §10에 근거 기록). 이 슬라이스에 들어가는 것은 인게임에서 4방향 배선을 실제로 검증하기 위한 **버릴 플레이스홀더** 4장이다.

- 생성 방식은 AI가 아니라 **PIL 코드 드로잉**(`F:\ai\gen_placeholder_4dir.py`)이다. 마법사를 단순 사람으로 바꿔도 시점 문제는 모델 쪽 한계라 그대로 남는 것을 실측으로 확인했고(아래 「최종 아트로 넘긴 제약」), 실테스트에 필요한 것은 예쁜 그림이 아니라 **지금 어느 프레임이 떠 있는지 한눈에 보이는 것**이기 때문이다.
- 파일: `game/assets/art/player/player_4dir_{front,back,left,right}.png`. 각 384×512(종횡비 0.75). 브릿지 `player_mage_bridge.png`는 지우지 않고 남겨 둔다(되돌릴 근거).
- 파일명에 `mage`를 넣지 않은 이유는, **최종 아트 슬라이스가 같은 파일을 덮어써 Cocos UUID와 씬 배선을 유지한 채 교체**하도록 하기 위해서다. 이름을 바꾸면 `@property` 4개를 다시 연결해야 한다.
- 방향 구분 신호: 정면은 두 눈·양팔·벌린 다리, 후면은 얼굴 없는 머리색 머리통·등 세로선·어두운 몸통, 측면은 코 돌출·머리 묶음·한 팔·모은 다리·좁은 몸통. 여기에 **머리 위 노란 화살표**가 향한 방향을 가리켜 작게 보일 때도 즉시 읽힌다.
- **정합은 측정이 아니라 구성으로 보장된다.** 캔버스 크기와 발 밑선 위치를 스크립트가 직접 정하므로 네 장이 어긋날 여지가 없다. 스크립트가 저장 후 다시 재서 확인하며, 실측값은 네 장 모두 `center_x=192.0` · `foot_y=496`으로 동일하다(PASS). 검사 기준은 "캔버스 중심과 일치"가 아니라 **"네 장이 서로 같은가"**다 — 정수 픽셀에 좌우 대칭 도형을 그리면 중심이 캔버스 중심에서 0.5px 어긋나는 것을 피할 수 없고, 네 장이 똑같이 어긋나면 그 오차는 상수라서 방향 전환에서 튐을 만들지 않는다.

### 최종 아트로 넘긴 제약 (다음 슬라이스가 다시 재지 않도록)

오늘 SDXL+LoRA로 4방향 마법사를 뽑으려다 세 번 실패했고, 진단(`F:\ai\probe_view_control.py`)으로 원인을 갈랐다. 정본 기록은 art-direction §8-1의 콜아웃이다.

- **뒷모습은 LoRA 강도 0.3까지 내려야 겨우 나온다.** 브릿지와 같은 0.8에서는 얼굴 네거티브를 `(face:1.6)`까지 걸어도 정면 얼굴이 그대로 나오고 0.5도 같다 — `f58_anime_style`이 정면 일러스트로 학습돼 룩만이 아니라 **구도까지** 정면으로 잠근다.
- **완전한 측면은 강도 0.0에서도 안 나온다.** 이건 LoRA가 아니라 SDXL 1.0 base의 시점 통제 한계다. 실제 산출물은 "몸이 돌아간 게 아니라 목만 조금 돌아간" 상태였다.
- **시점과 인물 일관성이 서로를 잡아먹는다.** 강도를 내리면 시점이 조금 열리지만 룩과 인물 동일성이 무너져 0.3에서 이미 브릿지와 다른 사람으로 보인다. 그래서 프롬프트 조정으로 빠져나올 수 없다.
- **프롬프트 토큰 순서가 영향을 준다.** 시점 지시를 공통 문구 뒤에 두면 같은 강도에서도 힘을 잃는다(SDXL이 앞쪽 토큰에 더 큰 비중을 준다). 진단이 성공한 조건은 시점 지시를 트리거 바로 뒤, 맨 앞에 둔 것이었다.
- **강도를 내리면 바닥·배경 불이 커지고, 그것이 정렬을 깬다.** 마감 스크립트(`F:\ai\finish_mage_4dir.py`)가 불투명 픽셀 최하단을 발 밑선으로 잡아 정렬하므로, 발밑 불이 이미지마다 다르게 뻗으면 기준선이 발이 아니라 불이 된다. 다만 불을 네거티브로 강하게 누르면 그 항목들이 시점 네거티브와 경합해 시점 통제가 약해지는 것으로 보인다 — 이 경합이 다음 슬라이스가 확인할 남은 변인이다.
- 해법 후보는 셋이고 각각 결정이 따라붙는다 — **ControlNet(openpose) 설치**(모델 약 2.5GB, 방향별 골격을 직접 줌, 현재 미설치), **다시점 캐릭터 LoRA 학습**(art-direction §8-1의 원래 계획, 인물 동일성까지 해결), **베이스 체크포인트 재검토**(부록 C 라이선스 판단 재개).
- 최종 아트가 오면 지켜야 할 것: 좌·우를 런타임 미러링으로 만들지 않는다(노드 `scale.x` 뒤집기는 리깅 때 스켈레탈 디스플레이로 이월돼 숨은 재작업이 된다), 지팡이·불꽃이 캔버스 밖으로 잘리지 않게 한다, 네 장을 같은 시드 한 벌로 고른다(방향마다 따로 고르면 서로 다른 인물처럼 보인다).

## 수동 테스트 체크리스트 (7단계 인게임)

**방향 전환**

> 플레이스홀더 판별법: 정면은 두 눈·양팔·벌린 다리, 후면은 얼굴 없는 갈색 머리통·등 세로선·어두운 몸통, 측면은 코 돌출·머리 묶음·한 팔·모은 다리다. **머리 위 노란 화살표가 향한 방향을 가리키므로** 어느 프레임인지는 화살표만 봐도 즉시 판별된다.

- [ ] 위·아래·좌·우로 걸을 때 각 방향에 맞는 그림이 뜬다(위로 걸으면 뒷모습·화살표 위, 아래로 걸으면 정면·화살표 아래, 좌우도 화살표가 그 방향).
- [ ] 걷다 멈추면 **마지막으로 보던 방향을 유지**한다(정면으로 되돌아가지 않는다).
- [ ] 방향이 바뀔 때 캐릭터가 **위치·크기로 튀지 않는다** — 특히 발 높이가 그대로인지 본다(네 프레임 정합).
- [ ] 대각선으로 걸으면 좌우 그림으로 읽힌다(상하로 흔들리지 않는다).
- [ ] **벽에 밀고 있는 동안**에도 그 방향을 계속 바라본다(못 움직여도 방향은 유지).
- [ ] 일시정지·레벨업 카드 선택 중에는 방향이 얼어붙는다(소프트 일시정지와 일치).

**커진 그림 — 크기와 판정**

- [ ] 플레이어가 브릿지(50×64)보다 뚜렷하게 크다(72×96). 세로로 선 비율이 화면에서 어색하지 않은지 본다 — 최종 아트의 크기 판단 근거가 된다.
- [ ] 그림이 눌리거나 늘어나 보이지 않는다(Content Size 종횡비가 소스 0.75와 맞는지 — 어긋나면 인물이 뚱뚱하거나 홀쭉해 보인다).
- [ ] 적이 **머리·발 높이**로 접촉해도 피해가 들어온다(피해 박스 반높이 30→44 확인. 30을 그대로 뒀다면 박스가 그림의 62%만 덮어 이 항목이 실패한다).
- [ ] 적이 **좌우로 스쳐 지날** 때 억울한 피격이 없다.
- [ ] 적 발사체가 같은 기준으로 명중·회피된다.
- [ ] **벽·건물 미끄러짐과 아레나 클램프가 그대로다**(이동 원 무변경). 커진 발·머리가 벽에 겹치는 정도가 견딜 만한지 눈으로 판단한다 — 거슬리면 그것이 **발치 오프셋**을 다음 슬라이스로 올릴 근거다(계획 §8, ADR 006).

**무변경 회귀**

- [ ] 이동 속도·한강 물속 감속이 그대로다.
- [ ] 경험치 픽업 반경·흡수가 그대로다.
- [ ] 마법 발사와 조준이 그대로다(이 슬라이스는 조준에 손대지 않는다 — `_facing`은 그림 선택에만 쓰인다).
- [ ] 카메라 추적이 그대로다(플레이어가 화면 중앙, 아레나 벽에서 멈춤).
