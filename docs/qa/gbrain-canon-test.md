# QA — gbrain 절차 복구 + 셋업 문서 정본 승격 (gbrain-canon)

- **브랜치:** `feat/gbrain-canon`
- **계획:** [`2026-08-14-gbrain-canon-plan.md`](../development/sessions/2026-08-14-gbrain-canon-plan.md)
- **이전 문서:** [`art-canon-move-test.md`](art-canon-move-test.md) — 같은 계열(정본 이전)의 직전 슬라이스다. 거기서 확인한 이동 규칙(절 번호 보존·표시 텍스트 일치·평문 사각지대)을 그대로 물려받고, **이번에 다른 것은 옮기는 문서가 절차 문서라 「읽어서 맞는가」가 아니라 「따라 해서 도는가」를 봐야 한다는 점**이다.
- **성격:** 문서 구조 작업 + 절차 수정. 게임 코드(`game/assets/scripts/`)와 씬·프리팹은 **한 줄도 건드리지 않고**, `.claude/` 도구도 그대로다.

## 이 슬라이스에서 무엇을 확인하나

둘이다. 첫째, `gbrain-setup.md`가 `spec/ops-gbrain.md`로 옮겨 가고 시점 기록 두 절이 세션 문서로 내려갔는데 그 이사를 따라가지 못한 참조가 없는가. 둘째, **고친 §6.2를 그대로 따라가면 색인이 실제로 갱신되는가.**

첫째는 앞 슬라이스와 같은 종류라 검사기가 대부분 덮는다. **이 슬라이스의 무게는 둘째에 있다.** 고치려는 고장이 「문서에 적힌 명령이 실행되지 않는데 실패가 조용했다」이기 때문에, 고친 절차가 실제로 도는지는 **사람이 한 번 완주해야만** 알 수 있다. 읽어서 그럴듯한 절차와 따라 해서 도는 절차는 다르고, 이 슬라이스는 정확히 그 차이 때문에 존재한다.

완주에는 `gbrain serve` 중단과 `/mcp` 재연결이 들어가므로 **세션을 한 번 건드린다.** 그 점이 이 QA를 앞 슬라이스들과 다르게 만든다 — 게임을 켜는 대신 도구 연결을 끊었다 다시 붙인다.

**통과 근거(2026-08-14):** 전체 스위트 45파일 797/797, 타입체크 범위 `full`.

- [x] `git grep -n "gbrain-setup\.md"` — 결과가 **시점 기록(세션 넷·QA 둘)과 아카이브·이력 줄뿐**인가. 아카이브 항목과 정본 이력 줄은 "무엇이 어디로 갔나"를 말하려고 옛 이름을 일부러 든다. `CLAUDE.md`·`workflow/`·`spec/` 본문·열린 백로그에 남아 있으면 놓친 것이다
- [x] `CLAUDE.md`의 검색 라우팅이 **실행되는 도구**를 가리키는가 — MCP `sources_status`로 바꿨다. 옛 문장은 두 겹으로 실행 불가능했다(이 장비에 `gbrain`이 PATH에 없고, 있더라도 `serve`가 잠금을 쥔다)

- [ ] 옮긴 정본을 처음부터 끝까지 읽어, **구 §7을 근거로 부르던 자리에 결론이 문장으로 남았는가.** 링크가 사라진 것만으로는 검사기가 초록을 준다 (§3.1은 "세 질의가 0.84~0.90으로 최상위", §3.2는 "1024차원으로도 정답을 최상위로 집는다"로 결론을 옮겼다 — 사람이 한 번 읽어 확인)

### 절차가 실제로 도는가 — 이 슬라이스의 핵심

**고친 §6.2를 문서만 보고 그대로 따라간다.** 기억으로 보충하지 않는다 — 보충하면 문서가 부족한지 알 수 없고, 그것이 이번에 고치려는 바로 그 고장이다.

- [ ] 잠금 안내에서 현재 `gbrain serve` PID를 확인한다. 문서에 박힌 숫자를 쓰지 않고 **찾는 법**이 적혀 있는가(PID는 세션마다 달라진다)
- [ ] **끝내는 명령이 자기 셸에 맞게 적혀 있는가.** 리뷰가 잡은 구멍이라 따로 본다 — 찾는 법만 있고 종료하는 법이 없었다. Git Bash를 쓴다면 `taskkill //F //PID`의 **두 슬래시**가 실제로 필요한지도 여기서 확인된다(하나면 `잘못된 인수/옵션 - 'F:/'`로 죽는다)
- [ ] serve를 중단하고 `sync --source monster --full` + `sync --source monster --strategy code --full` 두 줄을 돌린다. 잠금 오류 없이 도는가
- [ ] 삭제한 파일이 있으면 코드 전략 잔재를 손으로 지운다. 문서가 **왜 손으로 지워야 하는지**(문서 전략은 정리하지만 코드 전략은 안 한다)를 적어 두었는가
- [ ] Claude Code에서 `/mcp`로 gbrain을 다시 붙인다. CLI로는 못 살린다는 것이 문서에 있는가
- [ ] MCP `sources_status`로 `last_sync_at`이 방금인지, `last_commit`이 머지 커밋인지 확인한다. **갱신을 돌렸다는 것과 갱신이 됐다는 것은 다르다** — 지금까지 후자를 확인할 자리가 없었던 것이 원인 둘째다
- [ ] 검색 스모크 — 이번 슬라이스가 만든 문서(`ops-gbrain`)를 의미 검색으로 부르면 새 경로가 나오는가. 옛 슬러그(`docs/development/gbrain-setup`)가 아직 나오면 §5.7대로 손 삭제 대상이다
- [ ] **완주 중에 문서가 부족했던 지점을 적어 둔다.** 한 번이라도 기억으로 메웠다면 그 자리가 다음 사람이 막힐 자리다

### 문서가 사람에게 제대로 보이는가

- [ ] GitHub PR의 **Files changed**에서 옮긴 정본을 열어 본문 링크를 클릭 — 전부 열리는가
- [x] `docs/development/spec/README.md`의 「목록」 표에 `ops-gbrain.md`가 사전순 자리(`ops-environment` 다음, `ops-skill-routing` 앞)에 있는가 — `CanonDoc.test.ts`의 인덱스↔폴더 정합 단언이 이것을 잰다
- [x] 옮긴 정본에서 §1 다음이 §3으로 건너뛰는데, **이력 절이 그 이유를 설명하는가.** 없으면 다음 사람이 사고로 읽는다
- [x] `CLAUDE.md`가 14,000자·240줄 예산 안인가 — **13,862자 / 212줄**(여유 138자). **계획이 「늘어나지 않는다」고 적었던 것은 틀렸다** — 41자 늘었다(179 → 138). 검색 라우팅에 더한 설명이 라우팅 표에서 줄인 것보다 컸다. 처음엔 +81자였고, 이유의 전문은 정본 §6.2가 드니 라우팅에는 포인터만 남겨 절반을 되돌렸다
