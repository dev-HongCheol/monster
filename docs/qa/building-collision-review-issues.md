# 코드 리뷰 이슈 — 건물 충돌 최소판 (feat/building-collision)

- **리뷰 커밋:** base `efa163f` → head `06881b6` (1차 리뷰 head `245505b`, 수정 반영 `06881b6`)
- **리뷰어:** subagent (superpowers:requesting-code-review 템플릿, 2026-07-17)
- **결과:** Critical 0 · Important 1 · Minor 5 — "With fixes"

리뷰어가 해소 수학(경사 미끄러짐·코너 대각·터널링 서브스텝 상호작용)을 손으로 재계산해 정확성을 확인했고, `setPosition` 전수 조사로 배선 누락 없음(발사체·XP·카메라 무변경 = D2 스코프 일치), QA 배치표 8개 좌표를 `seoul.json` 물 폴리곤과 대조해 자체 경고에 걸리지 않음을 확인했다. 아래는 지적 사항.

## Important

### I-1. 비활성 자식 노드도 색인돼 투명 벽이 된다 — **수정됨**

- `MapManager._indexObstacles`가 `root.children`을 순회하며 `activeInHierarchy`를 확인하지 않았다. 에디터에서 박스 하나를 비활성화(일시적으로 꺼두기 — 통상 작업 흐름)하면 그림은 사라지는데 충돌은 남아, F47이 경고하는 "허공에 막힘"이 경고 없이 재현된다 — §2.2 불변식(시각=충돌 같은 출처)이 조용히 깨진다.
- **수정:** 루프 초입에서 `!child.activeInHierarchy`면 건너뛴다. 비활성화는 렌더와 충돌이 함께 꺼지므로 시각=충돌 일치가 유지된다(의도적 끄기라 경고는 내지 않는다). QA 수동 항목에 "박스 비활성화 → 충돌도 함께 사라짐" 추가.

## Minor

### M-1. 회전·루트 변형이 scale과 같은 "시각≠충돌" 부류인데 경고가 없다 — **수정됨**

- 자식의 `angle ≠ 0`이면 그림은 회전하는데 충돌은 축정렬로 남는다. 루트 노드 자체의 scale/angle도 색인이 무시한다. 계획 §4.2 경고 목록의 빈틈(계획 결함)이지만 scale 경고가 있는 이유와 동일하므로 함께 막는다.
- **수정:** 자식 `angle ≠ 0` 경고 + 루트 scale ≠ (1,1)/angle ≠ 0 경고를 색인에 추가.

### M-2. `?? []`가 MapManager 부재 프레임마다 새 빈 배열을 할당 — **수정됨**

- `PlayerController._move`·`EnemyController._resolveObstacles`의 `mm?.obstacles ?? []`는 드문 경로지만 F36 자세와 어긋난다.
- **수정:** `ObstacleLogic`에 공유 불변 `NO_OBSTACLES`를 export하고 두 소비처가 폴백으로 쓴다.

### M-3. `_warnNarrowGaps` 주석이 지표를 과대 서술 — **수정됨**

- `max(sepX, sepY)`는 통로 폭의 **보수적 하한**(대각 배치에선 실제 간격이 더 넓어 경고가 과하게 울릴 수 있음)인데 주석이 "통로의 폭이다"라고 단정했다. 주석 정확성 규칙(CLAUDE.md) 위반.
- **수정:** 하한임과 대각 배치에서의 과경고 방향을 명시.

### M-4. QA 문서 통과 커밋 SHA 미기재 — **수정됨**

- "커밋(11단계) 후 기재" placeholder가 남아 있었다. **수정:** 재검증 완료 커밋 SHA로 기재.

### M-5. 테스트 공백 — 2패스 경로·내부 탈출+이동·서브스텝 무상한 — **수정됨**

- 방어용 2패스 해소(겹친 장애물), 내부 겹침 상태에서 이동까지 겹친 경우가 미검증이었고, `steps = ceil(dist/radius)`에 상한이 없어 병리적 입력(radius 0.001 등)이면 한 호출이 수십억 서브스텝을 돌린다.
- **수정:** `MAX_SUBSTEPS = 64` 상한 추가(상한이 무는 입력은 한 프레임에 아레나를 넘는 순간이동뿐이라 프레임 정지 대신 관통을 감수 — 실제 장애물 최소 두께 120px + 2r 대비 서브스텝이 항상 얇음). 테스트 3개 추가(겹친 장애물 2패스 비침투 속성, 내부+이동, 거대 이동 상한 완주). 주의: 상한 테스트는 미구현 상태에선 사실상 무한 루프(행)라 RED를 관찰하지 않고 구현과 함께 작성했다 — 2패스·내부+이동 테스트는 기존 동작의 특성화(characterization) 테스트다.

## 재리뷰 (수정 반영분, base `245505b` → head `4b9bff1`)

지적 6건(I-1, M-1~M-5) 전부 해소 확인 — "Ready to merge: Yes". 재리뷰어가 확인한 것:

- `activeInHierarchy` 체크 시점 안전성 — `_indexObstacles`는 `DataManager.onReady` 콜백으로 불리며, 동기 발화 경로(`_isReady` 참)라도 `start()`는 씬 노드 트리 활성화 후 실행되므로 두 경로 모두 값이 유효.
- `MAX_SUBSTEPS = 64` 산술 검증 — 상한이 무는 조건은 dist > 64×radius(1,152~2,560px/프레임, 최고 속도 380px/s 기준 dt ≥ 3초). 물었을 때 관통 조건은 dist > 9,984px/프레임인데 아레나 내 최대 변위가 ~3,394px이라 **새 터널링 없음**.
- 신규 테스트 3개 실효성 — 겹친 장애물 테스트는 패스 1만으로는 단언이 실패하는 배치(2패스 경로를 실제로 문다), 상한 테스트는 상한 제거 시 사실상 행.
- 전체 스위트 513/513 GREEN 직접 실행 확인.

### R-1. 서브스텝 상한 주석의 임계값 과대 서술 (Minor) — **수정됨**

- `ObstacleLogic.ts`의 상한 주석이 "상한이 무는 입력은 아레나(2400px)를 넘는 순간이동뿐"이라 단정했으나, 실제 임계는 64×radius(r=18이면 1,152px — 아레나 절반)부터다. 안전 논거 자체는 4배 여유로 성립하나 M-3과 같은 "주석이 임계값을 단정" 부류.
- **수정:** 임계값(64×radius, 최소 약 1,150px + dt 3초 환산)을 명시하고 안전 논거를 정확한 수치로 재서술.
