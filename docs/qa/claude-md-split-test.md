### 4.4 배달 로직 — 샌드박스 E2E

>
> **`start-verification`·`start`·`approve-pr`은 테스트에서 부르지 않는다.** `start-verification`은 vitest가 vitest를 재귀 호출하고, `start`는 git 브랜치 조작을, `approve-pr`은 tsc를 띄운다. 배달은 커맨드 안이 아니라 **디스패치 뒤 한 곳**에 붙으므로, 아래 전이들로 그 기구 전체를 덮는다.

- [x] **전이 성공 시 배달한다**: `approve-plan`(planning→qa-setup)이 `qa-setup.md` 본문을 출력한다.

- [x] **`steps <phase>`는 상태 파일이 없어도 돈다**: 절차를 잃어버렸을 때 치는 커맨드라, 상태까지 잃은 상황에서 안 돌면 쓸모가 없다.
- [x] **`check-docs`가 단독으로 돈다**: 정합하면 종료코드 0, 누락이 있으면 1. `check-meta`·`check-qa`와 같은 결이다.
- [x] **`check-docs`가 `README.md` 누락도 잡는다**: 판정 규칙이 `tests/helpers/WorkflowSteps.ts`의 순수 함수와 같아야 한다 — CLI가 그 모듈을 import할 수 없어 생긴 복사본이라, 한쪽만 고치면 테스트는 통과하는데 CLI가 다르게 동작한다. 이 단언이 그 규율의 기계 장치다(코드리뷰 RESIDUAL-1: 이게 없을 때 CLI 쪽만 되돌려도 전부 통과했다).
- [x] **커맨드 키 정합**: 인자 없이 실행하면 커맨드 목록이 나오고(종료코드 0) 거기에 `steps`와 `check-docs`가 들어 있다. 치명적 판정을 런타임 로드 시점에 두지 않는 이유는 그 자리가 `status`·`check-meta`·도움말까지 모든 경로가 지나는 곳이라, 오타 하나로 진단 수단까지 죽고 훅이 상태 파일 편집을 막아 사람이 갇히기 때문이다.

### 5.1 규칙 인벤토리 대조 (부록 A)

> **이 슬라이스에서 가장 위험한 작업은 배달 로직이 아니라 규칙 이전이다.** 레포 전체가 굴러가는 규칙 약 13,000자를 전보체에서 서술형으로 다시 쓰면서 하나도 잃지 않아야 한다. 규칙이 조용히 빠지면 몇 슬라이스 뒤에 사고로 나타난다 — `.meta` 게이트도, QA 확정 게이트도, `invalidate` 재실행 루프도 전부 사고를 겪고 나서 추가된 것들이다. 파일의 43%를 들어내는 변경에서 리뷰어가 실제로 검토할 수 있는 대상은 이 표뿐이다.
