# 개발 백로그 — 게임 (living)

> **목적:** 구현·테스트 중 떠오른 "지금 슬라이스 밖" 할 일 중 **플레이어에게 전달되는 것**(콘텐츠·밸런스·게임필·UI/UX·메타)을 모은다.
> **코드 쪽 백로그는 [`backlog-implement.md`](backlog-implement.md)에 있다** — 아키텍처·리팩터·타입·툴체인·성능·미발현 로버스트니스 버그.
> **작성 시작:** 2026-06-11 · **분리:** 2026-07-10 (한 문서가 너무 길어져 게임/코드 두 축으로 분리)
> **성격:** 계속 갱신하는 living 문서. 슬라이스를 가로지르는 항목만 담는다(한 슬라이스 안의 작업 단계는 `pnpm wf`·세션 투두가 관리).

---

## 사용법 / 운영 규칙

- **조회(슬라이스 시작 시 필수):** 새 슬라이스를 계획할 때 **두 백로그를 모두** 본다. 이번 슬라이스의 테마·영향 범위에 걸리는 항목을 골라 스코프에 포함하고, 계획 문서에 "이 슬라이스가 닫는 백로그 항목"으로 명시한다. 같은 영역을 건드리는 김에 후속·로버스트니스 항목을 함께 처리해 왕복을 줄이는 게 이 문서의 목적이다.
- **추가:** 구현·테스트하다 떠오르면 즉시 해당 테마 표에 한 줄 추가한다. 요약(왜 중요한가)과 출처를 같이 적어야 나중에 의미가 산다.
- **항목 ID는 영구하다.** 세션·QA 문서와 PR 본문이 `F27`·`G1`·`B2`처럼 **ID로만** 참조한다. 재번호·재사용하지 않으며, 파일이 갈려도 ID는 그대로 따라간다. 새 항목은 해당 계열의 다음 번호를 쓴다.
- **새 번호는 `origin/main` 기준으로, 두 파일을 함께 보고 딴다.** 계열 번호는 `backlog.md`와 `backlog-implement.md`에 걸쳐 하나로 이어지므로 **한 파일만 보면 안 되고**, 로컬 main이 뒤처져 있으면 이미 머지된 번호를 다시 딴다. 실제로 이렇게 두 번 충돌했다(2026-07-17 정리) — 피처 브랜치가 낡은 main에서 분기해 `F47`·`F48`을 각각 두 항목이 나눠 가졌다. 번호를 따기 전에 `git fetch` 후 아래로 확인한다.
  ```bash
  git fetch origin
  git show origin/main:docs/development/backlog.md origin/main:docs/development/backlog-implement.md \
    | grep -oE '^\| [A-Z][0-9]+' | grep -oE '[A-Z][0-9]+' | sort -t. -k1.2 -n | uniq -d   # 중복 검사(비어야 정상)
  ```
- **충돌이 이미 났으면 선착순으로 판정한다.** 그 번호를 **먼저 쓴 항목이 지키고**, 나중에 딴 쪽이 다음 빈 번호로 옮긴다(도입 커밋 날짜로 가린다 — `git log -S'<항목 제목>' --reverse`). "참조가 많은 쪽이 지킨다"로 정하지 않는다 — 그 기준은 셀 때마다 답이 바뀌어 또 다툰다. 옮긴 항목에는 `(구 F48 — ID 충돌로 <날짜> 재번호)`를 남겨 옛 참조를 따라온 사람이 길을 잃지 않게 한다.
- **요약은 짧게, 상세는 출처에.** 이 문서는 출처를 **대체가 아니라 집약**한다. 진단·수치·변경 범위 같은 상세는 각 슬라이스의 `*-review-issues.md`·`*-plan.md`(불변 시점 기록)에 두고 여기선 링크만 건다.
- **완료·승격:** 완료되면 표에서 빼고 문서 하단 「완료 아카이브」로 한 줄 옮긴다. 한 슬라이스 분량으로 커지면 `sessions/<날짜>-<feature>-plan.md`로 승격하고 아카이브에 링크를 남긴다.
