# user-verification — Draft PR과 사용자 검증

에디터 세팅과 인게임 테스트는 **사용자가 한다.** AI가 이 phase에서 하는 일은 진입 시점의 문서 정리와 Draft PR 생성, 그리고 사용자가 `PR 승인`했을 때의 마무리다.

## 진입하면 순서대로

### 1. 문서 정리 — PR을 올리기 **전에** 한다

관련 세션·플랜 문서의 내용을 이번 구현에 맞춰 최신화하고, 이번 슬라이스가 건드린 문서를 아래로 훑는다. 여기는 **부피를 줄이는** 자리다 — 정본에 **내용을 채우는** 일은 앞 phase의 정본 선언 게이트가 이미 받아 갔다. 상태를 "완료"로 바꾸는 것은 사용자 검증이 끝난 뒤의 일이라 여기서 하지 않는다.

자주 읽는 문서(세 백로그·`docs/design/` 정본·`CLAUDE.md`)는 슬라이스마다 조금씩 자란다. 한 슬라이스 안에서는 티가 안 나지만 쌓이면 다음 슬라이스의 조회 비용이 된다 — 2026-08-06에 두 백로그 조회만 57.6k 토큰이었고 그 부피의 38%가 항목 **여섯 개**에 몰려 있었다. 그래서 **이번 슬라이스가 건드린 문서만** 본다(전수 점검이 아니다).

- **백로그 행은 요약이지 본문이 아니다.** 이번에 추가·수정한 항목이 몇 문단으로 자랐으면 진단·수치·대안 비교 같은 상세를 출처 문서(세션 `*-plan.md`·ADR·`docs/design/` 정본)로 옮기고, 행에는 **무엇을·왜·상태 + 정확한 링크**만 남긴다. 행은 출처를 대체하지 않고 **집약**한다.
- **출처에 "이 대화"를 남기지 않는다.** 슬라이스 밖에서 난 결정도 세션 문서로 적고 행은 그 문서를 링크한다. 근거를 적을 데가 없으면 **행에 쓰게 되고**, 그렇게 부푼 행은 아무도 다시 줄이지 않는다. **검토하고 접은 안도 세션 문서에 남긴다** — 기각 기록이 없으면 그 항목을 집는 다음 사람이 같은 안을 다시 낸다.
- **낡은 참조를 고친다.** 아카이브로 옮긴 항목 ID를 가리키는 참조, 이번에 닫은 항목을 아직 "진행 중"으로 적은 문서, 깨진 링크.
- **문서끼리의 참조가 규칙을 지키는가** — 링크 방향·순환 참조·절 번호·과거 기록 불수정·이력 축약 다섯을 [`../spec/docs-references.md`](../spec/docs-references.md)가 든다. 그중 기계가 잡는 것은 **둘뿐이다** — 링크 방향(§2)과 앵커가 붙은 절 참조(§5). 나머지 셋은 손으로 본다.

완료 항목을 아카이브로 옮기는 것은 여기가 아니라 `pr-ready`다. 항목이 실제로 닫혔는지는 사용자 검증이 끝나야 확정되고, 여기서 옮겼다가 리워크가 나면 도로 꺼내야 하기 때문이다.

정리가 끝난 상태로 push해야 그 결과가 Draft PR의 diff에 들어간다. 머지 직전에 고치면 **사용자가 검토한 적 없는 변경이 머지된다.** 8·9단계에서 문서에 허용되는 변경은 **상태 표시**(플랜을 "완료"로, 백로그 행의 상태 어휘, 아카이브 한 줄 이동)뿐이고, 내용을 옮기거나 줄이는 일은 여기서 끝나 있어야 한다. 리워크로 돌아왔다가 다시 올릴 때도 push 전에 다시 훑는다 — PR을 올릴 때마다가 이 정리의 시점이다.

### 2. 검토용 Draft PR 생성

브랜치를 push하고 `gh pr create --draft`로 PR을 만든다. Draft 상태라 GitHub Merge 버튼이 비활성화되어 실수 머지가 막힌다. assignee로 레포 소유자를 지정한다. 이미 Draft PR이 있으면(리워크 후 재진입) 새로 만들지 말고 push로 본문과 diff만 갱신한다.

**신규 `.meta`가 하나도 들어가면 안 된다.** AI는 `.meta`를 만들지 않으며, 작업 중 어떤 경로로든 생겼다면 push 전에 뺀다. 모든 신규 `.meta`는 아래 사용자 테스트에서 Cocos가 만들고 `PR 승인` 시점에 커밋된다.

### 3. 사용자에게 알린다

"7단계입니다. Draft PR(`<링크>`)의 Files changed와 `docs/qa/<feature>-test.md` 체크리스트를 참고해 에디터 세팅 및 인게임 테스트를 진행해 주세요."

## PR 본문 작성 규칙 (Draft 생성·갱신·머지 공통)

사용자가 코드 리뷰를 쉽게 하도록 **코드를 상세히 설명한다.** 문체는 `docs/development/spec/docs-writing-style.md`, 특히 「PR 본문은 사람이 한 번 읽고 넘기는 글이다」 절을 따른다. **본문을 쓰기 전에 그 절을 읽는다** — 사람이 한 번 읽고 마는 글이라 `docs/` 문서보다 조건이 더 붙는다(명사구 압축 금지, 줄표로 인과 대체 금지, 비유로 설명 대체 금지). 문체는 `docs/` 문서와 같은 `~한다`체를 쓴다.

- **변경 배경과 목적** — 무엇을 왜 바꾸는가.
- **파일·로직 단위 변경 설명** — 핵심 파일마다 무엇이 어떻게 바뀌었고 왜 그렇게 했는지를 서술한다. 신규 로직은 입력에서 처리를 거쳐 출력에 이르는 흐름을 풀어 쓴다. 파일 목록 나열이 아니라, 리뷰어가 코드를 열기 전에 맥락을 잡을 수 있을 만큼 구체적으로.
- **리뷰 중점 포인트** — 특히 봐야 할 부분, 트레이드오프, 의도적 결정.
- **테스트·검증 방법** — 자동 테스트 결과(N/N)와 수동 검증 항목.

## 사용자가 하는 일

에디터에서 씬 노드를 구성하고 `@property`를 연결한 뒤(QA 문서의 체크리스트 참고), 수동 인게임 테스트를 한다.

**버그가 나오면** 사용자가 `리워크`라고 입력하고, AI가 `pnpm wf rework`를 실행해 구현으로 돌아간다. 검증은 초기화되고 스크립트 편집이 다시 열린다. **Draft PR은 닫지 않는다** — 재구현과 재검증을 거쳐 이 phase로 다시 들어와 push하면 자동으로 갱신된다.

## 나가는 게이트: `approve-pr`

사용자가 **`PR 승인`**이라고 입력하면 두 가지를 순서대로 한다.

1. 사용자 테스트 중 Cocos가 만든 **모든 신규 `.meta`를 먼저 커밋·push한다.** 순수 로직 `.ts`와 `resources/*.json`의 것도 포함된다.
2. `pnpm wf approve-pr`을 실행한다.

`approve-pr`은 추적되지 않은 `.meta`를 검사해 누락이 있으면 차단한다. 머지 후 모든 환경에서 UUID가 재생성돼 씬·프리팹 참조가 깨지는 것을 막는 마지막 안전장치다. 차단되면 누락분을 커밋하고 다시 승인받는다. 미리 `pnpm wf check-meta`로 확인할 수 있다.

**이 시점에 문서를 더 손봐야 한다면 그건 정리가 아니라 누락이다.** 사용자가 검토하지 않은 변경이 생긴다는 뜻이므로, 위 1번으로 되돌려 처리한다.
