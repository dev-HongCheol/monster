## 1. 이 슬라이스가 하는 일

플레이어가 **적·적 발사체에 맞는 피해 히트박스**를 원(반지름 25)에서 **AABB 박스**로 바꾼다. 순수 로직 하나 + `player.json` 데이터 + 피해 소비처 두 곳 배선이 전부다. 적은 원을 유지하고, **플레이어의 이동·벽 충돌도 원을 유지**한다(§3).

## 2. 왜 지금·여기서 자르는가

ADR 006대로 주인공을 4방향으로 세로 크게 그리려면 세로로 긴 피해 판정이 필요한데, 그 판정 인프라를 아트보다 **먼저** 깐다 — 히트박스가 자리잡은 뒤에 세로 아트를 얹어야 나중에 충돌을 재작성하지 않는다. 순수 로직이라 TDD RED→GREEN에 맞고, 적 진영·이동 충돌을 안 건드려 저리스크다. 현재 브릿지 스프라이트(50×64)에선 체감 변화가 작다 — 값은 선행 인프라에 있다.

## 3. 이동 충돌은 왜 원으로 남기나 (스코프 핵심 — Eng 관점)

코드를 보면 플레이어의 `collisionRadius`를 **세 곳**이 쓴다.

1. `EnemyController._checkContactDamage` — 적 접촉 피해 (반지름 합 판정)
2. `EnemyProjectile` — 적 발사체 명중 (반지름 합 판정)
3. `PlayerController._move` — 이동/장애물/아레나 충돌 (`resolveCircleMove` collide-and-slide + 벽 클램프)

가이드 §4가 말한 억울한 피격·머리발 누락은 **①②(피해 판정)**의 문제지 ③(이동)의 문제가 아니다. 이동은 벽·건물을 따라 미끄러지는데, **원은 코너에 걸리지 않아 박스보다 매끄럽다**(박스로 바꾸면 모서리에 걸려 이동감이 나빠진다). 그래서 **①②만 박스로 바꾸고 ③은 원을 유지**한다. 결과적으로 플레이어는 두 콜라이더를 갖는다 — **이동용 원**(몸통 코어) + **피해용 박스**(세로 실루엣). `resolveCircleMove`·아레나 클램프는 한 줄도 안 바뀐다.

> **세로 겹침 후속:** 이동을 원으로 두면 스프라이트가 원보다 세로로 길 때 벽에 세로로 밀칠 때 머리·발이 `절반 높이 − 반지름`만큼 벽 안으로 겹쳐 보인다(현 브릿지 50×64·반지름 25면 약 7px라 무시할 만하나, 세로 4방향 아트가 오면 커진다). 해법은 **이동 원을 발치 풋프린트로 내리는 것**이며 실제 세로 비율이 있어야 정하므로 4방향/리깅 슬라이스가 가져간다 — 상세·근거는 [`../../decisions/006-collision-hitbox.md`](../../decisions/006-collision-hitbox.md) 「결과·후속」. 이 슬라이스(피해 히트박스)는 이동을 건드리지 않으므로 무관하다.

## 4. 건드리는 곳

| 파일 | 변경 |
|------|------|
| `logic/HitboxLogic.ts` (신규) | `circleIntersectsBox(cx, cy, r, bx, by, halfW, halfH): boolean` — 원 중심을 박스 범위로 clamp한 최근접점과 원 중심 거리로 겹침 판정. 순수·cc 무관. |
| `data/GameTypes.ts` `IPlayerData` | 피해 박스 필드 추가(`hurtboxHalfWidth`·`hurtboxHalfHeight`, 가칭). `collisionRadius`는 유지(이동). |

| `EnemyController._checkContactDamage` | 반지름 합 → `circleIntersectsBox`(적 원 중심·반지름 vs 플레이어 박스). |
| `EnemyProjectile` (`init`·플레이어 명중 판정) | 반지름 합 → 같은 원-대-박스 판정. |
| **무변경** | `Projectile._checkEnemyHit`·`SpatialGrid`·`ExplosionLogic`(적은 원), `PlayerController._move`(이동 원). |

## 5. 데이터 계약

피해 박스는 **몸통+머리 세로 실루엣**에 맞춘다. 현 브릿지(50×64, 몸통 코어 ≈50px)에선 잠정값(예: `halfWidth 18` · `halfHeight 30` ≈ 36×60, 가이드 §4 권장치)으로 넣고, **4방향 세로 아트가 오면 실제 실루엣에 맞춰 재튜닝**한다(값은 데이터라 코드 무변경). 이동 원 `collisionRadius = 25`는 불변, 픽업 반경도 불변.

## 6. 테스트 (RED 먼저)

`tests/logic/PlayerHitbox.test.ts` — `circleIntersectsBox`를 검증한다.

- 박스 내부/외부 원 중심, 변·모서리 근처(clamp 최근접점이 변 위 vs 모서리로 갈리는 경계).
- **세로로 긴 박스에서 머리·발 높이의 원이 명중** — 원-원(반지름 25)이면 놓쳤을 케이스가 박스에선 잡히는지.
- **좌우로 스쳐 지나가는 원이 박스와 안 겹침** — 세로 원(높이 기준)이었다면 났을 억울한 피격이 박스에선 사라지는지.

순수 로직이라 `skip-test` 아님 — RED 확인 후 구현한다.
