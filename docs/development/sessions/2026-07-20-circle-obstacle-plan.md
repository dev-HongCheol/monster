## 1. 배경 — 왜 지금 필요한가

지금 장애물 충돌은 축정렬 사각형(AABB) 하나만 다룬다. 그래서 원형 건물(동대문 체육관 돔 등)을 넣으려면 원을 사각형으로 감싸야 하는데, 반지름 R인 원을 한 변 2R 사각형으로 감싸면 대각선 코너에서 원 표면까지 `R(√2−1) ≈ 0.41R`의 빈 공간이 남는다. 반지름 200px 돔이면 대각선 방향 약 83px 지점에서 이동 주체가 막힌다 — 플레이어 눈에는 "건물에 닿지도 않았는데 벽에 걸리는" 현상으로 보이고, 서울을 다양한 랜드마크로 채우려는 맵 다형성이 그만큼 죽는다.

이 문제는 이동 주체가 **이미 원(반지름 `collisionRadius`)으로 취급된다**는 사실 덕분에 값싸게 풀린다. 원 대 원 판정은 두 중심 거리가 두 반지름 합보다 작으면 중심을 잇는 선을 따라 밀어내는 한 줄이라, 사각형처럼 축별 클램프나 내부 면 선택이 필요 없다. 원형 장애물은 현재 코드에 **가장 싸게 추가할 수 있는 프리미티브**다.

## 2. 확정 스코프 (설계 §2, Approach A)

**볼록 프리미티브 seam(형태 추상화)을 도입하되, 이번 슬라이스는 원(circle)만 구현한다.** 회전 사각형(OBB, 대각선 버스용)과 캡슐(긴 타원 경기장용)은 같은 seam 위에서 후속 슬라이스로 얹는다.

이렇게 나눈 이유는 충돌 코어가 `feat/building-collision`의 C-1(목표 클램프 코너 극한 순환)을 잡아 겨우 안정된 상태이기 때문이다. 프리미티브 하나 + 그에 맞는 우회 스티어링 한 갈래씩만 얹어야, 회귀가 나도 어느 도형의 어느 단계가 깨졌는지 원인이 좁아진다. seam은 지금 넣되 구현은 원만 채우므로, OBB·캡슐 슬라이스는 데이터 형태와 밀어내기·스티어링 분기만 추가하면 되고 코어 구조를 다시 짜지 않는다.

### 상속하는 하드 제약 (로드맵 D2·D4·F36)

- **D2 — 벽은 이동만 막는다.** 발사체·근접 부채꼴은 통과한다. 프리미티브를 늘려도 그대로다.
- **D4 — 「방」을 만들지 않는다.** 볼록 형태만, 한 변(또는 지름) ≤ 300px, 벽을 붙여 복도·막힌 방을 만들지 않는다. 원은 날카로운 코너가 없어 오히려 적이 모서리에 걸리는 일이 사각형보다 적다.
- **F36 — 핫패스 무할당.** 장애물은 로드 시 1회 색인하고, 밀어내기·스티어링은 호출당 객체를 새로 만들지 않는다.

## 3. 엔지니어링 리뷰 — 아키텍처

> codex 부재 머신이라 단일 보이스로, 충돌 코드(`ObstacleLogic.ts`·`MapManager.ts`·소비처 5곳) 정독을 근거로 한다. 판정: **아키텍처 건전**. seam은 기존 per-obstacle 루프 안에 형태 분기를 넣는 것이 전부라 갓 안정된 코어를 다시 짜지 않는다.

### 3.1 형태 seam — 판별 유니온

`ObstacleRect` 단일 인터페이스를 판별 유니온으로 넓힌다. `kind`를 **양쪽 arm에 모두** 박아 TypeScript가 좁히기(narrowing)를 정확히 하게 한다.

```ts
export interface ObstacleRect   { kind: 'rect';   cx: number; cy: number; halfW: number; halfH: number; }
export interface ObstacleCircle { kind: 'circle'; cx: number; cy: number; r: number; }
export type Obstacle = ObstacleRect | ObstacleCircle;
```

`kind`를 선택 필드로 두어 rect 리터럴을 안 건드리는 대안은 채택하지 않는다 — "있을 수도 없을 수도 있는 판별자"는 좁히기가 불안정하고(P5 명시성 위반), 소비처가 `'r' in ob` 같은 우회 판정에 의존하게 된다. 대신 기존 rect 리터럴(`MapManager` 색인 1곳 + `BuildingCollision.test.ts` 픽스처 ~8곳)에 `kind: 'rect'`를 더하는 기계적 변경을 받는다. `NO_OBSTACLES`와 세 소비처 시그니처(`readonly ObstacleRect[]` → `readonly Obstacle[]`)도 함께 넓힌다.

### 3.2 형태 판별 — `CircleObstacle` 마커 컴포넌트 (2026-07-20 사용자 결정)

씬 노드가 원인지 사각인지는 기하만으로 알 수 없다(원 스프라이트도 UITransform은 정사각이다). 명시적 신호가 필요하므로, **원 노드에만 붙이는 빈 마커 cc 컴포넌트 `CircleObstacle`**를 새로 만든다. 색인은 `child.getComponent(CircleObstacle)`가 있으면 원, 없으면 사각으로 판별한다 — **사각형이 기본값**이라 기존 배치·데이터는 그대로 산다.

- 원 반지름은 노드의 `UITransform.width / 2`에서 유도한다. `width ≠ height`면 원이 정사각 노드가 아니라는 뜻이라 경고를 낸다(그림이 타원인데 충돌은 원이 되어 어긋난다).
- 명명 규칙(이름 접두사) 대안은 기각했다 — 이름을 바꾸면 조용히 사각형으로 되돌아가고, 신호가 Inspector에 드러나지 않아 오배치 방어가 약하다. 마커 컴포넌트는 `@property` 배선과 같은 house 패턴이고 Inspector에 보인다.
- `CircleObstacle.ts`는 cc 의존이라 순수 로직 단위 테스트 대상이 아니다(마커 의미가 자명). `.meta`는 7단계에서 Cocos가 생성한다.

### 3.3 밀어내기 일반화 (`resolveCircleMove`)

내부 per-obstacle 본문에 `ob.kind` 분기를 넣는다. 서브스텝 분할·2패스·무할당 위생은 형태 불가지라 그대로다.

- **사각형:** 지금의 "중심을 사각형에 클램프한 최근접점 → radius까지 밀기"를 유지한다.
- **원:** 중심선 방사 밀어내기다. `d2 = (x−cx)² + (y−cy)²`, 밀어낼 거리 `R = ob.r + radius`. `d2 ≥ R²`면 통과, 아니면 `scale = R/√d2`로 `x = cx + (x−cx)·scale`. 이동 주체 중심이 장애물 중심과 정확히 겹치면(`d2 = 0`) 방향이 없으므로 임의 축(+x)으로 `R`만큼 민다. 사각형의 내부 면 선택 분기가 필요 없어 더 단순하다.

### 3.4 원 접선 우회 스티어링 (`steerAroundObstacles`) — 진짜 비용·리스크

설계 P4가 짚은 대로 **작업의 대부분과 유일한 리스크가 여기 있다.** 골격(첫 블로커 선택, 안 막히면 `desiredDir` 그대로 반환, 목표에서 멀어지는 이동 제외, chirality 고정)은 형태 불가지라 재사용하고, 형태별로 다음 세 조각만 원용으로 새로 짠다.

1. **막힘 판정.** `from→target` 선분이 확장원(중심 `(cx,cy)`, 반지름 `R = ob.r + radius`)에 `STEER_EPS`만큼 못 미치게 다가오는가 — 선분·원 최근접 거리로 판정한다. 여러 장애물 중 진입이 가장 이른(가까운) 것을 블로커로 고른다.
2. **경유점 = 접선점.** `from`에서 확장원에 그은 두 접선의 접점 중, 진행 방향 90° CCW(사각형 코너 타이브레이크와 같은 규약)로 고른 쪽을 첫 경유점으로 겨눈다. 접선점을 돌아 나가면 목표까지 직선이 뚫려 스티어링이 `desiredDir`로 복귀한다.
3. **목표가 확장원 안(엄폐 대치).** 적 반지름이 플레이어 반지름을 넘어(12종 중 9종) 벽에 붙은 플레이어가 확장원에 삼켜지면, 어느 접선점에서도 목표가 안 보여 우회가 전멸한다. 목표를 확장원 경계의 방사 최근접점으로 끌어내 "어느 쪽으로 돌지"만 얻는다. **그다음 막힘 판정을 끌어낸 목표로 다시 해야 한다** — 원래 목표가 확장원 안이면 거기로 긋는 선분이 그 안에서 끝나 어느 위치에서도 "막혔다"가 나오고, 우회가 영영 안 풀려 ① 플레이어 바로 옆에서도 옆으로 새고 ② 접선점을 지나는 순간 방향이 뒤집혀 2프레임 극한 순환에 빠진다. 이것이 사각형에서 났던 C-1의 원 판(版)이다.

**리스크 요지:** 경유점 사상이 접선점에서 불연속이고, 첫 다리 길이가 0에 수렴해도 정규화하면 방향은 full 크기라 미세한 위치 차가 180° 반전으로 증폭된다. 사각형은 이 순환을 목표 클램프 뒤 재판정으로 막았고 도달 스윕으로 전수 검증했다. 원도 **같은 재판정 + 같은 도달 스윕**을 접선점 기준으로 반드시 깐다(§6). 어긋나면 증상은 "원형 건물 뒤 플레이어를 향해 적이 벽에 붙은 채 굳음"이다.

### 3.5 함께 닫는 데이터 경계 항목 (F50·F55) — `MapManager._indexObstacles`

F50·F55는 둘 다 D2 원칙대로 **데이터 경계인 색인**에 붙는다. 색인은 이미 크기 0·scale·angle·300px 초과·경계 밖·통행 간격을 경고로 거르고 있어, 그 배터리에 두 줄을 더하는 것이다.

- **F50 — 비유한 좌표 스킵.** `resolveCircleMove` 내부 루프의 `d2 ≥ r2`는 `ob.cx`·`halfW`·`r`가 NaN이면 비교가 false로 새서(NaN 비교) 위치가 NaN으로 오염된다 — from·to·radius는 이미 핫패스에서 가드되지만 장애물 항목 자체는 무방비다. 색인이 각 장애물의 유도값에 `Number.isFinite`를 적용해 하나라도 비유한이면 스킵+경고한다. 핫패스에는 분기를 새로 안 만든다.
- **F55 — 최소 변(지름) 하한 경고.** 색인이 `MAX_OBSTACLE_SIDE`(300) 초과만 경고하고 하한은 안 본다. 맵이 4800으로 커지며 서브스텝 상한 길이가 ~106px가 되어(설계·백로그 F55 참조) 얇은 장애물 관통 마진이 절반으로 줄었다. `MIN_OBSTACLE_SIDE = 120`(F55가 인용한 안전 하한) 미만이면 경고를 낸다 — 사각형은 한 변, 원은 지름 기준. 하드 차단이 아니라 경고다(MAX와 같은 성격).

### 3.6 소비처 — 변경 없음

`PlayerController._move`는 `resolveCircleMove`만 부르고(사람이 조종하니 우회 불필요), `EnemyController`는 `_steerAround` + `_resolveObstacles`를 4개 이동 모드에 이미 배선해 뒀다. 둘 다 `MapManager.instance.obstacles`(이제 rect·circle 혼합)를 그대로 받으므로 **배선 코드는 손대지 않는다** — 형태 분기는 전부 순수 로직 안에서 끝난다.

## 5. NOT in scope (이번에 안 하는 것)

- **OBB(회전 사각형)·캡슐.** 같은 seam 위 후속 슬라이스(설계 §2). 대각선 버스·경기장은 이번엔 축정렬 AABB로 유지.
- **`MAX_RESOLVE_PASSES`·`MIN_OBSTACLE_GAP` 상수 튜닝.** 좁은 틈 상시 배치의 2패스 진동은 7단계 체감 항목(설계 §5·§8). 체감 전 투기적 상향 안 함.
- **좁은 틈으로 미로 만들기.** 짧은 클러스터(쌍·소수)까지만. 이어 붙여 복도를 만들면 D4 부활(설계 §5).
- **최종 아트.** 원형 건물의 픽셀 아트는 F41(아트 단계). 이번엔 placeholder 원 스프라이트.

## 6. 테스트 계획 — `tests/logic/CircleObstacle.test.ts` (RED부터)

피처 테스트 파일명은 슬라이스 슬러그 PascalCase(`CircleObstacle`)를 따른다(wf `ready-impl` RED 게이트가 이 이름을 찾는다). `BuildingCollision.test.ts`의 원 대응판이다.

**`resolveCircleMove` — 원 해소**
- [ ] 원 정면 진입 — 표면에서 `ob.r + radius` 거리에 멈춘다.
- [ ] 원 비스듬 진입 — 중심선 방사로 밀려 접선 미끄러짐이 생긴다(축 스냅 아님).
- [ ] `from`이 원 내부(스폰 겹침) — 방사 방향으로 표면 밖 탈출.
- [ ] 이동 주체 중심 == 원 중심(`d2=0`) — 임의 축으로 `R` 탈출(NaN 없음).
- [ ] 작은 원 고속 관통 방지(터널링) — 서브스텝 분할로 막힌다.
- [ ] 재해소 무변화(벽에 붙어 선 위치가 안 튄다).
- [ ] rect·circle 혼합 배열에서 각자 올바른 형태로 해소.

**`steerAroundObstacles` — 원 접선 우회**
- [ ] 정면 일직선(적-원-플레이어) — 접선 쪽으로 방향을 튼다(변위 0 정지 회귀 방지).
- [ ] 좌우 동률 — 진행 방향 90° CCW로 고정(떨림 방지).
- [ ] 접선점 도달 후 목표로 복귀(코너 아닌 호에 붙어 맴돌지 않음).
- [ ] 목표가 확장원 안(엄폐 대치) — 방사 클램프 후 우회, 재판정으로 순환 차단.
- [ ] 접선점에 정확히 선 적 vs 0.01px 지난 적 — 방향 뒤집힘 없음(C-1 원 판 극한 순환).
