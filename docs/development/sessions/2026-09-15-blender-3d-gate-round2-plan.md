## Implementation plan

### 1. 무엇을 판정하나

1라운드(2026-09-11~15)는 VRoid `.vrm`을 Blender 스크립트로 구워 Cocos에서 재생하는 사슬이 선다는 것을 정면 걷기 8장으로 증명했다(게이트 다섯 통과, QA §10). 그러나 그 증명은 시험 캐릭터 · 정면 한 방향 · 테스트 씬에 머물렀다.

2라운드는 **이 방식으로 플레이어 아트를 생산해도 문제가 없는가**를 게임 본편에서 판정한다. 끝나면 출하된 2D 4방향 아트를 3D 렌더로 교체하고, 지팡이와 방패를 기본 무기로 들린다. 앞으로 붙을 옷과 장비가 같은 방식 위에 설 수 있는지는 상의 한 층 교체로 확인한다. 3D 워크플로우가 확정되기 전에는 main에 머지하지 않는다.

이 경로를 고른 이유는 가림 문제다. 2D 생성에서는 지팡이가 머리카락 위를 지나므로 지팡이를 걷어 내면 그 뒤에 그려진 것이 없었다(F67). 3D에서는 몸과 지팡이를 같은 카메라로 따로 굽고, 지팡이 층을 구울 때 몸을 가림 전용으로 두면 몸에 가려진 지팡이 픽셀이 투명하게 나온다. 게임에서는 그 층을 몸 위에 얹기만 하면 된다.

### 2. 결정 (2026-09-15, 사용자)

번호에 `R2-`를 붙인다. 정본 쪽 「재조사 D10」(`art-direction.md:169`) 같은 옛 번호와 섞이지 않게 하려는 것이다.

- **R2-D1 끝 지점은 본편이다.** `main.scene`에서 생산 캐릭터가 4방향으로 움직이는 것까지 본다. 판정 박스 · 발치 · 방향 전환 문제는 본편에서만 드러나기 때문이다.
- **R2-D2 캐릭터는 정본 외형으로 새로 만든다.** 젊은 여성 마법사 · 긴 주홍 머리 · 호박색 눈 · 창백한 피부 · 천옷 · 4등신(`art-direction.md` §6). 툰 세팅 값은 머리색과 의상에 따라 달라지므로 시험 캐릭터로 맞춘 값은 버려진다.
- **R2-D3 동작은 걷기 · 대기 두 개다.** 게임이 이동 중에도 쿨다운마다 자동 발사하므로(`SpellCaster.update`) 시전 포즈를 따로 구우면 걷기가 끊긴다. 시전은 지금처럼 이펙트로만 표현한다. 피격 · 사망은 게임에 그림 연출 자체가 없어 범위 밖이다.
- **R2-D4 지팡이는 별도 층으로 굽는다.** F67 결정과 규격 정본 §3.3(지팡이가 구워진 몸 금지)을 그대로 지킨다.
- **R2-D7 걷기 · 대기는 스타일 키프레임으로 짠다(F106 ①).** 성인 모션을 저등신에 옮기면 비율로 못 빼는 성분 둘(발목 좌우 3.2cm · 발바닥 최대 16°)이 남는다. Dead Cells도 사실적 모션이 아니라 2D식 핵심 프레임을 최소로 짜서 3D로 구웠다.
- **R2-D8 방패 층을 더한다.** 지팡이 하나로는 장비끼리 서로 가릴 때 조합마다 다시 구워야 하는지를 잴 수 없다.
- **R2-D9 옷은 모듈 방식으로 증명한다.** 맨살 몸 층 위에 상의 층(A · B)을 몸을 가림 전용으로 두고 구워 교체한다. 풀세트 몸 층 교체는 조합마다 몸 층을 다시 굽게 되고, 정본 워드로브에서 가장 실패하기 쉬운 층 겹침을 증명하지 못해서 기각했다.
- **R2-D10 모양을 갖춘 지팡이와 방패를 v1 기본 무기로 장착해 v2 전까지 쓴다.** v2 스킨까지 단계가 많이 남았기 때문이다. 방패 · 상의 B · 개발용 옷 전환 입력도 최종 PR로 main에 넣는다.
- **R2-D11 반복 한도는 AI가 같은 기술 문제를 연속으로 풀지 못할 때만 센다.** 구현한 코드의 린트 · 타입체크 · 테스트 오류나 굽기 스크립트 오류를 같은 원인으로 3번 연속 고치지 못하면 멈추고 상황을 보고한다(`CLAUDE.md` 행동 규칙). 사람이 판정하는 반복(화풍 · 동작 · 가림 선택 · 인게임 확인)은 한 이슈를 풀기 위한 반복이라 세지 않고, 계속할지 보류할지는 사용자가 판단한다.
- **라이선스.** 개발자가 VRoid로 만든 캐릭터를 렌더해 상업 게임에 싣는 것은 허용 범위다(사용자가 교차 확인한 판정). 다만 VRoid 기본 데이터는 CC0가 아니고(권리는 pixiv, 약관으로 이용 허락), 캐릭터 생성 · 내보내기 서비스를 만들면 별도 라이선스가 필요하며, 제3자 에셋(BOOTH 등)은 개별 조건을 따른다. **그래서 캐릭터와 옷은 VRoid 기본 프리셋 + 직접 수정 + 직접 만든 텍스처로만 구성한다.**

기각한 안(한 줄씩):
- 시험 캐릭터로 먼저 끝내기 — 툰 · 크기 값을 생산 캐릭터에서 다시 맞추게 된다.
- 멈췄을 때만 시전 포즈 / 상체 · 하체 분리 시전 — 이번 라운드 밖(R2-D3).
- 지팡이를 몸과 한 장으로 굽기 — F67 · §3.3 위반.
- 지팡이만 굽기 — 장비끼리 가림 조합 문제가 미지수로 남는다(R2-D8).
- 풀세트 몸 층 교체 — 모듈 워드로브를 증명하지 못한다(R2-D9).
- 방패 · 상의 B를 브랜치 증명물로만 두기 — 기본 무기로 쓰기로 했다(R2-D10).
- 게이트별 회차 상한 — 사람 판정 반복까지 세면 한 이슈의 다듬기가 한도에 걸린다(R2-D11).
- 모션 필터(F106 ②) — 필터로 춤추는 느낌이 안 빠지면 반복만 쓰고, 모션 파일 라이선스 행이 남는다.
- 정지 1장 + 코드 흔들림 — 프레임 애니메이션 능력을 본편에서 시험하지 않는다.
- 게임 연결을 `cc.Animation` 클립으로 하기 — 방향 · 동작 · 층 조합만큼 클립이 늘고, 클립이 `.meta` UUID를 참조해 사람이 손으로 만들어야 하며, 옷 교체 때 재생 위치를 유지하는 방법이 매뉴얼로 확인되지 않았다.
- 가림 대안으로 Object Index 쓰기 — 픽셀당 값 하나라 경계가 계단지고, EEVEE 지원 여부도 확인되지 않았다. 대안은 Cryptomatte다.

### 4. 제약

- **판정 규칙은 바꾸지 않는다.** 피격 사각형과 이동 원은 `resources/data/player.json` 고정값이다(ADR 007). 방패와 상의는 외형만 바꾸고 판정을 바꾸지 않는다. **발치 오프셋만은 아직 Player 노드의 `UITransform.height`에서 유도된다**(`PlayerController.ts:83`, 규격 정본 §3.1, F64 미이행). 그래서 **Player 노드의 UITransform과 몸 Sprite를 옮기거나 크기를 바꾸지 않는다.** Player를 빈 컨테이너로 바꾸면 반높이가 0이 되어 발치가 조용히 23 올라간다.
- **그림 규격은 기존 값이다.** 캔버스 246×493 · 발 밑선 489행 · 머리 꼭대기 2행(`tests/helpers/FrameSet.ts`의 `PLAYER_FRAME_SPEC`).
- **게임 코드는 워크플로우 게이트를 탄다.** `game/assets/scripts/**` 편집은 implementation · verification phase에서만 열린다. 동작 · 프레임 선택은 `logic/` 순수 함수로 두고 테스트를 RED로 먼저 세운다(ADR 002 · 003).
- **슬러그는 `blender-3d-gate`를 유지한다.** 새 RED 테스트는 기존 `tests/logic/Blender3dGate.test.ts`에 더한다. `ready-impl`은 이 파일이 실패해야 통과하는데, 1라운드 테스트 50건이 이미 초록이기 때문이다(`workflow.mjs:602-611`). QA 문서도 기존 `docs/qa/blender-3d-gate-test.md`에 2라운드 절을 더한다. 진행 중인 슬라이스의 문서라 PR을 올리기 전까지 고칠 수 있다. `approve-plan`은 1라운드 계획 문서만으로도 통과하므로 실제 관문은 사용자의 `계획 승인`이다.
- **Draft PR #92를 재사용한다.** 2라운드가 user-verification에 들어갈 때 제목과 본문을 2라운드 범위로 갈아 쓴다.
- **`.meta`는 AI가 만들지 않는다.** 새 에셋의 `.meta`는 사용자가 Cocos에서 생성하고 PR 승인 때 커밋한다. AI는 Cocos가 만든 `.meta`를 읽어서 검사만 한다.
- **레포는 공개이고, 브랜치에 푸시한 것은 PR ref로 남는다.** squash merge라 main 히스토리에 안 남는다는 것은 main 기준일 뿐이다. 1라운드 `character.vrm`(메타 `personalNonProfit`)이 이미 올라가 있으므로 G0 판정 대상에 넣는다. **생산용 `.vrm` · `.vroid`는 G0 통과 전에 푸시하지 않는다.**
- **개발용 옷 전환 입력은 `cc/env`의 `DEV` 조건 안에 둔다.** 빌드 시점 상수라 릴리스 빌드에서 코드가 제거된다. 상의 B 아틀라스는 컴포넌트가 참조하므로 릴리스에 실리고, 사용자가 main 포함을 정했으므로 받아들인다.
- **장비 · 스킨 시스템 자체는 만들지 않는다.** 슬롯 규칙 · 저장 · 구매 UI · 트랜스모그 우선순위는 v2(F61)다.
- **굽기는 Windows 한 장비에서만 돌면 된다.** 환경은 1라운드 고정값(Blender 5.2.1 LTS · VRM 애드온 v4.7.1, QA §3)을 따른다.
- **옛 이미지 워크플로우 정리는 이번 라운드 밖이다.** 확정 뒤 별도로 하며, 그때 ADR 008(셋업 문서 보존)과 fal.ai를 계속 쓰는 적 · 이펙트 범위를 함께 본다.

| **G4 굽기** | implementation | 고정 카메라로 4방향 × {걷기, 대기} × {맨살 몸, 상의 A, 상의 B, 지팡이, 방패}를 굽는다. 층별 판정, 겹침 측정, 장비끼리 가림 두 판을 로컬 합성 HTML로 비교해 채택하고, 아틀라스를 만든다 | 굽기 · 판정 도구의 같은 오류를 3번 연속 못 고치면 멈추고 보고한다 |
| **G5 본편** | implementation → verification → user-verification | 순수 함수 · 동기화 컴포넌트 · 자식 노드 · 개발용 옷 전환을 구현하고 자동 검증과 정본 선언(G6)을 끝낸 뒤, 사람이 `main.scene`에 연결해 720p · 1440p에서 확인한다 | 린트 · 타입체크 · 테스트의 같은 오류를 3번 연속 못 고치면 멈추고 보고한다. 인게임 문제는 사용자가 `리워크`로 되돌린다 |
| **G6 정본 · ADR** | verification(`pass` 전) | §9 목록과 새 ADR을 쓰고 `wf canon-done`으로 기록한다. rework가 나면 정본 선언이 지워지므로 다시 기록한다. 최종 PR 정리(§10)는 user-verification의 문서 정리 때 한다 | 문서 작업이다 |

라운드를 보류로 닫을지는 사용자가 판단한다. 보류로 닫으면 출하 2D를 유지하고 3D 경로를 보류하며, 판정 결과는 QA 문서에 통과 · 실패를 모두 적는다.

### 6. 렌더 설계

#### 6.1 맨살이 비는 경우

VRoid가 옷 아래 몸 메시를 지워 상의를 끈 렌더에 맨살이 비면, 먼저 상의를 벗긴 판을 VRoid에서 따로 내보낸다. 그래도 맨살을 얻을 수 없을 때만 상의 층을 풀세트 몸 층 교체로 강등하고, QA 문서에 「모듈 워드로브 증명 실패」로 기록한다. 강등하면 R2-D9의 증명은 이번 라운드에서 닫히지 않는다.

#### 6.2 카메라

카메라는 한 번만 계산해 고정한다. 세로 배율과 위치는 **맨살 몸 층의 모든 방향 · 동작 합집합**으로 정해 머리 꼭대기 2행 · 발 밑선 489행을 지킨다. 무기와 상의는 이 계산에 넣지 않는다. 넣으면 머리 위로 올라간 지팡이 때문에 몸의 머리가 2행에서 내려간다.

가로 중심은 상자 중심이 아니라 **루트 본의 회전축**에 고정한다. 상자 중심에 두면 오른손 지팡이 · 왼손 방패 · 3/4 뷰 때문에 몸통이 밀리고, 노드 원점 중심인 피격 사각형(규격 정본 §3.3)이 방향마다 어긋난다.

카메라 위치 · 회전 · 직교 배율과 모델 회전각을 굽기 결과에 기록하고, 모든 굽기가 같은 값인지 판정한다. 1라운드는 굽기마다 합친 상자를 새로 계산했으므로(`retarget_render.py:468-491`, 호출 `:590`) 이 부분은 새로 짠다.

#### 6.3 방향 · 층 · 가림

- **방향은 모델을 돌려 만든다.** 정면 0°, 뒤 180°, 좌우는 3/4 각도다(규격 정본 §3.4). 좌우는 반전하지 않고 따로 굽는다. 지팡이와 방패를 서로 다른 손에 들어서, 반전하면 손이 바뀐다.
- **층은 다섯이다.** 맨살 몸 층(머리 · 하의 · 신발 포함, 상의 없음), 상의 A 층, 상의 B 층, 지팡이 층, 방패 층. 맨살 몸 층을 뺀 네 층은 맨살 몸을 가림 전용으로 두고 굽는다. 기능은 뷰 레이어의 컬렉션 Holdout과 Film Transparent다.
- **가림용 몸과 표시 몸은 늘 같은 판이다.** 모든 굽기에서 가림 전용으로 쓰는 몸은 맨살 몸 층을 구운 바로 그 판(상의 없는 판)이다. 상의 A · B 판에서는 상의 메시만 가져온다. 판마다 흔들림 본 수와 옷 아래 몸 메시가 달라질 수 있어서, G1에서 포즈를 적용한 뒤 머리 · 몸 정점 위치가 판끼리 일치하는지 수치로 잰다.
- **무기는 손 본에 부모로 붙인다.** 지팡이는 오른손, 방패는 왼손이다. 1라운드 `BASE_ARM_POSE`가 왼손을 배꼽 높이에 두어 보조 무기 자리를 비워 뒀다.

#### 6.4 층 합성의 한계와 대안

층을 합성한 결과는 한 번에 렌더한 결과와 같지 않다. 앞에 선 물체(앞머리, 팔)의 경계 픽셀에서 몸 층은 머리와 맨살을 섞어 불투명으로 담고, 상의 층은 그 픽셀에 알파만 남긴다. 둘을 합치면 경계에 맨살색이 스며드는 테두리가 생기고, 상의가 몸에 드리우는 그림자도 몸 층에 없다. 그래서 G2에서 층 합성과 한 번에 렌더한 기준 컷을 픽셀 차이 수치로 견준다. 기준값은 G2에서 실측으로 정하고, 게임 크기(48×96)에서 눈에 띄는지를 사람이 함께 본다.

가림 전용 렌더가 안 될 때의 대안은 Cryptomatte다. 안티앨리어싱된 물체별 매트를 준다. 몸 알파를 빼는 방식은 쓰지 않는데, 방패가 몸통 앞에 있거나 지팡이가 머리카락 앞을 지나는 자리에서 보여야 할 픽셀까지 지우기 때문이다. 이 대안에서도 맨살 몸 층은 상의 없는 판을 단독으로 렌더한다. 상의를 입힌 채 뽑으면 상의에 가려졌던 자리가 비어, 다른 상의 아래에서 구멍으로 드러난다.

외곽선 방식(인버티드 헐 · Line Art · 컴포지터)은 가림과 함께 고른다. 방식에 따라 가림 뒤에 외곽선이 남거나 사라지므로 G2 탐침 컷에서 함께 판정한다.

#### 6.5 장비 · 상의끼리의 가림 실험

먼저 방향 · 프레임마다 두 층의 알파가 겹치는 픽셀 수(지팡이∩방패, 상의∩지팡이, 상의∩방패)를 잰다. 겹침이 0인 조합은 실험하지 않는다. 겹치는 조합만 두 판을 굽는다. 첫째 판은 서로를 가림 전용으로 넣고, 둘째 판은 맨살 몸만 가림 전용으로 넣는다.

두 판을 본편이 아니라 로컬 합성 HTML에서 방패 켜고 끄기 · 상의 A/B 전환으로 보고 사람이 고른다. **판정 기준은 「켜고 끌 때 다른 층에 구멍이 보이면 탈락」이다.** 첫째 판을 채택하면 무기 층이 상의마다 달라져 층 수와 파일 수가 늘어나므로, 그때 §12의 용량 추정을 다시 셈한다.

### 7. 게임 설계

- **PlayerController의 그림 역할을 옮긴다.** 지금 `PlayerController`는 방향 슬롯 넷(`frameFront`~`frameRight`)으로 방향이 바뀔 때 몸 Sprite를 직접 바꾼다(`PlayerController.ts:195-203`, 씬 연결 `main.scene:5189-5204`). 새 동기화 컴포넌트까지 같은 Sprite를 쓰면 실행 순서에 따라 방향 전환 순간 2D 그림이 한 프레임 비친다. 그래서 슬롯 넷과 `_applyFacingFrame`을 지우고, `PlayerController`는 방향 · 이동 여부를 읽기 전용 getter로 내준다. 씬의 슬롯 참조는 사용자가 에디터에서 푼다.
- **「이동 중」은 입력 의도로 판정한다.** `FacingLogic`이 방향을 입력 의도로 정한 것과 맞춘다(`FacingLogic.ts:10-12`). 대가로 벽을 밀면 제자리에서 걷는다.
- **노드 구조.** Player 노드는 지금 자식이 없다(`main.scene:5072`). 맨살 몸 Sprite는 Player에 그대로 두고, 상의 · 지팡이 · 방패를 자식 노드로 더한다. 자식은 Player와 같은 크기 · 원점 (0, 0) · Size Mode CUSTOM · Trim 끔이다. 같은 캔버스 · 같은 카메라로 구웠으므로 오프셋이 필요 없다. 형제 순서는 상의 → 지팡이 → 방패로 시작하고, G4 가림 실험 결과로 확정한다.
- **동작 · 프레임 선택은 순수 함수다.** 규칙은 셋이다. 동작이 바뀌면 프레임을 0으로 되돌린다. 걷는 중 방향이 바뀌면 프레임 번호를 이어 간다. 일시정지 · 레벨업 중에는 시간이 흐르지 않는다(`PlayerController.update`는 Playing이 아니면 빠진다, `:126`).
- **동기화 컴포넌트가 한 시계로 네 Sprite를 넘긴다.** 몸 · 상의 · 지팡이 · 방패에 같은 프레임 번호의 SpriteFrame을 넣는다. 옷 전환은 상의 층이 참조하는 묶음만 바꾸고, 재생 위치가 유지되는지는 이 컴포넌트 쪽 테스트가 본다. `onLoad`에서 모든 층의 (방향, 동작)별 프레임 수가 같은지 검사하고, 다르면 `console.error` 후 컴포넌트를 끈다.
- **프레임 참조는 plist 아틀라스를 권장한다.** 굽기 도구가 plist + png 아틀라스를 만들고, 컴포넌트는 `SpriteAtlas` 속성으로 받아 `getSpriteFrame(이름)`으로 꺼낸다. `@property` SpriteFrame 배열로 하면 사람이 인스펙터에 프레임 수백 개를 끌어다 놓아야 한다. `resources/`에는 아트를 두지 않으므로(규격 정본 §9.1) 경로로 불러오는 방식은 쓰지 않는다. Cocos가 우리 plist를 받아들이지 않으면 `@property` 배열로 물러선다.

### 8. 자동 검증

- 맨살 몸 층에 발 밑선 · 머리 행 · 이웃 차이 · 루프 이음새 판정. 머리 · 발 행은 방향 · 동작 세트마다가 아니라 층 전체 합집합에 건다.
- 상의 · 무기 층에 층 전용 판정: 기록된 카메라 값이 같다, 트림 상자가 캔버스 변에 닿지 않는다. 발 · 머리 행 규칙은 걸지 않는다.
- 모든 층의 (방향, 동작)별 프레임 수가 같다.
- 네 노드의 Sprite Trim이 꺼져 있고 모든 plist 프레임의 원본 크기가 246×493이다. **이 검사는 vitest가 아니라 도구 명령으로 둔다.** `.meta`는 PR 승인 전까지 추적되지 않아, vitest에 넣으면 Cocos를 안 연 장비에서 `start-verification`의 GREEN 게이트가 깨진다. 결과는 QA §8에 「돌렸고 결과는 이러했다」 형태로 적는다.
- 다시 구울 때는 PNG만 바꾸고 `.meta`는 남기는 교체 도구를 쓴다. 렌더 스크립트가 기존 파일을 덮지 않고(`retarget_render.py:553`), `.meta`를 함께 지우면 UUID가 끊긴다.

### 11. 구현 쟁점 — 이 리뷰가 닫는다

설계 방향은 위에서 정했고, 아래는 구현 방법을 정해야 하는 자리다. 설계 초안의 독립 리뷰 2회차가 짚었다.

1. **`frameSetIntegrity`를 세트 판정과 합집합 판정으로 나누는 방법.** 지금 함수는 세트 단위 머리 · 발 판정을 끌 수 없다(`FrameSet.ts:201-224`). 나누는 RED 테스트를 먼저 세운다.
2. **형제 순서가 방향마다 달라야 하는 경우.** 그러면 컴포넌트가 방향마다 `setSiblingIndex`를 하고 테스트가 붙는다.
3. **순수 함수의 매개변수.** 프레임 주기 · 대기 방식(§12의 1 · 2)을 매개변수로 받을지, qa-setup 전에 닫을지. 한 프레임의 `dt`가 한 주기를 넘을 때 여러 장을 건너뛰는지도 정한다.
4. **아틀라스 계약.** 프레임 이름 규칙, plist를 층 · 방향 · 동작 중 어느 단위로 나눌지, 투명 여백을 트림해 담고 offset · 원본 크기로 복원할지. 트림 없이 담으면 한 장이 121,278px이고 다섯 층 240장이면 RGBA로 약 116MB라 GPU 메모리가 먼저 문제다.
5. **정상 산출물을 떨어뜨리지 않는 판정.** 미세한 숨쉬기 대기는 이웃 두 장의 불투명 픽셀 수가 같을 수 있다. 뒷모습에서 몸에 완전히 가려진 지팡이는 비는 것이 정상이다. 대기용 이웃 기준과 방향별 「보여야 할 프레임」을 정한다.
6. **최종 PR 정리의 세부 순서.** §10 표의 도구 교체와 삭제를 어느 커밋에서 할지.

### 12. 남은 질문

1. **대기를 프레임으로 굽을지, 서 있는 한 장 + 노드 트윈(숨쉬기)으로 할지.** 정본 `art-direction.md` §3.2가 노드 트윈을 허용한다. 한 장이면 아래 7번의 용량이 크게 준다. G3 전에 정한다.
2. **걷기 프레임 수와 재생 속도.** 1라운드는 8장 · `Sample` 12였고, 원본 속도인 6은 끊겨 보였다.
3. **카메라 고도.** 1라운드는 수평 직교였다. 탑다운 게임이라 약간 내려다보는 각이 출하 2D와 더 비슷할 수 있어서, G2 비교 시트에서 출하 2D와 견줘 정한다.
4. **지팡이 · 방패 모델 출처.** Blender에서 직접 만든 저폴리, AI 3D 생성 유료 플랜(Tripo · Meshy), 커미션 중 G0에서 정한다. Hunyuan3D는 라이선스가 한국을 이용 지역에서 빼므로 쓰지 않는다.
5. **VRM 메타 값.** `commercialUsage`는 개인 판매면 `personalProfit`, 법인 전환 가능성이 있으면 `corporation`이다. `allowRedistribution` · `modification` · `creditNotation`은 공개 레포 커밋 판정과 함께 G0에서 정한다.
6. **무기 크기 상한.** 머리 위 여백이 2행뿐이고 가로 여백도 양쪽 약 30px라, 지팡이가 머리 위로 올라가거나 방패가 옆으로 뻗으면 잘린다. G1에서 잰 뒤 무기를 맞출지 캔버스 규격을 바꿀지 정한다.
7. **텍스처 용량과 파일 수.** 걷기 8장 · 대기 4장이면 층마다 48장, 다섯 층에 240장이다(가림 첫째 판을 채택하면 더 는다). 맨살 몸 층은 1라운드 프레임처럼 장당 약 113KB, 무기 층은 2D 지팡이 PNG(26.9KB)에 가깝게 작을 것이다. 스프라이트 하나가 빌드 파일 약 둘이 되므로(`ops-build.md` §6.2), 아틀라스 없이는 480개 안팎이 되어 itch.io 여유 928개의 절반을 넘는다. 상의 B는 릴리스에서 보이지 않아도 실린다. 아틀라스 · 트림 · 텍스처 압축 적용 뒤의 실측으로 G4에서 확정한다.
8. **G3 수치 기준을 재는 축.** 「발바닥이 카메라로 향하는 각」과 「발목 좌우 이동」은 정면 기준이다. 3/4 뷰에서는 앞뒤 보폭이 화면 가로로 투영되고, 뒷모습은 발끝을 뗄 때 발바닥이 카메라를 향하는 것이 정상이다. 그래서 모델 기준의 좌우 축으로 재고 정면 뷰에 한정하는 것을 제안한다.
9. **대각선 이동의 방향 표시.** 지금 `facingFromMoveDir`은 대각선을 가로로 접는다. 걷기 애니메이션도 그대로 따르는지 인게임에서 본다.
10. **개발용 옷 전환 입력의 형태.** `DEV` 조건 안의 디버그 키로 할지, 인스펙터 값으로 할지 G5에서 정한다.

- 카메라는 G3 선택 뒤에 명시적 명령으로 한 번 계산해 JSON으로 남기고, 키프레임 정의 · 고도 · 모델 판의 해시를 함께 기록한다. 해시가 현재 입력과 다르면 굽기가 실행을 거부한다. G1은 몸 키 대비 무기 상자 비율만 잠정으로 재고, 무기 수용의 실제 관문은 G4의 「트림 상자가 캔버스 변에 닿지 않는다」다. 대기 기준으로 네 방향의 가장 낮은 발 행이 1px 안에 드는지 보는 판정을 더한다.
- `frameSetIntegrity`를 세트 검사(개수 · 캔버스 · 빈 프레임 · 이웃 · 이음새 · 프레임별 발)와 여러 세트를 받는 합집합 행 검사로 나누고, 기존 함수는 둘을 조합하는 래퍼로 남긴다. 이웃 비교는 불투명 픽셀 수가 아니라 픽셀별 차이(알파나 RGB가 임계값을 넘게 다른 픽셀이 1개 이상)로 바꾼다. 상의 · 무기 층은 빈 프레임을 허용하되 (방향, 동작) 세트마다 비지 않은 장이 1장 이상이어야 하고, 예외는 키프레임 정의와 함께 커밋한 가려짐 목록으로만 둔다.
- 게임 로직을 `scripts/logic` 순수 함수로 정한다. `advanceAnim(state, {facing, moving, ticking, dt}, {fps, counts})`는 동작이 바뀌면 0으로 되돌리고, 걷는 중 방향 전환은 번호를 잇고, ticking이 거짓이면 시간을 멈추고, 번호를 `floor(elapsed * fps) % count`로 구하며 elapsed는 한 주기로 나눈 나머지로 유지한다. `frameName(layer, action, facing, index)`는 확장자 없는 이름을, `validateLayers`는 층별 프레임 수 불일치 목록을, `resolveLayerFrame`은 null일 때 직전 프레임과 이름별 한 번 로그 여부를 돌려준다. 컴포넌트 테스트는 짜지 않는다(레포에 `cc` 모킹이 없다). 옷 전환이 재생 위치를 유지한다는 것은 같은 AnimState에서 상의 A · B의 프레임 이름이 같은 번호를 가리키는지로 단언한다. 이 RED 테스트는 `Blender3dGate.test.ts` 안에서 동적 `await import()`로 불러 그 테스트만 실패하게 하고, `ready-impl` 전에 vitest 출력에서 1라운드 단언과 새 굽기 판정이 통과하는지 확인해 QA에 적는다. 대기 방식(§12.1)과 걷기 프레임 수 · 속도(§12.2)는 이 RED 테스트 전에 닫는다.
- 아틀라스 이름 규칙이 두 곳에 사는 것을 테스트로 묶는다. 작성기(`tools/`, qa-setup)와 `frameName`(`scripts/logic`, implementation)이 모든 (층, 동작, 방향, 번호)에서 같은 문자열을 내는지 vitest가 단언한다. 작성기의 원본 크기는 `PLAYER_FRAME_SPEC`을 import한다.
- 아틀라스 계약을 정한다. 층 × 동작 단위로 나누고, 투명 여백을 트림해 TexturePacker Trim 모드와 같게 원본 크기 246×493과 offset을 plist에 담는다. 회전은 끄고 패딩 2px 이상 · extrude 1로 둔다(밉맵을 켜면 패딩 8). 패킹은 새 패키지 없이 셸프 패킹을 직접 짠다. 트림 상자와 plist 값으로 246×493을 복원해 원본 알파와 바이트가 같은지 보는 왕복 테스트를 둔다. Cocos가 offset을 어떻게 읽는지는 G4 첫 임포트에서 좌우 · 상하가 비대칭인 표식 프레임으로 확인하고, 프레임 이름에서 확장자가 떨어지는지도 그때 본다. G4에서 밉맵을 켠 판과 끈 판을 비교하고, G5 720p 확인에 「걷기 중 반짝임」을 넣는다.
- 동기화 컴포넌트는 `lateUpdate`에서 돈다. `PlayerController`는 `facing` · `isMoving`(입력 의도) · `isTicking`(`_dataReady`이고 Playing일 때) getter를 내주고, 컴포넌트는 그 값만 쓴다. fps는 `@property`로 받고 프레임 수는 아틀라스에서 읽는다. `onLoad`에서 (층, 방향, 동작)별 SpriteFrame 배열을 한 번 만들어 누락 이름을 그때 이름별로 한 번 보고하고, 실행 중에는 매 프레임 이름 문자열을 만들지 않으며 빈 칸이면 직전 프레임을 유지한다. 아틀라스 속성이 비어 있으면 그 층 노드만 끄고 오류를 한 번 남겨, 층별 프레임 수 불일치로 컴포넌트 전체를 끄는 경우와 가른다. 프레임 수 검사 도구는 굽기 폴더가 아니라 `game/assets/`에 들어간 plist를 읽는다.
- 굽기 도구의 생산 입력(`.vrm` · 키프레임 정의) 경로는 인자로 받고, 없으면 무엇이 어디 필요한지 적고 실패한다. G0이 `.vrm`을 레포에 넣지 않는다고 정해도 main의 도구가 없는 레포 경로를 가리킨 채 남지 않게 하려는 것이다. Blender 호출에 `--disable-autoexec`를 명시하고, 외부 무기 모델은 `.glb` · `.obj`로만 받는다. G0 · G1에 VRM 메타의 `authors` · `contactInformation` · `references`에 실명 · 계정 · 연락처가 들어가지 않았는지 확인을 더한다.
- Trim · 원본 크기 검사 도구 명령에 Player `_contentSize` 48×96, 자식 노드 원점 (0, 0), 네 Sprite의 Trim 끔 확인을 함께 넣는다. 판정 함수는 인라인 픽스처로 단위 테스트하고, 실제 `.meta` · 씬에 대한 실행 결과는 QA §8에 적는다.
- G5의 옷 전환 확인은 에디터 프리뷰에서 한다고 명시하고, 디버그 웹 빌드에서 `DEV` 값이 무엇인지 G5에서 확인해 QA에 적는다. 상의 B 아틀라스의 GPU 메모리와 바이트를 §12.7에 넣는다.
- G4에서 층별 아틀라스 바이트 합계가 지금 웹 빌드 전체(4.6MB, `ops-build.md` §6.2)를 넘으면, 줄이는 수단 셋(대기 한 장 + 노드 트윈, 텍스처 압축 프리셋, 캔버스를 절반으로 굽기)을 실측 수치와 함께 사용자에게 올린다. 캔버스 규격은 정본이라 바꿀지는 사용자가 정한다.
- G2 비교 시트에 둘 요괴 표본은 fal 파이프라인이 아니라 사용자가 GPT 웹 프롬프트로 만든 귀신 두 장이다(2026-09-15 최종 관문 D17). 비교용이라 커밋하지 않고, 두 장을 받은 뒤에 비교 시트를 만든다. AI는 `art-generation-playbook.md`의 화풍 조건을 따른 프롬프트 초안을 준비한다. 비교가 보는 것은 컨셉이 아니라 그리는 방식(윤곽 굵기 · 음영 단계 · 채도 · 표시 크기의 선명도)이 한 화면에서 하나의 게임으로 읽히는지다. §4 마지막 항목의 「fal.ai를 계속 쓰는 적 · 이펙트 범위」는 「GPT 웹 프롬프트로 만드는 적 · 이펙트 범위」로 읽는다.

#### 리뷰 절 1~10 (주 리뷰)

**1. 아키텍처.** 새 구성요소의 의존 관계는 이렇다.

```
  VRoid(.vroid) ──내보내기──▶ .vrm(맨살 판 · 상의 A 판 · 상의 B 판)
        │
        ▼
  tools/blender 굽기(카메라 한 번 계산 · 가림 전용 층) ──▶ 층별 PNG ──▶ plist 아틀라스 작성기
        │                                                                     │
        └──판정── tests/helpers/FrameSet.ts(몸 층) · 층 전용 판정                  ▼
                                                              Cocos 임포트(SpriteAtlas, Trim 끔)
                                                                              │
  PlayerController ──getter(방향 · 이동 여부)──▶ 동기화 컴포넌트 ◀──── 동작·프레임 순수 함수
                                                  │
                                    몸 Sprite(Player) · 상의 · 지팡이 · 방패 Sprite(자식)
```

결합이 새로 생기는 곳은 `PlayerController` → 동기화 컴포넌트(getter 둘)뿐이고, 방향 판정을 중복하지 않으므로 받아들인다. 단일 실패 지점은 **아틀라스 프레임 이름 계약**이다. 이름이 어긋나면 `getSpriteFrame`이 null을 돌려 층이 조용히 빈다 — 오류 표면 규칙을 수용 요구사항에 넣었다. 롤백은 출하 2D를 G5 통과 전까지 지우지 않는 것으로 이미 확보돼 있다.

**2. 오류 · 복구 맵.** 아래 「Error & Rescue Registry」에 표로 적었다. 빈틈은 둘이다. 프레임 이름 누락이 조용히 빈 층이 되는 것, 그리고 출하 PNG 삭제로 `AiMatting.test.ts`가 무관해 보이는 이유로 깨지는 것이다. 둘 다 수용 요구사항으로 닫았다.

**3. 보안 · 위협 모델.** 런타임에 새 네트워크 · 인증 · 입력 표면이 없다. 개발용 옷 전환 입력은 `cc/env`의 `DEV`로 릴리스에서 제거된다(가능성 낮음 · 영향 낮음 · 완화됨). 새로 드러난 위협은 공개 레포 노출이다. 이미 푸시된 1라운드 `character.vrm`(`personalNonProfit`)과, 앞으로 올릴 생산 `.vrm` · `.vroid`의 재배포 조건이다(가능성 중 · 영향 중). 푸시 금지 규칙은 이미 있고, 판정 항목(유료 스킨 판매 · 구체 처리안 · 백업 위치)을 G0에 더했다.

**4. 데이터 흐름 · 상호작용 엣지.** 굽기 흐름의 그림자 경로는 이렇다. `.vrm`이 없거나 본 이름이 판끼리 다르면 G1 판정이 잡는다. 맨살이 비면 §6.1 순서를 탄다. 가림 전용 렌더가 알파를 안 비우면 G2 탐침이 잡는다. plist를 Cocos가 거부하면 `@property` 배열로 물러선다. 게임 쪽 상호작용은 걷는 중 방향 전환, 일시정지 · 레벨업 중 정지, 걷는 중 옷 교체, 대각선 입력, 벽을 미는 제자리 걷기다. 앞의 넷은 §7 규칙이 덮고, 벽 제자리 걷기는 받아들인 대가다. 새로 드러난 빈틈은 없다.

**5. 코드 품질.** 프레임 수 · 캔버스 규격을 굽기 스크립트, 판정, 컴포넌트가 각자 들면 한쪽만 고쳤을 때 조용히 어긋난다. 1라운드가 `PLAYER_FRAME_SPEC`으로 이미 한 곳에 모은 방식을 따르게 하는 것이 맞고, 그 배치는 Eng 리뷰(§11-3 · §11-4)가 정한다. 새 추상화 중 필요 없는 것은 없다.

**6. 테스트.** 새 코드 경로는 동작 · 프레임 선택 순수 함수(단위), 동기화 컴포넌트의 프레임 수 불변식과 이름 누락 처리(컴포넌트 테스트), 층 전용 판정(단위), 합집합 판정 분리(단위), Trim · 원본 크기 검사(도구 명령)다. 빈틈은 출하 PNG를 지울 때 깨지는 `AiMatting.test.ts`의 표본과, 프레임 이름 누락 처리 테스트다. 둘 다 수용 요구사항에 넣었다.

**7. 성능.** 플레이어 한 명이 매 프레임 Sprite 넷을 바꾸는 비용은 무시할 수준이다. 층마다 아틀라스를 따로 두면 플레이어가 드로우콜을 최대 넷 쓰는데, 화면 전체에서 작다. GPU 메모리(트림 없이 약 116MB)는 §11-4가 Eng 리뷰로 넘겼다. 새로 더할 것은 없다.

**8. 관측성.** 굽기 결과에 카메라 기록값이 남고, 게임은 불변식 위반을 `console.error`로 알린다. H1로 굽기 벽시계 시간 · 아틀라스 바이트 · 파일 수가 더해진다. 프레임 이름 누락도 한 번씩 로그로 남기게 했다.

**9. 배포 · 롤아웃.** 긴 브랜치에서 `main.scene`을 고치는 것이 가장 큰 위험이다(H3). G5 착수 직전에 main을 병합하고 씬 편집을 짧은 창에 모으는 규칙을 수용했다. 출하 2D는 G5 통과 전까지 남아 되돌릴 자리가 있다. Draft PR #92 재사용은 이미 적혀 있다.

**10. 장기 궤적.** 되돌릴 수 있는 정도는 3/5다. 정본 일곱과 ADR을 다시 쓰고 출하 2D를 지우지만 git 이력에서 되살릴 수 있다. 부채는 굽기 도구 사슬의 유지비(M5)와, 동작 · 방향이 곱으로 늘어나는 비용 구조다. 이 경로 의존이 옳은지는 C1 탐침이 가른다.

**11. 디자인 · UX.** UI 범위가 없어 건너뛴다(Phase 0 판정: UI 단어 0건).

- **A1 씬이 출하 PNG를 두 곳에서 참조한다(H1).** 방향 슬롯 넷(`:5189-5204`)만이 아니라 몸 Sprite의 `_spriteFrame`(`:5160-5163`)도 정면 PNG를 직접 가리킨다. 코드에서 속성을 먼저 지우면 인스펙터에서 슬롯이 사라지고, 몸 Sprite 참조는 그대로 남은 채 PNG가 지워질 수 있다. 사용자가 몸 Sprite를 아틀라스 프레임으로 바꾸고 슬롯을 비워 저장한 뒤 속성을 지우고, UUID 0건 검사가 통과해야 PNG를 지운다. 슬롯을 비운 동안 `_applyFacingFrame`은 null이면 아무것도 안 하므로(`PlayerController.ts:201`) 동기화 컴포넌트와 다투지 않는다. 수용(P1).
- **A2 정리가 검증 뒤에 온다(H2).** `approve-pr`은 타입체크와 `.meta`만 본다(`workflow.mjs:829-859`). 그래서 user-verification에서 PNG · 도구 · 단언을 지우면 스위트가 돌지 않은 트리가 머지된다. 정리를 implementation 안, `start-verification` 전으로 옮긴다. 그러면 사람의 씬 연결도 implementation 안으로 들어오는데, CEO가 수용한 「G5 착수 직전 main 병합 · 짧은 씬 편집 창」이 바로 이 구간이다. 「교체 전과 같은 발치」 비교는 창을 열 때 남긴 720p 캡처로 한다. 보류로 닫으면 브랜치를 머지하지 않으므로 main의 2D는 그대로다. 수용(P1 · P5).
- **A3 층 순서와 가림 판정(H3).** 옷은 맨살 몸보다 크다. 맨살 몸만 가림으로 둔 판에서는 소매 뒤, 몸 실루엣 밖에 걸친 지팡이 픽셀이 지워지지 않고, 지팡이 노드가 상의 위에 있어 소매 앞에 그려진다. 구멍이 아니라서 「켜고 끌 때 구멍」 기준을 통과한다. 판정을 게임에 있는 조합마다 기준 컷과 견주는 것으로 바꾸고 두 오류를 모두 센다. 방패는 v2 전까지 늘 장착이라 게임의 조합은 상의 A · B 둘이다. 서로를 가림으로 둔 판에서는 층마다 보이는 픽셀만 남아 형제 순서가 경계 픽셀에만 영향을 준다. 대신 무기 층이 상의마다 생기므로 곱 항을 처음부터 용량 추정과 비용 공식에 넣는다. 수용(P1), 프레임별 순서 JSON은 조건부(P3).
- **A4 카메라 결정 순서와 고도(H5).** 카메라 배율은 맨살 몸의 모든 방향 · 동작 합집합으로 정하므로 G3 이후에야 나온다. 그런데 G1이 「고정 카메라」로 무기 수용을 잰다고 적혀 있다. 고도를 주면 발이 카메라에서 떨어진 거리에 따라 다른 행에 투영되어 방향마다 발 밑선이 달라지고, 합집합 판정은 이를 못 잡는다. 카메라를 명시적 명령과 입력 해시로 고정하고 방향 간 발 행 판정을 더한다. 수용(P1 · P5).
- **A5 시계와 실행 순서(M3).** 동기화 컴포넌트가 스스로 멈춤을 판정하면 레벨업 중에도 시계가 흐를 수 있고, `update` 순서에 따라 한 프레임 늦는다. `lateUpdate`와 `PlayerController` getter 셋으로 기준을 하나로 둔다. 수용(P5).

#### 절 2. 코드 품질

- **Q1 아틀라스 이름 규칙이 두 곳에 산다(주 리뷰).** 작성기는 qa-setup(G4)에 `tools/`에서 만들고 `frameName`은 implementation에 편집 게이트 대상인 `scripts/logic`에서 만든다. #### 절 4. 성능

- **GPU 메모리.** 트림 없이 담으면 약 116MB다(§11-4). 층 × 동작 아틀라스에 트림을 걸면 몸 48장이 약 5.0M px(RGBA 약 20MB)이고, 몸 걷기 32장은 2048×2048 한 장에 들어간다. 상의 · 무기는 트림 효과가 커서 전체는 40~60MB로 추정한다. 서로를 가림으로 둔 판을 채택하면 무기 몫이 상의 수만큼 곱해진다. G4 실측으로 확정한다.
- **다운로드 용량(주 리뷰).** 지금 웹 빌드는 72파일 · 4.6MB다(`ops-build.md` §6.2). 몸 층만 1라운드 프레임 기준 장당 약 113KB × 48장 ≈ 5.4MB라, 아틀라스로 묶어도 빌드가 두세 배가 될 수 있다. CEO가 수용한 G4 아틀라스 바이트 기록에 트리거를 붙인다. 합계가 지금 빌드 전체를 넘으면 줄이는 수단 셋을 수치와 함께 사용자에게 올린다. 표시 크기는 720p에서 48×96, 1440p에서 96×192라 절반 캔버스(123×247)도 1440p에서 1.28배 여유가 있다. 다만 캔버스는 정본 규격(`art-asset-spec.md` §12, 2026-08-07 실측)이라 사용자가 정한다.
- **축소 반짝임.** 출하 PNG는 `mipfilter` none이다. 246×493을 48×96으로 약 5배 줄이면 정지 그림에서는 안 보이던 반짝임이 걷기에서 드러날 수 있다. G4에서 밉맵 판과 견주고 G5 720p 확인에 넣는다(M2).
- **드로우콜 · 할당.** 층 넷이 서로 다른 텍스처라 드로우콜이 약 넷 늘지만 플레이어 하나라 받아들인다. 매 프레임 이름 조립은 Q5로 없앤다. 네트워크 · DB가 없어 N+1 · 캐시 항목은 해당 없다.

- 아틀라스 이름 규칙이 두 곳에 사는 것을 테스트로 묶는다. 작성기(`tools/`, qa-setup)와 `frameName`(`scripts/logic`, implementation)이 모든 (층, 동작, 방향, 번호)에서 같은 문자열을 내는지 vitest가 단언한다. 작성기의 원본 크기는 `PLAYER_FRAME_SPEC`을 import한다.
- 아틀라스 계약을 정한다. 층 × 동작 단위로 나누고, 투명 여백을 트림해 TexturePacker Trim 모드와 같게 원본 크기 246×493과 offset을 plist에 담는다. 회전은 끄고 패딩 2px 이상 · extrude 1로 둔다(밉맵을 켜면 패딩 8). 패킹은 새 패키지 없이 셸프 패킹을 직접 짠다. 트림 상자와 plist 값으로 246×493을 복원해 원본 알파와 바이트가 같은지 보는 왕복 테스트를 둔다. Cocos가 offset을 어떻게 읽는지는 G4 첫 임포트에서 좌우 · 상하가 비대칭인 표식 프레임으로 확인하고, 프레임 이름에서 확장자가 떨어지는지도 그때 본다. G4에서 밉맵을 켠 판과 끈 판을 비교하고, G5 720p 확인에 「걷기 중 반짝임」을 넣는다.
- 동기화 컴포넌트는 `lateUpdate`에서 돈다. `PlayerController`는 `facing` · `isMoving`(입력 의도) · `isTicking`(`_dataReady`이고 Playing일 때) getter를 내주고, 컴포넌트는 그 값만 쓴다. fps는 `@property`로 받고 프레임 수는 아틀라스에서 읽는다. `onLoad`에서 (층, 방향, 동작)별 SpriteFrame 배열을 한 번 만들어 누락 이름을 그때 이름별로 한 번 보고하고, 실행 중에는 매 프레임 이름 문자열을 만들지 않으며 빈 칸이면 직전 프레임을 유지한다. 아틀라스 속성이 비어 있으면 그 층 노드만 끄고 오류를 한 번 남겨, 층별 프레임 수 불일치로 컴포넌트 전체를 끄는 경우와 가른다. 프레임 수 검사 도구는 굽기 폴더가 아니라 `game/assets/`에 들어간 plist를 읽는다.
- 굽기 도구의 생산 입력(`.vrm` · 키프레임 정의) 경로는 인자로 받고, 없으면 무엇이 어디 필요한지 적고 실패한다. G0이 `.vrm`을 레포에 넣지 않는다고 정해도 main의 도구가 없는 레포 경로를 가리킨 채 남지 않게 하려는 것이다. Blender 호출에 `--disable-autoexec`를 명시하고, 외부 무기 모델은 `.glb` · `.obj`로만 받는다. G0 · G1에 VRM 메타의 `authors` · `contactInformation` · `references`에 실명 · 계정 · 연락처가 들어가지 않았는지 확인을 더한다.
- Trim · 원본 크기 검사 도구 명령에 Player `_contentSize` 48×96, 자식 노드 원점 (0, 0), 네 Sprite의 Trim 끔 확인을 함께 넣는다. 판정 함수는 인라인 픽스처로 단위 테스트하고, 실제 `.meta` · 씬에 대한 실행 결과는 QA §8에 적는다.
- G5의 옷 전환 확인은 에디터 프리뷰에서 한다고 명시하고, 디버그 웹 빌드에서 `DEV` 값이 무엇인지 G5에서 확인해 QA에 적는다. 상의 B 아틀라스의 GPU 메모리와 바이트를 §12.7에 넣는다.
- G4에서 층별 아틀라스 바이트 합계가 지금 웹 빌드 전체(4.6MB, `ops-build.md` §6.2)를 넘으면, 줄이는 수단 셋(대기 한 장 + 노드 트윈, 텍스처 압축 프리셋, 캔버스를 절반으로 굽기)을 실측 수치와 함께 사용자에게 올린다. 캔버스 규격은 정본이라 바꿀지는 사용자가 정한다.
- G2 비교 시트에 둘 요괴 표본은 fal 파이프라인이 아니라 사용자가 GPT 웹 프롬프트로 만든 귀신 두 장이다(2026-09-15 최종 관문 D17). 비교용이라 커밋하지 않고, 두 장을 받은 뒤에 비교 시트를 만든다. AI는 `art-generation-playbook.md`의 화풍 조건을 따른 프롬프트 초안을 준비한다. 비교가 보는 것은 컨셉이 아니라 그리는 방식(윤곽 굵기 · 음영 단계 · 채도 · 표시 크기의 선명도)이 한 화면에서 하나의 게임으로 읽히는지다. §4 마지막 항목의 「fal.ai를 계속 쓰는 적 · 이펙트 범위」는 「GPT 웹 프롬프트로 만드는 적 · 이펙트 범위」로 읽는다.

### 단계를 가로지른 주제

CEO와 Eng의 독립 리뷰어가 서로 다른 입력에서 같은 곳을 짚은 것이다. 신호가 강한 곳이라 구현 때 먼저 본다.

- **출하 2D를 지우는 경로.** CEO는 `AiMatting.test.ts`가 출하 PNG를 직접 읽어 삭제로 깨지는 것을 짚었다. Eng는 몸 Sprite가 같은 PNG를 씬에서 직접 참조하는 것(A1)과 정리가 검증 뒤에 오는 것(A2)을 짚었다. 세 지적은 모두 「2D를 지우는 순간 무관해 보이는 곳이 깨진다」는 한 가지 위험이다. 수용 항목이 픽스처 이전 → 씬 참조 끊기 → UUID 0건 확인 → 삭제 → GREEN 게이트 순서로 묶었다.
- **게임 코드 테스트의 계약.** CEO는 RED 테스트가 아직 정해지지 않은 계약(대기 방식 · 프레임 수 · 아틀라스 · 형제 순서)에 기댄다는 것을 짚었다. Eng는 계획이 적은 컴포넌트 테스트를 이 레포 방식으로 짤 수 없다는 것(H4)과 아틀라스 이름 규칙이 두 곳에 산다는 것(Q1)을 짚었다. 계약은 G4까지 닫고, 판단은 순수 함수로 빼고, 이름 규칙은 같음 단언으로 묶었다.
- **곱으로 늘어나는 비용.** CEO는 생산 비용이 측정되지 않았다는 것(H1)을 짚었다. Eng는 상의마다 무기 층을 따로 굽는 경우의 곱 항(A3)과 빌드 용량이 두세 배가 될 수 있다는 것을 짚었다. G4 비용 기록에 곱 항과 용량 트리거를 붙였고, ADR 009 비용 공식이 나중 판단의 근거를 남긴다.
- **공개 레포 노출.** CEO는 이미 푸시된 1라운드 `.vrm`의 처리와 `.vroid` 보관(M4)을, Eng는 VRM 메타의 개인정보 필드(M6)를 짚었다. 둘 다 G0 · G1 판정 항목에 들어갔다.
- **`main.scene` 편집.** CEO는 긴 브랜치의 씬 충돌(H3)을, Eng는 씬에 남은 옛 UUID(A1)를 짚었다. 씬 편집을 G5 착수 직전 main 병합 뒤의 짧은 창에 모으고, 그 창 안에서 참조 끊기와 검사를 끝낸다.
