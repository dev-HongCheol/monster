## 1. 무엇을 판정하나

1라운드(2026-09-11~15)는 VRoid `.vrm`을 Blender 스크립트로 구워 Cocos에서 재생하는 사슬이 선다는 것을 정면 걷기 8장으로 증명했다(게이트 다섯 통과, QA §10). 그러나 그 증명은 시험 캐릭터 · 정면 한 방향 · 테스트 씬에 머물렀다.

2라운드는 **이 방식으로 플레이어 아트를 생산해도 문제가 없는가**를 게임 본편에서 판정한다. 끝나면 출하된 2D 4방향 아트를 3D 렌더로 교체하고, 지팡이와 방패를 기본 무기로 들린다. 앞으로 붙을 옷과 장비가 같은 방식 위에 설 수 있는지는 상의 한 층 교체로 확인한다. 3D 워크플로우가 확정되기 전에는 main에 머지하지 않는다.

3D 경로를 고른 이유는 셋이다.

- **몸과 무기의 가림.** 2D 생성에서는 지팡이가 머리카락 위를 지나므로, 지팡이를 걷어 내면 그 뒤에 그려진 것이 없었다(F67). 3D에서는 몸과 지팡이를 같은 카메라로 따로 굽고, 지팡이 층을 구울 때 몸을 가림 전용으로 두면 몸에 가려진 지팡이 픽셀이 투명하게 나온다.
- **프레임 사이의 인물 일관성.** 2D 생성으로 같은 인물을 얻은 것은 4방향 정지 그림까지다(2026-08-06). 걷기처럼 방향마다 여러 프레임이 필요하면 프레임끼리 같은 인물인지 보장할 수단이 없다. 3D는 모든 프레임을 한 모델에서 굽는다.
- **옷 · 장비를 갈아입는 한계비용.** 옷 한 벌을 층 하나로 굽고 게임에서는 층만 바꾸므로, 옷을 더해도 몸 층을 다시 굽지 않는다. 다만 장비끼리의 가림 결과에 따라 무기 층이 상의 수만큼 늘 수 있고, 그 비용은 G4에서 잰다.

## 2. 결정

### 2.1 설계 결정 (2026-09-15, 사용자)

번호에 `R2-`를 붙인다. 정본 쪽 「재조사 D10」(`art-direction.md:169`) 같은 옛 번호와 섞이지 않게 하려는 것이다.

- **R2-D1 끝 지점은 본편이다.** `main.scene`에서 생산 캐릭터가 4방향으로 움직이는 것까지 본다. 판정 박스 · 발치 · 방향 전환 문제는 본편에서만 드러나기 때문이다.
- **R2-D2 캐릭터는 정본 외형으로 새로 만든다.** 젊은 여성 마법사 · 긴 주홍 머리 · 호박색 눈 · 창백한 피부 · 천옷 · 4등신(`art-direction.md` §6). 툰 세팅 값은 머리색과 의상에 따라 달라지므로 시험 캐릭터로 맞춘 값은 버려진다.
- **R2-D3 동작은 걷기 · 대기 두 개다.** 게임이 이동 중에도 쿨다운마다 자동 발사하므로(`SpellCaster.update`) 시전 포즈를 따로 구우면 걷기가 끊긴다. 시전은 지금처럼 이펙트로만 표현한다. 피격 · 사망은 게임에 그림 연출 자체가 없어 범위 밖이다.
- **R2-D4 지팡이는 별도 층으로 굽는다.** F67 결정과 규격 정본 §3.3(지팡이가 구워진 몸 금지)을 그대로 지킨다.
- **R2-D7 걷기 · 대기는 스타일 키프레임으로 짠다(F106 ①).** 성인 모션을 저등신에 옮기면 비율로 못 빼는 성분 둘(발목 좌우 3.2cm · 발바닥 최대 16°)이 남는다.
- **R2-D8 방패 층을 더한다.** 지팡이 하나로는 장비끼리 서로 가릴 때 조합마다 다시 구워야 하는지를 잴 수 없다.
- **R2-D9 옷은 모듈 방식으로 증명한다.** 맨살 몸 층 위에 상의 층(A · B)을, 몸을 가림 전용으로 두고 구워 교체한다. 풀세트 몸 층 교체는 조합마다 몸 층을 다시 굽게 되고, 정본 워드로브에서 가장 실패하기 쉬운 층 겹침을 증명하지 못해서 기각했다.
- **R2-D10 모양을 갖춘 지팡이와 방패를 v1 기본 무기로 장착해 v2 전까지 쓴다.** v2 스킨까지 단계가 많이 남았기 때문이다. 방패 · 상의 B · 개발용 옷 전환 입력도 최종 PR로 main에 넣는다. 상의 B와 옷 전환 입력을 게임에 연결하는 몫은 증명 자체에는 필요 없고, 이 결정으로 싣는다.
- **R2-D11 반복 한도는 AI가 같은 기술 문제를 연속으로 풀지 못할 때만 센다.** 구현한 코드의 린트 · 타입체크 · 테스트 오류나 굽기 스크립트 오류를 같은 원인으로 3번 연속 고치지 못하면 멈추고 상황을 보고한다. 사람이 판정하는 반복(화풍 · 동작 · 가림 선택 · 인게임 확인)은 한 이슈를 풀기 위한 반복이라 세지 않고, 계속할지 보류할지는 사용자가 판단한다.
- **라이선스.** 개발자가 VRoid로 만든 캐릭터를 렌더해 상업 게임에 싣는 것은 허용 범위다(사용자가 교차 확인한 판정). 다만 VRoid 기본 데이터는 CC0가 아니고, 캐릭터 생성 · 내보내기 서비스를 만들면 별도 라이선스가 필요하며, 제3자 에셋은 개별 조건을 따른다. **그래서 캐릭터와 옷은 VRoid 기본 프리셋 + 직접 수정 + 직접 만든 텍스처로만 구성한다.** 원문 확인은 G0이 한다.

### 2.2 최종 관문 결정 (2026-09-15, 사용자)

- **D15 런타임 3D 탐침은 하지 않는다.** 이 슬라이스의 목표가 굽기 흐름의 판정이기 때문이다. G4 용량 트리거가 걸리면 그 수치가 런타임 3D를 다시 꺼낼 근거가 된다.
- **D16 라운드에 달력 기한을 두지 않는다.** R2-D11대로 보류 판단은 사용자가 한다.
- **D17 G2 화풍 비교에 귀신 표본 두 장을 둔다.** 사용자가 GPT 웹 프롬프트로 만들고 커밋하지 않는다. 2D 이미지 생성은 fal.ai 대신 GPT 웹 프롬프트로 하기로 했다(fal에서 채택한 모델도 gpt-image였다).
- **D18 방패는 R2-D10대로 유지하고, G5에서 막기 수단으로 오해되는지 확인한다.**

### 2.3 기각한 안

- 시험 캐릭터로 먼저 끝내기 — 툰 · 크기 값을 생산 캐릭터에서 다시 맞추게 된다.
- F67의 2D 생성 경로(지팡이를 지운 변형본 생성) — 가림은 풀어도 걷기 프레임의 인물 일관성과 옷 교체 비용을 풀지 못한다.
- 멈췄을 때만 시전 포즈 / 상체 · 하체 분리 시전 — 이번 라운드 밖(R2-D3).
- 지팡이를 몸과 한 장으로 굽기 — F67 · §3.3 위반.
- 지팡이만 굽기 — 장비끼리 가림 조합 문제가 미지수로 남는다(R2-D8).
- 풀세트 몸 층 교체 — 모듈 워드로브를 증명하지 못한다(R2-D9).
- 방패 · 상의 B를 브랜치 증명물로만 두기 — 기본 무기로 쓰기로 했다(R2-D10).
- 게이트별 회차 상한 — 사람 판정 반복까지 세면 한 이슈의 다듬기가 한도에 걸린다(R2-D11).
- 모션 필터(F106 ②) — 필터로 춤추는 느낌이 안 빠지면 반복만 쓰고, 모션 파일 라이선스 행이 남는다.
- 정지 1장 + 코드 흔들림 — 프레임 애니메이션 능력을 본편에서 시험하지 않는다.
- 게임 연결을 `cc.Animation` 클립으로 하기 — 방향 · 동작 · 층 조합만큼 클립이 늘고, 클립이 `.meta` UUID를 참조해 사람이 손으로 만들어야 하며, 옷 교체 때 재생 위치를 유지하는 방법이 매뉴얼로 확인되지 않았다.
- Cocos Auto Atlas — 프레임 240장 이상이 개별 PNG와 `.meta`로 들어가고, 런타임에 이름으로 꺼내는 경로가 매뉴얼로 확인되지 않았다.
- 가림 대안으로 Object Index 쓰기 — 픽셀당 값 하나라 경계가 계단지고, EEVEE 지원 여부도 확인되지 않았다. 대안은 Cryptomatte다.

## 4. 공통 제약

- **판정 규칙은 바꾸지 않는다.** 피격 사각형과 이동 원은 `resources/data/player.json` 고정값이다(ADR 007). 방패와 상의는 외형만 바꾸고 판정을 바꾸지 않는다. 발치 오프셋만은 아직 Player 노드의 `UITransform.height`에서 유도되므로(`PlayerController.ts:83`, F64 미이행), Player 노드의 UITransform과 몸 Sprite를 옮기거나 크기를 바꾸지 않는다.
- **그림 규격은 기존 값이다.** 캔버스 246×493 · 발 밑선 489행 · 머리 꼭대기 2행(`tests/helpers/FrameSet.ts`의 `PLAYER_FRAME_SPEC`).
- **게임 코드는 워크플로우 게이트를 탄다.** `game/assets/scripts/**` 편집은 implementation · verification phase에서만 열린다. G1~G4는 `main.scene`과 `game/assets/scripts/**`를 열지 않는다. 판정은 `logic/` 순수 함수로 두고 테스트를 RED로 먼저 세운다(ADR 002 · 003).
- **긴 브랜치의 씬 충돌을 막는다.** G5 착수 직전에 `origin/main`을 이 브랜치로 병합하고 씬 편집을 짧은 창에 모은다. 그 창 동안 main에 `main.scene` · `PlayerController.ts`를 건드리는 머지를 하지 않는다.
- **슬러그는 `blender-3d-gate`를 유지한다.** 새 RED 테스트는 기존 `tests/logic/Blender3dGate.test.ts`에 더하고, QA 문서도 기존 `docs/qa/blender-3d-gate-test.md`에 2라운드 절을 더한다. 게이트 판정 결과는 QA 문서에 적는다(G0만 게이트 문서에 적는다). `approve-plan`은 1라운드 계획 문서만으로도 통과하므로 실제 관문은 사용자의 `계획 승인`이다.
- **Draft PR #92를 재사용한다.** 2라운드가 user-verification에 들어갈 때 제목과 본문을 2라운드 범위로 갈아 쓴다.
- **`.meta`는 AI가 만들지 않는다.** 새 에셋의 `.meta`는 사용자가 Cocos에서 생성하고 PR 승인 때 커밋한다. AI는 Cocos가 만든 `.meta`를 읽어서 검사만 한다.
- **레포는 공개이고, 브랜치에 푸시한 것은 PR ref로 남는다.** squash merge라 main 히스토리에 안 남는다는 것은 main 기준일 뿐이다. 생산용 `.vrm` · `.vroid`는 G0 통과 전에 푸시하지 않는다.
- **개발용 옷 전환 입력은 `cc/env`의 `DEV` 조건 안에 둔다.** 확인은 에디터 프리뷰에서 한다. 상의 B 아틀라스는 씬이 참조하므로 릴리스에 실리고, 사용자가 main 포함을 정했으므로 받아들인다.
- **장비 · 스킨 시스템 자체는 만들지 않는다.** 슬롯 규칙 · 저장 · 구매 UI · 트랜스모그 우선순위는 v2(F61)다.
- **굽기는 Windows 한 장비에서만 돌면 된다.** 환경은 1라운드 고정값(Blender 5.2.1 LTS · VRM 애드온 v4.7.1, QA §3)을 따른다.
- **옛 이미지 워크플로우 정리는 이번 라운드 밖이다.** 확정 뒤 별도로 하며, 그때 ADR 008(셋업 문서 보존)과 GPT 웹 프롬프트로 만드는 적 · 이펙트 범위를 함께 본다.
