## 1. 이 검토가 나온 맥락

"맥북 M1 Air 16GB에서 아트 작업이 가능한가"라는 물음에서 시작했다. M1 Air의 제약을 짚다 보니, 무거운 생성은 지금의 윈도우 머신(RTX 3070 Ti 8GB)에 남기고 맥은 그 결과물을 받아 마감·통합만 하는 **크로스머신 분리** 구도가 자연스럽게 떠올랐다. 이 문서는 그 구도가 성립하는지, 성립한다면 경계를 어디에 긋는지를 정리한다.

## 2. M1 Air 16GB의 제약 — 생성은 되고 학습은 막힌다

아트 부하는 성격이 다른 두 가지로 갈리고, M1 Air에서의 가능 여부가 이 둘에서 갈린다.

- **이미지 생성(ComfyUI 추론):** 된다. ComfyUI가 애플 실리콘 MPS 백엔드를 지원하고, 16GB 통합 메모리는 오히려 지금의 8GB VRAM보다 추론용 여유가 크다(다만 OS·앱과 공유). 대신 base M1의 GPU(7~8코어)라 장당 시간이 3070 Ti보다 크게 늘고, **에어는 팬이 없어** 후보를 배치로 뽑으면 발열 스로틀로 뒤로 갈수록 느려진다.
- **LoRA 학습(kohya):** 사실상 막힌다. `kohya-setup.md` §3의 8GB 레시피는 그 대들보가 `--optimizer_type AdamW8bit`인데, 이 8bit 옵티마이저를 제공하는 bitsandbytes가 **CUDA 전용**이라 애플 실리콘에서 돌지 않는다. 옵티마이저를 일반 AdamW로 바꾸면 옵티마이저 상태 메모리가 4배로 늘어(8bit→32bit) 통합 메모리에서 OOM으로 떨어진다. `bf16`·`sdpa`·`max_split_size_mb`도 Ampere/CUDA 기준으로 튜닝된 값이라 맥에서 그대로 넘어오지 않는다.

**함의:** 학습은 지금의 윈도우 3070 Ti 머신에 묶여 있다. `kohya-setup.md` §1.1이 "로컬로 확정"한 것은 그 8GB 윈도우 머신 실측에 근거한 결론이라, 맥으로는 그 결론이 넘어오지 않는다. 학습이 다시 필요한 시점(다음 리깅 슬라이스의 **캐릭터 LoRA**, art-direction §8-1)에는 윈도우에서 굽거나, 정 맥에서만 작업해야 하면 클라우드 GPU(RunPod 등)로 학습만 돌린다.

**단, 이번 F60(마법사 브릿지) 슬라이스는 학습이 아니라 생성만 필요하고 쓸 LoRA(`f58_anime_style`)는 이미 구워져 있으므로**, 이 슬라이스에 한해서는 학습 제약이 걸리지 않는다.

## 3. 제안하는 분리 — GPU 스텝은 윈도우, 편집 스텝은 맥

두 머신 사이에 오가는 **핸드오프 산출물이 PNG 파일 하나**라는 점이 이 분리를 깨끗하게 만든다. PNG에는 CUDA/MPS 같은 하드웨어 종속이 묻지 않으므로, 경계가 물리적으로 또렷하게 그어진다. art-direction §8의 후속 단계를 필요 자원 기준으로 가르면 아래와 같다.

| 단계 | 필요 자원 | 머신 |
|------|-----------|------|
| SDXL+LoRA 생성 | 디퓨전 모델(GPU) | **윈도우** |
| 배경 제거 | LayerDiffuse=GPU / rembg=CPU(가벼움) | 경계 — §4 참조 |
| 엠버 발광 엣지 손터치 | 사람 눈·CPU | **맥** |
| Cocos 임포트·조립 | 에디터 | **맥** |
| (후속) 파츠 컷 | 이미지 편집 | 맥 |
| (후속) 인페인팅 | 디퓨전(GPU) | 윈도우 |
| (후속) 리깅(Spine) | 데스크톱 툴(F59) | 맥 |

원칙 하나로 요약하면, **디퓨전 모델을 만지는 스텝은 전부 윈도우로 두고, 파일 편집·에디터·리깅·통합은 맥으로 둔다.** 후속 슬라이스(인페인팅은 GPU, 파츠 컷·리깅은 편집)까지 이 선이 그대로 성립한다.

## 4. 경계를 어디에 긋나 — 미확정 결정 3개

아래 셋은 확정하지 않는다. 나중에 실제로 세팅할 때 고르고, 고른 근거를 그 시점 문서에 박는다.

1. **배경 제거를 어디서 하나.** 권장은 **윈도우가 배경까지 뺀 최종 투명 PNG를 넘기는 것**이다. 그러면 맥은 "바로 임포트 가능한 완성 에셋"만 받고 rembg조차 필요 없다. 특히 계획서(F60 §5·§132)가 짚은 **LayerDiffuse(투명 네이티브)를 쓰면 배경 제거가 별도 스텝이 아니라 생성 자체에 흡수**되어 맥 쪽이 더 단순해진다. 다만 rembg는 CPU만으로도 충분히 가벼워 맥에서 해도 되긴 한다.
2. **핸드오프 방식.** (A) 파일/폴더 동기화 — 윈도우가 PNG를 폴더에 떨구고 맥과 동기화, 맥은 최종 선택본만 집는다. 지금 규약(대용량은 `F:\ai` 레포 밖, 텍스트만 커밋)과 맞고 추가 인프라가 거의 없어 **검토 단계엔 A를 권장**한다. (B) 생성을 LAN API 서비스로 — 아래 §5.
3. **동기화 수단.** 단발이면 AirDrop·USB, 상시면 SMB(맥 내장) 또는 Syncthing(P2P, 클라우드 불필요) 중에서 고른다.

## 5. 프로세스 계약 — 재현성이 이미지에 따라붙게

경계를 진짜 "블랙박스 프로세스"로 만들려면, 입력과 출력을 이렇게 못박는다.

- **입력 = 생성 스펙:** 체크포인트 해시, LoRA와 강도, 프롬프트/네거티브, 샘플러/스텝/CFG, 해상도, 시드 목록.
- **출력 = PNG + 그 스펙을 담은 매니페스트 JSON:** PNG 옆에 `<이미지>.json`을 함께 떨군다.

이건 새로 만드는 규약이 아니라 `comfyui-setup.md` §6과 F60 계획서 §123의 "재현 규약"을 이미지에 붙여 내보내는 것뿐이다. 이렇게 하면 맥은 SDXL/CUDA를 전혀 몰라도 PNG와 매니페스트만 소비하면 되고, 나중에 생성을 클라우드로 옮겨도 계약은 그대로이며 엔드포인트만 바뀐다.

**LAN API로 갈 경우(§4의 B):** ComfyUI를 `--listen 0.0.0.0`으로 LAN에 열면 맥이 워크플로 JSON을 윈도우로 POST하고 `/view`로 결과를 당겨온다. 지금 드라이버(`F:\ai\gen_mage_bridge.py`)가 이미 `post_prompt`/`wait_result`/`view` 구조라, 클라이언트만 맥으로 옮기고 SERVER를 윈도우 LAN IP로 바꾸면 된다.

## 6. 맥에 새로 깔 것 / 안 깔 것

AI 스택은 맥에 **하나도 깔지 않는다** — 그게 이 분리의 핵심 이득이다.

| 용도 | 도구 | 맥 설치 |
|------|------|---------|
| 최종 PNG 받기 | AirDrop·USB / SMB(맥 내장) / Syncthing | 대부분 무설치(Syncthing만 설치) |
| 엠버 발광 엣지 손터치 | Photopea(브라우저) 또는 Krita | Photopea=무설치 / Krita=설치 |
| Cocos 임포트·조립 | Cocos Creator 3.8 | 게임 개발용 — 이미 세팅돼 있으면 0 |
| 레포·`wf` 워크플로 | git · Node · pnpm | 게임 개발용 — 이미 있으면 0 |
| 배경 제거(맥에서 할 경우만) | rembg(Python pip) | 윈도우가 투명 PNG로 내보내면 불필요 |
| SDXL·ComfyUI·LoRA·CUDA | — | 전혀 불필요 |

맥에 새로 까는 것이 있다면 그건 AI 준비가 아니라 게임 개발·이미지 마감 준비다. 그 맥이 아직 이 레포의 개발 환경으로 세팅돼 있지 않으면 Cocos Creator와 Node/pnpm/git 정도는 깔아야 한다.

## 7. 보안 주의 — LAN API로 갈 때만

`--listen 0.0.0.0`은 **인증이 없는** 노출이다. ComfyUI는 커스텀 노드로 임의 코드 실행이 가능한 표면이라, 신뢰된 홈 LAN 안에서만 쓰고 포트포워딩으로 외부에 열지 않는다. 외부에서 접근이 필요하면 SSH 터널을 쓴다. 인터넷에 그대로 노출하면 누구나 워크플로를 밀어 넣어 그 머신에서 코드를 돌릴 수 있으므로 원격 코드 실행 위험이 된다.

## 8. 이게 안 바꾸는 것

생성 드라이버는 원래 레포 밖(`F:\ai`)에 있으므로, 이 분리를 프로세스화해도 게임 레포와 `wf` 워크플로를 건드리지 않는다. 레포가 보는 것은 텍스트 기록(세션·QA 문서)과, 나중에 임포트한 PNG 에셋 및 Cocos가 생성하는 그 `.meta`(PR 승인 시점 커밋)뿐이고, 이 셋은 이 분리와 무관하게 그대로다.
