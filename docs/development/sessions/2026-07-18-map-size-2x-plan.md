- **작성일:** 2026-07-18
- **상태:** 계획 — 사용자 승인 대기
- **브랜치:** feat/map-size-2x
- **백로그:** 이 슬라이스가 새로 닫는 사전 등록 항목은 없다(맵 사이징은 F40 다중맵·F41 아트·F42 카메라와 별개). **함께 처리:** F38·F43 완료 아카이브 이동(building-collision이 닫았으나 아직 열림 표에 남아 있는 것 — 이 브랜치에 얹는다).

## 1. 배경 — 왜 2배로

지금 서울 아레나는 2400×2400이다. 앞으로 도로 배경·부서진 차량·건물·유명 랜드마크(부서진 경복궁·남산타워)를 채워 "귀신에게 침략당한 서울"을 표현하려는데, 현재 크기로는 그 콘텐츠를 벌려 놓을 공간이 빠듯하다. 맵을 먼저 넓혀 두면 뒤이을 콘텐츠 슬라이스(도로·장애물·랜드마크 배치)가 여유를 갖는다. 이 슬라이스는 **리사이즈만** 담당하고, 실제 콘텐츠 배치는 후속이다.

## 2. 확정 스코프 (2026-07-18 사용자)

| 결정 | 값 |
|------|-----|
| "2배"의 정의 | **각 변 ×2 → 4800×4800** (면적 4배) |
| 한강(물 구역) | **폴리곤도 함께 ×2** — 강이 넓어진 맵을 계속 가로지른다 |
| 기존 장애물 | **이 슬라이스에서 흩뿌린다**(7단계 에디터) — 중앙 클러스터로 두지 않는다 |

## 3. 변경 범위 (엔지니어링 실사 결과)

코드 실사에서 **맵 크기를 하드코딩한 함수는 없음**을 확인했다 — 배경 크기·아레나·카메라 클램프·스폰(카메라 상대)이 전부 `map.size`에서 자동 유도된다. 그래서 실제 변경은 데이터 두 곳과 주석 한 곳으로 좁다.

### 3.1 데이터 — `game/assets/resources/data/maps/seoul.json`

- `"size": [2400, 2400]` → `[4800, 4800]`.
- 한강 `regions[0].poly` 14정점을 전부 ×2로 스케일한다. 정점이 정확히 새 벽(±2400 = 새 halfW)에 앉으므로 `MapManager._hasVertexOutside`의 경계 경고가 뜨지 않는다(현재 ±1200 벽에 앉은 것과 같은 구조). 스케일 후 최대 |y|는 1200으로 새 halfH(2400) 안이다. 스케일 결과:

  | 현재 | ×2 |
  |------|-----|
  | [-1200, 370] | [-2400, 740] |
  | [-700, 250] | [-1400, 500] |
  | [-200, 20] | [-400, 40] |
  | [0, -30] | [0, -60] |
  | [300, 70] | [600, 140] |
  | [700, 250] | [1400, 500] |
  | [1200, 600] | [2400, 1200] |
  | [1200, 160] | [2400, 320] |
  | [700, -190] | [1400, -380] |
  | [300, -370] | [600, -740] |
  | [0, -470] | [0, -940] |
  | [-200, -420] | [-400, -840] |
  | [-700, -190] | [-1400, -380] |
  | [-1200, -70] | [-2400, -140] |

  `playerSpeedMul`·`enemySpeedMul`은 그대로 둔다(감속 세기는 크기와 무관).

### 3.2 주석 — `game/assets/scripts/logic/ObstacleLogic.ts:31`

`MAX_SUBSTEPS` 근거 주석이 "아레나(2400px) 안의 최대 변위에서 서브스텝 길이가 … 관통이 나지 않는다"고 적혀 있다. 아레나가 4800으로 커지면 이 분석의 전제 수치가 바뀌므로 **재검증 후 주석을 갱신**한다.

재검증: 상한이 무는 것은 이동거리 > 64×radius(반지름 18~40 기준 1152~2560px/프레임)부터다. 새 아레나 대각선(약 6788px)을 한 프레임에 건너는 극단에서도 서브스텝 길이는 6788/64 ≈ 106px로, 장애물 확장 두께 하한(최소 변 120 + 2×반지름 ≥ 156px)보다 얇아 **관통이 나지 않는다 — 결론은 4800에서도 유지된다.** 주석의 "2400px"를 "4800px"로 고치고 이 수치를 반영한다(순수 주석 변경, 로직 불변).

### 3.3 에디터 (7단계) — 장애물 재배치

building-collision이 씬에 놓은 장애물 노드를 넓어진 맵 전역으로 흩뿌린다. §2.1 배치 제약(볼록·한 변 ≤300px·통행 간격, D4 방 금지)을 그대로 지킨다. 좌표는 손 타이핑이 아니라 에디터에서 옮기고, 색인은 `MapManager`가 노드 바운드에서 다시 유도한다(맵 로드 1회).

## 4. 테스트 전략 — 스킵

**신규 순수 로직 파일이 없다.** 변경은 데이터(JSON)와 주석뿐이고, `MapManager`·`RegionLogic` 순수 로직은 불변이다. 기존 `HanRiverHazard.test.ts`는 합성 픽스처(SQUARE·NOTCHED·DIAMOND)로 `pointInPolygon`·`playerSpeedMulAt`을 검증하므로 seoul.json 폴리곤 스케일과 무관하게 그대로 통과한다. → `pnpm wf skip-test`로 사유를 기록한다. 검증은 7단계 인게임 수동으로 한다(§6).

## 5. 밸런스 — 7단계 체감 항목

- **카이팅 룸 증가.** 면적 4배라 플레이어가 도망칠 공간이 넓어진다. 스폰은 카메라 뷰 사각 밖(카메라 상대)이라 **플레이어 주변 적 밀도는 그대로**지만, 넓은 맵에서 지속 카이팅이 더 쉬워질 수 있다. F48(거리 재활용의 카이팅 탱크 편향)과 같은 관찰 축이다.
- **한강 감속 구역 확대.** 강이 ×2라 건너는 데 걸리는 거리·시간이 늘어난다. 비대칭 감속(플레이어만)의 위험지대가 넓어지는 셈 — 체감으로 과한지 본다.
- 이 항목들은 코드가 아니라 배치·수치 튜닝으로 대응한다(필요 시 후속).

## 6. 검증 체크리스트 (7단계 수동)

- [ ] 아레나 경계·카메라 클램프가 4800×4800에 맞게 넓어진다(벽까지 팬 가능).
- [ ] 배경 스프라이트가 4800×4800으로 덮인다(placeholder는 늘어나 흐릿할 수 있음 — 최종 아트 F41이 해결, 이 슬라이스에선 허용).
- [ ] 한강이 넓어진 맵을 계속 가로지르고, 양쪽 강안이 새 벽(±2400)에 닿는다. 물속 감속이 정상 작동.
- [ ] 재배치한 장애물이 새 위치에서 충돌·우회로 정상 작동(플레이어·적 모두).
- [ ] MapManager 콘솔에 경계·간격·크기 경고가 뜨지 않는다(배치가 제약 안).

## 7. 함께 처리 — F38·F43 완료 아카이브

building-collision(PR #60)이 닫은 **F38**(건물 충돌화, `backlog.md`)·**F43**(적 장애물 회피, `backlog-implement.md`)이 아직 열림 표에 `진행중`으로 남아 있다. 이 브랜치에서 두 항목을 각 파일의 「완료 아카이브」로 한 줄씩 옮긴다(요약 + PR #60 + 출처 링크).

## 8. 리스크

- **배경 아트 해상도.** placeholder 배경이 2배로 늘어나 흐릿해진다. 최종 아트(F41)가 4800 해상도로 대체하므로 이 슬라이스에선 수용한다.
- **장애물 재배치 시 제약 이탈.** 넓은 맵에 흩뿌리다 §2.1(간격·크기·경계)을 어기면 D4가 깨진다. 에디터 배치 후 MapManager 경고로 확인한다(§6).
- **서브스텝 관통.** §3.2에서 4800 아레나에서도 관통 없음을 재검증했다 — 상한이 극단 dt에서만 물고, 그때도 서브스텝이 장애물 두께보다 얇다.
