## Problem Statement

TypeScript 프론트 개발자가 Cocos Creator를 처음 배우며 로그라이크 액션 게임을 개발한다.
프로토타입 목표: 색깔 사각형이 이동하고 프로젝타일을 발사하는 최소 전투 루프.
최종 목표: 앱스토어 출시 (모바일 iOS/Android + 웹).

핵심 결정: 어떤 Cocos 버전으로 시작할 것인가?
- Cocos Creator 3.8 LTS (안정, 문서 완비) vs COCOS 4 (신규, MIT, 문서 미성숙)

## What Makes This Cool

- TypeScript로 게임을 만든다 — 웹 개발 경험이 게임 개발로 직접 연결
- 로그라이크 + 한국/일본/중국 챕터 컨셉 — 독창적인 문화 교차 메커니즘
- 솔로 개발 + AI 아트 파이프라인 — 현대적인 인디 개발 스택

## Constraints

- 솔로 개발자 (시간 제약)
- Cocos 완전 초보 (TypeScript는 숙련)
- 모바일 + 웹 동시 타겟
- 아트 에셋은 프로토타입 완성 후
- 개발 환경: macOS (에디터 지원됨)

## Premises

1. Cocos Creator는 올바른 엔진 선택이다 (모바일 + 웹 타겟, TypeScript 친화적) ✅
2. 버전 선택은 '학습 효율' vs '장기 프로젝트 기반' 트레이드오프이다 ✅
3. Cocos 4 (PinK IDE)는 2026.01 출시, 문서와 IDE가 아직 미성숙 상태다 ✅
4. 3.8 LTS는 안정적이나 장기적으로는 4.x 전환을 고려해야 한다 ✅
5. 프로토타입 완성 전까지는 아트 에셋 반입이 우선순위가 아니다 ✅

## Approaches Considered

### Approach A: Cocos Creator 3.8 LTS — 안정 우선 (선택)
- 검증된 LTS로 학습+프로토타입 완성, 이후 4.x 마이그레이션 평가
- 공식 문서 완비(한국어 포함), Creator IDE(Dashboard + 씬 에디터)
- Effort: S / Risk: Low
- 단점: 전투 루프 완성 후 4.x 마이그레이션 가능성

### Approach B: COCOS 4 + PinK IDE — 미래 기반 우선
- MIT 라이선스 완전 오픈소스, 엔진+에디터 분리 아키텍처
- Effort: M / Risk: High
- 단점: PinK IDE 미성숙, 문서 부족, 첫 학습자 기준 디버깅 비용 급증

### Approach C: 3.8 LTS → 전투루프 완성 후 4.x 평가
- Effort: M / Risk: Low-Med
- 단점: '나중에 전환' 계획 실행 가능성 불확실

## Recommended Approach

**Cocos Creator 3.8 LTS로 시작.**

근거:
- 첫 Cocos 학습에서 IDE 문서 부재는 학습 속도를 절반으로 줄인다
- COCOS 4 생태계는 6-12개월 내 더 성숙할 것 — 전투 루프 완성 후 전환 결정이 합리적
- 3.8 LTS 엔진 코어는 COCOS 4와 동일, 학습한 TypeScript 컴포넌트 패턴은 이전 가능

### 라이선스 정리

| | Cocos Creator 3.8 LTS | COCOS 4 |
|---|---|---|
| 엔진 코어 | MIT | MIT |
| 에디터/IDE | Cocos User Service Agreement (무료, 로열티 없음) | MIT (완전 오픈소스) |
| 수익화 | 제한 없음 | 제한 없음 |
| 실질 차이 | IDE 라이선스 조항 존재 | 모든 조항 제거 |

→ 실질적으로 무료 사용 + 앱스토어 출시 모두 가능. 차이는 IDE 약관 조항 유무.

### 지원 OS

| 구분 | 지원 |
|---|---|
| 개발 환경(에디터) | Windows, macOS |
| 빌드 타겟(게임) | iOS, Android, Web(모바일/데스크톱), Windows, macOS, Linux, 미니게임 |

macOS 개발 환경이면 완전 지원.

## What I noticed about how you think

- "현재는 학습이지만 학습 후 출시까지 진행하는게 목표야" — 단계를 명확히 구분하면서도 최종 목표를 잊지 않는다.
- 라이선스와 OS 지원을 구체적으로 물어봤다 — 추상적 방향보다 실제 제약 조건을 먼저 확인하는 엔지니어 사고방식.
- A안을 선택하면서도 4.x 전환 가능성을 열어두었다 — 현실적인 선택과 장기 목표 사이의 균형.
