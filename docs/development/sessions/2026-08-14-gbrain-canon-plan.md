- **정본:** 이 슬라이스가 확정하는 것은 `docs/development/spec/ops-gbrain.md`(신설)와 `CLAUDE.md`, `docs/development/workflow/pr-ready.md`다. 이 문서는 그때 무엇을 왜 정했는지의 기록이지 현재 명세가 아니다.

## 1. 왜 지금인가

### 1-1. 고치려는 고장

색인 갱신이 2026-07-25부터 8월 13일까지 19일 동안 조용히 건너뛰어졌다. 진단은 [`2026-08-13-gbrain-sync-lock.md`](2026-08-13-gbrain-sync-lock.md)에 있고, 이 슬라이스는 그 문서가 「남은 처방」으로 남긴 것을 실행한다.

원인은 **두 겹**이다.

**첫째, 절차가 실행될 수 없는 상태였다.** `§6.2`가 지시하는 `bun src/cli.ts sync`는 상시 실행 중인 `gbrain serve`가 PGLite를 잡고 있어 DB를 열지 못한다. 서버는 Claude Code가 띄운 stdio 자식 프로세스라 세션 내내 살아 있으므로, AI가 절차를 따르려 할 때는 **항상** 잠겨 있다. 읽기 전용 명령조차 막힌다.

```
$ bun src/cli.ts sources status
GBrain's local database is already open through `gbrain serve` (MCP, PID 19996).
This brain uses PGLite, so a separate CLI process cannot open it at the same time.
Stop `gbrain serve`, then retry this CLI command. Or keep it running and use its MCP tools instead.
```

**둘째, 실패를 아무도 읽지 않았다.** 처음에는 종료 코드가 0이라 실패가 조용했다고 적었는데 **그것은 측정 오류였다**(파이프라인 뒤에서 `$?`를 읽어 `head`의 값을 봤다). 실제로는 1이고, 리뷰가 이를 잡았다.

그래서 인과가 다르다. 실패 자체는 시끄러웠다. 19일이 보이지 않은 이유는 **그 코드를 아무도 읽지 않았다**는 것이다 — 손으로 도는 단계라 자동으로 `$?`를 보는 것이 없었고, 잠금 안내가 "그냥 MCP 도구를 쓰라"는 권유로 읽혀 실패가 아니라 선택지처럼 보였으며, 갱신이 안 돼도 뒤의 어떤 단계도 막히지 않았다.

이번 슬라이스는 첫째를 닫고, 둘째는 §2-2가 정한 만큼만 닫는다.

### 1-2. 다른 것 대신 지금 이걸 하는 이유

게임 백로그의 우선 「높음」은 셋이다.

**F60**(카테고리별 에셋 생성)은 12종 로스터 앞에 「원전 도상 시트」가 선행이고, **F68**(채택 모델 `openai/gpt-image-2`의 상업 이용 조건 확인)도 아직 열려 있다. 유료 전환 계획 §4가 가려 둔 것은 FLUX·Gemini·Midjourney이고 실제로 채택한 모델은 그 표에 없으므로, **가려 놓은 것과 쓴 것이 어긋난 채로 에셋을 불리면 나중에 전부 다시 뽑아야 한다.** 로스터 생성이 아직 시작되지 않았다는 바로 그 이유로 지금이 기회비용이 가장 낮은 창이라, F68은 **이 슬라이스 다음에 곧바로 집는다.** 이번에 백로그 우선을 「중」에서 「높음」으로 올려 다음 조회에서 먼저 잡히게 한다.

**J3**(세이브)와 **J5**(인트로 씬)는 지금 집을 수 있는 게임 작업이다. 다만 이 슬라이스는 이미 브랜치를 열었고 F77이 「다음 머지 전」 조건이라, 여기서 멈추면 그 조건을 또 한 슬라이스 미루게 된다.

**게임 코드가 2026-08-03(`31bdc7e`, input-focus-reset) 이후 멈춰 있고 순수 문서·도구 슬라이스가 네 번 연속이라는 것은 사실로 기록해 둔다.** 이번이 다섯 번째다. 그래서 이 슬라이스는 §2-2·§2-5처럼 **두 조각을 도로 빼서** 문서 작업만 남겼고, 다음은 F68 → 게임 작업으로 넘어간다.

### 1-3. 규모

새 정본 하나, 새 세션 문서 하나, 기존 문서 다섯 곳 수정이다. **코드 0줄·테스트 0건**이라 `wf skip-test` 경로로 간다. 사람이 할 일은 §6의 절차 완주 하나다.

## 2. 이번에 확정한 것

### 2-1. 권위 있는 값은 브레인이 들고, 절차가 그것을 묻는다

**`wf`라는 별도 프로세스는 색인 상태를 물을 수 없다.** 위 실측대로 읽기 전용 명령도 잠금에 막히고, 체크포인트는 PGLite 안에 있어 밖에서 읽을 수 없다(`~/.gbrain/`에 있는 것은 `config.json`·`sync-failures.jsonl`과 DB 디렉터리 `brain.pglite/`·`audit/`뿐이다).

**반면 AI는 잠금 중에도 MCP로 물을 수 있다.** `sources_status`가 `serve`가 살아 있는 채로 답한다.

```
sources_status(monster) → last_commit: 8722e7f3…, last_sync_at: 2026-08-14T09:31:42Z, page_count: 352
```

그래서 지연을 확인하는 자리를 둘로 잡는다. **머지 직후**에는 `pr-ready.md` §3이 갱신 뒤 `last_sync_at`을 확인하게 하고, **검색을 쓰는 순간**에는 `CLAUDE.md`의 검색 라우팅이 같은 도구를 가리키게 한다. 후자가 지금 죽어 있다는 것이 §3-1이다.

### 2-2. 「묻지 않아도 뜨는」 경고는 검토했지만 이번에 뺐다

원인 둘째(누락이 안 보인다)를 기계로 닫는 안을 설계까지 했다. `pnpm wf gbrain-synced`가 브레인의 체크포인트 SHA를 로컬 파일에 적고, `wf status`가 그 SHA와 `origin/main`을 비교해 뒤처지면 경고하는 것이다.

**값은 있지만 이 슬라이스에서 그 값에 비해 비싸다.** 새 커맨드, `.gitignore` 대상 상태 파일, 판정 여덟 갈래(비-저장소·미설치·기록 없음·기준 ref 없음·SHA 모름·조상 아님·0커밋·N커밋), 그리고 그것을 정직하게 검증할 git 샌드박스 테스트 헬퍼가 따라온다. 기존 `ClaudeMdSplit.test.ts`의 샌드박스는 `git init`을 하지 않아 그대로 쓰면 여덟 중 넷이 거짓 초록으로 통과하므로, 헬퍼를 새로 짜야 한다는 뜻이다. 문서 한 절을 고치러 온 슬라이스가 도구 슬라이스로 바뀐다.

**빼도 되는 이유는 원인 진단을 다시 읽으면 나온다.** 19일 누락은 누가 멀쩡한 단계를 건너뛴 것이 아니라, **적힌 명령이 실행 자체가 안 됐고 그 실패가 조용했던 것**이다. 실제로 도는 명령을 절차에 넣는 것은 그때와 성격이 다르다. 게다가 §3-1이 검색 라우팅을 고치면, 검색을 쓰는 그 자리에서 지연이 확인된다.

남는 차이는 「묻지 않아도 뜨느냐」 하나이고, 그것을 **F86**으로 등재해 검사 도구를 손보는 다음 슬라이스에서 F78·F82와 함께 집는다. 위 설계와 여덟 갈래는 이 문서가 들고 있으므로 그때 다시 설계하지 않는다.

### 2-3. 셋업 문서는 절차만 정본으로 올리고 근거는 세션으로 내린다

`gbrain-setup.md`는 한 파일에 두 층이 섞여 있다. 「어떻게 깔고 어떻게 갱신하나」는 지금도 유효한 명세이고, 「2026-07-25에 이 장비에서 재 본 수치」와 「그때 도입을 결정한 근거」는 시점 기록이다. 통째로 `spec/`에 옮기면 정본이 결정 기록을 품게 되어 「정본은 현재 결론을 스스로 든다」와 어긋난다.

가르는 선은 **지금도 참인가**다.

| 절 | 어디로 | 왜 |
|---|---|---|
| §1 무엇이 설치되는가 | `spec/ops-gbrain.md` | 현재 구성 |
| §2 이 장비 실측 | `sessions/2026-07-25-gbrain-setup.md` | 2026-07-25 시점의 장비 수치 |
| §3 왜 이 구성인가 | `spec/ops-gbrain.md` | 지금도 강제되는 제약(모델이 브레인당 고정)을 든다 |
| §4 재현 절차 | `spec/ops-gbrain.md` | 현재 절차 |
| §5 알려진 함정 | `spec/ops-gbrain.md` | 지금도 만나는 함정 |
| §6 운영 | `spec/ops-gbrain.md` | 이번에 고치는 대상 |
| §7 도입 판단 근거 | `sessions/2026-07-25-gbrain-setup.md` | 도입 여부를 정할 때 쓴 실측 |
| §8 아직 하지 않은 것 | `spec/ops-gbrain.md` | 현재 미도입 상태를 말한다 |

**절 번호는 그대로 둔다.** 문서 밖에서 절을 번호로 부르는 곳을 전수로 훑었더니 **전부 §6.2와 §8이고 §2·§7을 부르는 곳은 0건**이다 — `workflow/pr-ready.md:28`, 백로그 F77, 진단 문서 여섯 곳(§6.2)과 한 곳(§8)이다. 그러니 §2·§7은 들어내도 안전하고, 재번호하면 그 §6.2 참조 여덟이 조용히 어긋난다. **비는 번호는 참조를 깨지 않지만 옮긴 번호는 깬다.** §1에서 §3으로 건너뛰는 것이 사고처럼 보이지 않도록, 이력 절에 무엇을 왜 분리했고 번호를 왜 비웠는지 한 줄 남긴다.

**§7.3만은 정본에 흔적을 남긴다.** 손수 관리하는 AI 인덱스(`.ai/*.json`)를 기각한 기록인데, 이것은 시점 기록이 아니라 **지금도 참인 결론**이다(파생 사본은 게이트가 없으면 반드시 낡는다). 통째로 내리면 다음에 검색 개선을 집는 사람이 같은 안을 다시 낸다. 「이력은 지우지 말고 한 줄로 줄인다」에 따라 이름과 이유만 한 줄로 남기고, 정본에서 세션 문서로 링크는 걸지 않는다.

파일명은 `ops-gbrain.md`다. 접두사 `ops-`는 닫힌 집합 안에 있고, 답하는 질문은 "레포를 의미로 검색하려면 무엇을 깔고 색인을 언제 갱신하나"다.

### 2-4. README 세 개가 색인에서 통째로 빠진다 — 이번에는 제약으로 적기만 한다

`docs/development/spec/README`·`docs/design/spec/README`·`docs/development/workflow/README` **셋 다** `get_page`가 `page_not_found`를 돌려준다. gbrain이 메타파일 다섯을 의도적으로 배제하기 때문이다.

```js
// ~/gbrain/src/core/sync.ts:343
export const SYNC_SKIP_FILES = ['schema.md', 'index.md', 'log.md', 'README.md', 'RESOLVER.md'];
```

증분 동기화(`isSyncable`)와 전체 동기화·임포트 walker(`import.ts:587`)가 **같은 상수**를 타므로 `--full`로 다시 돌려도 들어오지 않고, 설정으로 끌 수 있는 값도 아니다. 우리 레포에서 걸리는 셋은 전부 정본·절차 인덱스다. `CLAUDE.md`가 "무엇을 왜 그리나 → `docs/design/spec/README.md`가 목록"으로 보내는데, 의미 검색으로는 그 셋에 닿지 못한다.

**이번에는 구조를 바꾸지 않는다.** 개별 정본은 전부 색인돼 있어 실해가 작고, 목록 본문을 다른 파일명으로 옮기면 `wf canon`의 등재 대상·`DocLinks` 테스트·문서 참조 경로가 함께 움직여 F77과 무관한 변경이 슬라이스에 섞인다. 대신 정본 §5에 함정으로 적고 **F85**로 등재해, 다음에 집을 사람이 배경을 다시 조사하지 않게 한다. `index.md`도 같은 배제 목록에 있어 개명으로 우회할 때 쓸 이름이 좁다는 것도 함께 적는다.

### 2-5. F81(`CLAUDE.md` 크기 예산)도 이번에 뺐다

처음에는 「에셋 `.meta` 관리 규칙」(1,156자)을 `spec/ops-assets.md`로 내보내 예산 여유를 179자에서 약 1,130자로 넓힐 계획이었다. 두 가지가 드러나 뺐다.

**F81은 이 슬라이스의 차단 요인이 아니다.** 라우팅 표의 「안 옮긴 것은 `gbrain-setup.md`(F77 뒤)와…」 문구가 짧아지고(남는 것은 로컬 환경 복구 매뉴얼 둘이다), §2-2대로 커맨드 표에 행을 더하는 일도 없어졌다.

**다만 「늘어나지 않는다」고 적었던 것은 틀렸다.** 구현 뒤 실측이 **13,862자**로, 시작할 때의 13,821자보다 **41자 늘었다**(여유 179 → 138자). §3-1이 검색 라우팅에 "CLI가 왜 답이 아닌가"를 더한 것이 표 행에서 줄인 것보다 컸다. 처음 잰 값은 +81자였고, 그 설명의 전문은 정본 §6.2가 드니 라우팅에는 한 줄 포인터만 남겨 절반을 되돌렸다. 방향은 그대로다 — 이 슬라이스가 F81을 강제할 만큼 늘리지는 않는다.

**그리고 `.meta` 규칙은 옮기는 판단 자체가 따로 검증받아야 한다.** 그것은 AI가 실제로 어겨서 못박힌 안전 규칙이고, 지금 `CLAUDE.md`에 있는 이유는 상주 파일이 압축에 저항해 재주입되기 때문이다. `spec/` 문서는 찾아 읽어야 닿는다. 그런데 절차를 상주에서 도구 출력로 옮긴 것이 준수율을 떨어뜨렸는지 보는 **F71이 아직 열려 있다** — 그 판정이 나기 전에 같은 방향으로 한 걸음 더 가는 셈이고, 이번엔 옮기는 대상이 절차가 아니라 안전 규칙이다.

**F81은 열린 채로 둔다.** 백로그 행에 이번 재검토 결과(트리거가 안 당겨졌고, `.meta` 절 이관은 F71 뒤가 순서다)를 한 줄 반영한다.

## 3. 하는 것

1. **`CLAUDE.md`의 죽은 복구 명령을 고친다.** 「검색 라우팅」이 "결과가 비었거나 엉뚱하면 `gbrain sources status`로 마지막 동기화 시점을 본다"고 하는데, **이것이 이 슬라이스가 막으려는 위험의 유일한 방어선인데 실행되지 않는다.** 이 장비에는 `gbrain`이 PATH에 없고(`bun ~/gbrain/src/cli.ts`로 부른다), 있더라도 `serve`가 잠금을 쥐고 있다. MCP `sources_status`로 바꾼다. **한 줄이고 이 슬라이스에서 값이 가장 크다.**

## 5. 위험과 함정

**절 번호를 건드리면 조용히 깨진다.** §2·§7을 들어내되 나머지 번호는 그대로 둔다(§2-3에 전수 결과가 있다).

**새 정본이 `CANON_SCOPE`에 들어간다.** `DocLinks.test.ts:270`이 `docs/development/spec/`를 덮으므로, 옮긴 뒤에는 `sessions/`·`decisions/`로 나가는 링크를 하나도 걸 수 없다. 지금 위반은 0건이지만 §6.2를 다시 쓰면서 진단 문서를 근거로 링크하고 싶어지는데 **그게 곧 빨간불이다.**

**링크 검사기는 절반만 잡는다.** §3-6 표대로 다섯 중 둘만 링크이고 셋은 코드 스팬 평문이다. 평문은 손으로 훑는다.

**`clone_state`가 상태에 따라 뒤집힌다.** 슬라이스를 열기 전에는 `healthy`였는데 브랜치를 `feat/gbrain-canon`으로 옮긴 뒤 같은 호출이 `corrupted`를 돌려준다. 색인 자체는 정상이다(352페이지, 체크포인트가 main tip). 원인은 이번에 파지 않으니, 정본 §5에 **관측 사실과 "색인 건강과는 무관해 보인다"까지만** 적어 다음 사람이 이 값을 보고 색인이 깨졌다고 오독하지 않게 한다.

## 6. 검증

**새 테스트는 쓰지 않는다.** 이 슬라이스에 순수 로직이 없다 — 문서를 옮기고 절차를 고칠 뿐이다. `pnpm wf skip-test`로 사유를 남긴다.

**대신 이미 있는 회귀망이 이번 이동을 덮는다.** `DocLinks.test.ts`가 레포 전체의 마크다운 링크와 앵커를 검사하므로, 옮긴 경로를 가리키는 깨진 링크와 표시 텍스트 불일치를 `start-verification`의 GREEN 게이트가 잡는다. `ClaudeMdSplit.test.ts`의 크기 예산·절차 문서 예산 단언도 그대로 돈다. 언제든 `pnpm wf check-links`로 중간 확인이 된다.
