# 줄 끝 정책을 git이 강제하게 한다 (F72)

- **작성일:** 2026-08-18
- **브랜치:** `feat/eol-policy`

- **정본:** 없음 — 줄 끝 정책의 정본은 `.gitattributes`와 `.editorconfig` 파일 자신이다. 두 파일이 정책을 선언하고 동시에 강제하므로, 같은 내용을 `spec/`에 옮겨 적으면 [`spec/docs-references.md`](../spec/docs-references.md#3-1-소유권-지목이-기본이다) §3-1이 금지하는 두 벌 소유가 된다

## 1. 무엇이 문제인가

이 레포에는 `.gitattributes`가 없다. 그래서 git이 줄 끝을 정하지 않고, **파일을 마지막으로 저장한 도구가 정한다.** 커밋된 바이트가 그대로 남으므로 한번 CRLF로 들어온 파일은 계속 CRLF고, 옆 파일은 LF다.

그런데 `.editorconfig`는 이미 정책을 선언하고 있다.

```
[*]
end_of_line = lf
```

즉 **정책은 진작 정해져 있고 강제만 없는 상태**다. F72를 "줄바꿈 정책을 결정한다"로 읽으면 결정할 것이 남은 것처럼 보이는데, 실제로 남은 일은 이미 선언된 것을 git이 지키게 만드는 일 하나다.

강제가 없어서 두 종류의 사고가 났다.

**첫째, 유령 diff다.** 편집 도구가 파일 전체를 반대 규약으로 다시 쓰면 한 줄만 고쳐도 파일 전체가 바뀐 것으로 나온다. `claude-md-split` 슬라이스에서 실제로 122줄이 그렇게 붙었다가 되돌렸다. 이 상태에서는 리뷰어가 실제 변경을 못 찾고, `git blame`도 그 줄들에서 끊긴다.

**둘째가 더 나쁘다. 게이트가 거짓으로 실패했다.** 어제 `feat/docs-references`에서 새 검사기가 CRLF 문서의 `정본:` 줄을 못 찾아 "줄이 없다"고 보고했다. 원인은 검사기가 `\n`으로만 줄을 쪼개 끝에 `\r`가 남은 것인데, 자바스크립트 정규식의 `.`이 `\r`를 안 먹으므로 `$`에 닿지 못했다. 그 커밋 메시지가 원인을 이렇게 적었다.

> 가정이 아니라 이 레포에 CRLF 문서가 셋 있고, `.gitattributes`가 없고 `core.autocrlf`가 `false`라 작성 도구가 줄 끝을 정한다.
> — `f2f1910` 커밋 메시지

**F72의 우선순위가 「낮음」인 것은 이 사고 이전에 매긴 값이다.** 등록 당시 근거는 유령 diff 하나뿐이었고, 게이트를 거짓 실패시킨다는 것은 어제 처음 드러났다. 방어 코드(`normalizeEol`)가 헬퍼 둘에 걸쳐 생긴 것도 그 결과다.

## 2. 실측 — 무엇이 어긋나 있나

추적 파일 전체를 확장자별로 셌다. 기준일은 2026-08-18이고, 세는 방법은 `git ls-files`로 목록을 받아 각 파일에 `\r\n`이 있는지 보는 것이다.

| 확장자 | LF | CRLF | 비고 |

| `.md` | 223 | **8** | 어긋난 것은 여기뿐이다 |
| `.ts` | 113 | 0 | |
| `.meta` | 101 | 0 | Cocos가 만든 것도 LF다 |
| `.json` | 27 | 0 | |

CRLF 여덟 개와 그 줄 수는 이렇다. 합계 **1,777줄**이며, 이것이 재정규화가 만들 diff의 크기다.

이 실측이 계획의 범위를 바꿨다. **`game/assets/`를 특별 취급할 이유가 없다.** 원래는 Cocos가 어떤 줄 끝으로 쓰는지 모르니 그 폴더를 정책 밖에 두려 했는데, `.meta` 101개와 씬·프리팹 12개가 전부 이미 LF다. 즉 Cocos도 LF로 쓴다. 폴더를 갈라 두면 `.editorconfig`는 `[*]`로 전체를 말하고 `.gitattributes`는 일부만 말하는 상태가 되어, 다음 사람이 어느 쪽이 진짜 정책인지 물어야 한다.

## 3. 무엇을 넣나

`.gitattributes` 한 파일이다. 전체를 LF로 고정하고, 바이너리는 텍스트 변환에서 뺀다.

```
* text=auto eol=lf

*.png binary
… (이미지·오디오·폰트·Spine 바이너리)

*.url -text
```

세 가지를 이렇게 정하는 이유를 적어 둔다.

- **`eol=lf`는 작업 트리까지 LF로 고정한다.** `text=auto`만 쓰면 저장소 안은 LF로 통일되지만 체크아웃 시 플랫폼 관례를 따르므로, 윈도우 작업 트리는 CRLF가 된다. 그러면 §1의 검사기 문제가 그대로 남는다. 도구가 읽는 것은 작업 트리 파일이기 때문이다.
- **바이너리를 명시한다.** `text=auto`는 NUL 바이트 휴리스틱으로 바이너리를 알아서 거르지만, 휴리스틱이 틀리면 조용히 파일이 깨지고 그때는 원인을 찾기 어렵다. 지금 레포에 있는 바이너리는 PNG 20개뿐인데, **곧 들어올 것이 정해져 있다** — 리깅 도구가 Spine으로 확정돼 있어 `.skel`(바이너리)이 오고, J6이 오디오를 가져온다. 그때 사고가 나서 배우지 않도록 지금 적는다.
- **`.url` 하나만 뺀다.** `game/.creator/asset-template/`의 윈도우 인터넷 바로가기는 Cocos가 생성한 산출물이고 INI 형식이라, 굳이 정규화할 이유가 없다.

## 4. renormalize의 함정 — 인덱스와 작업 트리는 다르다

**`git add --renormalize .`는 인덱스만 고치고 작업 트리 바이트는 건드리지 않는다.** 실행 뒤 `git status`가 깨끗해 보이는 것은 git이 비교할 때 같은 필터를 적용하기 때문이지, 디스크의 `\r\n`이 사라져서가 아니다.

지금 상태를 `git ls-files --eol`로 보면 이렇게 나온다.

```
i/crlf  w/crlf  attr/     docs/development/backlog.md
```

왼쪽이 인덱스, 가운데가 작업 트리다. 재정규화 후에는 `i/lf w/crlf`가 된다. **여기서 회귀 가드를 작업 트리 기준으로 쓰면 영영 초록이 되지 않는다.** 파일을 `fs.readFileSync`로 읽는 검사는 `\r\n`을 계속 보고, 5단계 GREEN 게이트에서 슬라이스가 막힌다. 게다가 증상이 "재정규화가 안 먹은 것"처럼 보여서 엉뚱한 데를 파게 된다.

그래서 두 가지를 한다.

- **가드는 인덱스를 본다.** `git ls-files --eol`의 `i/` 칸에 `crlf`가 하나도 없는지 단언한다. 지켜야 할 대상은 저장소에 들어가는 바이트이고, `core.autocrlf=true`로 설정한 기여자의 작업 트리가 CRLF여도 이 단언은 옳게 통과한다.
- **작업 트리는 손으로 맞춘다.** 재정규화를 커밋한 뒤 그 여덟 파일만 지우고 다시 체크아웃하면 git이 인덱스의 LF로 새로 쓴다. 레포 전체를 `git reset --hard`로 되돌리는 방법도 있지만, 커밋 안 한 변경까지 날리므로 대상 여덟 개만 건드린다.

## 5. 회귀 가드 — `tests/logic/EolPolicy.test.ts`

단언은 셋이다.

1. **인덱스에 CRLF가 0건이다.** `git ls-files --eol`을 실행해 `i/crlf`인 줄을 센다. 지금은 8건이라 RED에서 출발한다.
2. **`.gitattributes`가 존재하고 전체 규칙을 든다.** 파일이 지워지거나 `* text=auto eol=lf` 줄이 빠지면 1번은 한동안 초록을 유지하다가(이미 정규화된 파일은 그대로다) 새 파일부터 조용히 어긋난다. 정책 파일 자체를 봐야 그 경로가 막힌다.
3. **검사가 실제로 파일을 봤다.** 추적 파일이 하나 이상 잡혔는지 단언한다. 명령이 실패해 빈 목록을 돌려주면 1번이 "위반 0건"으로 초록을 내는데, 그것은 통과가 아니라 검사를 안 한 것이다. `DocsReferences.test.ts`가 같은 이유로 「하나 이상」 단언을 건다.

## 6. 커밋 순서와 PR 분리

**이 슬라이스는 F72 하나만 담고 별도 PR로 낸다.** 원래는 F76·F83과 한 슬라이스로 묶으려 했는데, 이 레포가 squash merge를 쓴다는 사실이 그 계획을 깬다. 브랜치에서 재정규화를 첫 커밋으로 떼어 놓아도 main에는 문서 편집과 뭉쳐진 커밋 하나로 도착하므로, `git blame`이 1,777줄 전부에서 그 커밋을 가리킨다. 되돌릴 방법도 없다 — `.git-blame-ignore-revs`에 적을 SHA가 재정규화만 든 커밋이어야 하는데 그런 커밋이 main에 없기 때문이다.

PR을 갈라 내면 그 squash 커밋이 재정규화 단독이 되어 SHA 하나로 무시 목록을 만들 수 있고, GitHub가 그 파일을 자동으로 읽는다. 특히 대상에 `backlog.md`가 끼어 있는데, 이 문서는 "이 항목이 언제 어느 슬라이스에서 들어왔나"를 실제로 되짚는 문서다.

브랜치 안 커밋 순서는 이렇다.

1. `.gitattributes` 추가와 `git add --renormalize .`를 **같은 커밋**에 넣는다. 속성 파일이 있어야 필터가 적용되므로 순서가 뒤집히면 재정규화가 아무것도 하지 않는다.
2. 작업 트리 여덟 개를 다시 체크아웃한다(§4).
3. 가드 테스트를 추가한다.

## 7. 하지 않는 것

- **`game/assets/`를 정책에서 빼지 않는다.** 실측 결과 이미 전부 LF라 재정규화로 바뀌는 바이트가 0이고(§2), 폴더를 가르면 `.editorconfig`와 `.gitattributes`가 서로 다른 범위를 말하게 된다.
- **`normalizeEol`과 `blankFences`를 지우지 않는다.** `.gitattributes`가 들어와도 남긴다. 이번에 건드리는 코드가 아니고, 테스트 픽스처 문자열처럼 git을 거치지 않는 입력에는 여전히 필요하다.
- **줄 끝 정책의 정본 문서를 새로 만들지 않는다.** 머리말에 적은 대로 `.gitattributes`와 `.editorconfig`가 정책을 선언하면서 동시에 강제하므로, `spec/`에 사본을 두면 소유가 갈린다. 그 대신 **왜 이 정책인지를 `.gitattributes` 주석이 든다** — §1의 두 사고를 파일 안에서 복원할 수 있게 적는다.
- **biome에 `lineEnding`을 명시하지 않는다.** biome 2.x 기본값이 `lf`라 이미 정합하고, 지금 적으면 같은 값을 세 곳(`.editorconfig`·`.gitattributes`·`biome.json`)이 들게 된다.
