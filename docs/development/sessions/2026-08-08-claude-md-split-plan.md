# CLAUDE.md 3층 분할 — phase가 절차를 배달한다

- **날짜:** 2026-08-08
- **브랜치:** `feat/claude-md-split`
- **상태:** **완료** (PR #76, 2026-08-13 사용자 검증 통과 후 squash merge). 계획은 2차 개정판이며 독립 리뷰 3건 + 검증 리뷰 1건을 반영했다.
- **성격:** 문서 구조 + 툴체인 결정. 코드 변경 대상은 `.claude/workflow.mjs` 하나다.
- **정본:** 이 슬라이스가 확정하는 것은 `CLAUDE.md` 본문과 `docs/development/workflow/` 절차 문서다. 이 문서는 그때 무엇을 왜 정했는지의 기록이지 현재 명세가 아니다.

> **개정 이력.** 초판을 CEO·Eng·DX 독립 리뷰 3건에 걸었고 다섯 항목이 3/3으로 일치해 되돌렸다. 무엇이 어떻게 뒤집혔는지는 §9에 남긴다.

---

## 1. 배경 — 무엇이 문제인가

`CLAUDE.md`가 **24,971자 / 355줄**까지 자랐다. 이 파일은 매 세션 시작 시 통째로 컨텍스트에 들어가고, 공식 권장치는 200줄 이하다. 지금은 그 **177%**다.

부피가 어디에 있는지는 측정하면 분명하다.

| 절 | 자수 | 비중 |
|---|---:|---:|
| `### 기능 개발` (9단계 절차 전체) | 10,725 | 43% |
| `## Knowledge Base` | 3,981 | 16% |
| `## QA 문서 작성 규칙` | 2,602 | 10% |
| `### 워크플로우 상태` | 2,397 | 10% |
| Cocos 규칙 + 에셋 `.meta` 규칙 | 1,703 | 7% |
| 나머지 | 3,563 | 14% |

> **측정 방법을 못 박는다.** 이 레포 문서는 전부 한국어라 PowerShell의 `Get-Content`를 `-Encoding utf8` 없이 쓰면 시스템 코드페이지로 읽혀 자수가 약 1.18배 부풀고, `Measure-Object -Line`은 빈 줄을 세지 않아 줄 수가 과소집계된다. 초판의 「29,129자 / 265줄」이 그렇게 나온 값이다. **문서 크기는 `node -e 'fs.readFileSync(f,"utf8")'`로 잰다.**

상위 세 절만 합쳐도 전체의 69%인데, 그 대부분은 **특정 단계에서만 필요한 절차**다. 6단계 검증 순서, PR 본문 작성 규칙, QA 문서 작성 규칙은 계획 단계에도 구현 단계에도 계속 자리를 차지하지만 그 단계에 들어가기 전에는 한 번도 쓰이지 않는다.

### 왜 그냥 나누면 안 되는가

분할 수단마다 로드 시점이 다르고, 그 차이가 이 작업의 성패를 가른다. 출처는 Claude Code 공식 문서 `code.claude.com/docs/en/memory`(2026-08-08 조회)다.

| 수단 | 로드 시점 | 컨텍스트 절감 | `/compact` 후 재주입 |
|---|---|---|---|
| `@path` import | launch 시 인라인 확장 (최대 4홉) | **0** | 루트와 함께 재주입 |
| `.claude/rules/*.md` (frontmatter 없음) | launch 시 전부 | **0** | 재주입 |
| `.claude/rules/*.md` + `paths:` | 매칭 파일을 **읽을 때** | 있음 | **안 됨** |
| 일반 `docs/*.md` (Read로 열기) | 읽을 때 | 있음 | **안 됨** |
| **스킬** | 인덱스(이름+설명)는 상시, 본문은 호출 시 | 있음 | 재호출 가능 |
| Bash 도구 출력 (`wf` 배달) | 실행 시 1회 | 있음 | **안 됨** |

**스킬을 왜 안 쓰는지 적어 둔다.** 이 레포는 스킬을 대량으로 쓰므로(gstack·superpowers) 가장 익숙한 수단이고, 진행 표에서 유일하게 「압축 후 재호출 가능」인 칸이다. 매력적인 조합도 있다 — `wf`가 3,000자를 뱉는 대신 `Skill(workflow-verification) 호출` **한 줄**을 뱉으면 전이 시점 강제와 압축 후 재로드를 둘 다 얻고 배달 비용이 40자가 된다. 게다가 스킬 설명이 인덱스에 상시 있으므로 「절차 문서가 존재한다」는 사실 자체가 항상 알려져 있어 §4의 탐지 문제가 native로 풀린다.

**그런데도 v1에서 채택하지 않는다.** 두 가지 이유다. 첫째, 호출 여부가 **모델 판단**이라 이 슬라이스가 없애려던 바로 그 honor system이 한 겹 다시 들어온다 — `wf`가 지시해도 안 부르면 그만이다. 둘째, 이 레포의 스킬은 전부 플러그인이고 **프로젝트 로컬 스킬은 선례가 0건**이라, C층을 접은 것과 같은 이유(선례 없는 메커니즘 + 실패가 무음)가 그대로 적용된다.

**기각이 아니라 보류다.** 배달이 실제로 굴러간 뒤 문서 크기가 부담이 되면 이 조합이 첫 후보다 — `wf steps`가 이미 「이름으로 절차를 부르는」 인터페이스라 스킬로 갈아끼우는 비용이 작다.

`@import`로 파일만 쪼개면 상시 컨텍스트는 한 톨도 줄지 않는다. 실제로 줄이려면 로드 시점을 옮겨야 하는데, 여기서 **대가가 하나 생긴다.**

### 대가를 정직하게 적는다 — 압축 저항성은 떨어진다

공식 문서는 이렇게 말한다.

> *"Project-root CLAUDE.md survives compaction: after /compact, Claude re-reads it from disk and re-injects it into the session."*

즉 **지금 `CLAUDE.md`에 있는 절차는 압축을 견딘다.** 압축이 몇 번 돌든 원문이 디스크에서 다시 주입된다. 반면 `wf` 배달은 전이 순간 1회이고, 배달된 내용은 트랜스크립트의 도구 출력이라 압축에 똑같이 뭉개진다.

**그래서 이 슬라이스는 압축 저항성 축에서 개선이 아니라 후퇴다.** 그것도 가장 나쁜 자리에서 후퇴한다 — 유실 확률은 phase 길이에 비례하는데 가장 긴 `verification`(cso → 타입체크 → lint → 커밋 → 코드리뷰 → `invalidate` 시 전부 재실행)이 가장 큰 문서를 받는다.

초판은 이걸 반대로 적었다("분할 후가 분할 전보다 준수율이 오히려 높다"). 그 문장은 배달 경로에 대해서만 참이고 복구 경로에 대해서는 거짓인데, 구조상 복구 경로가 더 중요하다. **이 후퇴를 메우는 것이 §3 배달 설계의 절반이다.**

### 준수율에 대해서는 단정하지 않는다

초판은 배달이 준수율을 높인다고 단정했다. 이건 **가설이지 검증된 것이 아니다.** 근거를 정직하게 나누면 이렇다.

- 참인 부분: `pnpm wf` 전이는 건너뛸 수 없다. 훅이 상태 파일 직접 편집을 막고 phase 순서를 검증한다.
- 참이 아닌 부분: **배달은 게이트가 아니라 출력이다.** 찍힌 문서를 무시해도 아무것도 막지 않는다. `gate-scripts.mjs`는 `game/assets/scripts/**/*.ts`만 게이팅하므로 이 슬라이스의 파일은 전부 그 밖이다.
- 반증 사례: 메모리의 「워크플로우 그대로 따르기」는 절차 전문이 **상주하던 시절에** 임의 단축이 일어났다는 기록이다. 상주해도 건너뛰었다는 뜻이므로, 비상주로 바꾼다고 좋아진다는 보장이 없다.

**그래서 이 슬라이스는 "준수율을 높인다"가 아니라 "컨텍스트를 줄이면서 준수율을 떨어뜨리지 않는다"를 목표로 한다.** 가설이 틀렸는지는 다음 두세 슬라이스에서 절차 누락이 나는지로 관찰한다. 나면 롤백 후보다.

## 2. 이 슬라이스가 닫는 백로그 항목

**없다.** 두 백로그를 모두 확인했고(0-1단계), 이번 테마에 걸리는 열린 항목이 없다.

인접 항목 하나를 검토했으나 제외했다.

- **F69** (정본 문서에서 결정 기록으로 가는 링크 걷어내기) — 대상이 다르다. F69는 `docs/design/`·`docs/planning/` **본문의 링크**를 정리하는 일이고, 이번 슬라이스는 `CLAUDE.md` 자체의 구조를 바꾼다. 다만 **`CLAUDE.md:92`의 인라인 ADR 004 링크는 이번에 함께 고친다**(§3 A층) — 그 줄은 이 슬라이스가 어차피 다시 쓰는 절이라 놔두면 새 본문에 그대로 따라온다.

### 계획 중 정정한 것

초기 분석에서 「주석 3원칙이 `CLAUDE.md`·`conventions.md`·`writing-style.md` 3중 복사본」을 중복 제거 대상으로 잡았는데 **이미 닫힌 항목이었다.** `backlog-implement-archive.md`의 **F51**이 2026-07-25에 `writing-style.md`를 정본으로 두고 나머지 둘을 링크로 줄여 해결했다.

오진의 경로를 남겨 둔다. 근거로 삼은 것이 `docs/qa/spawn-geometry-review-issues.md`였는데 그 문서는 **그 슬라이스 시점의 기록**이라 이후 닫힌 것을 알 수 없다. `CLAUDE.md`가 경고하는 함정에 그대로 걸린 것이다.

## 3. 3층 → 2층 배치

C층은 뺐다(§9 참조). A층과 B층 둘이다.

### A층 — 루트 `CLAUDE.md` 잔류 (목표 **≤14,000자 / ≤240줄**)

> **목표치를 산술로 정한다.** 아래 잔류 목록을 현재 상태 그대로 더하면 **213줄 / 13,997자**이고, 여기에 신규 9단계 뼈대(~30줄 / ~900자)가 붙어 **~243줄 / ~14,897자**다. 압축 여지가 실제로 있는 곳은 `Knowledge Base` 하나뿐이고(3,980자의 산문 문단 → 라우팅 표, 약 1,500자 회수), 나머지는 이미 표이거나 긴 불릿 덩어리라 문장을 줄여도 줄 수가 거의 안 준다.
>
> **그래서 공식 권장치 200줄은 도달 불가다.** 도달하려면 압축 생존이 필요한 규칙을 더 들어내야 하는데, 그건 이 슬라이스가 지키려는 것을 깨는 것이다. 200줄을 목표로 걸면 구현이 끝난 뒤 `start-verification`의 GREEN 게이트에서 넘을 수 없는 벽에 부딪히고, 그때 남는 선택지는 급히 도려내거나 임계값을 올리는 것뿐이다 — 후자는 이 계획이 §5(c)에서 「반증 불가능한 탈출구」라며 비판한 바로 그 행동이다.
>
> **결론: 게이트는 자수 ≤14,000 · 줄 수 ≤240으로 두고, 둘 다 지금 확정한다.** 자수가 주 지표다 — 컨텍스트 비용이 실제로 사는 곳이고, 이 파일은 한 줄이 200자를 넘는 곳이 30군데라 줄 수가 비용의 대리지표로 나쁘다. 24,971자 → 14,000자면 **-44%**다.

`/compact` 이후 재주입되는 것은 루트뿐이므로 이 경계가 곧 압축 생존선이다. 남기는 기준은 **"어느 턴에 어겨도 사고가 나는가"**와 **"쓰는 동안 작동해야 하는가"** 둘이다.

| 남기는 것 | 이유 |
|---|---|
| 문서 구조 트리 + ADR 색인 | 새 문서의 저장 위치를 정하는 자리. **`development/workflow/`를 트리에 추가한다** |
| Safety Rules 전량 | 어느 턴에 어겨도 사고 |
| Knowledge Base (라우팅) | 어느 질문에 어느 정본인지. 압축 후에도 있어야 한다 |
| 상태 머신 표 + 사람 게이트 3개 | 트리거 단어(`계획 승인`·`PR 승인`·`리워크`)가 여기 없으면 사용자 입력을 못 알아듣는다 |
| **9단계 뼈대** (신규) | 아래 별도 항목 |
| **「문서 정리 규칙」** | **집필 규범이라 A층이다.** 5·6단계에서 문서를 *쓰는 동안* 작동해야 하는 규칙인데 7단계에 배달하면 이미 부푼 행을 뒤늦게 줄이는 청소가 된다 |
| Cocos 「Context7 먼저, 추측 금지」 + `.meta` 원칙 + 「누가 언제」 표 | 파일을 *만들 때* 필요하다. 읽을 때가 아니다 |
| 도구 스택 + gstack 규칙 + Skill routing | 라우팅 |

**9단계 뼈대는 제목 나열이 아니다.** "6단계: AI 검증" 한 줄은 체크리스트 구실을 못 한다. 각 단계에 **자기가 쳐야 하는 커맨드 이름**이 들어가야 절차 기억이 0인 상태에서도 게이트를 조용히 건너뛸 수 없다.

```
#### 6단계: AI 검증
`start-verification`(GREEN 게이트) → /cso → `pass cso` → `pnpm typecheck` → `pass ts`
→ `pnpm check --write` → `pass lint` → 기능 단위 커밋 → 코드리뷰 → `pass review`
코드 수정이 끼면 `invalidate`로 cso부터 다시. 상세: `pnpm wf steps verification`
```

**ADR 004 인라인 링크를 뺀다.** 현재 `CLAUDE.md:92`는 `### 워크플로우 상태 ([ADR 004](...))`인데, 이건 정본 절이 결정 기록을 명세처럼 가리키는 형태이고 「문서 정리 규칙」이 금지한 링크 방향이다. 이 레포는 2026-08-08에 `art-direction.md`가 같은 짓을 해 사용자가 폐기된 명세를 현재 명세로 읽는 사고를 겪었다. ADR 004는 색인 줄에만 남긴다.

`CLAUDE.md`의 트리거 줄·명령 표·짧은 라벨은 **전보체를 유지한다**(`writing-style.md` 「적용 대상」).

### B층 — `docs/development/workflow/<phase>.md`

**매니페스트를 쓰지 않는다.** 전이의 목표 phase가 결정적이므로 매핑은 파생 가능하다.

```
planning · qa-setup · implementation · verification · user-verification · pr-ready
```

파일명이 곧 phase 이름이고, phase 어휘는 `workflow.mjs`의 `PHASES` 배열이 들고 있는 진짜 어휘라 안 바뀐다. 초판의 `01/03/06/07/09`는 CLAUDE.md 단계 번호에서 딴 휘발성 인덱스였고, 이 레포는 「정본 절 번호를 바꾸지 마라」는 규칙을 이미 갖고 있다 — 같은 병을 겪었다는 뜻이다.

| 파일 | 내용 |
|---|---|
| `planning.md` | 백로그 확인(0-1), `/office-hours`·`/autoplan`, 계획 문서 작성 |
| `qa-setup.md` | QA 문서 작성 규칙 전문, 에디터 조립 레시피, 잠정→확정 |
| `implementation.md` | `conventions.md` 선행 읽기, TDD GREEN→REFACTOR, 무관 이슈는 백로그로 |
| `verification.md` | cso→ts→lint→커밋→리뷰 순서, `invalidate` 재실행 루프 |
| `user-verification.md` | Draft PR 생성, PR 본문 작성 규칙, 8단계에서 할 일 |
| `pr-ready.md` | 상태 표시 확정, Draft 해제, squash merge, gbrain 색인 갱신 |
| `README.md` | phase 도표 + 각 문서 한 줄 요약 + 「새 문서를 넣는 법」 |

`README.md`가 통독 가능성을 되살린다. 현행 「기능 개발」 절의 가장 큰 미덕은 계획→머지가 위에서 아래로 한 번에 읽힌다는 것인데, 분할이 그걸 없앤다.

이 문서들은 읽고 이해하는 글이므로 **서술형으로 쓴다.** 잘라 붙이는 것이 아니라 다시 쓰는 작업이다. **B층은 정본이므로 `sessions/`·ADR을 링크하지 않는다** — 지금 `CLAUDE.md`에서 옮기면 링크가 그대로 따라오므로 이전 중에 걷어낸다.

## 4. 배달 설계

### 언제 배달하는가

| 계기 | 배달 |
|---|---|
| 전이 성공 (`start`·`approve-plan`·`ready-impl`·`start-verification`·`pass`(전이 시)·`rework`·`approve-pr`) | 새 phase 문서 |
| `invalidate` | `verification.md` 재배달 (phase는 안 바뀌지만 절차를 다시 돈다) |
| `pnpm wf steps [phase]` | 읽기 전용 재출력. 인자 없으면 현재 phase |
| `pnpm wf status` | 현재 phase 문서 **경로 한 줄**만 (본문 아님) |
| `pr-done` (→ `done`) | **배달하지 않는다** |

**`done`은 배달 대상이 아니다.** phase는 일곱인데 문서는 여섯이다(`done` 제외). 불변식 1대로 「디스패치 뒤에서 phase 변화를 보고 배달」하는 일반 구현을 하면 `pr-done`이 `done.md`를 찾다 없어서 **매 슬라이스 마지막에 누락 경고를 헛발화**한다. 배달 대상 phase 집합에서 `done`을 명시적으로 뺀다.

**`wf steps`가 압축 후 복구 경로다.** 초판의 안전장치는 "절차가 컨텍스트에 없으면 문서를 읽는다"였는데, 이 조건이 참인지 판정하려면 에이전트가 **자기가 모른다는 것을 알아야** 한다. 부재는 스스로를 알리지 않는다. 압축 요약은 "verification 진행 중, cso 완료"라고 말할 뿐이다.

`status`에 경로 한 줄을 넣는 것이 이 문제를 뒤집는다. `status`는 "나 어디 있지"의 정본 커맨드라 일상적으로 돌아가고, 그러면 **부재가 아니라 존재로 신호가 온다.** A층 복구 지시도 "문서를 읽어라"가 아니라 `pnpm wf steps`를 적는다.

`wf start`를 재배달 수단으로 오해하면 안 된다 — `start`는 phase 가드가 없어 무조건 상태를 초기화한다. `planning.md` 안에 「다시 보려면 `wf steps planning`, `wf start`를 다시 치지 말 것」을 명시한다.

### 어떻게 출력하는가

```
[게이트 출력: vitest / typecheck / meta — 현행 유지]
✓ start-verification → phase=verification            ← 상태 줄 먼저
──────────────────────────────────────────────
▶ verification 절차: docs/development/workflow/verification.md
   (다시 보려면 `pnpm wf steps verification`)
──────────────────────────────────────────────
<문서 본문>
──────────────────────────────────────────────
✓ start-verification → phase=verification            ← 한 번 더
```

- **상태 줄을 앞뒤로 두 번 찍는다.** 배달물이 자체 `#` 제목을 가진 마크다운이라 구분자가 없으면 문서 제목이 CLI가 하는 말처럼 읽힌다. 40바이트로 "맨 아래를 보는 사람"과 "멈춘 데를 보는 사람"을 둘 다 만족시킨다.
- **경로를 본문보다 먼저 찍는다.** `start-verification`은 vitest 전체 출력 뒤에, `approve-pr`은 tsc 2회 뒤에 배달하므로 도구 출력 절단에 걸릴 수 있다. 잘려도 경로가 남으면 회복된다.
- **스트림을 가르지 않는다.** 초안은 「본문은 stdout, 상태는 stderr」로 두 청중을 나누려 했는데, 현행 `workflow.mjs`의 `✓ …` 상태 줄이 전부 `console.log`(stdout)라 기존 줄을 옮겨야 하고, 무엇보다 **두 스트림은 리다이렉트 시 순서가 보장되지 않아** 위에서 공들인 「상태 줄 먼저 · 경로를 본문보다 먼저」가 깨진다. 순서 보장이 이 배치의 요점이므로 **상태·경로·본문은 전부 stdout**에 순서대로 낸다. stderr로 가는 것은 **누락 경고 하나뿐**이다(기존 `fail()`과 같은 취급).
- **`WF_QUIET=1`로 본문 억제.** `invalidate` 사이클을 세 번 도는 사람이 두 번째에 찾는다. 억제는 전부 아니면 전무 — 잘린 절차는 이 설계가 막으려던 실패다.

### 반복 배달은 차등으로 낸다

`invalidate`는 한 슬라이스에서 여러 번 돌고(cso 이슈 → 수정 → 재검증, 코드리뷰발 수정도 같은 경로), 그때마다 `verification.md` 전문을 다시 쏟으면 사람에게는 벽이고 에이전트에게는 「이거 아까 봤는데」 둔감화다.

그래서 **같은 phase 안에서 두 번째부터는 요약만** 낸다 — 절 제목 + 게이트 이름 줄 + `전문: pnpm wf steps verification`. 절차를 다시 돌라는 신호(게이트 목록)는 유지하면서 부피는 열 줄로 줄어든다.

상태는 `workflow-state.json`에 `docs_delivered: []`로 들고 **phase가 바뀔 때·`rework`·`start`에서 비운다.** 리워크는 진짜로 새 회차이므로 전문을 다시 받아야 한다.

이 필드는 `verification` 객체 **밖**에 둔다. 이유를 정확히 적는다 — 초안은 "`every(Boolean)` 판정에 배열이 섞이면 안 된다"고 했는데 **그건 틀렸다.** JS에서 빈 배열은 truthy라 `pass()`의 `Object.values(s.verification).every(Boolean)`을 망가뜨리지 않는다(`ts_check_scope`는 `null`이 될 수 있어 사정이 다르다). **진짜 이유는 `resetVerification()`이 `CHECK_FLAG` 키만 순회한다는 것**이다 — 안에 넣으면 그 함수가 못 지워서 `invalidate` 이후에도 배달 기록이 남는다.

**구현 주의 둘.** ① `docs_delivered` 초기화를 `resetVerification()`에 넣으면 안 된다 — `invalidate`가 그 함수를 부르므로 매번 전문이 나가 차등화가 통째로 무력해진다. 초기화는 phase 변경·`rework`·`start` 지점에서 명시적으로 한다. ② 기존 `workflow-state.json`에는 이 필드가 없어 첫 실행 시 `undefined`다. `freshState()`에 `docs_delivered: []`를 넣고 읽는 쪽도 `?? []`로 받는다.

### 불변식 셋 (구현이 어기면 안 되는 것)

1. **배달은 디스패치 성공 직후, `save()` 이후.** `workflow.mjs`의 모든 실패 경로는 `fail()` → `process.exit(1)`이라 실패한 전이에는 자동으로 배달이 안 간다. 이 성질을 공짜로 얻으려면 배달을 커맨드 함수 **안**이 아니라 디스패치 **뒤**에 둔다.
   - 특히 `pass`는 `allClean` 이후에도 **QA 잠정 태그 게이트에서 죽을 수 있다**(`workflow.mjs:354-366`). `allClean` 시점에 배달하면 전이하지도 않은 `pass`에서 `user-verification.md`가 샌다.
2. **배달은 절대 throw하지 않고 종료코드를 바꾸지 않는다.** `try/catch`로 전부 삼킨다. 배달이 던지면 상태는 이미 전이됐는데 커맨드가 실패로 보이고, 재실행하면 `requirePhase`가 막아 사람이 갇힌다.
3. **문서가 없어도 전이를 막지 않는다.** 막으면 문서 누락 하나로 워크플로가 멈추는데 빠져나올 경로가 없다.

### 경고 문구

계획이 "경고만 한다"고 적으면 구현자는 `console.warn("문서 없음")` 한 줄을 쓴다. 이 파일의 기존 수준(`approve-pr`의 범위 실패, `requireAssetMeta`)에 맞춘다.

```
⚠ [배달] verification 절차 문서를 찾지 못했습니다.
   경로: docs/development/workflow/verification.md
   원인: 디렉터리는 있으나 이 파일만 없음 (형제 5개는 존재)
   결과: 이 전이에서 절차가 전달되지 않았습니다 —
         다음 단계를 기억에 의존해 진행하게 됩니다.
   조치: git 이력에서 복구(`git log --diff-filter=D -- <경로>`)하거나 사용자에게 알리세요.
```

원인은 **두 가지를 구분한다** — 파일만 없는 경우와 디렉터리 자체가 없는 경우는 고치는 법이 다르고 코드가 쉽게 구별할 수 있다. 그리고 `check-meta`·`check-qa`와 같은 결로 **`pnpm wf check-docs`를 단독 커맨드로** 둔다.

**"안전망이 워크플로 안에 있다"는 주장은 과장이었다.** `start-verification`이 전체 스위트를 돌려 문서 누락을 잡는 건 맞지만, `start`(planning)와 `approve-plan`(qa-setup)은 그보다 **먼저** 일어난다. 그 문서가 없었다면 그물이 걸리는 시점은 이미 그 단계를 절차 없이 마친 뒤다. 정직하게는 **지연 탐지**다.

### 커맨드 키 가드는 경고로만

초판은 "로드 시점 가드"로 치명적 검증을 하려 했다. 두 가지가 틀렸다.

- **TDZ.** `commands`는 `workflow.mjs:220`의 `const`라 파일 상단에서 참조하면 ReferenceError다. 놓을 수 있는 자리는 `:475`(객체 리터럴 끝)와 `:477`(디스패치) 사이뿐이다.
- **폭발 반경.** 그 자리는 `status`·`check-meta`·도움말을 포함한 **모든 경로**가 지난다. 여기서 `fail()`을 부르면 오타 하나로 진단 수단까지 죽고, 훅이 상태 파일 직접 편집을 막으므로 사람이 갇힌다. 게다가 결과가 더 가벼운 실패(배달만 안 됨)에 더 무거운 처벌을 매기는 셈이라 심각도 순서가 뒤집힌다.

**런타임에서는 경고만 한다.** 치명적 판정은 테스트와 `wf steps`(진단 전용이라 죽어도 워크플로를 안 막는다)에서 한다.

## 5. 테스트

초판의 가장 큰 결함은 **이 슬라이스가 만드는 유일한 코드(배달 로직)에 자동 검증이 0**이었다는 것이다. `biome.json`이 `.claude`를 제외하고, `pnpm typecheck`는 `.mjs`를 안 보고, CI가 없다. 5줄짜리 데이터 파일에는 TDD 의례가 걸리고 정작 새 코드에는 안 걸리는 구조였다.

### (a) 순수 함수 + fixture — `tests/helpers/WorkflowSteps.ts`

`findStepDocIssues(phases, filesOnDisk)`를 순수 함수로 둔다. `I18nKeyGuard`가 확립한 관용구다 — 순수 함수를 헬퍼에 두고 fixture로 한 군데씩 비틀어 결함 종류별 단위 테스트를 돌린 뒤, 마지막에 실물 게이트 1건을 붙인다.

이렇게 하면 (1) fixture로 각 결함을 실제로 잡는 걸 증명할 수 있고, (2) `tests/**/*.ts`라 **타입체크를 받고**, (3) 실물 단언이 한 건으로 줄어든다.

단언 대상:
- `done`을 제외한 모든 phase에 문서가 있다.
- `workflow/` 안의 `.md` 중 phase 이름도 `README.md`도 아닌 파일이 없다.
- **Windows 주의:** 존재 검사를 `fs.existsSync`로 하면 안 된다. Windows는 대소문자를 무시해서 `Verification.md` 오타가 이 장비에선 통과하고 Linux에서만 깨진다. `readdirSync` 결과에 대한 **정확한 문자열 포함 검사**로 한다. 경로 비교에는 `workflow.mjs:283`의 관용구(`.split(path.sep).join("/")`)를 쓴다.

### (b) 샌드박스 E2E — 배달 로직을 실제로 돌린다

`workflow.mjs:12`가 `ROOT = process.env.CLAUDE_PROJECT_DIR || process.cwd()`이고 모든 경로가 `ROOT` 기준이다. 그래서 임시 디렉터리에 최소 상태를 꾸미고 실제로 실행할 수 있다.

```
임시 디렉터리에 .claude/workflow-state.json + docs/qa/<feature>-test.md
+ docs/development/workflow/*.md 를 만들고
execFileSync(process.execPath, [path.join(REPO, '.claude/workflow.mjs'), 'pass', 'review'],
             { cwd: sandbox, env: { ...process.env, CLAUDE_PROJECT_DIR: sandbox } })
→ stdout에 user-verification.md 내용이 들어 있는가
```

덮는 것: 전이 시 배달된다 / 전이 실패 시 배달 안 된다 / 문서 없으면 경고하고 전이는 된다 / 부분 `pass`는 배달 안 된다 / `steps`가 상태를 안 바꾼다.

**`start-verification`은 절대 테스트에서 부르지 않는다** — vitest가 vitest를 재귀 호출한다. 외부 프로세스를 안 띄우는 `approve-plan`과 `pass cso|lint|review`만 쓰면 위 전부를 덮는다.

커맨드 키 정합은 인자 없이 실행하면 목록이 나온다는 성질을 쓴다(`node .claude/workflow.mjs` → `commands: start, approve-plan, …`, 종료코드 0).

### (c) 재성장 차단 — 이 슬라이스의 유일한 영구 효과

- **`CLAUDE.md` ≤ 14,000자 · ≤ 240줄** 단언. 이게 없으면 6개월 뒤 이 슬라이스는 없었던 일이 된다. 최근 커밋 5개 중 4개가 `CLAUDE.md`를 건드렸다(#73·#74·#75가 연속으로 규칙 추가). 분할은 시계를 되돌릴 뿐 태엽을 안 건드린다.
- **B층 문서 개당 ≤ 4,000자 · 합계 ≤ 16,000자.** 새 위치에서 같은 일이 반복되는 걸 막는다. 이동 대상이 약 11,000자이고 전보체를 서술형으로 풀면 늘어나므로(§3) 1.3배를 잡아 여유를 두되, 두 배로 부푸는 것은 막는다.

**수치는 §3의 산술에서 나왔고 탈출구를 두지 않는다.** 초판은 자수 목표를 걸면서 §7에 "못 줄이면 목표치를 올린다"는 문장을 함께 두어 반증 불가능했다. 이번에는 잔류 목록을 실제로 더해 도달 가능한 수를 **지금** 정했다. 구현 중에 이 수를 못 맞추면 임계값이 아니라 **잔류 목록을 다시 본다.**

## 6. 규칙 인벤토리 — 이 슬라이스의 주 산출물

**가장 위험한 작업은 배달 로직이 아니라 규칙 이전이다.** 레포 전체가 굴러가는 규칙 약 13,000자를 전보체에서 서술형으로 재작성하면서 하나도 잃지 않아야 한다. 규칙이 조용히 빠지면 몇 슬라이스 뒤에 사고로 나타난다 — `.meta` 게이트도, QA 잠정 태그도, `invalidate` 재실행 루프도 전부 사고를 겪고 나서 추가된 것들이다.

초판은 이 작업의 검증을 §6의 불릿 한 줄로 뒀다. 그 사이 5줄짜리 매니페스트는 전용 JSON + 테스트 4건 + 런타임 가드를 받았다. **노력 배분이 리스크와 역상관이었다.**

그래서 인벤토리를 **커밋되는 산출물**로 만든다. `docs/qa/claude-md-split-test.md` 부록에 현재 `CLAUDE.md`의 모든 규범 문장을 번호로 나열하고, 각 항목의 최종 위치를 적는다.

| # | 규칙 (현행 문장) | 최종 위치 | 비고 |
|---|---|---|---|

### 2차 개정 (검증 리뷰 반영)

개정판을 검증 전용 리뷰에 다시 걸었다. 지적 12건은 전부 닫힌 것으로 확인됐고(되돌릴 오류 없음), **개정 과정에서 새로 들어온 문제 5건**을 마저 고쳤다.

| 문제 | 처리 |
|---|---|
| **`≤200줄` 목표가 잔류 목록과 산술적으로 불가능** (실측 213줄 + 뼈대 30 = ~243줄) | §3에 산술을 적고 게이트를 **≤14,000자 · ≤240줄**로 확정. 200줄이 왜 도달 불가인지와, 구현 중 못 맞추면 임계값이 아니라 잔류 목록을 다시 본다는 것을 명시 |
| `pr-done` → `done`에 문서가 없어 누락 경고를 헛발화 | 배달 대상 phase에서 `done` 제외를 명시 |

| `docs_delivered`를 밖에 두는 **사유가 틀렸다** (`[]`는 truthy라 `every(Boolean)`을 안 깬다) | 진짜 사유(`resetVerification()`이 `CHECK_FLAG` 키만 순회)로 교체 + `resetVerification`에 초기화를 넣지 말 것 + 기본값 명시 |
| B층 상한에 수치가 없어 구현 불가 / E2E 예시가 상대경로 | 개당 ≤4,000자·합계 ≤16,000자로 확정. `execFileSync`에 절대경로 + `cwd` |

**이 5건 중 첫째가 가장 위험했다.** `≤200줄`은 기계 게이트라 구현을 다 끝낸 뒤 `start-verification`에서 막혔을 것이고, 그 시점의 선택지는 급히 도려내거나 임계값을 올리는 것뿐이다. 후자는 이 계획이 §5(c)에서 비판한 바로 그 행동이라, 계획이 자기 규칙을 스스로 어기는 자리로 걸어 들어가고 있었다.

**기각한 지적도 남긴다.** DX·Eng 모두 `.claude/rules/` + `paths:`를 "출처 없는 주장"이라며 Cursor 기능과의 혼동을 의심했으나, 공식 문서에 명시돼 있다(`code.claude.com/docs/en/memory` 「Organize rules with `.claude/rules/`」·「Path-specific rules」). 두 에이전트는 로컬 선례만 찾고 1차 출처를 확인하지 않았다. **다만 C층을 접는 결론 자체는 채택했다** — 근거가 "기능이 없다"가 아니라 "손익이 안 맞는다"로 바뀌었을 뿐이다.

## 11. 구현 결과 — 계획과 달라진 것

목표치는 전부 실측으로 충족했다. `CLAUDE.md` 24,971자 / 355줄 → **13,807자 / 226줄**(-45%, 한도 14,000 / 240), 절차 문서 7개 **합계 11,964자**(한도 16,000, 최대 `qa-setup.md` 2,697자 / 한도 4,000). 테스트 42건, 전체 스위트 671건 통과.

구현하면서 계획을 벗어난 곳이 일곱이다. 대부분 코드리뷰 3회차에서 나왔다.

1. **`parsePhases`를 새로 뒀다.** §5(a)는 `findStepDocIssues(phases, filesOnDisk)`만 정했고 `phases`가 어디서 오는지는 비워 뒀다. 목록을 테스트에 베껴 두면 `PHASES`가 늘었을 때 아무도 모르므로, `workflow.mjs` 소스에서 파싱해 어휘의 출처를 하나로 유지한다. 파싱 실패는 빈 배열이 아니라 **예외**다 — 빈 배열이면 기대 문서가 0개가 되어 정합 검사가 조용히 통과한다.
2. **`README.md`도 기대 목록에 넣었다.** §5(a)의 단언은 "phase 이름도 `README.md`도 아닌 파일이 없다"뿐이라 README 자체가 사라지는 경우를 안 봤다. 분할이 없앤 통독 가능성을 되살리는 경로가 그것뿐이라 누락을 잡는다.
3. **`done.md`가 있으면 잉여로 잡는다.** §4는 `done`을 배달 대상에서 빼기만 했는데, 그러면 `done.md`를 만들어도 아무도 안 읽는 채로 낡는다.
4. **누락 원인을 셋으로 나눴다**(§4는 둘). 디렉터리 없음 / 파일만 없음 / **파일은 있으나 읽을 수 없음**. 셋째가 없으면 권한 오류나 파일 자리의 디렉터리가 **완전히 무음**으로 지나간다 — 배달 쪽 `catch`가 예외와 함께 진단까지 삼키기 때문이고, 이 기구가 막으려는 결과가 정확히 그것이다.
5. **상태 줄을 커맨드 원본 표기로 찍는다.** §4의 스케치는 커맨드 자신의 줄을 그대로 되풀이하는 그림이었는데, 배달 코드는 커맨드가 무엇을 덧붙였는지 모른다. 인자를 포함한 표기(`pass review`)를 쓰고, phase가 안 바뀐 재배달은 `→ phase=`가 전이를 함의하므로 `— phase=… 절차 재배달`로 갈랐다.
6. **`steps <phase>`가 상태 파일 없이 돈다.** 계획엔 없던 것이다. 절차를 잃었을 때 치는 커맨드가 상태까지 잃은 상황에서 안 도는 것은 모순이라, 인자가 있으면 상태를 읽지 않는다.
7. **판정 로직이 두 곳에 복사돼 있다.** `check-docs`(CLI)가 `tests/helpers/WorkflowSteps.ts`를 import할 수 없어 생긴 복사본이다. §10이 `workflow.mjs` 모듈화를 스코프 밖으로 뺐으므로 그대로 두되, 양쪽에 경고 주석을 달고 **CLI 쪽에도 단언을 걸었다** — 그 단언이 없을 때 CLI만 되돌려도 전 테스트가 통과하는 것을 리뷰가 mutation으로 확인했다.

§5(c)가 말한 「이 슬라이스의 유일한 영구 효과」는 그대로 남았다. 크기 예산 넷이 테스트 단언이라, 다음에 이 파일들이 다시 부풀면 `start-verification`의 GREEN 게이트가 막는다.

**남은 관찰 하나.** §1이 "준수율을 떨어뜨리지 않는다"를 다음 두세 슬라이스에서 관찰하겠다고 적었는데 그것을 추적할 자리가 없어, `backlog-implement.md`에 **F71**로 남겼다. 이번에 새로 판 항목이 하나 더 있다 — 백로그 파일을 CRLF로 다시 쓰는 사고를 겪고 레포 전역 줄바꿈 정책을 **F72**로 열었다.
