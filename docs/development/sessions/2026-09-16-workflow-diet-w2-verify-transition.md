#### W2. 통합 검사 경로와 전이 판정 — `.claude/lib/verify.mjs` + `workflow.mjs`

- `runVerify(runners = defaultRunners)`: `runners = {typecheck, biome, vitest}`를 기본값 있는 매개변수 하나로 받아 순서대로 돌린다. 러너 추상 계층이나 출력 형식 프레임워크는 만들지 않는다. 러너 출력은 캡처한다. `typecheck.mjs`의 `runTypecheck`에 `{ capture: true }` 옵션을 더해 stdout/stderr를 돌려주게 하고(`pnpm typecheck` 단독 실행은 지금처럼 `inherit`), vitest는 `--reporter=json --outputFile=<실행마다 fs.mkdtempSync로 만든 폴더의 파일>`로 돌려(끝나면 지운다 — 원 폴더와 worktree 두 세션이 동시에 돌 때 고정 경로면 남의 결과를 읽는다. `shell: true`라 인자는 따옴표로 감싼다. 파일이 안 생겼으면 아래 「결과 없이 종료」 구제로 보낸다) 실패 항목의 이름과 첫 실패 메시지 첫 줄만 찍고, biome는 `--reporter=summary`로 돌린다. 각 러너는 `{status, scope?, summary, details}`를 돌려주고, `runVerify`는 `{ok, results: {typecheck, biome, vitest}}`를 돌려주며 검사마다 한 줄 요약을 찍고 실패한 검사의 상세(40줄까지, 넘으면 「…N줄 생략」)와 재현 명령(`pnpm typecheck`·`pnpm check`·`pnpm exec vitest run`)만 찍는다. 첫 실패에서 멈추지 않고 셋을 다 돌린다(한 턴에 세 결과를 보게). 기본 러너 `defaultRunners`는 `typecheck.mjs`의 `runTypecheck`, `pnpm exec biome check --write .`, `pnpm exec vitest run`이고 `verify.mjs` 한 곳에만 적는다. biome의 `--write`는 T3(2026-09-17 승인)다 — 포맷 차이는 자동 적용하고 린트 위반만 차단하며 요약에 「n개 파일 재포맷」을 찍는다(설계 Q7 「비파괴」를 뒤집는다. lint-staged가 커밋 때 이미 재포맷하므로 「검사와 수정이 섞인다」는 근거가 약했다). 자동 적용은 `start-verification`·`verify`에서만이고 `pass`의 전이 직전 재실행은 `--write` 없는 check-only다 — 커밋·리뷰 뒤에 트리를 더럽히지 않게. `runVerify(runners = defaultRunners, { write = true } = {})`처럼 옵션 하나로 가른다. `package.json`에 `"verify:ci": "node .claude/lib/verify.mjs"` 스크립트를 두어 CLI와 미래 CI가 같은 정의를 부른다. 이름에 `:ci`를 붙이는 이유는 `wf verify`(상태에 기록)와 구분하기 위해서다. `verify.mjs`를 직접 실행하면 마지막 줄에 「상태에 기록하려면 `pnpm wf verify`」를 찍는다. 오류 구제 둘: 러너 스폰 실패(ENOENT)는 「러너 `<이름>`을 실행할 수 없다(`pnpm` 경로 확인)」로 잡아 status 1로 내고, vitest가 출력 없이 0이 아닌 코드로 끝나면 「테스트 러너가 결과 없이 종료됐다, `pnpm exec vitest run`으로 재현」을 낸다. 시험용 러너는 단위 테스트가 함수로 넣는다. 환경변수 우회는 만들지 않는다. vitest 실패 출력에 `tsconfig.cocos.json`이 보이면 「Cocos 생성 파일이 없어 게임 스크립트 import가 실패했다 — Cocos로 프로젝트를 한 번 열거나 F113 참조」를 덧붙인다(새 클론·worktree에서 39개 파일이 이 이유로 죽는데 이 슬라이스가 vitest를 하드 게이트로 세운다). `shell: true`는 유지한다(Node 22는 shell 없는 `.cmd` 스폰을 EINVAL로 막는다). 출력 테스트는 검사마다 요약 한 줄이 있고 실패 검사에만 상세가 붙는지만 단언한다.
- `start-verification`: 지금의 GREEN(vitest만) 대신 `runVerify`를 돌린다. 모두 통과해야 `verification`으로 전이하고, `ts_check_clean`·`lint_clean`·`ts_check_scope`를 기록한다. `resetVerification`은 전이 전에 지금처럼 부르되, 기록은 그 뒤에 쓴다.
- `verify` 명령(신설, phase `verification`): 같은 경로를 다시 돌려 기계 플래그(`ts_check_clean`·`lint_clean`·`ts_check_scope`)만 다시 쓴다. **전이하지 않는다.** `DELIVERING_COMMANDS`에 넣지 않는다(전이가 없으면 배달도 없다). 역할은 「전이 없이 지금 결과만 보고 싶을 때」다 — `pass`가 전이 직전에 스스로 검사하므로 `invalidate` 뒤 `verify`를 먼저 칠 의무는 없다. `implementation`에서 치면 phase 거부 메시지에 「`pnpm wf start-verification`(같은 검사 + 전이)」를 안내한다. `verify.mjs`는 `import.meta.url === pathToFileURL(process.argv[1]).href`일 때만 CLI로 동작하고(`typecheck.mjs`와 같은 방식), import만으로는 아무것도 돌지 않는다는 것을 테스트로 고정한다. 반대편도 고정한다: 툴체인 없는 샌드박스에서 `node .claude/lib/verify.mjs`를 직접 띄우면 러너 실행 실패 메시지와 종료코드 1이 나와야 한다(가드가 거짓으로 빠져 조용히 0으로 끝나는 것을 잡는다).
- 전이 판정은 `.claude/lib/transition.mjs`의 순수 함수 `decideTransition({state, gates, qaClean, canonDeclared, verifyResult}) → {transition, blockers, patch}`다. 순서: 「적용되는 판단 게이트가 모두 `true`」(`cso_done`은 `cso`가 적용될 때만, `code_review_clean`은 늘) → QA 확정 게이트(`qaDocClean`) → 정본 선언 게이트 → **전이 직전에 `runVerify`를 한 번 더 돌려 그 결과로 기계 플래그를 덮어쓴다(AI 턴 0, 약 7초)** → 통과면 `user-verification`. `ts_check_clean`·`lint_clean`·`ts_check_scope`는 **선행조건이 아니라 기록**이다(3D 호환 키로 남긴다) — 선행조건에 넣으면 `invalidate`가 그것을 `false`로 만들어 회차마다 `wf verify` 한 턴이 강제되는데, 그 회차가 이 슬라이스가 줄이려는 되감기다. `workflow.mjs`는 `runVerify()` → `decideTransition` → `patch` 적용 → `save`만 한다. 전이 직전 검사에 실패하면 `code_review_clean`은 보존하고 기계 플래그만 덮어쓰며 다음 행동은 「고친 뒤 `pnpm wf pass review`를 다시」다(그때 검사가 다시 돈다). 전이는 `pass`만 일으킨다. 리뷰 뒤 코드를 고치고 `verify`를 잊어도 낡은 타입·린트·테스트 결과로는 넘어가지 않는다. `cso`가 해당 없음이면 `cso_done`은 `false`여도 통과다. 막힐 때 메시지는 `status`와 같은 형식의 게이트 줄(새로 적용된 게이트는 어느 파일이 변경 집합에 들어와서인지 포함)과 다음 명령(`/cso` → `pnpm wf pass cso`)을 찍고, `verify`·`pass`·`start-verification`의 모든 실패 메시지 끝에 「절차: `pnpm wf steps verification`」을 둔다. 실패 경로에는 절차 문서가 배달되지 않으므로 이 포인터가 유일한 문서 연결이다. `verification.md`에 규칙 한 문장을 둔다: 「검증 중 코드를 고쳤으면 `wf verify`로 확인한다. 고친 파일이 `/cso` 적용 경로에 들거나 리뷰가 이미 끝났으면 `invalidate`다.」
- `pass`: 인자는 `cso|review`만 받는다. `ts`·`lint`를 치면 「`pnpm wf verify`를 쓴다」를 안내하고 종료코드 1. `pass cso`는 `cso`가 해당 없음이면 「표시할 것이 없다」며 거부한다.
- `pass cso`는 「변경 집합 ∩ `CSO_PATHS`」의 경로 목록을 정렬해 상태 키 `cso_paths`에 저장한다(UC2, 2026-09-17 승인). 목록 수준이라 같은 파일의 내용만 바뀐 것은 잡지 못한다 — 그 구멍은 2단계 지문이 닫는다(§6).
- `skip-qa "<사유>"`(신설, phase `qa-setup`·`verification`, T1): 변경 집합에 `game/assets/**`가 없을 때만 받고, 있으면 「QA 문서가 필요하다」로 거부한다. `qa_skip_reason`을 저장하고 `qaDocClean`은 그 값이 있으면 통과한다. `skip-test`·`canon-skip`과 같은 모양이고 `status`가 사유를 찍는다.
- `invalidate`: 정본·QA·리뷰 플래그는 지금처럼 초기화한다. `cso_done`은 지금 「변경 집합 ∩ `CSO_PATHS`」 목록을 다시 재서 저장된 `cso_paths`와 같으면 보존하고 다르면 둘을 비운다(UC2). 옛 상태 파일에 `cso_paths`가 없으면 보존하지 않는다. 안내 문구는 보존됐으면 「`/cso`는 유효 — 커밋·리뷰부터」, 아니면 「`/cso`부터 다시」.
- 테스트: `decideTransition`을 가짜 `verifyResult`로 단위 시험한다(통과 → 전이·patch, 실패 → 전이 없음·`code_review_clean` 보존·기계 플래그 덮어씀, `cso` 비적용이면 `cso_done: false`여도 통과, QA·정본 게이트 차단). 가짜 러너로 `runVerify`의 성공·부분 실패·전부 실패의 기록과 종료코드, 러너 스폰 실패와 vitest 무출력 종료의 구제 메시지, `pass ts` 거부, `pass cso` 비적용 거부, 출력이 검사마다 한 줄 + 실패 상세만인지. **배선 E2E(회귀).** `pass`가 자식 프로세스로 뜨는 `ClaudeMdSplit.test.ts`의 「전체 pass → user-verification 배달」·「막힌 뒤 선언하고 다시 치면 전이」·「canon-done이 기록하면 전이가 열린다」 세 케이스는 새 `pass`가 전이 직전 기본 러너를 돌리므로 툴체인 없는 샌드박스에서 깨진다(지금 통과하는 이유는 `qaDocClean`이 `tests/logic` 부재를 건너뛰기 때문이고 `runVerify`에는 그 탈출구를 파지 않는다 — 파면 `tests/logic`을 지우는 것만으로 기계 검사가 꺼진다). W5의 `pnpm` 심으로 초록을 유지하고, 심이 vitest 실패를 흘리는 변형으로 「`pass review`가 전이 직전 검사에서 실패하면 전이하지 않는다」와 「`verify`는 전이하지 않는다」를 E2E로 고정한다. `pass cso`가 `cso_paths`를 저장하고 `invalidate`가 목록이 같으면 `cso_done`을 보존·다르면 비우는 것, `skip-qa`가 `game/assets/**` 변경이 있으면 거부하고 없으면 `qaDocClean`을 통과시키는 것도 여기다.
