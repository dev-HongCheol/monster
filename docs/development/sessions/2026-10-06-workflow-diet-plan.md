## 0. 이 문서에서 쓰는 말

- **슬라이스** — 기능 하나를 계획부터 머지까지 끝내는 작업 단위다. 브랜치 하나와 PR 하나로 이루어진다.
- **phase** — 슬라이스가 지금 있는 단계다. `planning` → `qa-setup` → `implementation` → `verification` → `user-verification` → `pr-ready` → `done` 순서로 간다.
- **전이** — 다음 phase로 넘어가는 것이다. `pnpm wf <명령>`을 쳐야만 일어난다.
- **상태 파일** — `.claude/workflow-state.json` 파일이다. 지금 phase와 각 검사의 통과 여부를 적어 둔다.
- **통과 표시** — 상태 파일의 `verification` 안에 있는 참·거짓 값 네 개(`cso_done`·`ts_check_clean`·`lint_clean`·`code_review_clean`)다. 처음엔 `false`이고, 검사를 통과하면 해당 값이 `true`가 된다.
- **변경 집합** — 이 브랜치가 main에서 갈라진 뒤 바뀐 파일과, 아직 git에 올리지 않은 새 파일을 합친 목록이다.
- **적용 경로** — 검사마다 정해 둔 파일 경로 목록이다. 변경 집합에 이 경로에 속하는 파일이 있으면 그 검사를 하고, 없으면 「해당 없음」으로 건너뛴다.
- **통합 검사** — biome(코드 형식과 린트), 타입 검사, 전체 테스트(vitest)를 명령 하나로 차례로 돌리는 것이다.
- **판단 검사** — 기계가 판정할 수 없어서 AI가 판단하는 검사다. 네 가지이고, 결과를 적는 방법이 서로 다르다.
  - 보안 점검(`/cso`)과 코드 리뷰: `pnpm wf pass cso`·`pnpm wf pass review`를 치면 상태 파일의 `cso_done`·`code_review_clean`이 `true`가 된다.
  - 정본 갱신 확인: 이번에 고친 정본 문서의 경로를 `pnpm wf canon-done <경로>`로 상태 파일의 `canon_updated` 목록에 적는다. 새 정본을 만들 때는 `wf canon`을 쓰고, 고친 정본이 없으면 `wf canon-skip "<사유>"`로 사유를 적는다.
  - QA 확정: QA 문서에 남은 `(잠정 …)`·`(가칭 …)` 표시를 실제 값으로 고친다. 상태 파일에는 적지 않고, 도구가 QA 문서를 직접 읽어서 표시가 남았는지 확인한다.
  - 이 문서에서 넷 가운데 일부만 말할 때는 「/cso와 코드 리뷰」처럼 해당 이름을 쓴다.
- **기록용 값 셋** — 상태 파일의 `ts_check_clean`·`lint_clean`·`ts_check_scope`다. 이 슬라이스 뒤로는 다음 phase로 넘어가는 조건에 쓰이지 않고, 마지막 통합 검사의 결과를 적어 두는 데만 쓰인다(§4).
- **원래 폴더** — main 브랜치가 꺼내져 있는 저장소 폴더(`F:\work\monster`)다. 이 슬라이스는 그 옆에 따로 만든 작업 폴더(git worktree)에서 한다. 그래서 이 슬라이스가 머지되기 전까지 원래 폴더에는 고치기 전의 도구가 그대로 있다.

## 1. 무엇을 하나

지금은 슬라이스가 크든 작든 같은 9단계를 전부 거친다. 문서 검사기 한 줄을 고치는 슬라이스도 QA 문서의 씬·에디터 절을 「없다」로 채우고, `/cso`를 하고, `.meta` 검사를 받는다. 검증 단계에서는 명령 네 개(`pnpm typecheck` → `pass ts` → `pnpm check --write` → `pass lint`)를 하나씩 친다. 리뷰를 받고 코드를 고치면 통과 표시 네 개를 전부 지우고 검사 네 개를 처음부터 다시 한다.

이 슬라이스는 두 단계로 나눈 계획의 **1단계**다. 검사가 무엇을 확인하는지는 바꾸지 않고, 아래 세 가지를 한다.

1. **해당 없는 검사를 건너뛴다.** 변경 집합을 보고 `.meta` 검사, 게임 전체 타입 검사, `/cso`를 할지 정한다. `game/` 폴더를 건드리지 않는 슬라이스는 사유를 적고 QA 문서를 쓰지 않아도 된다.
2. **기계 검사를 명령 하나로 돌린다.** `start-verification`이 통합 검사를 돌리고 결과를 상태 파일에 적는다. `pass ts`와 `pass lint`는 없앤다. `pass review`는 다음 phase로 넘기기 직전에 통합 검사를 한 번 더 돌린다.
3. **두 곳에 복사된 판정 코드를 하나로 합친다(F78).** 지금 `workflow.mjs`와 `tests/helpers/`에 같은 판정 코드가 따로 있다. 이것을 `.claude/lib/*.mjs`로 옮기고, 도구와 테스트가 같은 파일을 쓰게 한다.

**2단계**는 통과 여부를 기록하는 방식 자체를 바꾼다. 지금은 지킬 원칙 네 가지만 정하고(§6), 1단계를 머지해서 실제로 써 본 뒤 새 슬라이스로 시작한다.

이 슬라이스가 새 절차를 처음 쓰는 슬라이스다. 이 브랜치에서 고친 `workflow.mjs`가 이 슬라이스의 검증을 돌리므로, `verification`에 들어가는 순간 통합 검사와 적용 판정이 처음으로 실제로 돈다. 이 브랜치는 `.claude/**`를 고치므로 `/cso`를 해야 하고, `game/**`는 건드리지 않으므로 `.meta` 검사와 게임 전체 타입 검사는 「해당 없음」이 나와야 한다.

**1단계가 줄이는 부담.** 줄이려는 부담은 시간, AI가 읽는 양, 도구 유지비 세 가지다.

- 시간: 검증 명령 수를 줄이고 해당 없는 검사를 건너뛰어서 줄인다.
- 도구 유지비: 두 곳에 복사된 판정 코드를 합쳐서 줄인다.
- AI가 읽는 양: 검증 중에 나오는 출력이 줄어든다. 명령이 네 개에서 하나가 되고, 통합 검사 출력은 검사마다 요약 한 줄과 실패했을 때의 상세 40줄까지만 낸다.

절차 문서는 이번에는 길이가 늘지 않게만 한다(W6). 절차 문서를 줄이는 일은 새 백로그 항목으로 따로 만든다(W7). 1단계는 슬라이스마다 드는 비용을 줄이는 대신 도구 코드의 양은 늘린다(새 모듈 일곱 개, 시험용 임시 저장소 도우미, 테스트). 실제로 유지비가 어떻게 됐는지는 §6에서 줄 수와 테스트 시간으로 잰다.

## 2. 결정

### 2.1 사용자가 정한 것

- **줄일 것(2026-09-16).** 슬라이스에 드는 시간, AI가 읽는 양, 도구 유지비 세 가지다. 사람이 확인하는 지점은 줄이지 않는다. 아까운 것은 「규모와 상관없이 모든 슬라이스가 같은 전 과정을 거치는 것」이다.
- **할 검사를 변경 집합으로 계산한다(2026-09-16).** 「가벼운 절차」·「무거운 절차」 같은 구분을 상태 파일에 저장하지 않는다. 검사마다 적용 경로를 정해 두고, 필요할 때마다 변경 집합과 비교해 계산한다. 코드 리뷰와 전체 테스트는 경로와 상관없이 항상 한다. 계획에 적은 범위 밖에서 게임 파일이 바뀌어도 막지 않고, 필요한 검사를 자동으로 더한다.
- **`/cso`의 적용 경로(2026-09-17).** 「개발 장비에서 실행되는 코드·자동화·의존성·공급망·git 실행 동작을 바꾸는 파일」이 바뀌었을 때만 `/cso`를 한다.
- **`pass ts`·`pass lint`를 없앤다(2026-09-17).** 옛 명령과 새 명령을 함께 남기면 명령 수가 줄지 않는다.
- **두 단계로 나누고 PR도 두 개로 낸다(2026-09-16에 정하고, 2026-10-05에 범위를 줄여 다시 정했다).** 이 브랜치는 1단계만 구현한다. 2단계는 지킬 원칙 네 가지만 지금 적어서 함께 리뷰받고, 자세한 내용은 2단계를 시작할 때 정한다. 나누는 이유는 두 가지다. 첫째, 1단계는 지금의 통과 표시 방식을 그대로 두고 그 위에 적용 판정과 통합 검사를 더하지만, 2단계는 통과 표시 방식 자체를 바꾸므로 잘못됐을 때 영향이 훨씬 넓다. 둘째, 1단계를 써 본 결과를 보고 2단계를 할지 말지 정할 수 있다.
- **코드를 고친 뒤 `/cso`는 바뀐 부분만 다시 본다(2026-10-05).** 2026-09-17에는 「`/cso` 대상 파일의 목록이 그대로면 다시 하지 않는다」로 정했는데, 이것을 뒤집는다. 그 뒤 `/cso`에 직전 커밋 이후 바뀐 부분만 보는 방식이 생겼고, 3D 슬라이스에서 이미 그렇게 썼다. 옛 방식은 두 가지 문제가 있었다. 파일 목록이 같아도 그 파일의 내용을 고쳤다면 고친 내용이 보안 점검 없이 지나간다. 그리고 목록을 비교하려면 상태 파일에 새 값을 두고 비교 코드와 테스트를 만들어야 한다.
- **상태 파일을 git으로 추적할지는 이 슬라이스에서 바꾸지 않는다(2026-10-05).** 추적할지 말지는 백로그 F10에서 정한다. 2026-09-17에는 「장비를 옮길 때 phase가 함께 따라오는 이점이 브랜치끼리 충돌하는 불편보다 크다」고 보고 추적을 유지하기로 했다. 그런데 그 뒤 2026-09-30 리베이스에서 상태 파일이 실제로 충돌했고, 머지된 슬라이스의 상태가 main에 남는 일도 생겼다. 그래서 여기서 다시 정하지 않고, 이 두 사실을 F10에 넘긴다. 변경 집합을 계산할 때는 상태 파일을 뺀다.
- **새 ADR을 쓰지 않는다(2026-09-28).** 결정의 이유는 이 계획 문서에, 지금의 절차는 절차 문서 본문에 적는다. 절차 문서에 새 이력 줄도 만들지 않는다. 정본의 이력을 어떻게 적을지는 F116에서 정한다.
- **`/autoplan` 최종 승인에서 사용자가 고른 여섯 가지(2026-10-06, 모두 권장안대로).** `/autoplan`이 정답이 없는 선택지(Taste)로 분류해 사용자에게 물은 것들이다.
  1. 통합 검사가 실패한 뒤에는 「`invalidate`를 치고 절차대로 다시 한다」와 같게 처리한다. 형식이나 타입만 고친 경우라도 예외를 두지 않는다.
  2. `pass cso`를 칠 때 커밋하지 않은 변경이 있어도 경고하지 않는다. 절차상 거의 항상 커밋하지 않은 변경이 있어서 경고가 매번 뜨기 때문이다. 다만 `cso_commit`에 적힌 커밋이 지금 커밋(`HEAD`)의 조상인지는 확인한다.
  3. 2단계를 할지 정할 때 쓰는 근거는 상태 파일에 새 값을 더하지 않고, 전이할 때 출력되는 `HEAD` 해시로 잰다.
  4. 경로를 어떤 방식으로 맞춰 볼지는 git pathspec을 시험해 본 뒤 정한다. 지켜야 할 기준은 W1의 판정 표다.
  5. 검증 순서는 「커밋 → (`/cso`를 해야 할 때만) `/cso` → `pass cso` → 코드 리뷰 → `pass review`」다.
  6. `pass review`가 돌린 통합 검사가 타입·린트·테스트 오류로 실제로 실패하면, 도구가 그 자리에서 판단 검사 결과를 지운다. 형식 차이만 있어서 실패했거나 실행 환경 문제로 실패한 경우는 지우지 않는다.

  근거는 리뷰 기록의 결정 표 #13·#43·#45·#51·#61·#92에 있다.

- **`tests/` 아래를 무엇을 검사하나로 나눈다(2026-10-07).** `logic/`(게임) · `workflow/`(워크플로우 도구) · `docs/`(문서 규칙), 각 영역 안에 `helpers/` · `fixtures/`. 이 슬라이스는 새로 만들거나 고치는 파일만 옮기고, 기존 파일 옮기기와 `logic/` 세분화는 백로그로 둔다(W7 새 항목 10). `/cso` 적용 경로는 `tests/**/helpers/**` · `tests/**/fixtures/**`가 되고 테스트 파일은 어느 영역이든 해당 없음이다. Eng 리뷰는 다시 돌리지 않는다 — 파일 자리만 바뀌고 동작은 그대로다

### 2.2 기각한 안

- **게임 변경이 없을 때 검사를 건너뛰기만 하는 안, 또는 기계 검사를 하나로 묶기만 하는 안.** 둘 중 하나만 하면 리뷰 뒤 검사를 전부 다시 하는 구조, 계획에 드는 비용, 두 곳에 복사된 코드가 그대로 남는다. 둘 다 1단계에 포함돼 있다.
- **`/cso`를 「게임 변경이 없으면 해당 없음」으로 두는 안.** 게임 코드는 네트워크를 쓰지 않는 클라이언트 로직이라 `/cso`가 볼 것이 없고, 실제로 이 저장소에서 `/cso`가 게임 코드에서 문제를 찾은 적이 없다. 도구 경로(`.claude/**`·`tools/**`)에서도 찾은 적이 없다. `docs/qa/`에 `*-security-issues.md` 파일이 하나도 없다(2026-10-06 확인). 셸 명령을 실행하는 코드는 `.claude/**`·`tools/**`·`tests/helpers/**`에 있다. `tests/logic/**`는 적용 경로에서 뺀다. 넣으면 모든 슬라이스가 `tests/logic/<Feature>.test.ts`를 만들기 때문에 `/cso`가 「해당 없음」으로 나오는 경우가 한 번도 없게 된다. 그래서 프로세스를 띄우거나 파일을 쓰는 테스트 코드는 `tests/helpers/`에 둔다.
- **`pass ts`·`pass lint`를 옛 방식과 맞추려고 남기는 안.** 두 방식이 다 남으면 「명령 네 개가 하나로 줄었는지」 잴 수 없다.
- **`workflow.mjs`가 `tests/helpers/*.ts`를 직접 import하는 안.** 테스트와 훅이 옵션 없이 `node`를 실행하므로, `.ts` 파일을 읽게 하려면 별도 실행 파일, 지원 여부 확인 코드, 스스로 다시 실행하는 코드가 함께 필요했다. 복사본 두 개를 없애려고 그보다 큰 장치를 만들지 않는다.
- **사람이 확인하는 지점을 하나 더 만드는 안(`범위 승인`).** 사람이 확인하는 지점은 세 개뿐이라는 규칙과 맞지 않는다. 계획 범위 밖의 변경은 검사를 자동으로 더하고, `status`에 보여 주고, `PR 승인` 때 사람이 본다.
- **`start-verification`과 `verify`가 서로 다른 검사를 하는 안.** 전체 테스트는 4초도 걸리지 않는다. 문제는 시간이 아니라 AI가 치는 명령 수이고, 검사가 둘로 나뉘면 첫 검증에서 명령을 하나 더 쳐야 한다.
- **환경변수로 검사 실행기를 바꿔 끼우는 시험용 장치.** 환경변수 하나만 바꾸면 아무 검사도 돌리지 않고 통과로 기록할 수 있게 된다. 시험용 실행기는 함수 인자로 넘긴다.
- **도구를 고치는 슬라이스를 한동안 멈추는 안.** v1은 완성도를 높이는 쪽으로 가고 있고, 그 작업들이 모두 이 워크플로우를 계속 거친다. 2단계를 할지는 §6의 기준으로 정한다.
- **`approve-pr`의 `.meta` 검사를 항상 하는 안.** 건너뛰어서 아끼는 시간은 작다. 하지만 「할 검사는 변경 집합으로 계산한다」는 결정과 「main에서 이 슬라이스와 무관한 `.meta`가 빠져 있어도 도구 슬라이스가 막히지 않아야 한다」는 점이 더 중요하다. 따로 치는 `check-meta` 명령은 항상 검사한다.
- **CI용 스크립트 `verify:ci`를 두는 안(2026-10-05).** 이 저장소에는 CI가 없다. 같은 검사를 실행하는 입구만 두 개가 되어 관리 비용만 남는다.
- **측정 도구를 `tools/wf-measure/`로 커밋하는 안(2026-10-05).** 도구 유지비를 줄이려는 슬라이스가 유지해야 할 도구를 하나 더 만드는 것은 맞지 않는다.
- **1단계만 계획하고 2단계는 리뷰 없이 메모로만 붙이는 안, 그리고 1·2단계를 PR 하나로 내는 안(2026-10-05).** 앞의 안은 2단계를 시작할 때 계획을 처음부터 다시 세워야 한다. 2단계의 원칙과 시작 기준을 지금 리뷰하는 데도 비용이 들지만(§6이 한 절 분량이다), 나중에 처음부터 다시 세우는 것보다는 적다고 본다. 뒤의 안은 변경이 커지고, 1단계를 써 보고 2단계를 정한다는 판단 시점이 사라진다.
- **`pass cso`를 칠 때 커밋하지 않은 변경이 있으면 경고하는 안(2026-10-06, 리뷰에서 넣었다가 취소).** 절차가 커밋한 뒤에 `pass cso`를 치게 하지만, 실제로 칠 때는 거의 항상 커밋하지 않은 변경이 있다. 그러면 경고가 슬라이스마다 매번 떠서 의미가 없어진다.
- **`decideTransition`이 QA 판정과 통합 검사를 「필요할 때 실행하는 함수」 두 개로 받는 안(2026-10-06 Eng 리뷰).** 지금 정한 방식은 `decideTransition`이 「QA 판정이 필요하다」고 답하면 판정 결과를 넣어 다시 부르고, 「통합 검사가 필요하다」고 답하면 검사 결과를 넣어 또 다시 부르는 것이다. 두 방식 모두 무엇이 언제 실행되는지 똑같이 잘 드러나고, 다시 부르는 방식은 CEO 리뷰 단계에서 이미 정했다.
- **biome 결과를 `--reporter=json` 출력으로 분류하는 안(2026-10-06 Eng 리뷰).** biome 공식 CLI 문서에 `json`·`json-pretty` 출력은 「실험 기능이라 패치 버전에서도 바뀔 수 있다」고 적혀 있다. 그래서 분류는 종료 코드로 한다(W2).

### 2.3 이 슬라이스에서 정하지 않거나 미루는 것

- **상태 파일을 git 추적 대상에서 뺄지.** 정하지 않는다. F10에서 정한다(§2.1).
- **계획 절차 문서(`planning.md`)에 도구 슬라이스의 리뷰 방식을 적을지.** 미룬다. 계획 문서에 범위를 적게 하는 2단계에서 함께 정한다.
- **검사가 몇 번 돌았고 몇 번 막았는지를 파일에 기록할지.** 옛 계획은 이것을 2단계에 넣기로 했지만, 지금 2단계에 대해 정하는 것은 원칙 네 가지뿐이다. 2단계를 시작할 때 정한다.
- **요구사항 문서 §7에 후보로 올라 있었지만 뺀 것.** `approve-plan`이 계획 문서를 파일 이름으로만 찾는 문제, `wf start`가 진행 중인 슬라이스도 초기화해 버리는 문제, F71, F76, F86이다. 후보마다 뺀 이유는 설계 초안의 「요구사항 문서가 든 후보의 처리」 절에 있다.
- **`workflow.mjs`를 biome·tsc 검사 대상에 넣고, 명령 처리 코드를 `.claude/lib/`로 더 옮기는 일.** 이 슬라이스는 복사본을 없애는 데(F78)까지만 한다. 나머지는 W7에서 새 백로그 항목으로 만든다.
- **QA 판정(`qaDocClean`)을 통합 검사 안에 넣을지.** `pass review`가 `DocsHygiene.test.ts`를 두 번 돌리는 문제(§10)를 근거로 2단계에서 판단한다.

## 4. 제약

- **phase 이름을 바꾸지 않고, 상태 파일에 이미 있는 값을 없애지 않는다.** 새로 더하는 값은 두 개이고 상태 파일 맨 바깥에 둔다. `qa_skip_reason`은 QA 문서를 쓰지 않은 사유이고, `cso_commit`은 `pass cso`를 쳤을 때의 커밋이다. 상태 파일에 이 값이 없으면 「값이 없다」로 읽는다. 이 규칙은 옛 상태 파일만을 위한 것이 아니다. 새 도구도 `skip-qa`를 친 적이 없는 슬라이스의 상태 파일에는 `qa_skip_reason`을 쓰지 않는다. 그래서 새 값을 읽는 코드는 모두 「값이 없을 수 있다」를 처리해야 한다. 새 값을 `verification` 안에 넣지 않는 이유는, 옛 도구가 `verification` 안의 값이 전부 `true`인지로 통과를 판정하기 때문이다. 그 안에 넣으면 아래 복구 절차에서 옛 도구가 새 상태 파일을 제대로 읽지 못한다.
- **기록용 값 셋을 지우지 않는다.** `ts_check_clean`·`lint_clean`·`ts_check_scope`는 이제 다음 phase로 넘어가는 조건이 아니라 기록용이 된다(W2). 그래도 지우지 않는 이유는 세 가지다. `status`가 이 값으로 마지막 통합 검사 결과를 보여 준다. 복구 절차에서 옛 도구가 이 값을 읽는다. 기존 테스트가 이 값을 쓴다.
  - `invalidate`와 `rework`도 이 세 값은 지우지 않는다. 검사 목록 `CHECKS`에서 `ts`·`lint`를 빼면, 통과 표시를 지우는 함수 `resetVerification`이 이 값들을 자연히 건드리지 않게 된다.
  - 옛 도구로 복구할 때 이 값이 `true`로 남아 있어도, `cso_done`·`code_review_clean`이 `false`이므로 옛 도구도 다음 phase로 넘기지 않는다.
  - 2단계를 하지 않기로 정하면, 이 세 값을 정리할지 묻는 백로그 항목을 그때 만든다.
- **새 도구가 고장 났을 때의 복구 절차.** 새로 만드는 트러블슈팅 문서(W6)에 적는다. 요약하면 이렇다. `verification`에서 생긴 문제는 그 자리에서 고친다. `approve-pr`에서 생긴 문제는 `rework`로 돌아가 고친다. 그래도 안 되면 고장 나기 전의 `workflow.mjs`를 쓰되, 환경변수 `CLAUDE_PROJECT_DIR`에 이 작업 폴더를 지정해서 이 폴더의 상태 파일을 다루게 한다. 이 슬라이스가 머지되기 전에는 원래 폴더(`F:\work\monster`)에 있는 `workflow.mjs`가 고장 나기 전의 판이다. 이 방법은 `pnpm wf`로 치는 명령이 아니라서 사람 확인창이 뜨지 않는다. 그래서 AI가 스스로 쓰지 않고, 사용자가 직접 지시할 때만 쓴다.
- **정본에 이력을 적는 규칙은 건드리지 않는다.** `renderCanonDoc`을 `.claude/lib/canon.mjs`로 옮기지만, 새 정본에 `이력:` 줄을 찍는 문구는 그대로 옮긴다. 절차 문서를 고칠 때 본문에는 지금의 절차만 적는다.
- **전이를 시험할 때는 임시 폴더에서 한다.** 실제 상태 파일이 있는 곳에서 `wf start`를 돌리면 이 슬라이스의 상태가 사라진다(요구사항 문서 §6.2).
- **구현 단계에 들어가면, `workflow.mjs`를 고치기 전에 상태 파일을 한 번 커밋한다.** 반쯤 고친 도구가 상태 파일을 잘못 쓰면 `git restore`로 마지막 커밋의 상태 파일로 돌아가야 하기 때문이다.
- **글자 수 상한.** `CLAUDE.md`와 「항상 읽는다」고 적힌 정본 문서 세 개의 글자 수 합계는 상한이 38,000자이고, 지금 478자가 남아 있다(PR #94가 먼저 머지되면 301자). 이 슬라이스는 그 합계를 늘리지 않는다(W6에서 실제로 잰다).
- **`.meta`를 만들지 않는다.** 이 슬라이스는 `game/**`를 건드리지 않으므로 새 `.meta`가 하나도 없어야 한다.
- **Claude 자동 메모리는 머지할 때 고친다.** 절차를 설명하는 메모리 중 일부가 새 명령과 맞지 않게 되지만, 원래 폴더와 함께 쓰는 메모리라서 PR을 머지할 때 고친다(요구사항 문서 §5.2). 지금 아는 대상은 네 개다.
  - 커밋 워크플로우(`feedback_commit_workflow`)
  - 워크플로우 그대로 따르기(`feedback_follow_workflow`)
  - `pass ts`는 이제 진짜 게이트(`feedback_ide_diagnostics_open_files`)
  - 문서만 바뀌는 슬라이스는 wf를 생략한다(`feedback_doc_only_slice_skips_wf`). 이 슬라이스 뒤에는 문서 슬라이스도 `skip-qa`를 쓰고 `/cso`가 「해당 없음」이 되어 wf를 적은 비용으로 거칠 수 있으므로, 이 메모리가 여전히 맞는지 머지할 때 다시 본다.

  계획 승인 뒤에 목록을 마저 채운다.
- **서브에이전트 리뷰를 다른 도구로 옮기는 일은 이 슬라이스 범위 밖이다.**

## 5. 1단계 작업

## 6. 2단계 — 지킬 원칙 네 가지

2단계는 1단계를 머지하고 실제로 써 본 뒤 새 슬라이스로 시작한다. 지금 정하는 것은 아래 네 가지뿐이다. 값의 이름, 출력 모양, 파일 위치는 2단계를 시작할 때 정한다.

1. 검사를 통과시킬 때, 그때 검사한 파일 목록과 내용을 통과 기록과 함께 저장한다. 대상은 통과한 뒤 코드가 바뀌면 다시 해야 하는 판단 검사 네 가지(코드 리뷰, 보안 점검, 정본 갱신 확인, QA 확정)다.
2. `user-verification`으로 넘어갈 때와 `approve-pr`을 칠 때, 저장한 기록과 지금 파일을 비교한다. 다르면 해당 검사를 다시 하게 한다.
   - Cocos 에디터가 만든 `.meta`처럼 판단 검사의 대상이 아닌 파일은 비교에서 뺀다. 게임 슬라이스는 규칙에 따라 `PR 승인` 직전에 `.meta`를 커밋하므로, 빼지 않으면 매번 「다르다」고 나온다.
   - 같은 이유로, `user-verification`에 들어온 뒤 절차가 시키는 문서 정리(세션 문서, 백로그 행, 링크 고치기)와 상태 파일도 뺀다.
   - 사용자가 그 단계에서 에디터로 만들거나 고친 씬·프리팹도 뺀다. 사용자가 인게임에서 직접 확인한 것이기 때문이다.
   - 무엇을 뺄지 정확한 목록은 2단계를 시작할 때 정한다.
   - `approve-pr`에서 「다르다」고 나오면, 지금 있는 `rework`로 돌아간다. 새 방법을 만들지 않는다.
3. 계획에 적은 범위 밖의 파일이 바뀌어도 막지 않고, 필요한 검사만 자동으로 더한다. 사람이 확인하는 지점을 새로 만들지 않는다.
4. 1단계를 실제로 써 보고 잰 뒤에 2단계를 할지 정한다.

**2단계를 할지 정하는 기준.** 1단계를 머지한 뒤 슬라이스 두 개를 지켜본다. 그중 하나는 게임 슬라이스로 한다. 저장소 밖에서 한 번 쓰고 버리는 스크립트를 쓰거나, 세션 기록을 보고 손으로 센다. 결과는 2단계 백로그 항목에 적는다.

| 재는 것 | 무엇을 알려고 재나 | 기대하는 값 |
|---|---|---|
| ① 검증 중에 AI가 통합 검사 말고 따로 친 기계 검사 명령 수 | 1단계가 뜻대로 도는가 | 0 |
| ② `check-links`를 따로 친 횟수 | 따로 치는 일이 줄었는가 | 슬라이스당 1 + `user-verification`에 들어간 횟수 이하 |
| ③ 코드를 고친 뒤 다시 한 판단 검사 중, 그 검사가 보는 파일이 실제로는 바뀌지 않았던 것의 수 | 2단계가 줄일 수 있는 양 | 2단계를 할지 정하는 근거 |
| ④ phase가 `user-verification`인 동안 고친 코드·도구 파일 수 | 2단계가 막으려는 것 | 2단계를 할지 정하는 근거 |
| ⑤ 검증 phase에서 AI가 친 `pnpm wf`·`pnpm` 명령 총수 | 시간이 줄었는가 | 직전 슬라이스 두 개보다 적다 |
| ⑥ 그 명령들이 낸 출력의 글자 수 합계(세션 기록에서 센다) | AI가 읽는 양이 줄었는가 | 직전 슬라이스 두 개보다 적다 |
| ⑦ `.claude/**`와 `tests/**/helpers/**`의 줄 수, 전체 테스트 한 번 도는 시간 | 도구 유지비가 어떻게 됐나 | 줄 수는 는다. 얼마나 늘었는지 적는다 |
| ⑧ 계획 문서 글자 수 · 리뷰 횟수 · 계획 승인까지 걸린 세션 수 | 계획에 드는 비용 | 이 슬라이스(2026-09-16부터)가 첫 측정값이다 |

- ①이 세는 것은 `pnpm typecheck`·`pnpm check`·`pnpm exec vitest run`처럼 통합 검사가 이미 하는 일을 따로 친 경우다. 통합 검사가 실패해서 고치고 다시 친 `start-verification`과, 결과만 보려고 친 `verify`는 도구를 뜻대로 쓴 것이라 세지 않는다.
- ②의 기대값은 `check-links`를 따로 쳐야 하는 때를 센 것이다. 계획 문서를 쓴 직후에 한 번, 그리고 `user-verification`에 들어갈 때마다 문서를 정리한 직후에 한 번이다. 리워크가 있으면 들어간 횟수만큼 늘어난다. 그 밖에는 통합 검사의 전체 테스트 안에서 링크 검사가 함께 돈다. 1단계에서 달라지는 점은 두 가지다. `CLAUDE.md` 명령 표에 「통합 검사에 포함돼 있다」고 적히고, 검증 중에는 `verify`와 `pass review`가 링크 검사까지 다시 돌린다. 비교할 기존 값은 2026-08-18 이후 따로 친 횟수 137회(요구사항 문서 §3.1)를 그 기간의 슬라이스 수로 나눈 평균으로 한다(계획 승인 뒤에 센다).
- ①과 ②는 1단계가 뜻대로 도는지를 본다. 기대값을 벗어나면 1단계에 결함이 있다고 보고 백로그 항목을 만든다. 2단계를 시작하는 조건에는 쓰지 않는다.
- ③은 다시 한 검사 가운데 하지 않아도 됐던 것을 센다. 예를 들어 정본 문서는 그대로인데 정본 갱신을 다시 기록했거나, 문서만 고쳤는데 코드 리뷰를 다시 받은 경우다. 지금은 코드를 고칠 때마다 판단 검사를 전부 다시 하므로, 다시 한 횟수를 그냥 세면 「코드를 고친 적이 있다」는 사실만 알 수 있다. 보안 점검은 세지 않는다. 1단계에서 이미 바뀐 부분만 다시 보게 했기 때문이다. 재는 방법은 전이할 때 출력되는 `HEAD` 해시(W2)를 써서 `git diff --stat <그 해시> <다음 통과 때의 해시> -- <그 검사가 보는 경로>`를 보는 것이다.
- ④는 phase가 `user-verification`인 동안 리워크 없이 고쳐서 커밋한 코드·도구 파일만 센다. 세지 않는 것은 네 가지다. `.meta`, 상태 파일, 절차가 시킨 문서 정리(`docs/**`), 사용자가 에디터로 만들거나 고친 씬·프리팹·에셋이다. 앞의 세 가지는 절차대로 하면 늘 생기고, 마지막 것은 사용자가 인게임에서 직접 확인한 것이다. 리워크로 돌아가서 구현·검증 단계에서 한 커밋도 세지 않는다. 그 커밋은 검사를 다시 받기 때문이다.
- ⑤~⑧은 2단계를 시작하는 조건에 쓰지 않는다. 1단계가 줄이겠다고 한 세 가지(시간, AI가 읽는 양, 도구 유지비)가 실제로 줄었는지 보는 값이다. 비교할 기존 값은 계획 승인 뒤 직전 슬라이스 두 개의 세션 기록으로 재서 2단계 백로그 항목에 적는다. 이 숫자는 §2.2의 「도구 슬라이스를 멈추는 안」을 다시 검토할 때 근거가 된다.

2단계를 시작하는 조건은 둘 중 하나다. ④가 한 번이라도 0보다 크거나, ③이 두 슬라이스 모두에서 0보다 크면 시작한다. 둘 다 아니면 2단계를 하지 않고 2단계 백로그 항목을 닫는다. ③은 코드를 한 번이라도 고치면 보통 1 이상이 된다(`invalidate`가 정본 갱신 기록을 지우기 때문이다). 그래서 이 조건은 사실상 「두 슬라이스 모두에서 리뷰 뒤에 코드를 고쳤는가」를 묻는다.

**1단계가 막지 못하는 경우 두 가지.** 둘 다 지금도 막지 못하는 경우이고, 2단계의 원칙 1·2가 막는다. 2단계를 하지 않게 되더라도 잊히지 않도록, W7에서 백로그 항목 하나에 두 경우를 적어 둔다.

- `user-verification`에서 고친 파일은 검사 없이 `approve-pr`을 통과한다. `approve-pr`이 다시 돌리는 검사는 타입 검사뿐이다.
- `verification`에서 `/cso`나 리뷰를 통과한 뒤 코드를 고치고 `invalidate`를 치지 않으면, 고치기 전 코드로 받은 통과 표시가 그대로 남는다. 다음 phase로 넘기기 직전에 통합 검사는 다시 돌지만 판단 검사는 다시 하지 않는다. 1단계가 잡는 것은 그 통합 검사가 실제로 실패한 경우뿐이다(W2에서 그 자리에서 통과 표시를 지운다). 고친 코드가 통합 검사를 통과하면 여전히 그냥 넘어간다. 이 경우는 세션 기록만으로 세기 어려워서 위 기준에서는 세지 않는다.

## 7. 자동 검증과 손 확인

- **먼저 실패하는 테스트를 쓴다.** `tests/workflow/WorkflowDiet.test.ts`를 먼저 써서, `ready-impl`의 「테스트가 실제로 실패하는가」 조건을 통과한다. 이때는 `.claude/lib/*.mjs`가 아직 없어서 import 단계에서 실패하는데, 이것이 그 실패(RED)다.
- **통과.** 이 브랜치의 새 `start-verification`이 통합 검사를 돌린다. 비교 기준은 테스트 파일 48개, 통과 1,114개(건너뜀 1개)다(2026-09-30).
- **이 슬라이스의 QA 문서.** `docs/qa/workflow-diet-test.md`를 쓴다. `qa-setup`에 들어갈 때 출력되는 절차 문서는 아직 고치기 전의 것이므로, 그 절차대로 씬·에디터 절을 「없다」로 채운다. `skip-qa`는 이 슬라이스가 만드는 명령이라 이 슬라이스에는 쓰지 않는다.
- **통합 검사가 실제 실패를 실패로 읽는지 손으로 확인한다(구현 단계, 첫 `start-verification` 전).** 테스트는 시험용 실행기와 가짜 `pnpm`으로만 실패를 만든다. 그 실패 출력은 짐작해서 만든 것이라, 실제 biome 요약이나 vitest 결과 파일과 모양이 다르면 테스트는 통과하는데 도구는 실제 실패를 통과로 읽을 수 있다. 그리고 이 슬라이스의 검증은 모든 검사가 통과하는 경우만 거치므로 거기서도 드러나지 않는다. 그래서 타입 오류 하나, 린트 위반 하나, 실패하는 테스트 하나를 차례로 일부러 넣고, 그때마다 `start-verification`이 다음 phase로 넘어가지 않고 어느 검사가 실패했는지 출력하는지 확인한 뒤 되돌린다. 결과는 QA 문서에 적는다. 이 확인에서 친 명령은 §12의 명령 수에 넣지 않는다.
- **손 확인(검증 단계, `pass review` 전).** `pass`는 `verification` phase에서만 받으므로 이때 한다(`verify`는 `user-verification`에서도 돈다).
  - 이 브랜치에서 `pnpm wf status`가 `meta: 해당 없음`, `fullTypecheck: 해당 없음`, `cso: 적용`을 보여 준다.
  - `pnpm wf pass ts`가 안내 문구와 함께 실패한다.
  - `pnpm wf verify`가 검사마다 한 줄씩 결과를 낸다.
- **머지 뒤 손 확인.** 원래 폴더에서 main을 받은 뒤 `pnpm wf status`가 돌고, 다음 슬라이스의 `pnpm wf start`가 도는지 본다. 새 도구에서 `wf start`가 도는지는 머지 전에 기존 테스트가 임시 저장소에서 실제 프로세스를 띄워 이미 확인한다. 머지 뒤에 고장 나 있으면 W6에서 만드는 복구 문서대로 한다.

## 10. 구현하면서 재야 하는 것

- **W4에서 옮길 코드를 타입 검사 대상에 넣는 비용.** 함수 하나를 먼저 옮겨 보고 고칠 양을 잰다. `typecheck.mjs`에 `@ts-check`를 붙이는 비용도 함께 잰다.
- **글자 수.** W6의 두 표는 초안 문구로 잰 값이다. 실제로 구현한 문구로 다시 잰다.
- **통합 검사 한 번에 걸리는 시간.** 지금 재면 vitest 약 3.6초, 타입 검사 약 2.7초, biome 약 0.5초로 합쳐 약 7초다(2026-09-30). 구현 뒤에는 「전체 테스트」와 「임시 저장소 테스트 파일만」의 시간을 따로 적는다. 통합 검사까지 실제로 돌려 보는 처음부터 끝까지 테스트(E2E) 한 건이 Windows에서 node를 약 다섯 번 띄우므로, 임시 저장소 테스트가 전체 테스트 시간을 늘릴 수 있기 때문이다.
- **`pass review`는 `DocsHygiene.test.ts`를 두 번 돌린다.** QA 판정 `qaDocClean`이 환경변수 `WF_QA_DOC`을 주고 한 번 돌리고, 통합 검사의 전체 테스트에서 또 한 번 돈다(약 1초). 2단계에서 QA 판정을 통합 검사 안에 넣을지 판단할 때 근거가 된다.

## 12. 통과 조건

테스트가 확인하는 것은 작업 묶음 문서마다 「테스트」 절에 적었다. 여기에는 사람이 직접 보거나 머지 뒤에 재는 것만 적는다.
