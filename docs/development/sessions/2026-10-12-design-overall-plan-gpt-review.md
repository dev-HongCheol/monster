### 1. GPT에게

당신은 이 게임 프로젝트의 **디자인 결정 순서 계획**을 2차로 검증하는 검토자다. 1차 검토(Claude, 전략 · 엔지니어링 · 디자인 세 번)는 끝났다. 당신의 일은 요약이 아니라 **반박**이다 — 순서가 틀린 결정, 빠진 결정, 업계 관례와 어긋나는 전제, 근거가 약한 숫자를 찾아 달라.

지켜 달라.

- 당신은 저장소와 코드를 볼 수 없다. 판단에 필요한 사실은 「2. 배경」에 다 적었다. 적히지 않은 것을 추측하지 말고 「모른다 · 확인 필요」로 적어 달라.
- 결정마다 **동의 · 조건부 동의 · 반대** 셋 중 하나로 판정하고, 이유를 2~4문장으로 적어 달라. 조건부면 조건을, 반대면 대안을 적어 달라.
- 문서를 다시 써 주지 말아 달라. 고칠 자리와 고칠 내용만 짚어 달라.
- 마지막에 「빠진 결정 목록」과 「5. 검증 질문」의 답을 따로 모아 달라.
- 한국어로 답해 달라.

### 2. 배경 — 판단에 필요한 사실

#### 2.1 프로젝트

- Cocos Creator 3.8로 만드는 탑다운 생존 액션 게임(웹 빌드). 판타지 세계에서 온 마법사 영웅이 현대 서울에서 한국 · 중국 · 일본의 귀신 무리와 싸운다. 화풍은 애니 셀. 1차 출하(v1)는 한국어 · 영어.
- 플랫폼: v1은 itch.io 웹, v2는 Steam PC. **모바일은 v1 비목표이되 이후 구현을 고려한다**(2026-10-11 사용자 결정) — 터치 입력은 v1 범위 밖이되 지금 결정이 터치를 막지 않게 적는다. **게임패드는 결정에서 뺐다**(테스트 장비 없음, 필요하면 재생성).
- 개발자는 한 사람(사용자)이고 AI(Claude)와 함께 일한다. 그림 생산(ChatGPT 웹)과 에디터 조립은 사용자 손이다.
- 디자인 작업은 2026-07-20에 「코드보다 디자인 먼저」로 시작했고, 플레이어 캐릭터 하나에 **약 10주**가 들었다. 대부분이 그림이 아니라 **만드는 경로를 찾는 데** 쓰였다 — 2D 생성 경로(스타일 학습 · 로컬 생성 환경 · 배경 제거 서비스)를 차례로 시험하고 버린 뒤 3D 모델에서 층별로 굽는 경로로 바꿨고, 시험마다 라이선스 확인과 문서 정리가 따라붙었다. 이 계획은 남은 영역(적 · 마법 이펙트 · 맵 · UI · 사운드)에서 같은 일을 반복하지 않으려고 세웠다.

### 3. 결정 묶음 — 전반 프로세스

결정마다 같은 틀이다: **결정문 · 근거 · 버린 대안과 그 이유 · 우리가 틀릴 수 있는 지점 · 검증 질문.** 라이선스가 걸린 결정(P9)은 「확인한 약관 조항과 확인일」을 더했다.

#### P1. 결정을 두 단계로 검증한다

- **결정문:** 결정마다 Claude가 1차 방향을 잡고 GPT가 2차로 검증한다. 전반 프로세스(이 문서)를 먼저 넘기고, 합의되면 세부 결정을 **층 · 트랙 단위 묶음**으로 같은 틀로 넘긴다. GPT가 반대하면 최종 결정은 사용자가 하고, 반대 요지와 택한 이유를 기록에 남긴다. GPT가 답을 못 주면 Claude 1차만으로 사용자가 결정하고 「GPT 미검증」을 남긴다.
- **근거:** 플레이어 10주의 원인이 「한 모델 · 한 사람의 판단으로 경로를 골라 시험하고 버린 반복」이었다. 다른 모델의 반박이 경로 선택 전에 들어오면 시험 비용을 줄인다. 라이선스 · 미검증 영역(사운드 · 이펙트)은 더 엄격하게 본다.
- **버린 대안:** 결정 하나하나를 따로 넘기기 — 결정 11개 + 게이트 4개면 왕복 15회가 넘어 검증 비용이 설계 비용을 넘는다. 같은 층의 결정은 서로 기대므로(폰트는 예산 없이 검증할 수 없다) 따로 보면 검증이 안 된다. / 기간 기준 보고 지점(「탐색이 N일 넘으면 멈춰 보고」) — 사용자가 거부했다. 회차 상한은 AI가 같은 기술 문제를 3번 연속 못 풀 때만 세고, 사람이 판정하는 반복은 세지 않는다.
- **틀릴 수 있는 지점:** 묶음이 커지면 GPT가 묶음 안의 개별 결정을 놓칠 수 있다. 두 모델이 같은 훈련 데이터의 같은 편향을 공유하면 「검증」이 「동의」로 끝날 수 있다.
- **검증 질문:** 층 · 트랙 단위 묶음이 적절한 크기인가. 두 모델 검증의 알려진 한계를 보완하는 방법이 있나(예: 결정마다 「반대 근거를 하나는 꼭 적어라」 같은 규칙).

#### P2. 결정 순서 — 층 구조

- **결정문:** UI 줄기를 0~4층으로 세운다. 0층 컨셉 · 코드 계약(끝남) → 1층 선행 조건(P3) → 2층 색 · 글자 · 간격 · 예산(P4) → 3층 형태 언어 · 컴포넌트 치수 · UI 그림 제작 경로(P5) → 4층 아이콘 · 화면별 적용 · 모션 정책(P5). 배경은 **규약(1층 수치 띠)이 먼저고 그림은 나중**이다 — 띠가 서면 UI 색은 그 띠 위에서 읽히는 색으로 고르고 최종 맵 아트는 그 띠 안에서 그려서 둘이 서로 기다리지 않는다.
- **근거:** 업계의 UI 스타일 가이드 순서는 무드 · 레퍼런스 → 색 → 타이포 → 격자 · 간격 · 컴포넌트 → 아이콘 → 모션이고, 색과 타이포는 같은 층이며 둘 다 컴포넌트보다 앞이다. 컴포넌트 치수는 글자 너비와 팔레트가 정해진 뒤에만 선다. 게임 고유 사정 하나를 더했다 — HUD가 게임 화면 위에 겹치므로 배경 띠가 UI 색의 선행 조건이다.
- **버린 대안:** 「폰트 최우선」(사용자의 처음 가정) — 폰트는 컴포넌트보다 앞이지만 최우선은 아니다. 그 앞에 해상도 · 스케일 정책(이미 고정)과 최소 글자 크기 기준이 있어야 폰트 후보를 같은 크기에서 비교할 수 있다. / 「배경 그림을 먼저 그리고 UI를 맞춘다」 또는 그 반대 — 둘 다 한쪽이 다른 쪽을 기다린다. 규약을 수치로 먼저 세우면 기다림이 없다.
- **틀릴 수 있는 지점:** 층을 가르면 층 사이를 오가는 결정(예: 상태 표는 4층인데 3층이 컴포넌트를 잡으면서 상태를 빠뜨릴 수 있다)이 생긴다. 1층이 여덟 행으로 커져 「선행 조건」이 실제로는 한 묶음에 다 들어가지 않을 수 있다.
- **검증 질문:** 앞뒤가 바뀌어야 할 결정이 있나. 특히 「배경 띠 → UI 팔레트」와 「최소 글자 크기 → 폰트」의 선후. 1층이 여덟 행이면 한 검증 묶음으로 너무 큰가.

#### P3. 1층 — 선행 조건 여덟

- **결정문:** 1층에 여덟을 둔다. 가. **UI 무드 · 레퍼런스 브리프** — UI가 세 축(민속 공포 · 판타지 영웅 · 현대 서울) 중 어느 축을 주로 나르고 어느 축을 액센트로 두는지, 참고 그림 3~5장(가져올 것 · 안 가져올 것), 쓰지 않을 것 목록, 형용사 다섯. 사용자 판정. 나. **배경의 명도 · 채도 띠(수치)** — 단위(HSL · Lab · 상대 휘도)를 정하는 것이 첫 결정. 다. **최소 글자 크기** — 문자 체계별(라틴 · 키릴 / 한글 / 한자 · 가나), 1280×720 기준 px, 최소 지원 뷰포트 높이에서 확인. 판정은 §6.3 비교판을 그 배율로 렌더해 사용자가 실제 모니터에서 보고, 조건(모니터 인치 · 해상도 · 거리)을 기록. 출발값 14 · 20. 라. **다국어 길이 확장 규칙** — 산출물은 요소 목록 표(요소 · 컨테이너 종류 · 늘어나는 방향 · 최대 · 넘침 모드), HUD 모서리 고정 요소는 늘어날 수 없다는 예외, 「최대」 열만 3층이 채움. Cocos Label · Layout · Widget 제약을 공식 문서로 확인한 뒤 확정. 마. **입력 방식 — 키보드 조작 범위** — 레벨업 카드 · 일시정지 · 결과 · 메뉴를 키보드만으로 조작할 수 있게 하는가(포커스 이동). 「예」면 3층 컴포넌트 상태 표에 focused 열 + 코드 슬라이스. 포커스 이동은 터치와 공존하는 방식으로. 바. **화면 맞춤 정책** — 허용 비율 범위 · 안전 영역 · 최소 지원 뷰포트 높이. 방법은 비율 · 높이 조합으로 지금 HUD를 띄우는 화면 탐침. v1 데스크톱으로 정하되 세로 · 좁은 비율을 원리적으로 막는 구조는 피한다. 사. **화면별 정보 위계 표** — 화면 다섯(HUD · 레벨업 카드 · 일시정지 · 결과 · 메뉴)마다 1 · 2 · 3순위와 근거. HUD는 「흘깃 봐서 읽히는가」로 판정. 아. **접근성 규칙** — 색만으로 구분하지 않는다. 대비는 WCAG 대비비로 재고 후보값 본문 4.5:1 · 큰 글자 · UI 요소 3:1(게임 강제 기준은 아니라 내리면 근거를 적는다). 색각 통과 조건: 분류 3색이 1형 · 2형에서 구분되거나 4층 아이콘이 형태로 갈라 준다. 측정 대상 둘: 패널 위 글자, 그리고 배경 띠의 **가장 밝은 값** 위의 HUD 글자(못 미치면 외곽선 · 반투명 판이 3층 결정).
- **근거:** 가~아 전부 2층 이후가 입력으로 쓰는 것이다. 무드 브리프가 없으면 팔레트 · 폰트가 「배경 위에서 읽히는 중립색」으로 수렴해 범용 UI가 된다(지금 목업이 그것). 최소 글자 크기가 없으면 폰트 후보를 같은 조건에서 비교할 수 없다. 길이 확장 규칙을 나중에 바꾸면 컴포넌트를 전부 다시 잰다. 위계 표가 없으면 크기 · 굵기가 위계를 나르지 못한다. 접근성 값이 없으면 2층이 지킬 수가 없다.
- **버린 대안:** 상태 표를 1층에(위계 표 옆) — 성공 · 빈 상태의 모양은 3 · 4층 없이 그릴 수 없어 1층에서는 칸이 「미정」으로 남는다 → 4층으로(P5). / 무드는 아트 정본 테제를 그대로 따른다는 한 줄 — 테제는 세 축을 다 들고 있어 UI가 어느 축을 나르는지 정해지지 않는다. / 게임패드 지원 여부를 1층 결정으로 — 사용자가 테스트 장비가 없어 결정에서 뺐다. / 키보드 조작을 게임패드 결정에 딸려 두기 — 게임패드가 빠지면 키보드도 결정 없이 빠진다 → 독립 결정으로.
- **틀릴 수 있는 지점:** WCAG 값은 웹 기준이라 어두운 연출의 게임 HUD에는 과할 수 있다(그래서 내릴 근거를 적게 했다). 최소 글자 크기 판정이 사용자 한 사람의 모니터 · 눈에 묶인다. 무드 브리프는 취향 결정이라 검증보다 사용자 판정이 앞선다 — 2차 검증이 틀만 볼 수 있다. HUD 고정 요소의 예외 때문에 「컨테이너가 늘어난다」 원칙이 HUD에는 사실상 적용되지 않는다.
- **검증 질문:** 여덟 중 1층이 아닌 것이 있나(예: 위계 표는 3층 치수와 함께 정해야 한다는 반론). 빠진 1층 결정이 있나. WCAG 4.5:1 · 3:1을 게임 UI에 그대로 쓰는 것이 관례인가, 게임 쪽에 다른 통용 기준이 있나. 최소 글자 크기를 문자 체계별로 두는 것이 맞나.

#### P4. 2층 — 예산 → 폰트 → 팔레트 · 간격, 전부 `Theme.ts` 토큰 교체

- **결정문:** 2층 안의 순서는 **UI 성능 · 용량 예산 → 폰트 체계 → 팔레트 · 간격**이다(예산이 폰트 선택의 입력). 가. 예산 — 폰트 파일 상한 · UI 아틀라스 묶음 수 · 동시 Label 수 상한. 나. 폰트 체계 — 가족 · 굵기 · 역할, 크기는 §6.1 타입 스케일(단계 수 · 비율 · 문자 체계별 줄 높이 · 굵기; 입력은 최소 글자 크기와 위계 표; 출발값 28 · 20 · 14). 다. 팔레트 — 산출물은 **의미색 표**(이름 · 역할 · 값 · 쓰는 화면 · 예약색 충돌 검사). 예약색(분류 셋 · 티어 셋 · 상태바 둘 · 승리 · 패배 · 다시하기)과의 충돌 셋을 이 표가 푼다. 강조색은 하나이고 **주 행동 버튼 전용**. **support 분류색도 이 표에서 정하고** 코드 · 아트 정본 반영은 코드 슬라이스. 라. 간격 · 격자 단위 — 여백 배수 단위와 최소 클릭 크기(마우스 기준으로 정하되 손가락 기준 44px 안팎도 함께 적어 둔다). 결정값은 전부 `Theme.ts`의 `COLORS` · `FONT` · `SIZES` 토큰을 교체하고, 머리 주석은 그 슬라이스가 함께 고친다.
- **근거:** 예산 없이 CJK 폰트를 골라 놓고 빌드에서 알게 되는 일을 막는다. 예약된 색이 여덟이 넘는 화면에서 「중립 + 강조 하나」는 결정이 아니다 — 충돌 검사 열이 있는 표만이 실제 충돌을 푼다. 분류색 넷을 다 피해야 하는데 넷째 색을 비워 두면 나중에 넣을 때 팔레트와 부딪힌다. 토큰 교체를 적지 않으면 계획의 값과 코드의 값이 따로 산다.
- **버린 대안:** 팔레트 행을 「중립 패널색 + 강조색 하나」로 두기 — 충돌을 푸는 자리가 없다. / support 색은 support 마법이 데이터에 생길 때 — 그때 충돌 검사를 다시 한다. / `Theme.ts` 머리 주석을 확정 PR(문서 PR)에서 고치기 — 이 프로젝트는 코드 편집을 wf 구현 단계에서만 허용해 문서 PR에서 `.ts`를 못 고친다; 주석 한 줄 때문에 문서 PR을 wf 슬라이스로 돌리는 것은 비용이 크다 → 값 교체 슬라이스가 함께 고친다. / 크기는 지금 `FONT` 셋을 스케일로 인정 — 레이아웃 슬라이스의 임시값이고 제목 역할은 28보다 큰 단계가 필요하다.
- **틀릴 수 있는 지점:** support 색 결정이 UI 줄기에 들어와 2층이 코드 슬라이스를 하나 더 낳는다. 「강조색은 주 행동 버튼 전용」이 너무 좁아 선택된 카드 · 포커스 표시 같은 곳에 쓸 색이 모자랄 수 있다. 예산 값은 실측 전이라 폰트 결정이 예산을 기다린다.
- **검증 질문:** 2층 안의 순서(예산 → 폰트 → 팔레트 · 간격)가 맞나. 의미색 표의 열(이름 · 역할 · 값 · 쓰는 화면 · 충돌 검사)에 빠진 열이 있나(예: 상태별 변형, 대비비). 강조색 전용 규칙의 통상 예외가 있나.

#### P5. 3층 · 4층 — 형태 · 치수 · 그림 경로, 아이콘 · 화면별 · 모션

- **결정문:** 3층은 가. UI 형태 언어 · 컴포넌트 치수(글자 너비 · 팔레트 · 간격이 선 뒤 버튼 · 패널 · 카드 크기), 산출물에 **컴포넌트 상태 표**(버튼 · 카드 · 슬롯 × normal · hover · pressed · disabled; focused는 1층 키보드 조작이 「예」일 때만, 엔진에 없어 코드), 나. **UI 그림 제작 경로**(AI 생성 · 런타임 벡터 · 제작 도구 벡터 · 9-slice 중 무엇) — 형태 언어가 「그린 프레임」인지 「늘어나는 9-slice」인지에 따라 갈리므로 같은 층. 4층은 다. 아이콘 · 화면별 적용 — 화면 목록은 마법 아이콘 · 카드 · 결과 · 타이틀(지금 `menu.scene`) · 메뉴 · 설정 · 도감 · 일시정지 · 인트로 · 위치 카드. **컨셉 운반 화면**(타이틀 · 인트로 · 도감)은 무드 브리프가 가장 먼저 · 강하게 적용되는 자리, HUD는 흘깃 읽기가 우선이라 약하게. **화면 × 상태 표**(화면 다섯 × 기본 · 빈 · 부분 · 오류 · 성공 · 비활성)에 칸마다 보이는 것과 주인 — 빈은 4층, 부분은 길이 확장 규칙 + 코드, 성공은 모션 정책, 오류는 코드 슬라이스, 로딩은 지금 없고 메뉴 · 세이브 슬라이스가 만들 때. **결과 화면 폴리시** — 헤더는 제목 폰트 첫 자리, 첫 읽기는 승리 · 패배(문자열 추가는 코드 슬라이스), 웨이브 수는 보조줄. 라. 모션 정책 — 입력은 **감정 전환 여덟**(타이틀 진입 · 전투 시작 · 레벨업 진입 · 카드 선택 · 사망 · 승리 · 결과 공개 · 재시작), 요구 하나 「승리 ≠ 사망 연출」, 기준값 사망 페이드 0.8초.
- **근거:** 컴포넌트 상태는 화면마다 되풀이되는 결정이라 부품 단위 표에 한 번만 적는다. 첫 5초는 타이틀에서 결정되는데 그 화면이 목록에 없었다. 상태 표가 없으면 「빈 도감」 · 「오류」가 구현자 기본값으로 나간다. 모션은 그 자체가 목적이 아니라 기분이 바뀌는 순간을 알리는 도구이고, 지금 승리와 사망이 같은 길로 끝난다.
- **버린 대안:** 컴포넌트 상태를 화면 × 상태 표에 「비활성」 열로 합치기 — hover · pressed · focused는 화면이 아니라 부품의 상태라 열로 맞지 않고 화면 수만큼 되풀이된다. / 감정 전환 목록만 넣고 승리 ≠ 사망 요구는 연출 백로그가 알아서 — 디자인 요구가 없으면 길이만 맞춘 같은 페이드로 갈 수 있다. / 인트로 · 위치 카드는 아직 없는 화면이니 그 슬라이스가 알아서 — 첫 인상 화면이 디자인 줄기 밖에 남아 각자 스타일을 고른다.
- **틀릴 수 있는 지점:** 4층은 줄기의 끝이라 상태 표가 채워지는 시점이 늦다 — 그 전에 3층이 상태를 빠뜨릴 수 있다. 없는 화면 둘(인트로 · 위치 카드)이 목록에 들어와 그 슬라이스가 4층을 기다리거나 placeholder로 먼저 가야 한다. 「컨셉 강도를 화면별로 가른다」가 HUD를 너무 밋밋하게 만들 수 있다.
- **검증 질문:** 상태 표의 층 배치(4층)와 컴포넌트 상태 표의 층 배치(3층)가 맞나. UI 그림 제작 경로를 형태 언어와 같은 층에 두는 것이 맞나, 아니면 2층(색 · 글자와 함께)에 둬야 하나. 감정 전환 여덟에 빠진 순간이 있나(예: 피격 · 회복 · 웨이브 전환).

#### P6. 독립 트랙 넷과 첫 게이트

- **결정문:** 마법 이펙트 · 사운드 · 적 로스터 · 맵 아트는 0층 또는 1층 띠에만 걸리고 UI 줄기와 독립이라 **병행한다**. 각 트랙의 첫 게이트: 이펙트 — `ParticleSystem2D`를 텍스처 한 장으로 **웹 빌드를 브라우저에서** 실측, 통과 판정은 씬 스포너 값으로 계산한 종료 웨이브 최대 동시 적 수(교전 38 + 이동 중 25 = 63)에서의 fps이고 아트 정본의 수백 마리 밀도도 함께 기록, 실패하면 프레임 시트 스프라이트로. 사운드 — 톤 → 도구 · 라이선스 조사 → 브라우저 자동 재생 제한 · 포맷 · 용량 예산 → 샘플 시험 → 재생 코드. 적 — 12종 원전 도상 시트 → 3~4종을 실제 크기로 여러 마리 늘어놓고 구분되는지 → 나머지 생산. 맵 — 띠가 서면 규격 절부터 → 큰 배경 한 장을 뽑아 분할 · 용량을 잰다.
- **근거:** 미검증 방법(이펙트)은 게이트를 먼저 걸어 실패 시 대체 경로로 빠르게 간다. 적 변별은 한 마리가 아니라 호드에서 판정해야 한다.
- **버린 대안:** 통과 기준을 사양서 표의 코드 기본값(20 · 4)으로 — 씬 값(10 · 2)과 다르다, 코드(씬)가 이긴다. / 에디터 미리보기에서 측정 — 출하 환경(웹 빌드 · 임베드)과 다르다.
- **틀릴 수 있는 지점:** 63이라는 수는 15웨이브 가정(900초 ÷ 60초)에서 나왔고 밸런스가 바뀌면 달라진다. 「수백 마리」 목표와 63은 거리가 커서 어느 쪽을 통과 기준으로 삼느냐에 따라 결론이 뒤집힌다.
- **검증 질문:** 트랙 넷이 정말 독립인가(예: 적 로스터의 주조색이 UI 팔레트와 충돌할 가능성). 이펙트 게이트의 통과 기준을 「현재 씬 값」과 「목표 밀도」 둘 중 어느 쪽에 걸어야 하나.

#### P7. 다국어가 UI에 거는 조건

- **결정문:** 출하는 한 · 영이고 확장 후보 15개(아랍어 · 태국어 제외). 조건은 세 축으로 가른다 — 가. 글리프 커버(폰트 파일, 2층), 나. 길이 확장(레이아웃, 3층 전 규칙): 컨테이너가 글자에 맞춰 늘어남, 영어 × 1.3 기준, 넘침 정책은 요소마다(말줄임 모드는 엔진에 없어 줄바꿈 · 잘림 · 축소 셋, 축소는 마지막), 가짜 언어 카탈로그로 시험, 글자를 그림에 굽지 않음, 다. 엔진 배치 지원과 문장 조립: shaping · RTL은 확인하지 않음(아랍어 제외), 띄어쓰기 없는 줄바꿈은 일본어 대표로 확인, 복수형과 숫자 · 단위 형식은 적힌 곳이 없어 세부 계획에서 확인, **데이터 파일 안의 표시 문자열**(적 이름 12건)은 키로 옮기는 코드 슬라이스(도감 전). 묶음 2(라틴 확장 · 키릴) · 3(일본어 · 중국어)은 **대표 언어 셋(독일어 · 러시아어 · 일본어)**만 네 조건(글리프 · 파일 크기 · 엔진 지원 · 라이선스)으로 조사하고, 공수가 크면 한 · 영만 우선 출하한다.
- **근거:** 길이 확장을 나중에 바꾸면 컴포넌트를 전부 다시 잰다. 묶음 안의 나머지 언어는 대표와 같은 결론이 나온다는 가정으로 전수 조사를 피한다. 마법 · 카드는 이미 키인데 적만 데이터에 박혀 있어 영어 도감에 한국어 이름이 뜬다.
- **버린 대안:** 후보 15개 전수 조사 — 공수가 크고 묶음 안에서 결론이 같다. / 아랍어 · 태국어 포함 — 사용자가 뺐다(shaping · RTL이 따라붙는다). / 미리 한 · 영으로 좁히기 — 조사 뒤에 좁힌다.
- **틀릴 수 있는 지점:** 1.3배는 경험칙이고 UI 문구가 짧을수록 확장률은 더 커진다(짧은 라벨은 2배도 흔하다). 대표 언어가 놓치는 언어별 특수 조건(폴란드어 · 튀르키예어의 특수 글자, 번체의 글리프 수)이 있을 수 있다. Cocos의 Label 줄바꿈이 문자 체계별 규칙을 따르는지 확인 전이다.
- **검증 질문:** 1.3 기준이 적절한가, 짧은 라벨에 별도 기준이 필요한가. 대표 언어 셋의 전제가 맞나. 세 축 분류에 빠진 축이 있나(예: 날짜 · 시간 형식, 정렬 순서).

#### P8. 폰트 체계

- **결정문:** 폰트를 역할(UI 본문 · 제목 · 숫자)로 가른다. 제목은 대문자에 기대는 효과를 쓰지 않는다(한 · 중 · 일에 대문자가 없다). 데미지 숫자는 비트맵 폰트가 관례지만 **데미지 숫자 표시가 v1에 확정될 때만** 만들고 그 전에는 숫자도 본문 폰트로 그린다. 한 · 영 · 일 · 중을 한 가족으로 덮는 무료 폰트(Noto Sans CJK 계열, OFL)는 있으나 파일이 커서 서브셋이 필수다. 후보 3~4개를 **최소 글자 크기 조건에서 나란히 렌더한 비교판**(한 · 영 · 숫자 · 가짜 언어 · 카탈로그 기호 전부, 어두운 배경 띠 위, 최소 지원 높이 배율)으로 사용자가 고른다. 기호는 보유만이 아니라 실제 문장(「+10%」) 안에서 크기 · 굵기 · 높이 정렬이 어울리는지 본다.
- **근거:** 다국어 걱정은 결국 본문 폰트 하나에 걸린다. 후보를 나란히 놓고 고르는 방식은 플레이어 애니메이션에서 효과가 있었다. 폰트마다 기호의 크기 · 세로 위치가 달라 숫자 옆에서 튀거나 묻힌다.
- **버린 대안:** 데미지 숫자 비트맵을 지금 만들기 — 기능 자체가 미정(백로그)이다. / 기호 확인을 언어 글자 확인으로 갈음 — 언어 글자 확인은 기호를 보지 않는다.
- **틀릴 수 있는 지점:** CJK 폰트 파일 크기(10MB 넘음)는 미실측 수치다. 「비트맵 숫자 + TTF 본문」 분리가 웹 기반 엔진에서도 통상인지 확인이 필요하다.
- **검증 질문:** 역할 셋 분리가 통상인가. 데미지 숫자 비트맵 · 본문 TTF 분리가 Cocos 같은 웹 엔진에서도 관례인가. 비교판 방식의 알려진 함정이 있나.

#### P10. 진행 방식

- **결정문:** 가. 트랙에 착수할 때마다 정본 · 코드 · 백로그가 적고 있는 것과 실제가 맞는지 **먼저 보고하고 확인을 받는다**(「섰다」는 이 문서 시점의 판단). 나. 문서 분할 — 전반 계획 하나, 합의 뒤 트랙별 세부 계획 문서 하나씩, **UI 줄기만 개요 하나 + 층별 문서 넷**(2층 값은 1층 실측 뒤에만 쓸 수 있고 층 문서 하나 = 검증 묶음 하나). 다. 트랙은 독립이라 worktree로 폴더를 나눠 병행한다(별도 클론보다 브랜치 · 커밋이 바로 보이고 디스크를 덜 쓴다). 라. 초안과 GPT 기록은 `docs/temp/` 한 곳에만, 합의된 결정은 세션 문서로, 「지금」은 정본 · 백로그로. 전반 계획이 머지된 뒤에 트랙 브랜치를 만든다. 코드가 붙는 트랙은 wf(테스트 RED 게이트)로, 문서 · 실측만인 트랙은 문서 경로로.
- **근거:** 문서에 적힌 것이 낡았거나 잘못 이해된 채 결정돼 적힌 것일 수 있다. `docs/temp/`는 git 밖이라 폴더마다 따로 있어 복사본이 생기면 어긋난다.
- **버린 대안:** 별도 클론 — 저장소를 통째로 복사해 서로 모르는 상태가 되고 같은 브랜치를 두 폴더가 따로 당겨 어긋난다. / 결정마다 한 문서 — 층 안의 결정은 서로 기대 한 번에 완성할 수 없다.
- **틀릴 수 있는 지점:** 백로그 세 파일을 여러 트랙이 함께 고쳐 머지 충돌이 예상된다. 새 폴더에서 테스트가 안 도는 문제(Cocos가 만드는 설정 파일 부재)는 알려져 있고 해결 방법 둘이 있다.
- **검증 질문:** §8.1의 검증 틀(결정문 · 근거 · 버린 대안 · 틀릴 수 있는 지점 · 검증 질문)에 더하거나 뺄 칸이 있나. 「시도와 방향 전환을 반복하지 않는다」는 목적에 이 진행 방식이 맞나.

- **검증 질문:** 전제가 틀린 곳이 있나. UI 줄기에 산출물(위계 표 · 상태 표 둘 · 의미색 표 · 타입 스케일 · 요소 목록 표 · 무드 브리프)이 더해진 뒤에도 2~4주가 맞나.

#### P12. 플랫폼 범위 — 게임패드 제거, 모바일 이후 고려

- **결정문:** 게임패드 지원 여부는 1층 결정에서 **뺐다**(테스트 장비 없음, 필요하면 재생성). 모바일은 v1 비목표이되 **이후 구현을 고려**하므로, 지금 결정이 터치를 막지 않게 한다 — 최소 클릭 크기에 손가락 기준(44px 안팎)도 함께 적고, 화면 맞춤 정책이 세로 · 좁은 비율을 원리적으로 막는 구조를 피하고, 포커스 이동은 터치와 공존하는 방식으로.
- **근거:** 테스트할 수 없는 결정은 적어 두어도 검증할 수 없다. 모바일을 시작하는 날 2층 간격 · 3층 치수를 다시 재지 않으려면 지금 한 줄씩 조건을 적는 비용이 가장 싸다.
- **버린 대안:** 게임패드를 「아니오」로 닫고 Steam 때 다시 열기 — 사용자가 완전 제거를 택했다. / 모바일은 그때 가서 보기 — 2 · 3층을 다시 한다.
- **틀릴 수 있는 지점:** v1 범위가 아닌 조건이 행에 들어와 세부 단계가 「지금 값인가, 나중 조건인가」를 매번 가려 읽어야 한다. Steam(v2) 상점 페이지는 패드 지원 여부를 표기 항목으로 물으므로 그때 결정이 다시 필요하다.
- **검증 질문:** 「막지 않는다」 조건 셋이 충분한가, 더 걸어 둘 것이 있나(예: 안전 영역 · 글자 크기 · 포인터 없는 환경의 hover 상태).

---

### 4. 빠졌을 수 있는 것 — 우리가 스스로 의심하는 목록

검토자가 먼저 봐 주면 좋은 자리다.

- 1층 여덟 행 중 **값이 하나도 없다** — 이 문서는 자리와 주인과 출발값만 든다. 값 없는 결정 순서를 검증하는 것이 의미가 있는가, 아니면 1층 값이 나온 뒤 묶음으로 보는 것이 맞는가.
- 디자인 검토가 더한 결정 15개(상태 표 둘 · 무드 브리프 · 감정 전환 · 의미색 표 · 타입 스케일 · 기호 · 접근성 값 · 최소 글자 판정 · 요소 목록 표 · 키보드 조작 · 모바일 조건 · 적 이름 키)가 **UI 줄기 세부 계획을 너무 무겁게** 만들었을 수 있다.
- 사운드 트랙은 톤 결정이 첫 게이트인데 **톤을 누가 어떻게 정하는지**(무드 브리프와 같은 틀을 쓰는지)가 없다.
- 적 로스터 · 맵 아트 트랙은 ChatGPT 웹 생성이 **미실측**인 채로 「경로가 섰다」고 적혀 있다(§8.0 보고 규칙이 이를 받친다).

---

### 5. 검증 질문 — 모아서

원본 §10의 여덟에 디자인 검토 뒤 생긴 것 넷을 더했다.

1. §4.2의 층 구조에서 앞뒤가 바뀌어야 할 결정이 있는가. 특히 「배경 띠 → UI 팔레트」와 「최소 글자 크기 → 폰트」의 선후.
2. 1차 검토에서 더한 결정의 층 배치가 맞는가 — 접근성 1층, 간격 · 예산 2층(예산 → 폰트 순), 모션 4층, 상태 표 4층, 컴포넌트 상태 표 3층, 무드 브리프 1층. 아직 빠진 결정이 있는가.
3. §5.2의 길이 확장 규칙이 업계 관례와 어긋나는 곳이 있는가. 1.3배 기준이 적절한가, 짧은 라벨에 별도 기준이 필요한가.
4. §6.1의 「데미지 숫자는 비트맵, 본문은 TTF」 분리가 Cocos 같은 웹 기반 엔진에서도 통상적인가.
5. 「묶음별 대표 언어 셋(독일어 · 러시아어 · 일본어)만 조사하면 나머지도 같은 결론」이라는 전제가 맞는가. 대표가 놓치는 언어별 특수 조건이 있는가.
6. §7의 조사 항목에 빠진 것이 있는가. 특히 AI 생성 음악 · 효과음을 상업 게임에 넣을 때 플랫폼이 요구하는 것.
7. §8.1의 검증 틀에 더하거나 뺄 칸이 있는가.
8. §9의 비용 추정에서 전제가 틀린 곳이 있는가.
9. WCAG 대비비 4.5:1 · 3:1을 게임 UI(어두운 연출, 움직이는 배경 위 HUD)에 그대로 쓰는 것이 관례인가, 게임 쪽에 다른 통용 기준이 있는가.
10. 의미색 표(이름 · 역할 · 값 · 쓰는 화면 · 예약색 충돌 검사)와 「강조색은 주 행동 버튼 전용」이 통상 관례와 어긋나는 곳이 있는가.
11. 감정 전환 여덟(타이틀 진입 · 전투 시작 · 레벨업 진입 · 카드 선택 · 사망 · 승리 · 결과 공개 · 재시작)에 빠진 순간이 있는가.
12. 값이 없는 결정 순서 문서를 이 시점에 검증하는 것이 맞는가, 1층 값이 나온 뒤 묶음으로 보는 것이 맞는가.

## GPT 2차 검증 — 디자인 전반 계획

- 검토일: 2026-10-12
- 대상: `GPT 2차 검증 묶음 — 디자인 전반 계획(결정 순서와 검증 방식)`
- 결론: **전체 구조는 유지 가능. 다만 P7은 반대, 나머지 핵심 항목은 대부분 조건부 동의.**
- 수정 우선순위:
  1. 다국어 대표 언어 3개만으로 후보 15개를 대표한다는 전제 폐기
  2. 성능 게이트의 “현재 출하 기준”과 “미래 스트레스 목표” 분리
  3. 화면 맞춤 정책 → 최소 글자 크기의 1층 내부 선후 명시
  4. 접근성 수치를 “게임 업계 의무”가 아니라 프로젝트 내부 품질 기준으로 명시
  5. UI 예산을 아틀라스 개수·Label 개수 같은 임의 상한보다 실측 가능한 성능/용량 예산으로 재정의

---

### P1 — 판정: 조건부 동의

**이유:**  
층·트랙 단위로 묶어서 검토하는 방식은 결정 하나씩 15회 이상 왕복하는 것보다 효율적이고, 같은 층 안의 상호 의존성을 함께 볼 수 있다는 장점이 있다. 두 모델의 교차 검토도 한 모델의 경로 고착을 줄이는 장치로는 유효하다. 다만 두 모델이 같은 공개 자료와 일반적인 개발 관행에 크게 의존하므로, “두 모델이 동의했다 = 검증됐다”로 취급하면 안 된다.

현재 1층은 여덟 결정이므로 한 번에 검토하기에는 약간 크다. **층 자체는 유지하되 검증 묶음만 `1A(환경·가독성)` / `1B(상호작용·정보·접근성)` 정도로 쪼개는 것**을 권한다.

**조건 또는 대안:**  
검증 틀에 다음 두 칸을 추가한다.

- **증거 수준:** 공식 문서 / 실측 / 프로젝트 코드 / 업계 경험칙 / 취향 중 무엇인가
- **재검토 조건:** 어떤 사실이 바뀌면 이 결정을 다시 열 것인가

그리고 GPT에는 “반대 근거를 억지로 하나 만들라”보다 **“이 결정을 뒤집을 수 있는 반증 조건을 적어라”**가 더 낫다.

---

### P2 — 판정: 조건부 동의

**이유:**  
0→1→2→3→4층 구조 자체는 타당하다. 특히 **배경 그림이 아니라 배경의 시각 규약을 먼저 정하고, 그 규약을 UI 팔레트와 맵 그림이 각각 소비한다**는 구조가 좋다.

다만 “최소 글자 크기 → 폰트”는 맞지만, 최소 글자 크기를 확정하는 데 최소 지원 뷰포트가 필요하므로 **1층 내부에서는 `화면 맞춤 정책 → 최소 글자 크기 → 폰트`**가 되어야 한다. 무드·레퍼런스 브리프도 팔레트·폰트 선택의 상위 입력이므로 1층의 가장 앞에 두는 것이 맞다.

**조건 또는 대안:**  
층은 그대로 두고 1층 내부 선후만 명시한다.

1. UI 무드·레퍼런스 브리프
2. 화면 맞춤 정책
3. 배경 명도·채도 띠
4. 최소 글자 크기
5. 다국어 길이 확장 규칙
6. 정보 위계
7. 입력/포커스
8. 접근성

이것을 완전한 직렬 순서로 볼 필요는 없다. 일부는 병렬 조사 가능하지만 **확정 의존성**만 위처럼 기록하면 된다.

---

### P3 — 판정: 조건부 동의

**이유:**  
여덟 항목 모두 2층 이후가 소비하는 선행 계약이라는 점에서 1층 배치는 대체로 맞다. 무드 브리프와 정보 위계가 추가된 것도 이전 계획보다 낫다.

다만 세 가지를 고쳐야 한다.

첫째, **최소 글자 크기는 화면 맞춤 정책보다 먼저 확정할 수 없다.**

둘째, “문자 체계별 최소 px”는 좋은 시험 분류이지만 **라틴=몇 px, 한글=몇 px처럼 고정 규칙으로 만들면 안 된다.** 같은 nominal px라도 폰트의 x-height, 획 굵기, 렌더링 특성에 따라 체감 크기가 다르다.

셋째, 최소 클릭 크기는 간격 토큰이 아니라 입력·접근성 계약에 가깝다. 따라서 P4의 “간격·격자”에서 빼서 P3의 입력/접근성 쪽으로 올리는 것이 더 일관된다.

WCAG의 4.5:1(일반 텍스트), 3:1(큰 텍스트 및 의미 있는 UI 요소)은 **게임 전용 강제 기준은 아니지만 프로젝트 내부 품질 기준으로 사용하기에 합리적**이다. 움직이는 게임 배경에서는 평균 배경색이 아니라 실제 최악 조건을 봐야 한다.

**조건 또는 대안:**  
문서에는 다음처럼 적는 것을 권한다.

> WCAG AA를 법적/플랫폼 강제 기준으로 선언하지 않는다. 다만 프로젝트의 기본 가독성 기준으로 일반 텍스트 4.5:1, 큰 텍스트 및 의미 있는 UI 경계 3:1을 출발값으로 사용한다. 실제 게임 배경 위에서 미달하면 텍스트 효과 또는 backing plate로 보완하며, 예외를 둘 경우 이유와 실측 화면을 기록한다.

---

### P4 — 판정: 조건부 동의

**이유:**  
`예산 → 폰트 → 팔레트·간격`이라는 큰 방향은 맞다. 특히 CJK까지 고려하면서 폰트 용량을 나중에 확인하는 것은 리스크가 크므로 예산이 폰트 앞에 있어야 한다.

다만 **“UI 아틀라스 묶음 수 상한”과 “동시 Label 노드 수 상한”을 미리 숫자로 박는 방식은 권하지 않는다.** 실제 성능 병목은 기기·브라우저·폰트 캐시·배칭·드로우콜·업데이트 빈도에 따라 달라서, 임의의 Label 개수 자체가 좋은 성능 계약은 아니다.

2층 예산은 아래처럼 잡는 편이 낫다.

- 초기 다운로드/압축 해제 용량 중 UI+폰트 예산
- 폰트 파일 예산
- 대표 화면에서 UI가 소비할 수 있는 CPU/GPU frame-time 또는 전체 프레임 예산
- 텍스처 메모리 또는 아틀라스 총 용량
- 필요하면 draw call 관찰값

아틀라스 묶음 수와 Label 수는 **그 예산을 만족시키기 위한 구현 결과**로 두는 편이 좋다.

의미색 표에는 현재 열 외에 다음이 있으면 좋다.

- 토큰명
- foreground/background 역할
- 상태 변형(normal/hover/pressed/disabled/focus 등)
- 필요한 대비비
- 색 외의 중복 표현(아이콘·형태·텍스트)
- 예약색과 충돌 여부

“강조색은 주 행동 버튼 전용”은 너무 좁다. **Primary action 전용 색을 별도로 두고, focus/selection은 별도 semantic token 또는 같은 hue의 명시적 변형으로 관리**하는 편이 낫다.

support 색도 지금 반드시 실값을 확정할 필요는 없다. **팔레트가 미래 네 번째 분류색을 수용할 수 있는 여유를 확보한다**는 계약까지만 지금 정하고, 실제 support 색은 기능이 들어올 때 확정해도 된다.

---

### P5 — 판정: 조건부 동의

**이유:**  
컴포넌트 상태 표를 3층에 두고, 화면별 콘텐츠 상태를 4층에 두는 구분은 맞다. `normal/hover/pressed/disabled/focused`는 재사용 부품의 상태이고, `empty/error/success`는 화면 또는 데이터 상태이므로 서로 다른 표가 맞다.

UI 그림 제작 경로를 형태 언어와 같은 3층에 둔 것도 타당하다. “그린 프레임”을 택하면 AI/래스터 제작이, 확장형 프레임이면 9-slice나 벡터가 자연스럽게 따라오므로 둘은 서로 피드백을 주고받는다.

다만 제작 경로는 최종 형태 언어가 완전히 확정된 뒤에만 보는 것이 아니라 **3층 초반에 작은 제작성(producibility) 시험을 함께 해야 한다.**

화면×상태 표는 모든 화면에 `기본·빈·부분·오류·성공·비활성`을 강제로 채우지 않는 것이 좋다. 상태가 실제로 존재하는 화면에만 적용하는 **N/A 허용 매트릭스**로 두어야 한다.

감정 전환 여덟은 UI 모션 정책의 중심 목록으로 충분하다. 다만 **피격·회복은 UI 모션보다 combat feedback/VFX 범주**, 웨이브 전환은 UI와 게임 연출의 경계다.

**조건 또는 대안:**  
3층 시작 시 대표 컴포넌트 하나(예: 레벨업 카드 또는 기본 버튼)로 9-slice/벡터/AI 래스터 중 후보 경로를 실제 제작해 본 뒤 형태 언어를 닫는다.

### P6 — 판정: 조건부 동의

**이유:**  
네 트랙은 완전히 독립은 아니지만 **계약을 통해 병행 가능한 정도로 독립적**이다.

- 적 로스터 ↔ 배경 띠: 명도·채도·실루엣 대비
- 맵 ↔ 배경 띠: 직접 의존
- 이펙트 ↔ 적/배경: 전투 가독성과 화면 과밀
- 사운드: 가장 독립적

따라서 “독립”을 **“상대 트랙의 완성본을 기다릴 필요가 없다”**는 뜻으로 정의하면 맞다.

이펙트 성능 게이트는 수정이 필요하다. **현재 게임이 실제로 요구하는 출하 기준과 미래 목표인 ‘수백 마리’를 하나의 합격 기준으로 섞으면 안 된다.**

권장 방식:

- **Release gate:** 현재 밸런스/씬에서 실제 관측되는 최대 동시 적·이펙트 부하
- **Stress record:** 아트 정본이 목표로 한 수백 마리 부하를 별도 측정, 합격 필수 아님
- 두 결과 모두 기록

또한 “63”은 문서에 적힌 스포너 값의 산식이지만, `maxInbound=25`를 교전 38에 단순 더해 실제 동시 렌더 적 63으로 볼 수 있는지는 제공된 정보만으로 확정할 수 없다. **웹 빌드에서 실제 런타임 peak를 계측하는 값이 최종 기준이어야 한다.**

fps 하나보다 frame time을 기록하는 것이 좋다.

**조건 또는 대안:**  
성능 게이트 표에 다음을 추가한다.

- 테스트 PC/GPU/브라우저
- 해상도/창 크기
- 실제 동시 적 peak
- 실제 동시 이펙트/파티클 수
- 평균 frame time
- 1% low 또는 최저 구간
- 현재 출하 기준 통과 여부
- 스트레스 결과(참고)

### P7 — 판정: 반대

**이유:**  
세 축(글리프 / 길이·레이아웃 / 엔진 배치·문장 조립)으로 나누는 구조는 좋다. **반대하는 것은 “독일어·러시아어·일본어 세 언어를 조사하면 나머지 후보도 같은 결론이 난다”는 전제다.**

대표 언어만으로는 다음을 놓친다.

- 튀르키예어: `İ / ı` 등 별도 글리프·대소문자 문제
- 폴란드어: 확장 라틴 글리프
- 중국어 번체: 간체/일본어와 다른 glyph coverage
- 러시아어만으로는 우크라이나어의 모든 키릴 글리프를 보장하지 못함
- 일본어 줄바꿈 시험만으로 중국어 실제 문자열·폰트 coverage를 보장하지 못함
- 복수형은 언어별 규칙이 크게 달라 단순 `{param}` 치환만으로 장기 확장성이 보장되지 않음

그리고 영어×1.3은 **모든 문자열에 대한 보장값으로 쓰기에는 약하다.** 30% 여유는 출발점으로 쓸 수 있지만 짧은 문자열은 훨씬 더 크게 늘 수 있다.

따라서 전수 “수동 조사”는 필요 없지만 **전수 자동 coverage 검사는 싸게 해야 한다.**

**대안:**  

1. 후보 15개에 대해 폰트 glyph coverage를 자동 검사한다.
2. 실제 레이아웃/줄바꿈 수동 검증은 대표 언어로 한다.
   - 독일어: 긴 라틴 문자열
   - 러시아어 또는 우크라이나어: 키릴
   - 일본어: CJK 줄바꿈
   - 번체 중국어: CJK coverage 확인용 추가 샘플
3. pseudo-localization 기본 팽창은 **+40% 정도**로 하고, 1~2단어의 짧은 버튼/라벨에는 별도 worst-case 샘플을 둔다.
4. “영어×1.3 공간을 항상 확보”를 절대 규칙으로 두기보다 **responsive container + pseudo-localization 통과**를 실제 합격 기준으로 둔다.
5. 날짜·시간이 실제 UI에 없다면 지금 설계할 필요는 없다. 숫자·퍼센트·소수점·천 단위는 실제로 존재하므로 대상에 포함한다.
6. 정렬 순서(collation)는 도감/리스트에 정렬 기능이 생길 때 결정하면 된다.

### P8 — 판정: 조건부 동의

**이유:**  
본문·제목·숫자의 역할 구분 자체는 일반적이고 유효하다. 다만 **“데미지 숫자는 비트맵 폰트가 관례이므로 비트맵”을 기술 결정으로 미리 고정할 이유는 없다.**

BMFont/비트맵 폰트의 장점은 숫자·기호만 필요할 때 작은 atlas로 효과를 완전히 통제할 수 있고 런타임 glyph rasterization 부담을 줄일 수 있다는 점이다. 반대로 Cocos/web 환경에서 실제 성능 문제가 없다면 TTF 계열 또는 기존 폰트 렌더링으로도 충분할 수 있다. 따라서 **기능이 v1에 들어왔을 때 두 방법을 짧게 실측하고 선택**하는 것이 가장 안전하다.

“CJK는 파일이 크므로 서브셋이 필수”도 너무 강한 문장이다. **용량 예산을 넘는다면 서브셋이 필요하다**가 정확하다.

비교판 방식은 좋다. 단, HTML 비교판이 Cocos의 최종 렌더링과 완전히 같다고 가정하면 안 된다. **후보 축소용 HTML 비교판 → 최종 2개는 Cocos 실제 Label로 비교**가 더 안전하다.

**조건 또는 대안:**  

- HTML 비교판: 3~4개 → 2개로 축소
- Cocos 실제 화면: 최종 2개 비교
- 실제 ko/en 문자열, 숫자, `%`, `+`, `-`, `·`, 괄호, 굵기별 렌더링 확인
- 서브셋은 용량 예산 초과 시 적용
- 서브셋 시 해당 폰트의 OFL/RFN 확인 및 license notice 포함

### P9 — 판정: 조건부 동의

**이유:**  
조사 범주는 대체로 좋다. 현재 Steam/itch.io 같은 플랫폼 정책은 변경될 수 있으므로, 최종 정본에는 항상 **공식 원문 + 확인일**을 남기는 방식이 맞다.

조사 목록에는 다음이 추가돼야 한다.

- 생성 당시 사용 플랜과 약관 버전/확인일
- 생성 모델/서비스명
- 상업 이용 및 게임 내 재배포 권리
- attribution 의무
- 수정·편집 허용
- 생성물에 대한 Content ID/저작권 자동 클레임 가능성
- 음악 서비스의 독점성/비독점성
- 서비스 해지 후 기존 생성물의 권리 유지 여부
- 입력물의 서비스 학습/재사용 조건
- 유명 아티스트/성우 모방·voice cloning 관련 제한
- 플랫폼 AI disclosure 대상 여부
- 라이선스/약관 원문 snapshot 또는 확인 링크
- 생성물 provenance: 어느 자산을 어느 도구로 만들었는지

OFL 폰트에는 **license notice를 배포물에 포함하는 방법**도 조사 항목으로 추가하는 것이 좋다.

**조건 또는 대안:**  
라이선스 정본은 “서비스 단위” 표만 두지 말고 **자산 provenance와 연결**해야 한다. 예를 들어 `asset → tool/model → plan → terms checked date → disclosure needed → license evidence`가 추적되면 플랫폼 제출 때 다시 뒤질 필요가 없다.

- 결정문

### P12 — 판정: 조건부 동의

**이유:**  
테스트 장비가 없는 게임패드를 지금 지원 여부까지 확정하지 않는 것은 합리적이다. 모바일도 v1 범위가 아닌 만큼 실제 모바일 UI를 지금 설계할 필요는 없다.

지금 걸어 둘 최소 조건은 다음 정도면 충분하다.

1. hover만으로 의미나 조작을 전달하지 않는다.
2. 시각 크기와 hit area를 분리할 수 있게 한다.
3. 입력 이벤트를 특정 마우스 버튼에만 결박하지 않는다.
4. 레이아웃을 고정 좌표 하나에만 묶지 않는다.
5. safe-area를 나중에 도입할 수 있도록 HUD edge offset을 토큰/정책으로 둔다.
6. 세로 화면을 지금 지원할 필요는 없지만 구조적으로 완전히 불가능하게 만들지는 않는다.

44px는 웹의 CSS pixel 관례를 Cocos 논리 px에 그대로 복사하는 값으로 쓰면 안 된다. **모바일 구현 시 실제 물리 크기/디바이스 배율로 재검증하는 참고값**으로만 남기는 것이 맞다.

게임패드는 Steam v2에서 실제 장비를 확보했을 때 다시 여는 것으로 충분하다.

## 빠진 결정 목록

- **성능 측정 기준 환경:** 대표 PC/GPU, 브라우저, 해상도, frame-time 기록 방식.
- **출하 기준과 스트레스 기준 분리:** 특히 이펙트의 63 vs 수백 마리.
- **UI 텍스트 가독성 보조 정책:** outline/shadow/backing plate 중 언제 무엇을 쓰는지.
- **폰트 fallback 정책:** 후보 폰트가 모든 실제 출하 glyph를 포함하지 않을 경우 엔진이 어떻게 처리하는지.
- **자산 provenance 기록:** AI/외부 라이브러리 자산별 생성 도구·모델·라이선스 확인일·플랫폼 disclosure 여부 연결.
- **라이선스 파일/고지 배포 위치:** OFL, CC-BY 등 attribution/라이선스 텍스트를 게임/배포 패키지 어디에 둘지.
- **UI 제작성 게이트:** 3층 형태 언어를 닫기 전에 대표 버튼/카드 하나로 실제 제작 경로를 시험.
- **실제 peak 계측:** 스포너 수식으로 계산한 최대값과 런타임 실제 동시 적 수가 같은지 확인.
- **문자열 coverage 자동 검사:** 후보 언어 전체를 수동 QA할 필요는 없지만 후보 폰트가 필요한 글리프를 갖는지는 자동화 가능.
- **텍스트 overflow 금지 규칙:** 중요한 버튼/선택지에서는 CLAMP를 허용하지 않는 등 요소 중요도별 금지 overflow.

## 검증 질문 답 (1~12)

### 1. 층 구조의 선후

**대체로 맞다.**  
`배경 띠 → UI 팔레트`는 유지. `최소 글자 크기 → 폰트`도 유지하되, 그 앞에 **`화면 맞춤 정책 → 최소 글자 크기`**를 명시해야 한다.

무드 브리프는 1층 최상단 입력으로 두는 것이 좋다.

### 2. 추가 결정의 층 배치

- 접근성: **1층 맞음**
- 성능·용량 예산: **2층 맞음**
- 폰트: **예산 뒤 2층 맞음**
- 간격/격자: **2층 맞음**
- 최소 클릭/상호작용 크기: **1층 입력·접근성 계약이 더 적절**
- 모션 정책: **4층 맞음**
- 컴포넌트 상태 표: **3층 맞음**
- 화면/데이터 상태 표: **4층 맞음**
- 무드 브리프: **1층 맞음**
- 정보 위계 표: **1층 맞음**

### 3. 영어 × 1.3

**고정 통과 기준으로는 부족하다.**

30% 여유는 일반적인 출발값으로 쓸 수 있으나, 짧은 문자열은 훨씬 더 크게 늘 수 있다. 기본 pseudo-localization은 **약 +40%**를 권하고, 1~2단어 버튼·짧은 라벨에는 별도 worst-case 문자열을 둔다.

진짜 합격 기준은 `영어×1.3` 자체가 아니라 **responsive layout + pseudo-localization에서 잘리지 않음**이어야 한다.

### 4. 데미지 숫자 BMFont + 본문 TTF

**가능하고 흔한 패턴이지만 필수 관례는 아니다.**

숫자·기호만 들어가는 BMFont는 작은 atlas와 일정한 스타일이라는 장점이 있다. 그러나 Cocos/web에서 성능 문제가 실제로 있는지 측정하지 않고 BMFont를 강제할 필요는 없다.

**데미지 숫자 기능이 v1에 들어오면 TTF 방식과 BMFont 방식을 짧게 프로파일링하고 선택**하는 것이 가장 타당하다.

### 5. 대표 언어 셋 전제

**반대.**

독일어·러시아어·일본어는 좋은 대표 QA 언어지만 후보 15개 전체의 glyph/문법/형식 특성을 대표하지 못한다.

수동 UI 검증은 대표 언어로 줄여도 되지만 **glyph coverage는 후보 언어 전체를 자동 검사**해야 한다. 특히 튀르키예어, 폴란드어, 우크라이나어, 번체 중국어를 대표 셋만으로 보장할 수 없다.

### 6. AI 음악·효과음 조사 항목

현재 목록에 다음을 더한다.

- 생성 당시 플랜과 약관 버전
- 기존 생성물 권리가 구독 해지 뒤에도 유지되는지
- 게임 안에서 재배포 가능한지
- attribution
- 수정/편집 허용
- Content ID 및 제3자 자동 클레임
- 유명 아티스트/성우 모방 금지 조항
- 입력물의 학습/재사용 조건
- asset별 provenance
- Steam/itch AI disclosure 여부
- 약관 확인일과 원문 snapshot/링크

### 7. 검증 틀

현재 다섯 칸에 두 칸을 추가하는 것을 권한다.

- **증거/확인 방법**
- **재검토 트리거**

최종 권장:

`결정문 / 근거 / 증거 / 버린 대안 / 틀릴 수 있는 지점 / 재검토 트리거 / 검증 질문`

라이선스 결정이면 `약관 조항 + 확인일` 추가.

### 8. 비용 추정

12~19주는 **거친 범위로는 유지 가능**, 일정 약속으로 쓰기에는 근거 부족이다.

가장 위험한 것은 이펙트·UI라는 판단에 동의한다. 현재 산출물이 늘어난 UI는 **2~4주보다 3~5주를 출발 추정으로 잡는 편이 안전**하다. 1·2층 실측 후 다시 추정해야 한다.

### 9. WCAG 4.5:1 · 3:1

**게임 UI의 보편적 강제 표준은 아니지만 내부 기준으로 쓰기에 좋다.**

게임은 움직이는 배경이므로 계산값만 통과시키지 말고 실제 worst-case 장면에서 확인해야 한다.

문서에는 **“WCAG 준수 선언”이 아니라 “접근성 출발 기준으로 차용”**이라고 쓰는 것이 정확하다.

### 10. 의미색 표와 강조색

의미색 표 방향은 좋다. 다음 열을 더한다.

- token 이름
- foreground/background 역할
- 상태 변형
- 대비비
- 색 외 redundancy
- 예약색 충돌

“강조색 = 주 행동 버튼 전용”은 너무 강하다. Primary action 전용 token은 유지하되 focus·selection은 별도 semantic token 또는 명시적 변형을 허용한다.

### 11. 감정 전환 여덟

UI 줄기의 주요 감정 전환으로는 충분하다.

추가 검토 후보:

- 웨이브 시작/완료
- 일시정지→복귀
- 레벨업 선택 후 전투 복귀

피격·회복은 UI 모션 정책보다 **combat feedback/VFX**로 분리하는 것을 권한다.

### 12. 값 없는 결정 순서를 지금 검증하는가

**지금 검증하는 것이 맞다.**

지금 단계의 목적은 값의 옳고 그름이 아니라 **무엇을 먼저 정해야 하고 어떤 결정이 다음 결정의 입력인지**를 검증하는 것이다.

다만 이번 검증으로 프로세스 자체를 닫고, **1층 값이 나온 뒤에는 1층 값 묶음을 별도로 다시 검증**해야 한다.

1. 지금: 구조·의존성 검증
2. 다음: 1층 실제 값 검증
3. 이후: 2층 값 검증

이 순서가 적절하다.

### 전체 결론

전반 계획은 **폐기하거나 다시 설계할 필요가 없다.** 핵심 구조인 `상위 계약 → 층별 결정 → 독립 트랙 게이트 → 실측 후 생산`은 유지하는 것이 맞다.

확정 전에 반드시 고칠 것은 네 가지다.

1. P7의 대표 언어 3개 전제를 폐기하고 **전수 자동 glyph coverage + 대표 언어 수동 QA**로 바꾼다.
2. P6의 **현재 출하 성능 게이트와 수백 마리 스트레스 기록을 분리**한다.
3. P3에 **화면 맞춤 정책 → 최소 글자 크기** 선후를 명시한다.
4. P4의 UI 예산을 **임의의 Label/atlas 개수 상한보다 실제 용량·frame-time·메모리 기반 예산**으로 바꾼다.

이 네 가지를 반영하면 전반 프로세스는 확정하고 1층 세부 계획으로 넘어가도 된다.

사용자가 한 번에 「권고대로」로 받을 수 있는 묶음이다. 빼고 싶은 번호만 말하면 된다.

### 다. 이미 계획에 있어 바꿀 것 없음

- 출하 기준(63)과 수백 마리 스트레스의 분리 — §4.4가 이미 「통과 판정은 63, 수백 마리는 함께 기록」이다. GPT의 수정 우선순위 2는 더 뚜렷한 표 요구로 읽어 나-8에 넣었다.
- WCAG는 강제가 아니라 내부 출발 기준 — §4.2 접근성 행이 이미 「게임 강제 기준은 아니라 내리면 근거를 적는다」.
- 가독성 보조(외곽선 · 반투명 판)의 자리 — 접근성 행이 3층 형태 언어로 넘겨 두었다(빠진 결정 3).
- 조사 로그는 정본에 넣지 않는다 — §8.4.
- 서브셋 때 OFL · Reserved Font Name 확인 — §7.2 폰트 행.
- 층 배치 전부(접근성 · 무드 · 위계 1층, 예산 · 폰트 · 간격 2층, 컴포넌트 상태 3층, 화면 상태 · 모션 4층) — GPT 동의(질문 2).
- 값 없는 순서 문서를 지금 검증하는 것 — GPT 「맞다」(질문 12). 묶음 §4의 첫 의심은 닫혔다. 다음 검증은 1층 값 묶음, 그 다음 2층 값 묶음(§8.1 그대로).

### 라. GPT가 답하지 않은 것

- 묶음 §4의 「적 로스터 · 맵 아트의 ChatGPT 웹 생성이 미실측」 — 언급 없음. §8.0 보고 규칙으로 간다.
- 「UI 줄기 세부 계획이 너무 무거운가」 — 질문 12 답에서 「지금 검증은 맞다」만. 무게는 1층 값 묶음을 넘길 때 다시 본다.
- 사운드 톤 결정 주체 — 나-18로 Claude 1차 안.

### 2. 배경 — 판단에 필요한 사실

#### 2.1 앞 검증에서 나온 것과 이 프로젝트의 진행 방식

- 앞 묶음 P1에서 당신은 「1층 여덟 결정은 한 번에 검토하기에 크다. 층은 유지하되 검증 묶음만 1A(환경 · 가독성) / 1B(상호작용 · 정보 · 접근성)로 쪼개라」고 했다.
- 이 프로젝트는 **전반 구성을 먼저 잡고, 그 뒤 슬라이스 하나씩** 간다. 슬라이스는 층 하나(1층 · 2층 …) 또는 독립 트랙 하나(이펙트 · 사운드 · 적 · 맵)다. 슬라이스 하나 = 세부 계획 문서 하나 = GPT 검증 묶음 하나 = 사용자 검토 하나 = 구현 한 번이다.
- 사용자가 지적한 것: GPT 답은 사용자도 읽고 결정마다 최종 판단을 내린다. 그래서 묶음 크기는 GPT의 부담이기 전에 **사용자의 부담**이다. 앞 묶음 열두 결정의 답을 처리했더니 사용자 앞에 결정 열 줄과 권고 열여덟 줄이 한꺼번에 떨어졌고, 그것이 크다는 것이 출발점이다.
- 1층이 큰 이유에 대한 Claude의 진단: 결정이 여덟이라서가 아니라, 1차 디자인 검토가 행마다 **슬라이스 수준의 깊이**(표의 열 구성 · 판정 절차 · 기록 항목 · 출발값)를 넣었기 때문이다. 아래 2.2 표의 「지금 깊이」 열이 그것이다.

#### 2.2 1층 여덟 결정 — 지금 깊이와, 누가 무엇을 입력으로 쓰나

| 결정 | 지금 깊이(1차 디자인 검토가 더한 것) | 뒤 층이 입력으로 쓰는 것 |
|---|---|---|
| 가. UI 무드 · 레퍼런스 브리프 | 한 장: UI가 나르는 축, 참고 그림 3~5장과 장마다 가져올 것 · 안 가져올 것, 쓰지 않을 것 목록, 형용사 다섯. 사용자 판정 | 2층 팔레트 · 폰트, 3층 형태 언어, 4층 아이콘이 전부 이 브리프를 쓴다 |
| 나. 배경의 명도 · 채도 띠 | 단위(HSL · Lab · 상대 휘도 중 무엇) + 수치 범위 | 2층 팔레트(띠 위에서 읽히는 색), 1층 접근성(띠의 가장 밝은 값 위에서 HUD 글자 대비를 잰다), 맵 아트 트랙 |

1층 안에서 서로 기대는 것: 아(접근성)는 나(띠)의 가장 밝은 값을, 사(위계)는 다(최소 글자)를, 다(최소 글자)는 바(화면 맞춤)의 최소 높이를 쓴다. 당신이 제안한 1A · 1B 경계로 가르면 **나 · 다는 1A, 사 · 아는 1B**라 경계를 가로지르는 의존이 둘 있다.

#### 2.3 이미 정해졌거나 제안 중인 「이어 주는 장치」

- 검증 틀에 **증거 수준**(공식 문서 · 실측 · 코드 · 업계 경험칙 · 취향 중 무엇인가)과 **재검토 조건**(무엇이 바뀌면 다시 여나) 두 칸 — 당신의 권고를 받아 **확정**.
- 결정마다 상태 꼬리표(제안 중 · 확정 · 뒤집힘) — 사용자가 달기로 **확정**. 자리는 결정 기록이고 정본 본문에는 달지 않는다.
- 슬라이스 세부 계획 머리에 **「앞 슬라이스에서 받은 입력」 절**(값과 출처 · 결정 번호 · 날짜) — Claude 제안, 미확정.
- 슬라이스 착수 때 정본 · 코드 · 백로그가 적은 것과 실제가 맞는지 **먼저 보고하고 확인**받는 규칙 — 확정(앞 묶음 P10).
- 세션이 바뀌면 AI는 앞 세션을 기억하지 않는다. 이어지는 것은 문서에 적힌 것뿐이다. 위 장치들은 전부 그 전제 위에 있다.

### 3. 결정 묶음

#### Q1. 1층은 슬라이스 하나로 두고, 깊이를 걷어 내 쓰는 층으로 보낸다 (사용자 안, Claude 권고)

- **결정문:** 기준은 하나 — **「2층 이후가 입력으로 쓰는 것만 1층이 정한다.」** 여덟에 적용하면: 나 · 마 · 바 · 아 넷은 이미 얕아 그대로. 가(무드 브리프)는 한 장이라 그대로. **다(최소 글자)**는 출하 언어가 한 · 영이므로 한글 · 라틴 둘만 지금 정하고, 한자 · 가나는 2층 폰트 조사가 일본어를 볼 때 같이 잰다. **라(길이 확장)**는 원칙과 가짜 언어 통과 기준만 1층에 두고, 요소 목록 표는 3층이 치수를 잴 때 만든다. **사(위계)**는 화면마다 1순위 하나와 「크기 단계가 몇 개 필요한가」만 정하고, 1 · 2 · 3순위 전체 표는 4층 화면별 적용이 채운다.
- **근거:** 큰 이유가 결정 수가 아니라 깊이라면, 깊이를 걷어 내면 여덟이어도 묶음 하나 · 사용자 검토 하나에 들어간다. 서로 기대는 결정(나 → 아, 다 → 사, 바 → 다)이 한 문서에 남아 경계가 안 생긴다. 옮기는 셋은 버리는 게 아니라 **쓰는 자리로** 간다 — 요소 목록 표는 치수를 정하는 순간(3층)에, 전체 위계 표는 화면별로 적용하는 순간(4층)에, 한자 · 가나 크기는 그 글자를 가진 폰트를 보는 순간(2층)에 필요하다.
- **증거 수준:** 업계 경험칙(스타일 가이드의 선행 조건 층은 값 몇 개로 끝나는 것이 보통이라는 Claude의 이해) + 이 프로젝트의 사정(사용자 판정 부담). 실측 · 공식 문서 아님.
- **버린 대안:** 가. **1A · 1B 두 슬라이스**(당신의 안) — 묶음 둘 · 왕복 둘 · 세부 문서 둘. 경계를 가로지르는 의존이 둘(2.2 끝) 있어 1B는 1A 결과를 받아야 판정할 수 있고, 2.3의 장치로 메울 수는 있다. 나. **지금 깊이 그대로 슬라이스 하나** — 사용자 검토 부담이 그대로다. 출발점이 그 부담이었다.
- **틀릴 수 있는 지점:** 하나, 2층이 1층에 없는 입력을 발견해 되돌아온다 — 예를 들어 타입 스케일이 2 · 3순위 없이 단계 수를 못 정할 수 있다. 둘, 길이 확장 원칙이 3층 전까지 **검증되지 않은 원칙**으로 남는다 — 가짜 언어 시험은 요소 목록 표가 있어야 돌릴 수 있고 표가 3층이면 원칙이 틀렸을 때 3층에서야 안다. 셋, 한자 · 가나 최소 글자를 2층으로 미루면 폰트 비교판이 그 크기 조건 없이 돈다 — 출하가 한 · 영이라 괜찮다고 보지만 확장 후보 조사와 엇갈릴 수 있다. 넷, 1차 디자인 검토 결정 셋(위계 표 · 문자 체계별 최소 글자 · 요소 목록 표)의 **자리**가 바뀐다 — 내용은 유지.
- **재검토 조건:** 2층 착수 보고에서 「1층에 없는 입력」이 둘 이상 나오면 1층 깊이를 다시 정한다.
- **검증 질문:** 아래 4의 1~4.

#### Q2. 얕은 1층에서 2층으로 넘어갈 때 빠진 입력을 잡는 장치는 셋이면 되는가

- **결정문:** 세부 계획 머리의 「앞 슬라이스에서 받은 입력」 절(값 + 출처), 1층 결정마다 재검토 조건에 「2층이 이 값을 건드릴 수 있는 경우」를 미리 적기, 착수 때 보고. 이 셋으로 1층 → 2층 경계를 잇는다. Q1을 버리고 1A · 1B로 가더라도 같은 셋이 1A → 1B 경계에 쓰인다.
- **근거:** AI는 세션 사이를 기억하지 않으므로 이어지는 것은 문서뿐이고, 셋 다 문서에 남는 장치다.
- **증거 수준:** 이 프로젝트의 운영 경험(과거 슬라이스에서 문서에 없던 전제가 다음 슬라이스에서 어긋난 적이 있다). 업계 자료 아님.
- **버린 대안:** 장치 없이 세부 계획을 쓸 때 전반 계획을 다시 읽는다 — 읽는 사람이 의존을 놓치면 끝이다.
- **틀릴 수 있는 지점:** 전반 계획이 적어 두지 않은 의존은 어느 장치도 못 잡는다.
- **재검토 조건:** 한 슬라이스 경계에서 빠진 입력이 실제로 나오면 그때 장치를 더한다.

### 4. 검증 질문

1. 세 길 — 얕은 슬라이스 하나(Q1) · 1A · 1B 두 슬라이스(당신의 안) · 지금 깊이 그대로 슬라이스 하나 — 중 어느 것이 맞나. 조건부면 조건을 적어 달라.
2. 「2층 이후가 입력으로 쓰는 것만 1층이 정한다」는 기준이 맞나. 여덟 중 이 기준으로 더 얕게 하거나, 반대로 얕게 하면 안 되는 결정이 있나.
3. 옮기는 셋이 맞나 — 요소 목록 표를 3층으로, 1 · 2 · 3순위 전체 위계 표를 4층으로, 한자 · 가나 최소 글자를 2층 폰트 조사로. 특히 길이 확장 원칙을 3층 전에 가짜 언어로 검증하지 않아도 되나.
4. 위계를 「화면마다 1순위 하나 + 필요한 크기 단계 수」로 줄여도 2층이 폰트 역할(본문 · 제목 · 숫자)과 타입 스케일(단계 수 · 비율)을 정할 수 있나. 못 정한다면 최소한 무엇이 더 있어야 하나.
5. 1층 → 2층 경계를 잇는 장치 셋(입력 절 · 재검토 조건 · 착수 보고)이 충분한가. 더 둘 것이 있나.
6. 업계에서 UI 스타일 가이드의 선행 조건 층(무드 · 해상도 · 최소 글자 · 접근성 같은 것)은 보통 얼마나 얕은가 — 값 몇 개로 끝내는지, 표까지 만드는지. 이 프로젝트처럼 혼자 만드는 작은 게임에서 통상 어디까지 적나.

## GPT 추가 검증 답변 — 1층을 슬라이스 하나에 넣는 방법

- 검토일: 2026-10-12
- 결론: **얕은 1층 하나(Q1)를 유지하는 방향에 조건부 동의.**
- 핵심 조건:
  1. 길이 확장 원칙은 전체 요소표를 3층으로 보내되 대표 요소 3~5개 pseudo-localization 검증은 1층에 유지

### Q1 — 판정: 조건부 동의

**이유:**  
세 길 중에서는 **Q1의 “얕은 1층 하나”가 가장 적절**하다. 지금 문제의 핵심이 결정 개수가 아니라 각 결정이 슬라이스 수준으로 깊어진 데 있다면, 1A·1B로 문서와 검증을 두 번 나누는 것보다 선행 계약만 남겨 한 번에 닫는 편이 이 프로젝트의 운영 방식과 사용자 검토 부담에 더 잘 맞는다. 또한 `바 → 다`, `나 → 아`, `다 → 사`처럼 1층 내부 의존이 있으므로 한 문서에 두는 이점도 분명하다.

**조건 또는 대안:**  
**1층에서 없으면 2층이 결정을 시작할 수 없는 정보까지만 남긴다**는 기준을 적용하되, 길이 확장 검증과 위계는 너무 많이 미루지 않아야 한다.

---

### Q2 — 판정: 조건부 동의

**이유:**  
`앞 슬라이스에서 받은 입력` + `재검토 조건` + `착수 보고` 세 장치는 세션 간 기억이 없는 환경에서 상당히 강한 연결 장치다.

**조건 또는 대안:**  
하나만 더 추가하는 것을 권한다. **각 입력에 “소비하는 다음 결정”을 적는다.** 즉 `입력값 / 출처 결정 / 소비 결정`의 3열 연결이 있으면, 2층에서 필요한 입력이 실제로 모두 도착했는지 검사할 수 있다.

## 검증 질문 답 (1~6)

### 1. 세 길 중 어느 것이 맞나

**얕은 1층 하나(Q1)가 가장 낫다.**

우선순위:
1. **얕은 1층 하나**
2. 1A·1B 두 슬라이스
3. 지금 깊이 그대로 1층 하나

1A·1B는 기술적으로 안전하지만 검토·결정·문서·사용자 판단을 두 번 반복하게 된다. 반면 얕은 1층은 **선행 계약만 한 번에 닫고 상세 설계는 실제 소비 시점으로 미룬다**는 원칙과 잘 맞는다.

다만 **길이 확장과 위계는 일부 정보를 1층에 남겨야 한다.**

---

### 2. 「2층 이후가 입력으로 쓰는 것만 1층이 정한다」는 기준이 맞나

**맞다.**

더 정확한 문구:

> **다음 층이 결정을 시작하는 데 필요한 최소 입력만 1층이 확정한다.**

여덟 항목 기준:
- 무드 브리프: 지금 깊이 유지
- 배경 띠: 지금 깊이 유지
- 최소 글자 크기: 얕게 가능
- 길이 확장: 얕게 가능하나 너무 많이 미루면 안 됨
- 키보드 조작 범위: 지금 깊이 유지
- 화면 맞춤: 지금 깊이 유지
- 정보 위계: 얕게 가능하나 “1순위 하나”만으로는 부족
- 접근성: 지금 깊이 유지

---

### 3. 옮기는 셋이 맞나

#### 요소 목록 표 → 3층
**조건부 동의.**

전체 요소 목록 표는 3층으로 보내도 되지만, 1층에서 길이 확장 원칙이 실제로 가능한지는 대표 요소로 한 번 검증해야 한다.

권장:
- 고정 폭 버튼 1개
- 늘어날 수 있는 패널 1개
- HUD 모서리 고정 라벨 1개

같은 **대표 요소 3~5개로 pseudo-localization 탐침**을 1층에서 실시.

즉:
> **1층 = 원칙 + 대표 샘플 검증**  
> **3층 = 전체 요소 표**

#### 전체 위계 표 → 4층
**반만 옮기는 것이 좋다.**

상세한 `1·2·3순위 + 근거` 전체 표는 4층으로 보내도 된다. 다만 2층이 타입 스케일을 정하려면 다음은 1층에 남겨야 한다.

- primary
- secondary
- tertiary 필요 여부
- 숫자 강조 여부
- 필요한 단계 수

#### 한자·가나 최소 글자 → 2층 폰트 조사
**동의.**

v1 출하가 한·영이므로 1층에서는 라틴·한글만 실제 출하 기준으로 정하는 것이 합리적이다. 일본어/중국어 확장 조사의 값은 1층을 뒤집는 것이 아니라 **확장 후보용 별도 측정값 추가**로 취급하는 것이 좋다.

---

### 4. 위계를 「1순위 하나 + 필요한 크기 단계 수」로 줄여도 되나

**그대로는 약간 부족하다.**

2층이 폰트 역할과 타입 스케일을 정하려면 최소한:

- primary 역할
- secondary 존재 여부
- tertiary/supporting 존재 여부
- 각 단계가 텍스트인지 숫자인지
- 화면마다 필요한 위계 단계 수

정도는 알아야 한다.

따라서 1층 최소 표는 다음 정도를 권한다.

> 화면 / primary 역할 / secondary 존재 / tertiary 존재 / 숫자 강조 여부 / 필요한 단계 수

---

### 5. 경계를 잇는 장치 셋이면 충분한가

**거의 충분하다.**

현재:
1. 앞 슬라이스에서 받은 입력
2. 재검토 조건
3. 착수 보고

여기에 하나만 추가:

#### 입력 소비 매핑
각 입력에:
- 값
- 출처 결정 ID
- 날짜
- **이 값을 소비하는 다음 결정**

을 적는다.

예:

| 입력 | 출처 | 소비 결정 |
|---|---|---|
| 최소 뷰포트 높이 | L1-B6 | 최소 글자 크기 |
| 최소 본문 크기 | L1-C3 | 폰트 후보 비교 |
| 배경 최대 명도 | L1-B2 | 팔레트·대비 검사 |

복잡한 dependency graph까지는 필요 없다.

---

### 6. 업계에서는 선행 조건 층을 얼마나 얕게 하나

**보통 Q1처럼 얕게 두는 편이 맞다.**

선행 단계에서는 대체로:
- 디자인 원칙 / 무드
- 화면·플랫폼 제약
- 접근성 기준
- 기본 타이포 방향
- 색/대비 제약
- responsive 원칙
- spacing/token의 기본 원칙

같은 **규칙과 토큰 수준**을 정한다.

반대로 다음은 실제 컴포넌트를 설계하면서 깊어진다.

- 화면별 전체 위계 표
- 모든 문자열 요소별 overflow 정책
- 모든 버튼/패널의 실제 치수
- 컴포넌트별 상태 조합
- 개별 화면별 예외
- 전체 pseudo-localization 결과표

특히 혼자 만드는 작은 게임이라면 초기 단계에서 모든 표를 완성하는 것은 문서 유지 비용과 검토 부담을 키울 가능성이 높다.

권장 구조:

> **1층:** 원칙 + 다음 층이 필요로 하는 최소값 + 대표 샘플 검증  
> **2층:** 토큰/폰트/팔레트  
> **3층:** 컴포넌트와 요소 단위 상세표  
> **4층:** 화면별 적용과 예외
