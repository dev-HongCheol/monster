## 1. 프로젝트 개요

### 1.1 게임

- **장르:** 2D 탑다운 호드 서바이벌 액션(뱀파이어 서바이버류). 플레이어는 키보드로 움직이고 마법은 자동으로 발사된다. 적을 잡아 경험치를 모으면 레벨업 카드 셋 중 하나를 골라 마법 · 강화를 얻는다. 웨이브가 타이머로 진행되고, 죽거나 끝까지 버티면 결과 화면이 뜬다.
- **이야기 틀:** 판타지 세계에서 소환된 마법사 영웅이 현대 서울의 밤에 나타난 귀신들과 싸운다. 적은 한국 · 중국 · 일본의 대표 귀신이고, v1은 한국 귀신 12종이다.
- **비주얼 한 문장:** 「현대 서울의 밤, 판타지에서 소환된 영웅이 한국 민속 귀신들과 싸우는 — 민속 공포와 판타지가 부딪히는 탑다운 액션.」 기억에 남길 장면은 「밤의 한강 다리 위, 하얀 소복 귀신 떼가 몰려오는데 그 사이로 원소 마법이 터진다」이다.
- **톤:** 귀신은 종마다 특색을 지키되 살짝 귀엽고 무겁지 않게 그린다(2026-10-12 사용자 결정). 배경도 어둡고 무겁기만 하지 않게 한다.
- **콘텐츠 범위:** 마법 5종(파이어볼 · 아이스 미사일 · 라이트닝 볼트 · 프로스트 노바 · 인페르노), 적 12종은 v1에서 더 늘리지 않는다. 지금 개발 축은 완성도(맵 · 스토리 · 화면 흐름 · UI · 메타)다.
- **마법 분류:** 넷 — 화염 · 얼음 · 번개 · support. 분류마다 색이 있고(화염 적 · 얼음 청 · 번개 황), support 색은 아직 없다.
- **최악의 전투 화면:** 동시 적 200마리 + 발사체 수십 + 이펙트 여럿(스트레스 확인은 400).

### 1.2 플랫폼 · 기술

- **엔진:** Cocos Creator 3.8.8, TypeScript.
- **v1:** itch.io 웹 빌드(데스크톱 브라우저). **v2:** Steam PC. 모바일은 v1 목표가 아니지만, 지금 내리는 UI 결정이 나중의 터치를 막지 않게 한다.
- **화면:** 논리 해상도 1280×720, 맞춤 방식 `fitHeight`(창 높이에 맞춰 늘리고 가로 폭은 창 비율에 따라 변한다). HUD는 Widget 컴포넌트로 화면 모서리에 붙는다.
- **지금 웹 빌드 크기:** 약 4.5MB(엔진 3.0MB + 에셋 1.5MB). itch.io 한도는 압축 해제 후 500MB, 파일 하나 200MB라 한도 자체는 멀다.
- **다국어:** 자체 경량 `t()` 방식, 카탈로그 `ko.json` · `en.json`. 출하 언어는 한국어 · 영어 둘이다. 나중 후보는 15개(중국어 간체 · 번체 · 일본어 · 유럽어 아홉 · 러시아어 · 우크라이나어 · 튀르키예어). 다국어 라벨은 TTF 폰트를 쓴다(비트맵 폰트 금지). 플레이어가 글자를 입력하는 자리는 없다.
- **Cocos Label의 성질:** 라벨 하나에 글자 크기가 하나다. 리치 텍스트 라벨은 문자열 안에 `<color=#hex>` 태그로 일부 글자에 색을 입힌다. `Button` 컴포넌트의 상태는 Normal · Pressed · Hover · Disabled 넷이고 키보드 포커스(focused) 상태는 없다.

### 1.3 지금 UI 상태

- 화면 다섯 — 메뉴(타이틀), 전투 HUD, 레벨업 카드, 일시정지, 결과.
- 레이아웃은 있지만 스타일은 placeholder다. 폰트 파일은 0개이고, 씬 셋의 라벨 24개가 전부 시스템 Arial이다.
- 색 · 크기 토큰은 `ui/Theme.ts` 한 파일이 들고 있다(값은 `02-layer1-inputs.md` §2.3). 결과 화면의 티어 3색만 다른 파일(`ui/ResultController.ts`)에 hex 문자열로 따로 있다.
- 키보드는 이동 · ESC만 다루고, 버튼은 마우스 클릭만 된다.
- HUD와 결과 화면의 레이아웃 목업 둘이 확정돼 있다(색 · 폰트 · 형태는 정하지 않았다).
- 맵 배경은 placeholder이고, 귀신 스프라이트도 아직 최종 그림이 아니다.

### 1.4 UI를 정하는 방식 — 네 층

UI 스타일은 아래층부터 위로 정한다. 위층은 아래층의 값을 입력으로 쓰기 때문이다.

| 층 | 정하는 것 | 상태 |
|---|---|---|
| 1층 | 무드 · 화면 맞춤 · 배경 밝기 띠 · 최소 글자 · 다국어 길이 확장 · 화면별 정보 위계 · 입력 방식 · 접근성 | 끝(2026-10-13). GPT 2차 검증 반대 0 |
| **2층** | **예산 → 폰트 → 팔레트 · 간격** | **이번 묶음** |
| 3층 | 형태 언어 · 컴포넌트 치수 · 상태 표 · UI 그림 제작 경로 | 2층 뒤 |
| 4층 | 아이콘 · 화면별 적용 · 모션 | 3층 뒤 |

- 검증은 층 단위로 한 묶음씩 넘긴다. 같은 층의 결정은 서로 기대서, 따로 보면 검증이 안 되기 때문이다(예: 폰트는 예산 없이 검증할 수 없다).
- 사양서 · 아트 정본에는 실측 · 코드로 확인된 값만 올린다. 확인 전의 계획값은 디자인 로드맵(기획 문서)에 둔다.
- **이 묶음이 다루지 않는 것:** 형태 · 치수 · 상태를 어떻게 그릴지(3층), 아이콘 · 모션(4층), 가짜 언어 탐침과 키보드 포커스 구현(별도 코드 작업).

### 1.5 작업 환경 제약

- 디자인 문서 작업에서는 코드를 고치지 않는다. 결정값을 `Theme.ts` 등에 넣는 일은 나중의 코드 작업이다.
- 그림 생성 API 키가 없다. 후보 그림이 필요하면 사용자가 ChatGPT 웹이나 Gemini에서 뽑고, AI는 HTML 비교판을 만들어 띄운다.
- 개발 PC: Ryzen 9600X / RTX 3070 Ti(상한 장비). 약한 기기 측정은 출시 대상 기기가 정해진 뒤에 한다.

## 3. 검증할 2층 결정 열세 개

2층 안의 순서는 **예산 → 폰트 → 팔레트 · 간격**이다. 예산이 폰트 후보를 거르고, 폰트가 글자 크기 단계를 정해야 간격을 잡을 수 있어서다. 결정마다 일곱 칸으로 적었다. 증거 수준은 근거가 어디서 왔는지(공식 문서 · 실측 · 코드 · 업계 경험칙 · 취향)다. 열세 개 모두 사용자가 2026-10-16에 동의했다.

결정값 중 실제 숫자(폰트 최종 하나, 색 hex, 글자 단계 값)는 아직 없다. 이 결정들은 **그 값을 어떤 규칙과 조건으로 정할지**다. 값은 다음 단계에서 HTML 비교판으로 사용자가 판정한다.

### 3.1 공통 — 확인할 화면

#### 3A 대표 화면 셋

- **결정문:** 2층 결정은 가장 나쁜 경우 셋에서 확인한다. 색 충돌은 레벨업 카드, 글자는 한국어 결과 화면, 예산은 적 200마리 전투 HUD. 이 셋에서 통과하면 나머지 화면은 따로 재지 않는다.
- **근거:** 레벨업 카드는 분류색 넷 · 티어 셋 · 강조색 · 포커스가 한 장에 겹친다. 결과 화면은 크기 단계가 넷으로 가장 많고 한글이 가장 많다. 적 200마리 HUD는 배경이 가장 어지럽고 프레임 부담이 가장 크다.
- **증거 수준:** 코드(화면 구성) + 1층 위계 표 + 업계 경험칙(최악 경우 검사).
- **버린 대안:** 결과 화면 하나로 다 보기 — 카드의 색 겹침과 전투 프레임 부담을 못 본다. 화면 다섯 전부 — 확실하지만 비교판 작업이 가장 크다.
- **틀릴 수 있는 지점:** 메뉴(타이틀)는 제목 폰트의 개성이 가장 크게 드러나는 화면인데 셋에 없다. 일시정지의 딤 위 글자도 따로 보지 않는다.
- **재검토 조건:** 셋에서 통과했는데 다른 화면에서 문제가 나오면 그 화면을 대표에 더한다.
- **검증 질문:** 이 셋이 「가장 나쁜 경우」라는 판단을 뒤집을 화면이 있는가?

### 3.2 예산

#### 4A 상한 먼저, 실측 나중

- **결정문:** 재기 전에 상한을 먼저 정하고(2a), 폰트 후보는 이 상한으로만 거른다. 대표 화면이 생긴 뒤 실제로 재서 상한을 지키는지 확인한다(2b). 잠정 상한은 폰트 전체의 첫 다운로드 1.5MB 이하, 한 굵기 파일 800KB 이하, 대표 화면에서 UI가 쓰는 프레임 시간 1ms 이하. UI 텍스처 상한은 3층이 그림 제작 경로를 정한 뒤에 둔다.
- **근거:** 원래 계획은 「대표 화면에서 잰다 → 폰트는 예산 안에서 고른다」였는데, 대표 화면은 폰트가 있어야 만들 수 있어 순서가 맞물렸다. 지금 빌드가 약 4.5MB라 폰트가 빌드를 두 배로 불리지 않게 잡았다. 1ms는 60fps 한 프레임(16.7ms)의 약 6%다.
- **증거 수준:** 코드(빌드 실측 4.5MB) + 업계 경험칙(숫자 셋은 계산으로 잡은 출발값, 실측 없음).
- **버린 대안:** 상한 없이 폰트를 먼저 고르고 나중에 재기만 — 큰 CJK 폰트를 막을 기준이 없다. 상한만 두고 실측 생략 — 정본(사양서)에 올릴 실측값이 없다.
- **틀릴 수 있는 지점:** 웹 게임의 첫 로드 체감은 용량보다 요청 수 · 압축 · 캐시에 더 좌우될 수 있다. Cocos가 TTF를 런타임에 그리는 방식(글자를 텍스처에 그리는 비용)이 프레임 시간에 얼마나 걸리는지 모른다.
- **재검토 조건:** 2b 실측이 상한을 넘거나 크게 밑돌면 상한을 고친다. itch 웹에서 첫 로드가 느리다는 플레이 피드백이 나오면 다시 연다.
- **검증 질문:** 1.5MB · 800KB · 1ms가 이 규모의 웹 게임에서 지나치게 느슨하거나 빡빡한가? 빠진 예산 항목이 있는가?

#### 5A 측정 조건

- **결정문:** 이 PC(Ryzen 5 9600X · RTX 3070 Ti)의 Chrome에서 캐시를 비운 첫 로드로 잰다. 용량은 기기와 상관없는 파일 크기라 이 조건으로 확정된다. 프레임 시간은 약한 기기에서 더 커질 수 있으므로, 약한 기기 측정 백로그(F139)에 폰트 · UI 몫도 함께 재도록 적는다.
- **근거:** 마법 이펙트 측정과 같은 장비라 숫자를 나란히 비교할 수 있다. 출시 대상 약한 기기는 아직 정하지 않았다.
- **증거 수준:** 실측 관행(이전 측정) + 업계 경험칙.
- **버린 대안:** Chrome + Firefox — 측정이 두 배. 약한 기기도 지금 — 기기부터 정해야 한다.
- **틀릴 수 있는 지점:** 상한 장비에서 1ms 안이어도 약한 노트북 내장 그래픽에서는 몇 배가 될 수 있다. Safari(Mac)는 측정 대상에 없다.
- **재검토 조건:** F139가 약한 기기를 정해 재고 UI 몫이 상한을 넘으면.
- **검증 질문:** 브라우저 하나 · 상한 장비 하나로 재는 것을 뒤집을 조건은?

### 3.3 폰트

#### 1A 번역 라벨 최소 16px

- **결정문:** 번역되는 라벨은 최소 16px이다. 14px는 숫자만 나오는 라벨(HP 숫자 등)에만 쓴다. 언어마다 크기를 바꾸는 코드는 두지 않는다. 화면 다섯 × 글자 단계 표를 만들어 요소마다 단계를 적는다.
- **근거:** Cocos Label은 라벨 하나에 글자 크기가 하나라, 번역 라벨에 14를 주면 한국어로 바꿨을 때 한글이 14가 되어 1층 최소(한글 16)를 어긴다.
- **증거 수준:** 공식 문서(Label 성질) + 1층 실측 판정.
- **버린 대안:** 언어 전환 때 코드가 크기를 바꾸기(영어 14 · 한글 16) — 코드 작업이 하나 더 생기고 레이아웃이 언어마다 달라진다. 폰트를 고른 뒤로 미루기 — 단계 표를 지금 시작할 수 없다.
- **틀릴 수 있는 지점:** 영어 화면이 필요 이상으로 커져 HUD 모서리 자리가 모자랄 수 있다. 확정 폰트가 16에서도 한글이 흐리면 최소가 더 올라간다.
- **재검토 조건:** 확정 폰트로 다시 판정할 때 16 한글이 안 읽히거나, 영어 16이 HUD 자리를 넘칠 때.
- **검증 질문:** 「번역 라벨 = 가장 큰 문자 체계의 최소」 규칙을 뒤집을 조건은? 일본어 · 중국어가 들어오면 이 규칙이 어떻게 바뀌어야 하는가?

#### 6A 고르는 기준 — 한 · 영 서브셋 + 짝 폰트 비교 열

- **결정문:** 출하 폰트는 한 · 영 글자만 남긴 서브셋으로 넣어 한 굵기 800KB 상한을 지킨다. 후보마다 「일 · 중을 같은 모양의 짝 폰트로 늘릴 수 있나」를 비교 열로 둔다. 후보 — 본문: Pretendard(일본어 짝 Pretendard JP), Noto Sans KR(Noto CJK 가족), Nanum Gothic(1층 최소 글자 판정에 쓴 폰트). 제목: 무드의 「우아한 판타지」에 맞는 세리프 하나, Noto Serif KR · 마루 부리 중에서. 후보 셋 · 넷을 HTML 비교판으로 둘로 줄이고, 최종 둘은 Cocos 에디터에서 실제 Label로 넣어 사용자가 고른다.
- **근거:** 한 · 영 · 일 · 중을 다 담은 파일은 한 굵기만 수 MB라 상한을 넘는다. 「미리 한 · 영으로 좁히지 않는다」는 로드맵 원칙은 비교 열로 지킨다. 출하 렌더는 Cocos라 HTML과 굵기 · 힌팅이 다를 수 있어 최종 판정은 Cocos에서 한다.
- **증거 수준:** 업계 경험칙(파일 크기) + 취향(제목 세리프). 라이선스와 짝 폰트 존재는 Claude가 알고 있는 내용이고 **아직 확인하지 않았다.**
- **버린 대안:** Noto CJK 한 가족으로 고정 — 나중에 바꿀 일이 없지만 모양 선택지가 좁다. 한 · 영만 보고 확장성은 안 봄 — 로드맵 원칙과 어긋난다.
- **틀릴 수 있는 지점:** 본문 · 제목 두 가족을 쓰면 두 파일이라 1.5MB 안에 드는지 실측 전이다. 세리프 제목이 작은 크기 · 어두운 배경에서 획이 흐려질 수 있다. 짝 폰트가 같은 가족 이름이어도 글자 높이 · 굵기 느낌이 다를 수 있다.
- **확인한 약관 조항과 확인일:** 없음 — 후보를 확정할 때 OFL 조항과 확인일을 라이선스 판정 표에 적는다.
- **재검토 조건:** 후보 중 라이선스가 상업 웹 임베드 · 서브셋을 막으면 뺀다. 두 가족이 1.5MB를 넘으면 한 가족으로 줄인다.
- **검증 질문:** 이 후보 목록에 빠진 유력 후보가 있는가? 다섯 후보의 라이선스 · 짝 폰트 · 고정 폭 숫자 지원에 대해 아는 것과 「확인 필요」를 나눠 달라.

#### 7A 서브셋에 남길 글자 — 한글 2,350자 + 기호

- **결정문:** 자주 쓰는 한글 2,350자(KS X 1001) + 영문 · 숫자 + 카탈로그가 쓰는 기호를 남긴다. 2,350자 밖의 글자가 문구에 들어오면 글리프 검사 스크립트가 잡는다. 기호 목록은 카탈로그의 화면 문자열에서 뽑는다.
- **근거:** 플레이어가 글자를 입력하는 자리가 없어 화면 글자는 전부 카탈로그에서 온다. 그래도 카탈로그 글자만 남기면 문구를 고칠 때마다 폰트를 다시 만들어야 한다. 2,350자면 한 굵기 수백 KB로 상한 안에 들 것으로 본다.
- **증거 수준:** 업계 경험칙(용량 추정, 실측 없음).
- **버린 대안:** 카탈로그 글자만 — 가장 작지만 빌드에 폰트 재생성 단계가 필요하다. 한글 11,172자 전부 — 한 굵기가 800KB를 넘을 가능성이 크다.
- **틀릴 수 있는 지점:** 2,350자에 없는 글자(예: 일부 귀신 이름 · 의성어)가 문구에 쓰일 수 있다. Cocos가 서브셋 TTF를 웹에서 어떻게 불러오는지(동적 폰트 아틀라스 크기 등) 확인 전이다.
- **재검토 조건:** 검사 스크립트가 빠진 글자를 반복해서 잡으면 카탈로그 기반으로 바꾼다. 실측 용량이 상한을 넘으면.
- **검증 질문:** 게임 UI 서브셋으로 2,350자가 적절한가, 아니면 더 나은 표준 목록이 있는가?

### 3.4 팔레트 — 의미색 표

#### 2A 상태 행 일곱

- **결정문:** hover · pressed · disabled에 더해 일곱 상태의 색을 표에 둔다 — 키보드 포커스, 선택된 카드, HP 위험 구간, 쿨다운 진행 중 / 준비 완료, 보상 · 새 항목, 패배 · 경고, 화면 뒤 딤. 2층은 색만 정하고, 테두리로 쓸지 채움으로 쓸지와 깜빡임 같은 쓰는 방식은 3 · 4층이 정한다. hover는 뜻을 싣지 않는 보조 상태로만 둔다.
- **근거:** 이 상태들은 1층이 이미 요구했다(포커스 「예」, HP 위험 구간 강조). 표에 없으면 3층이 상태 표를 만들 때 색을 지어내고, 지어낸 색이 예약색과 부딪힌다.
- **증거 수준:** 1층 결정 + 업계 경험칙.
- **버린 대안:** 지금 화면에 있는 것만(포커스 · 선택 · HP 위험 · 딤) — 쿨다운 · 보상이 생길 때 다시 검사한다. 하나도 안 넣기 — 3층에 미룬다.
- **틀릴 수 있는 지점:** 쿨다운 · 보상 표시는 아직 구현되지 않은 기능이라 색이 실제 쓰임과 어긋날 수 있다.
- **재검토 조건:** 3층 상태 표가 이 일곱 밖의 상태를 요구하면.
- **검증 질문:** 호드 액션 게임 UI에서 빠진 상태가 있는가?

#### 8A 분류색도 이 표에서 함께 (백로그 F141을 이 계획이 닫는다)

- **결정문:** 분류색 셋(화염 · 얼음 · 번개)과 support 색을 UI 색과 같은 표의 행으로 넣고 한 번에 정한다. §2.4의 불만 셋이 입력이다. 상태 이상 색 층도 이 표의 값을 따른다.
- **근거:** 따로 정하면 한쪽이 바뀔 때마다 다른 쪽의 충돌 검사를 다시 해야 한다.
- **증거 수준:** 업계 경험칙 + 사용자 판정(불만 셋).
- **버린 대안:** 분류색을 먼저 따로 정하고 UI가 피해 가기 — 분류색을 UI 색을 모른 채 고른다. 분류색은 지금 값으로 고정 — 불만 셋이 남고, 나중에 바뀌면 표를 다시 검사한다.
- **틀릴 수 있는 지점:** 분류색은 가산 블렌딩 이펙트에서 보이는 색이라, 평평한 UI 비교판에서 고른 값이 실제 이펙트에서 다르게 보일 수 있다.
- **재검토 조건:** 이펙트 생산 작업에서 실제 AI 그림 위에 얹었을 때 분류색이 안 읽히면.
- **검증 질문:** 분류색을 UI 비교판과 이펙트 실험 중 어디서 최종 판정해야 하는가?

#### 9A 충돌 판정 규칙

- **결정문:** 가. 같은 화면에 함께 뜨는 두 색은 정상 시야와 1 · 2 · 3형 색각 시뮬레이션(Machado 2009) 모두에서 OKLab 거리 0.15 이상이어야 한다. 나. 이를 못 지키면 위치나 모양이 다른 쌍만 허용한다(예: XP 바는 화면 맨 아래 전폭이라 위치로 갈린다). 다. 가와 나를 둘 다 못 지키면 분류색이 아니라 UI 색이 비켜 간다. 판정 결과는 쌍마다 표에 적는다.
- **근거:** 전투 중에는 마법을 읽는 일이 먼저다. 1층 분류 3색끼리는 0.22로 통과했지만, UI 쪽 골드 · 아이보리 · 노랑이 몰려 있어 0.22는 지키기 어렵다고 봤다.
- **증거 수준:** 1층 실측(색각 시뮬레이션) + 업계 경험칙(0.15라는 값 자체는 근거 있는 표준이 아니라 출발값).
- **버린 대안:** 0.22로 더 엄격하게 — 골드 · 아이보리 · 노랑이 다 떨어지기 어렵다. 쌍마다 사용자가 어느 쪽이 비켜 갈지 정하기 — 판정마다 판단이 필요하다.
- **틀릴 수 있는 지점:** OKLab 거리는 큰 면적 기준이라, 얇은 선 · 작은 아이콘에서는 같은 거리도 덜 구분된다. 가산 블렌딩 이펙트는 겹칠수록 밝아져 색이 흰색 쪽으로 몰린다.
- **재검토 조건:** 0.15를 지키는데도 사용자가 눈으로 헷갈린다고 판정하면 값을 올린다.
- **검증 질문:** 0.15와 「위치 · 모양 예외」 규칙을 뒤집을 조건은? 작은 요소에는 다른 값이 필요한가?

#### 10A 골드의 역할

- **결정문:** 샴페인 골드는 주 행동 버튼의 강조색 하나로만 쓴다. 테두리 · 문양 같은 장식은 채도 · 밝기를 낮춘 별도 행(빛바랜 골드)으로 두고, 이 행은 누를 수 있다는 뜻을 싣지 않는다. 두 골드가 0.15 이상 떨어지지 않으면 모양(채움 대 선)으로 가른다.
- **근거:** 강조색은 하나이고 주 행동 전용이라는 규칙이 있다. 골드가 강조와 장식을 다 맡으면 플레이어가 장식과 누를 버튼을 구분하지 못한다. 무드의 금빛 장식은 유지해야 한다.
- **증거 수준:** 업계 경험칙 + 취향(무드).
- **버린 대안:** 골드는 장식 전용, 강조는 다른 색 — 무드의 금빛이 버튼에서 빠진다. 골드 하나로 둘 다 — 규칙을 어긴다.
- **틀릴 수 있는 지점:** 골드는 화염과 2형 색각에서 0.08로 붙어 있다(1층 실측). 강조 골드를 화염에서 떼려면 무드보다 노랗거나 연해질 수 있다.
- **재검토 조건:** 강조 골드와 화염이 충돌 판정을 못 지켜 UI가 비켜 가야 하는데, 비켜 간 골드가 무드에서 벗어나면.
- **검증 질문:** 장식색과 강조색을 같은 색상 계열로 두는 것을 뒤집을 조건은?

#### 11A 표의 행 목록

- **결정문:** 약 25행. 바탕(화면 뒤 딤 · 패널 · HUD 글자 바탕) / 글자(기본 · 보조 · 비활성 — 바탕 둘 각각에서 대비를 잰다) / 강조(골드) · 장식(빛바랜 골드) / 상태(포커스 · 선택 · 위험 · 경고 · 쿨다운 진행 / 준비 · 보상 · 새 항목) / 게임 값(HP · XP) / 결과(승리 · 패배 · 티어 셋) / 분류색(화염 · 얼음 · 번개 · support). 행마다 이름 · 토큰명 · 역할 · 글자색인지 바탕색인지 · 값 · 쓰는 화면 · 상태 변형 · 색 말고 무엇으로 구분되는지 · 대비비 · 충돌 판정을 적는다.
- **근거:** 모두 앞의 결정과 1층에서 나온 행이고 새로 지어낸 행은 없다.
- **증거 수준:** 1층 결정 + 코드(지금 색).
- **버린 대안:** 지금 코드에 있는 색만 — 포커스 · 위험 · 보상을 나중에 더하고 다시 검사한다.
- **틀릴 수 있는 지점:** 25행은 한 화면 게임 UI로는 많아 보일 수 있다. 행이 많을수록 충돌 검사 쌍이 늘어난다(검사는 스크립트가 한다).
- **재검토 조건:** 3층에서 쓰이지 않는 행이 나오면 합친다.
- **검증 질문:** 합쳐도 되는 행, 빠진 행이 있는가?

#### 12A 값 형식 — hex 하나

- **결정문:** 표에는 hex 하나만 적는다(알파가 필요한 행은 8자리). 나중 코드 작업이 `Theme.ts`에서 그 hex 하나로 Cocos `Color` 객체와 리치 텍스트용 문자열을 둘 다 만들게 하고, 결과 화면의 티어색도 `Theme.ts`로 옮긴다.
- **근거:** 지금 색이 두 형식으로 두 파일에 흩어져 있다. 같은 색이 두 곳에 있으면 한쪽만 고쳐지기 쉽다.
- **증거 수준:** 코드.
- **버린 대안:** 표에 RGB와 hex를 다 적고 코드도 두 자리 — 두 값이 어긋날 수 있다.
- **틀릴 수 있는 지점:** 없음으로 본다.
- **재검토 조건:** Cocos 리치 텍스트가 8자리 hex(알파)를 받지 못하면 알파 행의 형식을 바꾼다.
- **검증 질문:** 이 결정을 뒤집을 조건이 있는가?

### 3.5 간격

#### 13A 4px 배수 + 누르는 영역 + 안전 영역

- **결정문:** 화면의 모든 여백과 간격은 4px의 배수로만 쓴다. 주로 8 · 16 · 24 · 32이고, 4는 작은 라벨 안쪽처럼 아주 좁은 자리에만. 누르는 영역 토큰(최소 32×32 논리 px)을 보이는 크기 토큰(예: 마법 슬롯 48)과 따로 둔다. HUD 모서리 간격은 「기본 여백 + 안전 영역」을 더한 값으로 두고, 안전 영역은 v1 PC에서 0이다(나중에 휴대폰 카메라 홈 같은 가려지는 자리만큼 값을 넣는다).
- **근거:** 지금 토큰 간격 8 · 모서리 여백 24가 이미 4의 배수다. 단위가 없으면 화면마다 여백이 제각각이 되고, 맞추려면 사용자가 에디터에서 노드를 다시 배치해야 한다.
- **증거 수준:** 코드 + 업계 경험칙.
- **버린 대안:** 8의 배수 — 값 종류가 적어 일관되지만 4를 못 쓴다. 3층으로 미루기 — 3층 치수가 기댈 단위가 없다.
- **틀릴 수 있는 지점:** 4px 단위는 촘촘해서 화면마다 쓰는 값이 늘어날 수 있다.
- **재검토 조건:** 3층 치수에서 4의 배수가 아닌 값이 반복해서 필요해지면.
- **검증 질문:** 이 결정을 뒤집을 조건이 있는가?

4. **무드와 접근성:** 「딥 네이비 + 샴페인 골드 + 아이보리 글자」 무드가 본문 대비 4.5:1, 충돌 거리 0.15와 부딪힐 자리가 어디인가?
5. **예산 숫자:** 4A의 상한 셋(1.5MB · 800KB · 1ms)에 대해 비슷한 규모의 웹 게임 사례나 근거를 알면 적어 달라. 모르면 「모른다」.
6. **폰트 후보:** 6A 후보 다섯의 라이선스(상업 이용 · 웹 임베드 · 서브셋 허용), 일본어 · 중국어 짝 폰트, 고정 폭 숫자(tabular figures) 지원을 아는 것과 「확인 필요」로 나눠 달라.
7. **Cocos 쪽 위험:** Cocos Creator 3.8 웹 빌드에서 TTF 폰트를 쓸 때 알려진 문제(없는 글자 처리, 동적 글자 아틀라스, 외곽선 렌더 비용)를 아는 것과 「확인 필요」로 나눠 달라.
8. **빠진 결정:** 2층에서 정해야 하는데 이 열세 개에 없는 결정이 있는가? 3층 · 4층 몫인 것은 빼고 답해 달라.

### 0. 결론 요약

13개 결정을 전부 폐기할 이유는 없다. 다만 **그대로 확정하기보다 6개를 조건부 동의로 고쳐 두는 편이 안전하다.**

가장 중요한 수정은 네 가지다.

1. **4A 예산은 숫자보다 측정 단위를 먼저 고정해야 한다.**  
   `폰트 전체 첫 다운로드 1.5MB`, `한 굵기 파일 800KB`가 소스 TTF 크기인지, 빌드 산출물의 실제 리소스 크기인지, HTTP 전송 크기인지 현재 문장만으로는 알 수 없다. 이 상태에서는 같은 파일을 재도 사람마다 다른 숫자를 얻을 수 있다.

2. **팔레트 작업은 폰트 확정을 기다릴 필요가 없지만, 텍스트 대비의 최종 합격은 폰트·크기 확정 뒤 다시 해야 한다.**  
   의미색, HP/XP/마법 분류색, 골드 역할은 병렬로 설계해도 된다. 다만 작은 글자의 실제 가독성은 글꼴 획, 크기, 외곽선과 결합되므로 최종 승격은 폰트 이후가 맞다.

3. **9A의 `OKLab 거리 0.15`는 표준 합격선이 아니라 휴리스틱이다.**  
   큰 색면의 1차 자동 필터로는 쓸 수 있지만, 작은 아이콘·얇은 선·가산 블렌딩 이펙트까지 보장하지 않는다. 작은 요소에는 색 거리와 무관하게 형태/위치/아이콘 중 하나를 의무 중복시키고, 화염·번개는 실제 가산 블렌딩 결과에서도 별도 확인해야 한다.

4. **7A의 KS X 1001 한글 2,350자는 “안전한 한국어 전체 집합”이 아니다.**  
   입력 글자가 없는 게임이라 운영은 가능하지만 귀신 이름·고유명사·의성어에서 빠진 음절이 생길 수 있다. 따라서 2,350자를 쓰더라도 “카탈로그 실제 글리프 ⊂ 서브셋” 자동 검사를 릴리스 게이트로 두는 것이 필수다.

## 1. 결정별 검증

### 3A 대표 화면 셋

**판정: 조건부 동의**

레벨업 카드, 한국어 결과 화면, 적 200마리 전투 HUD를 각각 색·타이포그래피·전투 복잡도의 최악 사례로 잡은 논리는 좋다. 전체 다섯 화면을 매번 검사하는 것보다 비용 대비 효율도 높다.

다만 이 셋이 모든 속성의 최악 사례라는 뜻으로 사용하면 안 된다. 현재 문서 자체가 메뉴 타이틀에서 제목 세리프의 개성이 가장 크게 보이고, 일시정지는 딤 위 글자라는 별도 조건이 있음을 인정하고 있다. 따라서 대표 셋은 **2층 기본 회귀 테스트**이고, 특정 속성에 더 나쁜 화면이 있으면 그 속성만 추가 샘플을 쓰는 구조가 적절하다.

**뒤집을 조건:** 메뉴나 일시정지에서만 발생하는 실패가 반복되어 대표 셋 검사가 실제 문제를 놓친다는 증거가 생기면 대표 화면을 4개 이상으로 늘린다.

**권장 수정 문장:**  
“대표 화면 셋은 2층의 기본 회귀 세트다. 다만 특정 결정의 최악 조건이 이 셋 밖에 명확히 있으면 해당 결정에 한해 보조 화면을 추가한다.”

### 4A 상한 먼저, 실측 나중

**판정: 조건부 동의**

“상한을 먼저 정해 후보를 거르고, 실제 대표 화면이 생기면 다시 측정한다”는 순서는 맞다. 폰트를 고른 뒤 예산을 만들면 예산이 통제 장치가 아니라 사후 설명이 되기 쉽다.

문제는 현재 `1.5MB / 800KB / 1ms`가 **측정 대상이 불완전하게 정의**되어 있다는 점이다. 특히 폰트는 원본 TTF 크기, Cocos 빌드 폴더의 리소스 크기, 서버 압축 전 크기, 실제 네트워크 transfer size가 다를 수 있다. “첫 다운로드 1.5MB”라면 네트워크 기준인지 빌드 리소스 기준인지 반드시 정해야 한다.

`1ms`도 출발값으로는 합리적이지만 “UI 전체 프레임 시간”을 무엇으로 분리해 잴지 정의가 필요하다. 적 200마리 전투에서 전체 프레임 중 UI만 정확히 귀속시키기 어렵다면 동일 장면에서 UI on/off 차이를 여러 프레임 샘플로 비교하는 식의 측정법이 필요하다.

**뒤집을 조건:** 후보 폰트를 실제 서브셋·빌드한 결과, 좋은 후보 대부분이 합리적 로딩 체감인데도 800KB를 넘거나, 반대로 훨씬 작은데 로드 병목이 요청/디코드/캐시에서 발생한다면 상한 구조를 다시 정한다.

**수정 권고:**
- `폰트 전체 첫 다운로드 1.5MB 이하` → **첫 진입에서 실제 네트워크로 추가 전송되는 폰트 리소스 합계**인지 명시.
- `한 굵기 파일 800KB 이하` → **배포 빌드에 포함되는 해당 폰트 asset 1개 크기**인지 명시.
- 원본 소스 파일 크기는 후보 필터 참고치로만 둔다.
- UI 1ms는 `적 200마리, 동일 장면, 일정 시간 구간, UI on/off 차이의 중앙값 또는 p95`처럼 측정법을 별도 정의한다.

### 5A 측정 조건

**판정: 동의**

현재 개발 PC 하나에서 2층 후보를 상대 비교하고, 약한 기기 검증은 F139에서 별도로 수행하는 분리는 현실적이다. 파일 크기는 하드웨어와 무관하다는 설명도 맞다.

다만 Chrome 한 브라우저 측정이 “웹 전체 성능 확정”을 의미해서는 안 된다. 현재 단계에서는 **후보 간 상대 비교와 상한 장비 기준의 회귀 측정**으로 한정하면 충분하다.

**뒤집을 조건:** 실제 배포 대상에서 브라우저별 렌더링/폰트 로딩 차이가 제품 문제로 확인되거나, F139의 약한 기기에서 UI 몫이 상한을 반복적으로 넘으면 측정 매트릭스를 확대한다.

### 1A 번역 라벨 최소 16px

**판정: 동의**

한 Label에 한 font size를 쓰고 언어 전환 시 크기를 바꾸지 않겠다면, 번역 라벨 최소값을 가장 까다로운 출하 문자 체계 기준으로 잡는 것이 일관적이다. 현재 출하 언어가 한국어·영어이고 1층에서 한글 16px를 최소로 판정했으므로 16px 규칙은 직접 연결된다.

일본어·중국어가 들어올 때도 원칙 자체는 유지할 수 있다. 다만 그때는 “가장 큰 문자 체계”라는 표현보다 **지원 언어 전부에서 실제 판독성 테스트를 통과하는 공통 최소값**으로 정의하는 것이 정확하다. 글자의 물리적 크기보다 폰트의 x-height, 획 밀도, 힌팅 차이가 영향을 주기 때문이다.

**뒤집을 조건:** 최종 폰트에서 한글 16px가 판독 기준을 못 넘거나, 영어 16px 때문에 실제 HUD가 상한 폭을 넘고 공통 크기 규칙으로 해결할 수 없을 때.

### 6A 고르는 기준 — 한·영 서브셋 + 짝 폰트 비교 열

**판정: 조건부 동의**

HTML에서 1차 축소하고 Cocos Label에서 최종 판정하는 2단계 방식은 좋다. 웹 브라우저 CSS 렌더와 실제 게임 엔진 렌더가 동일하다고 가정하지 않는 점도 맞다.

다만 “짝 폰트”를 단순히 같은 브랜드/가족이 있다는 뜻으로만 평가하면 부족하다. **한글 본문과 나중 일본어·중국어 폰트의 cap/x-height, 한자 크기, baseline, weight 체감, 숫자 폭**을 한 줄 샘플로 함께 봐야 한다.

또한 제목 폰트와 본문 폰트를 두 가족으로 쓰면 용량뿐 아니라 글리프 누락 검사·라이선스 파일·스타일 토큰 관리도 두 배가 된다. 제목 세리프가 실제 메뉴/결과 헤더에서 주는 가치가 작으면 한 가족 체계가 더 낫다.

**뒤집을 조건:** 두 가족 체계가 1.5MB 예산을 넘거나, 제목 세리프가 실제 Cocos의 작은/중간 크기에서 흐려져 본문 계열보다 명확한 이득이 없으면 한 가족으로 줄인다.

#### 후보별 외부 확인

##### Pretendard
- **확인됨:** 공식 배포 저장소는 웹폰트와 dynamic subset 사용법을 제공한다.
- **확인됨:** 배포 LICENSE는 SIL Open Font License 계열 조건을 포함하며 임베드·수정·재배포를 허용하는 조항을 갖는다.
- **확인됨:** Pretendard 계열에 일본어 확장판이 존재한다. 다만 현재 확인된 검색 결과는 원 Pretendard 저장소가 아니라 WEMIX Pretendard JP 계열이므로, 프로젝트가 말한 “Pretendard JP”의 정확한 정본/유지 주체는 후보 확정 때 다시 확인하는 편이 좋다.
- **중국어 짝:** 확인 필요.
- **tabular figures:** 확인 필요. 최종 TTF의 OpenType `tnum` 지원 여부를 fontTools 같은 도구로 직접 검사하는 것이 가장 확실하다.

##### Noto Sans KR
- **확인됨:** Noto CJK는 한국·일본·중국(간체·번체·홍콩) 지역별 배포를 제공한다.
- **확인됨:** Google Fonts/Noto CJK 계열은 OFL로 배포된다.
- **확인됨:** Noto Sans KR은 한글·한자 외에 히라가나·가타카나·라틴 등도 지원한다.
- **일·중 짝:** 강함. Noto Sans JP/SC/TC/HK가 같은 Noto CJK 계열에 있다.
- **tabular figures:** 확인 필요. “Noto Sans Mono가 존재한다”와 “Noto Sans KR 자체가 tnum을 제공한다”는 다른 사실이므로 실제 파일 검사 필요.

##### Nanum Gothic
- **확인됨:** Google Fonts 메타데이터에서 OFL이며 Korean/Latin subset이 등록되어 있다.
- **확인됨:** 웹폰트 및 dynamic subset 배포 사례가 있다.
- **일·중 짝:** 같은 디자인 계열의 공식 JP/SC/TC 확장 가족이 있다는 근거는 이번 확인에서 찾지 못했다. **확인 필요**이 아니라 실무상 “Noto 계열보다 확장성 열세”로 보는 편이 안전하다.
- **tabular figures:** 확인 필요.

##### Noto Serif KR
- **확인됨:** Noto Serif CJK 계열에는 중국어 간체 등 지역별 대응 가족이 있고 Noto 프로젝트의 OFL 계열이다.
- **일·중 짝:** 강함. Noto Serif JP/SC/TC 계열로 확장 가능.
- **tabular figures:** 확인 필요.

##### Maru Buri
- **확인됨:** 네이버 글꼴 사용 조건상 개인·기업 무료 사용, 상업 사용, 번들/재배포, 수정이 허용된다는 안내가 있다.
- **확인됨:** 웹폰트용 dynamic subset 배포 사례가 있다.
- **일·중 짝:** 같은 디자인 언어의 공식 JP/SC/TC 가족은 이번 확인에서 찾지 못했다. 확인 필요.
- **tabular figures:** 확인 필요.

#### 라이선스 판정 방식 권장

후보를 고를 때 “라이선스 이름”만 적지 말고 아래 네 칸을 실제 파일 기준으로 확인한다.

### 7A 서브셋에 남길 글자 — 한글 2,350자 + 기호

**판정: 조건부 동의**

플레이어 자유 입력이 없고 모든 UI 문구가 카탈로그에서 온다는 전제에서는 서브셋 전략 자체가 매우 적절하다. 또한 “실제 문자열만”으로 너무 공격적으로 줄이지 않고 여유 글자 집합을 두려는 목적도 이해된다.

하지만 KS X 1001의 한글 2,350자는 현대 한국어의 모든 완성형 음절을 포괄하지 않는다. 귀신 이름, 고유명사, 의성어·의태어처럼 일반 빈도와 다른 단어에서 누락이 생길 가능성이 있다.

따라서 이 결정은 **2,350자를 안전망이 아니라 기본 풀(pool)**로 정의해야 한다. 실제 릴리스의 진짜 보증은 “ko/en 카탈로그의 모든 코드포인트가 최종 subset에 존재한다”는 자동 검사다.

**뒤집을 조건:** 누락 글리프 검사가 카피 수정 때 반복해서 실패하거나, 자동 subset 재생성이 빌드에 안정적으로 들어가면 KS 2,350 고정 풀을 버리고 `카탈로그 글리프 + 고정 기호/여유 집합` 방식으로 전환한다.

**권장 규칙:**
- 기본: KS X 1001 2,350자 + ASCII/Latin + 카탈로그 기호.
- 필수 게이트: 실제 `ko.json`, `en.json`의 모든 문자가 subset에 포함되는지 검사.
- 누락 발견 시 글자를 수동 예외 목록에 누적하지 말고, 가능하면 subset 생성 입력에 카탈로그를 합친다.

### 2A 상태 행 일곱

**판정: 동의**

포커스·선택·HP 위험·쿨다운·보상/신규·패배/경고·딤을 미리 semantic token으로 잡는 것은 3층이 임의 색을 발명하는 것을 막는다. hover를 의미 전달의 필수 채널로 쓰지 않는 것도 1층 입력 방식과 일치한다.

현재 구현되지 않은 쿨다운/보상 색은 값이 아니라 “예약된 역할”만 정하는 단계이므로 2층에서 다뤄도 무리가 없다.

**뒤집을 조건:** 3층 상태 설계에서 두 상태가 실제로 동일한 의미와 동일한 시각 처리를 가져 독립 토큰이 불필요하다는 것이 확인될 때 합친다.

### 8A 분류색도 UI 표에서 함께

**판정: 동의**

화염·얼음·번개·support가 전투 이펙트, 상태 이상, UI와 같은 화면에서 동시에 보이므로 단일 의미색 레지스트리에서 충돌을 검사하는 것이 맞다. 별도로 정하면 한쪽 변경 때 다른 쪽 검사를 다시 해야 한다는 이유도 충분하다.

단, **값을 정하는 장소와 최종 시각 판정 장소는 분리**해야 한다. UI 비교판에서 후보를 좁히되, 분류색은 최종적으로 실제 가산 블렌딩 이펙트 위에서 확인해야 한다.

**뒤집을 조건:** 실제 이펙트 제작에서 평면 색과 가산 블렌딩 결과의 인상이 반복적으로 달라 UI 팔레트 값 하나로 두 용도를 유지하기 어려우면 “semantic hue는 공유, render용 출력값은 별도” 구조를 검토한다.

---

### 9A 충돌 판정 규칙

**판정: 조건부 동의**

정상 시야 + 1·2·3형 색각 시뮬레이션에서 자동 거리 검사를 하고, 실패 시 위치/모양 중복을 허용하는 구조는 좋다. 또한 전투 판독성을 우선해 분류색보다 UI 색이 비켜 간다는 우선순위도 프로젝트와 잘 맞는다.

그러나 `OKLab 거리 0.15`는 WCAG처럼 표준화된 접근성 합격선이 아니다. 큰 면적의 색면을 빠르게 거르는 **프로젝트 내부 휴리스틱**으로만 써야 한다.

특히 다음 두 경우에는 별도 규칙이 필요하다.

1. **작은 요소/얇은 선:** ΔE가 충분해도 시각 면적이 작으면 구분이 어렵다. 작은 아이콘, 1~2px 선, 작은 쿨다운 표시는 색 거리 통과 여부와 무관하게 형태·아이콘·위치 중 하나를 중복해야 한다.
2. **가산 블렌딩 이펙트:** 번개·화염은 겹치며 흰색 쪽으로 이동할 수 있으므로 원색 hex끼리의 거리만 재면 실제 화면을 보장하지 못한다. 실제 이펙트 또는 그에 가까운 합성 샘플에서 다시 검사해야 한다.

**뒤집을 조건:** 0.15를 통과한 쌍을 사용자가 반복해서 혼동하거나, 반대로 0.15 미만인데 형태/위치 중복으로 전혀 문제가 없다는 실사용 결과가 누적되면 수치 임계값을 조정한다.

**권장 추가 규칙:**
- `0.15`는 “자동 경고 임계값”으로 이름을 바꾼다.
- 작은 요소는 ΔE와 무관하게 비색상 단서를 필수로 둔다.
- 발광 분류색은 실제 합성 샘플에서 2차 판정한다.
- 1층의 0.22와 2층의 0.15는 서로 다른 목적임을 문서에 명시한다: 0.22는 분류 3색끼리, 0.15는 화면 내 일반 충돌 경고.

---

### 10A 골드의 역할

**판정: 동의**

샴페인 골드를 주 행동 강조 하나에 예약하고, 장식 골드를 별도 저채도/저휘도 토큰으로 나누는 것은 의미 체계를 명확히 만든다. 무드의 금빛 장식을 살리면서 “골드 = 눌러야 할 것”이라는 행동 의미가 장식에 번지는 것을 막을 수 있다.

같은 hue 계열을 쓰는 것 자체가 문제는 아니다. 역할은 색상각 하나가 아니라 면적, 채도, 밝기, 채움/선, 위치가 함께 만든다.

**뒤집을 조건:** 화염과의 색각 충돌을 피하기 위해 강조 골드를 이동시킨 결과가 더 이상 사용자가 원하는 샴페인 골드 무드로 보이지 않거나, 실제 화면에서 장식 골드가 계속 클릭 가능 요소처럼 읽힐 때.

---

### 11A 표의 행 목록

**판정: 동의**

약 25행은 많아 보이지만 현재 행들이 단순 장식 변형이 아니라 서로 다른 semantic role이라면 과도하다고 보기 어렵다. 특히 행마다 역할, 사용 화면, 비색상 구분 수단, 대비, 충돌 판정을 함께 적는 구조는 “색 값 목록”이 아니라 검증 가능한 토큰 사전이 된다.

중요한 것은 행 수 자체가 아니라 중복이다. 3층 실제 적용에서 같은 역할·같은 상태·같은 값으로만 쓰이는 행이 나오면 합치면 된다.

**뒤집을 조건:** 3층 적용 후 서로 다른 이름의 토큰들이 항상 같은 용도와 값을 가져 독립 변경 가능성이 없다는 것이 확인되면 통합한다.

---

### 12A 값 형식 — hex 하나

**판정: 조건부 동의**

색의 정본을 하나로 만들고 `Theme.ts`에서 Cocos Color와 문자열 표현을 파생시키는 방향은 좋다. 결과 화면의 티어색도 같은 정본으로 옮기는 것이 맞다.

다만 “hex 하나”는 **표현 형식의 단일화**이지 색 관리 방식의 전부는 아니다. 알파가 포함된 8자리 hex의 파싱 순서가 `#RRGGBBAA`인지 엔진/API마다 혼동될 수 있으므로 코드 변환기의 계약을 고정해야 한다. 또한 Cocos RichText가 프로젝트에서 쓰려는 8자리 alpha hex를 실제로 지원하는지는 최종 구현 때 확인해야 한다.

더 안전한 정본은 `#RRGGBB` + 별도 alpha 필드일 수 있지만, 현재 요구가 표를 단순화하는 것이라면 8자리 hex를 유지해도 된다.

**뒤집을 조건:** Cocos RichText 또는 현재 파서가 8자리 hex alpha를 동일하게 처리하지 못하거나, alpha만 상태별로 자주 달라져 같은 RGB를 여러 토큰에 복제하게 되면 RGB와 alpha를 분리한다.

---

### 13A 4px 배수 + 누르는 영역 + 안전 영역

**판정: 동의**

4px grid는 1280×720 논리 해상도에서 충분히 세밀하면서 8/16/24/32 중심의 리듬을 만들 수 있다. 기존 8px 간격과 24px 모서리 여백도 그대로 흡수된다.

보이는 크기와 hit target을 분리한 점이 특히 좋다. v1이 데스크톱이어도 이후 터치 입력을 막지 않는다. 안전 영역을 `기본 여백 + safe-area token`으로 둔 것도 확장성 있는 구조다.

**뒤집을 조건:** 3층 실제 컴포넌트에서 광학 보정 때문에 4px 배수가 아닌 값이 반복적으로 필요하고, 예외가 규칙보다 많아질 때 grid 단위를 재검토한다.

## 2. 전체 검증 질문 1~8

### 1. 순서 — 예산 → 폰트 → 팔레트 · 간격

**답: 큰 막힘은 없지만, “완전 직렬”로 볼 필요는 없다.**

권장 흐름은 다음과 같다.

`예산 정의 → 폰트 후보 필터`와 동시에 `팔레트 역할/충돌 구조 설계`를 진행할 수 있다. 팔레트의 HP/XP/마법 분류/골드/상태색 역할은 폰트 종류와 독립적이기 때문이다.

다만 **텍스트색의 최종값과 최종 대비 합격**은 폰트와 타입 스케일이 정해진 뒤 승격해야 한다. 같은 4.5:1이라도 작은 글자에서 실제 획이 얇거나 외곽선이 다르면 눈으로 읽히는 정도가 달라진다.

따라서 실제 순서는 아래가 더 정확하다.

`예산 단위 확정`
→ `폰트 후보 축소`
↘ `팔레트 semantic role/충돌 후보 병렬`
→ `폰트 최종 + 타입 스케일`
→ `텍스트색 대비 최종 판정`
→ `간격/토큰 확정`

간격 역시 4px grid 자체는 지금 정해도 되지만, 실제 컴포넌트 padding 값은 타입 스케일 이후가 맞다.

### 2. 1층 결정 여덟 중 2층에서 쓰지 않은 값

완전히 버려진 1층 값은 없다. 다만 연결 강도가 약한 항목이 있다.

- **L1-1 무드:** 6A 제목 폰트, 10A 골드, 팔레트 전반이 사용.
- **L1-2 화면 맞춤:** 13A 안전 영역/모서리와 연결되지만, 16:10~21:9에서의 폭 변화가 2층 검증 질문에 직접 드러나지 않는다. 폰트/간격 비교판에서 **최소 16:10과 최대 21:9 한 번씩** 확인하도록 연결하면 더 좋다.
- **L1-3 배경 띠:** 11A의 패널/HUD 글자 바탕 대비와 연결. 실제 hex 선택 때 반드시 배경 띠 상한/대표색 위에서 검사해야 한다.
- **L1-4 최소 글자:** 1A, 6A와 직접 연결.
- **L1-5 길이 확장:** 1A와 13A에 간접 연결되지만, 2층 타입 스케일/간격 비교판에서 +40% 가짜 문자열을 쓰는 검사는 별도 코드 작업으로 빠져 있다. “2층 값 선택 때는 구조만 고려하고 실행 검증은 별도 작업”이라는 연결 문장을 넣으면 충분하다.
- **L1-6 정보 위계:** 1A 타입 단계, 6A 폰트 역할과 연결.
- **L1-7 입력 방식:** 2A 포커스 상태, 13A hit target과 연결.
- **L1-8 접근성:** 9A, 11A 및 텍스트 대비에 직접 연결.

**추가 연결 권고:** L1-2와 L1-5를 2층 검증 체크리스트에 명시적으로 걸어 두면 추적성이 더 좋아진다.

### 3. 색각 겹침 넷이 9A·10A·11A로 전부 풀리는가

**아직 전부 풀리지는 않는다. 규칙은 거의 갖췄지만 실제 해소를 보장하는 한 단계가 빠졌다.**

#### 번개 ↔ XP
9A의 거리 검사 + “UI가 비켜 간다”로 원칙상 해결 가능하다. XP는 위치가 화면 하단 전폭이라는 강한 위치 단서도 있다.

그러나 번개 이펙트가 가산 블렌딩으로 밝아질 때 XP/아이보리와 더 가까워질 수 있으므로 **합성 후 색** 검사가 필요하다.

#### 화염 ↔ HP
9A로 처리 가능하지만 HP는 생존 의사결정의 최우선 정보이므로 단순 “모양이 다름” 예외보다 더 엄격하게 보는 편이 좋다. HP는 바의 위치와 형태가 고정되어 있어 구분될 가능성이 높지만, 위험 상태에서 화염과 동시에 번쩍이면 색만으로는 혼동될 수 있다.

권장: HP 위험 상태에는 색 외에 **바 패턴/아이콘/펄스가 아닌 고정 표식** 중 하나를 3층에서 의무화.

#### 화염 ↔ 골드(2형)
10A에서 UI 골드가 비켜 가도록 되어 있어 원칙상 해결 가능하다. 다만 골드는 무드 핵심이라 이동 폭이 제한된다. 실제 2형 시뮬레이션에서 강조 골드 후보를 화염과 함께 반드시 봐야 한다.

#### 번개·XP ↔ 아이보리(3형)
11A에 아이보리와 XP/번개가 모두 들어가고 9A 거리 검사 대상이므로 잡히긴 한다. 그러나 **글자 아이보리는 색면보다 훨씬 얇기 때문에** OKLab 거리만으로 판정하면 부족하다.

권장 추가 규칙:
> “텍스트·1~2px 선·작은 아이콘은 색 거리 통과 여부와 관계없이 자체 배경/외곽선/형태 중 하나로 분리한다.”

이 규칙을 넣으면 네 겹침을 모두 구조적으로 다룰 수 있다.

### 4. 무드와 접근성이 부딪힐 자리

가장 위험한 곳은 세 군데다.

1. **빛바랜 골드 장식 vs 어두운 네이비**  
   장식은 의미 전달 요소가 아니면 4.5:1 본문 기준을 만족할 필요가 없지만, 경계/조작 요소 역할을 맡는 순간 3:1 UI 대비 대상이 된다. 장식과 기능선을 분리해야 한다.

2. **보조 아이보리/회색 글자**  
   현재 `TEXT_SECONDARY (170,170,180)`이 1층에서 이미 부족 후보로 표시됐다. 어두운 패널에서는 통과할 수 있어도 HUD 자체 바탕/외곽선 조건에 따라 달라진다. “은은한 보조 글자”를 만들려다 4.5:1 아래로 내려가기 쉽다.

3. **샴페인 골드 vs 화염·번개 계열**  
   정상 시야에서는 고급스러운 골드가 잘 보이더라도 색각 시뮬레이션에서는 화염 또는 번개와 가까워질 수 있다. 무드를 지키려면 hue를 과도하게 바꾸기보다 **골드는 UI 채움, 마법은 발광/입자 형태**처럼 렌더 문법을 갈라야 한다.

딥 네이비 + 아이보리 자체는 높은 명암 대비를 만들기 쉬운 조합이다. 문제는 “고급스럽게 보이기 위해 너무 낮은 대비를 쓰는 보조색”에서 주로 생긴다.

---

### 5. 1.5MB · 800KB · 1ms의 근거

#### 1.5MB 전체 / 800KB 한 굵기

**비슷한 규모 웹 게임의 업계 표준 수치라는 근거는 찾지 못했다.** 따라서 현재 문서의 표현대로 프로젝트용 출발 상한으로 취급하는 것이 맞다.

다만 외부 사례로 Noto Sans KR의 서브셋 웹폰트를 만든 공개 프로젝트에서 Regular WOFF2 약 419KB, Bold WOFF2 약 434KB라는 예가 있다. 이 숫자는 **WOFF2 웹폰트**이고 프로젝트가 Cocos TTF asset으로 실제 배포하는 크기와 같지 않으므로 800KB TTF 상한의 직접 근거로 쓰면 안 된다.

현재 빌드가 약 4.5MB라는 프로젝트 내부 수치에 비추면 폰트가 1.5MB 추가될 경우 현재 크기의 약 1/3이 더해진다. 따라서 “빌드를 폰트가 지배하지 않게 하겠다”는 제품 예산으로는 의미가 있다.

#### 1ms UI 프레임 시간

60fps 16.7ms 중 약 6%라는 계산은 맞지만, **1ms가 웹 게임 UI의 보편적 표준이라는 근거는 없다.** 프로젝트 내부 예산이다.

따라서 문서에는 다음처럼 적는 것이 정확하다.

> “세 상한은 업계 표준이 아니라 현재 빌드 크기와 60fps 프레임 예산에서 정한 초기 프로젝트 예산이다. 2b 실측 뒤 보정한다.”

### 6. 폰트 후보 다섯 — 라이선스·짝 폰트·고정 폭 숫자

#### 중요한 판정

`tabular figures`는 이름이나 가족만 보고 추정하지 않는 것이 좋다. 후보 TTF를 받았을 때 OpenType GSUB/GPOS feature의 `tnum`을 기계적으로 검사하고, Cocos 실제 Label에서 `00:00`, `11:11`, `88:88` 폭이 같은지도 확인하면 된다.

또한 **타이머만 고정 폭이 필요하다면 폰트 전체를 탈락시키기보다 숫자 전용 fallback/스타일을 둘 가치**가 있다. 다만 이는 두 폰트 체계를 늘리는 비용과 비교해야 하므로 최종 후보가 `tnum`을 지원하지 않을 때만 검토하면 된다.

### 7. Cocos Creator 3.8 웹 + TTF 위험

#### 확인된 사항

1. **TTF Label은 outline을 지원한다.**  
   Cocos Creator 3.8.2부터 Label 자체에 outline 기능이 내장되었다.

2. **Label CacheMode는 NONE / BITMAP / CHAR가 있다.**

3. **CHAR 모드는 1024×1024 공유 글자 아틀라스를 사용한다.**  
   Cocos 3.8 API 문서에 명시되어 있다.

4. **CHAR 모드는 SHRINK를 지원하지 않는 제약이 있다.**  
   따라서 긴 번역 문구를 SHRINK로 처리할 가능성이 있는 라벨과 조합할 때 주의해야 한다.

5. **공식 API 문서에는 `cacheMode`가 system font만 지원한다고 적힌 부분과, 3.x 매뉴얼에는 system/TTF에 적용된다고 설명된 부분이 혼재한다.**  
   즉, 현재 프로젝트의 정확한 3.8.8 동작은 실제 에디터/빌드에서 확인하는 것이 안전하다.

6. **RichText는 여러 Label 노드로 조립되며 복잡한 RichText는 draw call 증가 가능성이 있다.**  
   Cocos 3.8 RichText 문서도 CacheMode를 제공하는 이유로 이를 설명한다.

#### 확인 필요

1. **없는 글리프 처리 방식**  
   최종 TTF subset에서 글리프가 빠졌을 때 3.8.8 웹 빌드가 tofu(□), fallback system font, 공백 중 무엇으로 보이는지 공식 문서 근거를 이번 조사에서 확정하지 못했다. 반드시 작은 실행 탐침으로 확인.

2. **TTF + CHAR의 3.8.8 실제 적용 여부와 제약**  
   문서 표현이 혼재하므로 실제 프로젝트 버전에서 확인.

3. **outline의 구체적 GPU/CPU 비용**  
   “outline 지원”은 확인되지만 폭 1/2/3이 실제 프레임 시간에 주는 비용의 공식 수치는 없다. 대표 화면에서 실측해야 한다.

4. **서브셋 TTF와 동적 글자 아틀라스의 메모리 관계**  
   파일 크기가 작아져도 렌더 시 생성되는 글리프 texture 비용이 같은 비율로 줄어든다고 볼 수 없다. 실제 사용 글자 수·크기·outline 조합이 더 중요할 수 있다.

#### 따라서 4A/5A에 추가할 실행 탐침

- 한글/영문/기호가 섞인 결과 화면
- 없는 글리프 1개를 의도적으로 넣은 문자열
- outline 없음 / 1단계 / 최종 후보 폭
- HUD 숫자가 계속 변하는 상황
- CacheMode 후보별 비교
- 같은 장면에서 UI on/off 프레임 차이

크게 빠진 축은 많지 않다. **새 결정으로 추가할 가치가 있는 것은 3개**다.

### 5.1 Cocos 공식 문서로 확인한 것 (Context7, Cocos Creator 3.8 매뉴얼, 2026-10-16)

GPT가 「문서 표현이 섞여 있다」고 한 부분을 매뉴얼로 확인했다.

- **Cache Mode는 시스템 폰트와 TTF 둘 다에 적용된다**(Label 속성 표). NONE · BITMAP · CHAR 셋이다.
- **CHAR 모드:** 같은 폰트 · 크기 · 색 · 외곽선의 글자를 전역 공유 비트맵 하나(1024×1024)에 캐시한다. 비트맵은 씬을 바꿀 때만 비워지고, **가득 차면 새로 나오는 글자는 그려지지 않는다.** 넘침 SHRINK를 지원하지 않고, 굵게 · 기울임 · 밑줄이 안 되며, 그림자(LabelShadow)도 적용되지 않는다.
- **BITMAP 모드:** 지금은 NONE과 같이 라벨마다 비트맵을 만들고, 동적 아틀라스에 들어가면 드로 콜이 합쳐진다. 자주 바뀌지 않는 글자용이다.
- **3.8.2부터** Label에 외곽선 · 그림자가 내장돼 있다.
- **없는 글자 처리:** 매뉴얼에 설명이 없다. 실행 탐침으로 확인해야 한다.

이 프로젝트에 걸리는 것: 한글은 글자 종류가 많고 크기 단계 · 외곽선 조합마다 캐시가 따로라, CHAR 모드를 쓰면 1024×1024가 차서 글자가 사라질 수 있다. 숫자처럼 글자 종류가 적고 자주 바뀌는 HUD 라벨에는 CHAR가 맞고, 한글 문장 라벨에는 맞지 않을 수 있다. 어느 라벨에 어느 모드를 쓸지는 탐침에서 정한다.
