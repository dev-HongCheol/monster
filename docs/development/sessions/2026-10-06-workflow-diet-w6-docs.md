## 1. 매번 출력되는 절차 문서의 글자 수를 늘리지 않는다

`pnpm wf`가 phase를 바꿀 때 출력하는 절차 문서 여섯 개의 글자 수 합계는 지금 13,575자다. `ClaudeMdSplit.test.ts`에 이 합계가 상한을 넘지 않는지 확인하는 테스트를 하나 더한다. 상한은 구현을 시작할 때의 합계로 둔다(지금 13,575자, PR #94가 먼저 머지되면 13,560자). 다시 말해 이 슬라이스는 절차 문서를 한 글자도 늘리지 않는다. 이 테스트로 F95를 닫는다.

이 상한은 이 슬라이스 뒤에도 지킨다. 나중에 상한을 넘겨야 하면, 같은 PR에서 줄일 수 있는 문장을 먼저 찾는다. 그래도 안 되면 그 슬라이스의 계획 문서에 이유를 적고 상한을 올린다. 이 규칙은 테스트의 상한 상수 위 주석에 적는다. 주석에 「넘기려면 계획 문서에 이유를 적고 이 값을 올린다」가 있어야, 테스트를 끈 채로 커밋하는 일을 막을 수 있다. 글자를 세는 방법도 같은 주석에 적는다. `String.prototype.length`(UTF-16 단위)로 세고, 줄 끝 CRLF는 LF로 바꾼 뒤 센다. 적어 두지 않으면 다른 장비에서는 11자 차이 때문에 「상한을 넘었다」고 나온다.

바꿀 문구를 실제로 써서 쟀다(2026-10-05). 합계가 11자 줄어든다. 그 뒤 리뷰에서 문구가 더해졌으므로(아래 표의 「(`/cso`를 해야 할 때만)」 세 곳, 판단 검사를 설명하는 구절, biome 예외 구절), 구현한 문구로 다시 재서 표의 값을 고친다. 더한 만큼 줄일 문장도 표에 적었다.

줄이는 두 사례 문장은 정본 본문에 날짜가 붙은 경위를 적어 둔 곳이다. 「정본 본문에는 지금의 내용만 적는다」는 규칙(2026-09-29)을 이번에 고치는 문서에 적용한 것이다. 그 규칙이 왜 있는지(어기면 무엇이 잘못되는지)는 한 문장으로 남긴다.

`workflow/README.md`는 phase가 바뀔 때 출력되지 않는 문서라 글자 수 상한에 포함되지 않는다. 두 곳을 고친다. 표의 `verification` 행을 「(`/cso`를 해야 할 때만 보안 점검) · 커밋 · 코드 리뷰 / `pass cso`·`pass review`」로 고치고, 「어느 검사를 언제 하는지는 `pnpm wf status`가 보여 주고, 규칙은 `.claude/lib/change-set.mjs`의 상수 위 주석에 적혀 있다」 한 줄을 더한다.

## 2. `CLAUDE.md`

바꿀 문자열을 실제로 써서 쟀다(2026-10-05). 아래 열 군데를 바꾸면 전체가 17자 줄어든다. 구현할 때 문구가 달라지면 다시 재서 합계가 늘지 않게 맞춘다. 지금 있는 테스트는 합계가 38,000자 이하인지만 보므로, 「늘지 않았다」는 것은 이 표를 구현한 문구로 다시 재서 손으로 확인한다.

`CLAUDE.md`에는 이미 「정본 선언 게이트」라는 말이 명령 표 여러 곳에 쓰이고 있다. 이 말을 이번에 다른 말로 바꾸면 고칠 곳이 아래 열 군데 밖으로 넓어지고 글자 수 표도 다시 짜야 하므로, 이번에는 그대로 둔다. 새로 쓰는 문구에만 위의 쉬운 말 규칙을 적용한다.

| 위치 | 바꾸는 내용 | 글자 수 변화 |
|---|---|---:|
| 명령 표 `start-verification` 행 | 「전체 스위트 GREEN 검증 후 전환」을 「통합 검사: biome·타입·전체 테스트 통과 후 전환」으로 바꾼다. 그 아래에 `verify` 행(「통합 검사만 다시 실행 (phase는 그대로)」)을 더한다 | +59 |
| 명령 표 `pass` 행 | `pass <cso\|review>`로 줄이고, 설명을 「판단 검사 통과 기록(`cso`는 해야 할 때만). 둘 다 통과하면 QA 확정 게이트 · 정본 선언 게이트 · 통합 검사를 거쳐 자동으로 `user-verification`」으로 바꾼다 | −31 |
| 명령 표 `skip-test` 행 아래 | `skip-qa "<사유>"` 행(「QA 문서 생략 (`game/**` 변경이 없는 동안만 유효)」)을 더한다 | +71 |
| 명령 표 `approve-pr` 행 | 괄호 안을 「변경 집합에 해당 파일이 있을 때만 에셋 `.meta` 게이트 · 타입체크 범위 게이트」로 바꾼다 | −5 |

## 3. 그 밖의 문서

- **`docs/development/troubleshooting/wf-tool-recovery.md`(새 문서).** 「`pnpm wf`가 고장 났을 때」 할 일을 적는다.
  - 첫째 방법: `workflow.mjs`와 훅은 phase와 상관없이 고칠 수 있다. 그러니 `wf start` 없이 git으로 브랜치를 만들어 고친다. 이 방법에서는 도구가 검사를 요구하지 않으므로 검사를 손으로 한다. 전체 테스트, 타입 검사, 바뀐 부분에 대한 `/cso`, 서브에이전트 코드 리뷰를 하고 PR 본문에 결과를 적는다.
  - 둘째 방법: 진행 중인 슬라이스를 급히 다음 phase로 넘겨야 하면, 고장 나기 전 커밋을 임시 작업 폴더로 꺼내고(`git worktree add <임시 폴더> <커밋>`) 그 안의 `workflow.mjs`를 `CLAUDE_PROJECT_DIR=<작업 폴더> node <임시 폴더>/.claude/workflow.mjs <명령>`으로 실행한다. 이 방법은 사람 확인창이 뜨지 않으므로 사용자가 직접 지시할 때만 쓴다고 적는다.
  - 둘째 방법 끝에 한 줄을 더한다: 「이 방법을 쓴 뒤에는 `git diff .claude/workflow-state.json`으로 바뀐 값을 눈으로 확인하고 커밋한다. 옛 도구가 새 값(`qa_skip_reason`·`cso_commit`)을 모른 채 지워 버린 경우를 여기서 잡는다」.
- **`docs/development/troubleshooting/typescript-version-pin.md`.** 표의 `pnpm wf pass ts`를 `pnpm wf verify`로, 「`approve-pr`이 그 범위를 거부한다」를 「게임 코드를 바꾼 슬라이스면 `approve-pr`이 그 범위를 거부한다」로 고친다.
- **`docs/development/troubleshooting/workflow-state-cross-machine.md`.** 「정책을 확정하면 ADR 004에 절을 추가한다」를 「`workflow/README.md`에 적는다」로 고친다. 상태 파일 충돌을 푸는 명령을 넣는다. 리베이스 중이면 `git checkout --theirs -- .claude/workflow-state.json`, 머지 중이면 `--ours`다. 푼 뒤에는 `pnpm wf status`로 슬라이스 이름과 phase가 지금 작업 중인 슬라이스의 것인지 확인한다. 반대쪽을 고르면, 진행 중인 슬라이스의 상태가 main에 있던 다른 슬라이스의 상태로 바뀐다(2026-09-30에 실제로 충돌을 겪었다).
- **`docs/development/spec/ops-skill-routing.md`.** `/cso` 행에 한 줄을 더한다. 바뀐 부분만 보는 정확한 옵션(`/cso --diff --base <커밋>`)과, gstack이 고장 났을 때 대신 쓸 방법(Claude Code의 `security-review`는 브랜치에서 아직 main에 들어가지 않은 변경을 본다)이다.
- **`docs/development/spec/docs-references.md`.** §12 표의 `wf check-links` 두 행은 검사기가 어디 있는지를 말하는 것이라 고치지 않는다.
