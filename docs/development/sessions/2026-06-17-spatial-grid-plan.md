## 배경 / 목적

지금 게임은 동시에 등장하는 적이 100마리쯤을 넘어가면 프레임이 흔들리고, 300마리 이상에서는 깨진다. 목표 장르(뱀파이어 서바이버즈류)는 화면에 적이 우글거리는 것이 핵심 재미라, "수백~1000마리가 나와도 60fps를 유지"하는 것이 사용자가 명시한 우선순위다.

근본 원인은 충돌 검사가 **전수 비교(all-pairs)** 구조라는 데 있다. 발사체 하나가 "내가 누구와 부딪혔나"를 확인할 때마다 화면의 모든 적을 하나하나 검사한다. 발사체 `p`개, 적 `n`마리면 매 프레임 `p×n`번 거리 계산이 돈다. `Projectile.ts`의 충돌 검사가 그 전형이다.

```ts
// Projectile.ts:88 — 매 프레임, 발사체마다 적 배열을 통째 복사하고 전수 스캔
for (const enemy of [...GameManager.instance.enemies]) {
  const dist = Vec3.distance(pos, enemy.node.position);  // sqrt까지 매번
  if (dist < this._radius + enemy.collisionRadius) { ... }
}
```

이 한 줄에 백로그가 지목한 1·2순위 병목이 같이 들어 있다. 매 프레임 발사체마다 일어나는 **배열 복사(할당/GC 압박)** 와 **O(p×n) 전수 스캔**이다.

이 슬라이스(S1)는 그중 알고리즘 병목을 **공간 그리드(spatial grid)** 로 푼다. 월드 공간을 균일한 크기의 격자 칸으로 나누고 적을 칸에 등록해 두면, 발사체는 자기 주변 칸만 보면 되므로 멀리 있는 적 전부를 검사할 필요가 없어진다. 충돌 질의가 `O(p×n)`에서 평균 `O(p+n)`에 가까워진다.

> **전제: 맵은 화면보다 훨씬 크다.** 최종 게임의 맵은 카메라 화면보다 큰 영역이고, 반면 마법·발사체가 한 번에 영향을 주는 범위는 최대가 화면 크기쯤(또는 조금 더)으로 제한된다. 이 비대칭이 그리드 설계의 핵심 제약이라, 아래 「그리드 구조」에서 맵 크기에 의존하지 않는 방식으로 잡는다.

## 스코프 — 이 슬라이스가 하는 일 (S1)

1. **신규 `game/assets/scripts/logic/SpatialGrid.ts`** — Cocos에 의존하지 않는 순수 모듈. 균일한 셀 크기의 **희소 해시 격자**(점유된 칸만 보관)에 좌표를 등록(`insert`)하고 한 점 주변 반경 안의 후보를 돌려주는(`queryRadius`) 자료구조다. 셀 크기는 생성 시 주입한다. `tests/logic/SpatialGrid.test.ts`로 먼저 검증한다(RED → GREEN).
2. **`GameManager`가 그리드를 보유·관리** — 적 레지스트리(`_enemies`)를 이미 GameManager가 들고 있으므로, 그리드도 여기서 적 위치로부터 매 프레임 다시 채운다(아래 「설계 결정」 참조).
3. **`Projectile._checkEnemyHit` 충돌을 그리드 질의로 전환** — `[...enemies]` 복사·전수 스캔을 그리드 반경 질의로 바꾼다. 후보에 대해서만 정밀 거리 검사를 한다. `Vec3.distance`(sqrt)를 제곱거리 비교로 바꿔 sqrt를 없앤다.
4. **`Projectile._detonate` 폭발 후보 구성도 그리드 질의로** — 이미 `selectExplosionHits`가 후보 목록을 인자로 받는 "그리드-레디" 형태라(주석 §그리드-레디 G1), 전체 적 순회 대신 그리드 반경 질의 결과를 넘긴다. 폭발 판정 로직 자체(`ExplosionLogic`)는 건드리지 않는다.

### 닫는 백로그 항목

- **G1(부분)** — 공간 그리드 도입 + 충돌 핫패스의 배열 복사·sqrt 제거. G1의 나머지((c) 잔여 할당 위생, (e) 풀 한도, (a) 캡 제거)는 S2·S3로 분리.

## 이미 있는 것 (재사용)

- **`GameManager._enemies`** — 적 레지스트리. 그리드를 매 프레임 다시 채울 원본이다.
- **`EnemyController.spawnId`(개체 식별자)·`collisionRadius`** — 그리드 항목 식별과 정밀 충돌 검사에 그대로 쓴다.
- **`selectExplosionHits`(`ExplosionLogic`)** — 후보 목록을 받는 그리드-레디 인터페이스. 폭발 경로는 후보 구성만 바꾸면 된다.
- **`logic/` 순수 모듈 패턴** — `ObjectPoolLogic`·`SpellPatternLogic` 등과 같은 자리에 `SpatialGrid.ts`를 두고 vitest로 검증한다(ADR 002).

## 설계 / 아키텍처

```
EnemyController.update  ── 적이 매 프레임 자기 위치를 옮김
        │
        ▼
GameManager  ──보유──▶  SpatialGrid (순수 모듈)
        ▲                    │  rebuild(enemies): 매 프레임 1회, 적 위치로 다시 채움
        │ enemies            │  queryRadius(x, y, r): 주변 칸의 후보 spawnId/적 반환
        │                    │
Projectile.update ──질의──────┘
  _checkEnemyHit : 후보에 대해서만 정밀 제곱거리 검사
  _detonate      : 후보를 selectExplosionHits에 전달
```

### 그리드 구조 — 맵 크기에 의존하지 않게 (희소 해시 격자)

맵은 카메라 화면보다 훨씬 크다. 그래서 그리드를 **화면이나 맵 전체 크기에 맞춘 고정 2차원 배열**로 만들면 안 된다 — 빈 칸이 대부분이라 메모리와 재구축이 낭비되고, 맵을 키우면 비용이 따라 커진다. 대신 **희소 해시 격자**로 둔다. 점유된 칸만 `Map<셀키, 항목들>`에 담고, 셀키는 월드 좌표를 셀 크기로 내림나눗셈한 `(floor(x/c), floor(y/c))`로 만든다. 이렇게 하면

- 격자에 **고정 범위가 없다.** 큰 좌표도, 중앙 원점 좌표계의 음수 좌표도 그대로 들어가고, 맵을 아무리 키워도 구조가 같다.
- 메모리·재구축 비용이 맵 면적이 아니라 **살아 있는 적 수 `n`에 비례**한다(재구축 O(n)).
- **질의 비용이 맵 크기와 무관하다.** 이게 핵심이다. 마법·발사체의 질의 반경은 최대가 화면 크기쯤으로 유계라, 질의는 그 반경과 겹치는 한정된 칸만 훑는다. 맵이 10배 커져도 한 질의가 보는 칸 수는 그대로다.

정리하면 "맵은 크지만 한 번에 영향을 주는 범위는 화면 안팎으로 제한된다"는 이 게임의 특성이 곧 그리드가 큰 맵에서도 싸게 도는 이유다.

> 멀리 떨어진 적을 아예 갱신·스폰하지 않는 **컬링**은 그리드와 별개 문제로, 스폰·난이도 슬라이스(S3)에서 다룬다. 그리드 자체는 등록된 적이 몇 마리든 그 수에 선형이라 컬링이 없어도 정확히 동작한다.

### 핵심 결정 — 그리드를 언제 다시 채우나 (재구축 타이밍)

문제: 적은 `EnemyController.update`에서 움직이고, 발사체는 `Projectile.update`에서 충돌을 본다. 그런데 **이 프로젝트의 어떤 컴포넌트에도 `@executionOrder`가 없어** Cocos가 `update`를 부르는 순서가 보장되지 않는다. 그리드를 "GameManager.update에서 채운다"처럼 특정 순서에 의존하게 만들면, 적 이동과 발사체 질의 사이 어디에 끼는지에 따라 결과가 흔들린다.

채택: **프레임 단위 지연 재구축.** 그리드가 "마지막으로 채워진 프레임 번호"를 기억하고, 질의가 들어왔을 때 현재 프레임(`director.getTotalFrames()`)과 다르면 그 자리에서 적 레지스트리로부터 다시 채운다. 그러면

- 어느 컴포넌트가 먼저 질의하든, 그 프레임의 첫 질의에서 한 번만 재구축된다(프레임당 O(n) 1회). 업데이트 순서에 의존하지 않는다.
- 한 프레임 안에서 적 위치가 "한 프레임만큼" 낡을 수 있지만, 그리드는 **후보(broad phase)** 만 고르고 발사체가 후보에 대해 **현재 위치로 정밀 검사**를 다시 하므로 명중 판정 자체는 정확하다.
- 그 "한 프레임 낡음"이 후보 누락으로 이어지지 않도록 **셀 크기를 적의 프레임당 이동량보다 충분히 크게** 잡는다(아래). 적 속도와 dt가 작아 프레임당 이동량은 셀 크기보다 훨씬 작다.

### 셀 크기

고정 튜너블 상수로 둔다. 질의 반경(발사체 반경+적 반경, 그리고 강화로 커질 수 있는 폭발 반경)을 한두 칸 안에서 덮을 수 있는 크기를 기본값으로 잡는다(시작값 ~128px 안팎, 추후 프로파일링으로 조정). 너무 작으면 질의가 많은 칸을 훑고, 너무 크면 칸당 적이 많아져 그리드 이점이 준다. S1에서는 안전한 중간값으로 시작하고 밸런싱은 후속 과제로 남긴다.

### 동작 동일성(parity) 보장

그리드는 후보의 **상위집합**을 돌려주고 정밀 검사는 종전과 같은 거리 비교다. 따라서 그리드 도입 전후로 명중 결과가 같아야 한다. 이 불변식을 테스트로 못박는다(아래 테스트 계획의 parity 항목).

## 구현 대안 (검토함)

| 대안 | 요지 | 채택 여부 |
|------|------|-----------|
| **A. 프레임 단위 지연 재구축 + 균일 격자** | 위 설계. 순서 비의존, 단순, 프레임당 O(n) 1회 재구축. | **채택** |
| B. `@executionOrder`로 GameManager를 먼저 돌려 거기서 재구축 | 특정 순서를 강제. 그래도 적은 자기 update에서 움직이므로 "먼저"가 곧 "낡은 위치로 빌드"가 되어 더 나쁘다. 순서 가정이 깨지기 쉽다. | 기각 |
| C. 적 이동 시 칸을 증분 갱신(incremental) | 항목마다 현재 칸을 추적해 이동 때 옮긴다. 재구축 비용은 줄지만 상태·복잡도가 늘고, 프레임당 O(n) 재구축이 병목으로 보이기 전에는 과한 최적화다. | 후속(필요 시) |

대안 C는 프로파일링에서 재구축이 실제 병목으로 드러나면 그때 도입한다. S1은 "단순하고 정확하게 큰 알고리즘 이득"을 먼저 확보한다.

## 테스트 계획

### 자동 테스트 (`tests/logic/SpatialGrid.test.ts`, 순수 모듈)

코드 경로별로 다음을 덮는다.

| # | 검사 | 의도 |
|---|------|------|
| T1 | 한 칸 안 점들 `insert` 후 그 칸 반경 질의 → 모두 반환 | 기본 등록·조회 |
| T2 | 질의 반경이 **여러 칸에 걸칠 때** 경계 너머 항목도 반환 | 셀 경계 누락 방지(최대 위험) |
| T3 | 반경 밖 항목은 반환하지 않음(또는 후보에 섞여도 정밀검사 통과 못 함을 별도 검증) | 상위집합이되 과하지 않음 |
| T4 | 빈 그리드 질의 → 빈 결과 | 적 0마리 경계 |
| T5 | 음수 좌표·원점 인근 | 좌표계(중앙 원점) 경계 |
| T6 | **parity:** 무작위 위치 N개에 대해 `queryRadius` 결과가 전수 비교(brute force) 반경 내 집합을 **빠짐없이 포함** | 그리드 도입 전후 명중 동일성 |
| T7 | `rebuild` 후 위치가 바뀌면 질의가 새 위치 기준으로 동작 | 프레임 재구축 정확성 |
| T8 | 멀리 떨어진 두 군집(큰 좌표 차)에서 한쪽 질의가 반대쪽 항목을 반환하지 않고, 질의가 보는 칸 수가 군집 거리와 무관 | 희소 해시 격자 — 맵 크기 비의존 |

### 수동 테스트 (QA 문서에 상세화)

- 인스펙터에서 `maxEnemies`를 크게 올려(비커밋) 수백 마리 스트레스. **명중 누락이 없는지**(특히 빠르게 움직이는 적, 화면 가장자리), 프레임이 유지되는지 확인.
- 폭발 마법(파이어볼)으로 군집을 때렸을 때 중복 제거(같은 시전이 한 적을 1회만)·범위 동작이 종전과 동일한지.

> 자세한 씬/에디터 체크리스트와 회귀 범위는 3단계에서 `docs/qa/spatial-grid-test.md`로 작성한다.
