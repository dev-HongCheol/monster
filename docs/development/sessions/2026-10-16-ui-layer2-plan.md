## 1. 결정 넷

**진행 순서(GPT 2차 반영).** 예산 단위 확정 → 폰트 후보 축소와 팔레트 역할 · 충돌 설계를 함께 → 폰트 최종 + 글자 단계 → 글자색 대비 최종 판정 → 간격 · 토큰 확정. 팔레트의 역할(HP · XP · 분류색 · 골드 · 상태)은 폰트와 상관없어 같이 설계할 수 있지만, 작은 글자가 실제로 읽히는지는 폰트 획 · 크기 · 외곽선에 달려 있어 글자색 대비의 최종 판정은 폰트 뒤에 한다. 4px 단위는 지금 정하고 실제 안쪽 여백 값은 글자 단계 뒤에 정한다.

**1층과의 연결.** 폰트 · 간격 비교판은 보장 비율 끝 두 곳(16:10 · 21:9)에서 한 번씩 본다(L1-2). 가짜 언어 +40% 실행 검사는 F132로 빠져 있고, 2층 값은 그 구조(늘어나는 컨테이너)를 전제로 고른다(L1-5).

**대표 화면(결정 3A, 2026-10-16).** 2층 결정은 가장 나쁜 경우 셋에서 확인한다. 가장 나쁜 화면에서 통과하면 나머지 화면은 따로 재지 않는다. 이 셋은 2층의 기본 확인 세트이고, 어떤 결정의 최악 조건이 셋 밖에 분명히 있으면 그 결정에만 보조 화면을 더한다 — 제목 폰트는 메뉴 타이틀, 딤 위 글자는 일시정지.

| 확인할 것 | 대표 화면 | 가장 나쁜 이유 |
|---|---|---|
| 색 충돌 | 레벨업 카드 | 분류색 넷 · 티어 셋 · 강조색 · 포커스가 한 장에 겹친다 |
| 글자 | 결과 화면, 한국어 | 크기 단계가 넷으로 가장 많고(L1-6) 한글이 가장 많다 |
| 예산 | 적 200마리 전투 HUD | 배경이 가장 어지럽고 프레임 부담이 가장 크다(사양서 §8.1의 최악 화면) |

### 1.1 UI 성능 · 용량 예산

- **산출물:** 실측 항목 넷 — 폰트 파일 용량, UI와 폰트의 초기 다운로드 용량, 대표 화면에서 UI가 쓰는 프레임 시간, UI 텍스처(아틀라스) 총 용량. 드로 콜은 관찰값으로만 적는다.
- **정하는 방법:** 대표 화면에서 잰다. 값이 재어지면 사양서 §8에 절을 만든다(로드맵 §7).
- **두 단계(결정 4A, 2026-10-16):** 예산을 대표 화면에서 재려면 폰트가 있어야 하고, 폰트는 예산 안에서 골라야 해서 순서가 맞물린다. 그래서 재기 전에 상한을 먼저 정하고(2a), 폰트 후보는 이 상한으로만 거른다. 대표 화면이 생긴 뒤 실제로 재서 상한을 지키는지 확인한다(2b). 실측이 상한과 어긋나면 상한을 고치거나 후보를 다시 고른다.
- **잠정 상한(2a):** 폰트 전체의 첫 다운로드 1.5MB 이하, 한 굵기 파일 800KB 이하, 대표 화면에서 UI가 쓰는 프레임 시간 1ms 이하. 기준은 지금 웹 빌드 약 4.5MB(엔진 3.0 + 에셋 1.5, ops-build §6.1)다 — 폰트가 빌드를 두 배로 불리지 않게 잡은 출발값이고 실측 전까지 잠정이다. UI 텍스처 총 용량 상한은 3층이 그림 제작 경로를 정한 뒤에 둔다. 세 상한은 업계 표준이 아니라 지금 빌드 크기와 60fps 프레임 예산에서 정한 출발값이다.
- **무엇을 재나(2026-10-16 사용자 결정, GPT 2차 지적):** 800KB는 빌드 폴더에 들어간 폰트 파일 하나의 크기다. 1.5MB는 게임을 처음 열 때 네트워크로 받는 폰트 합계이고, 브라우저 개발자 도구의 전송 크기로 잰다. 1ms는 적 200마리 같은 장면에서 UI를 켰을 때와 껐을 때 프레임 시간 차이의 중앙값이다. 원본 폰트 파일 크기는 후보를 거를 때 참고로만 본다. 같은 파일을 재도 원본 · 빌드 · 전송 크기가 달라서 대상을 못 박았다. UI를 끄는 시험용 스위치는 코드 작업이다.
- **렌더링 측정(2026-10-16 사용자 결정):** UI 켬 / 끔 차이는 중앙값과 함께 상위 5%(느린 프레임 쪽)도 잰다. TTF 라벨은 글자가 바뀔 때마다 글자 그림을 새로 만들어 순간 끊김이 생길 수 있는데, 중앙값은 이를 가린다. 상위 5% 상한은 실측 전까지 비우고 기록만 한다. 폰트를 처음 쓸 때 멈추는 시간(게임 첫 화면 · 결과 화면이 처음 뜰 때)도 기록한다.
- **측정 조건(결정 5A, 2026-10-16):** 이 PC(상한 장비)의 Chrome에서 캐시를 비운 첫 로드로 잰다. 마법 이펙트 게이트(사양서 §8.4)와 같은 장비라 숫자를 나란히 비교할 수 있다. 용량은 기기와 상관없는 파일 크기라 이 조건으로 확정된다. 프레임 시간은 약한 기기에서 더 커질 수 있으므로, 백로그 F139에 폰트 · UI 몫도 함께 재도록 한 줄을 더한다.
- **대표 화면:** 적 200마리 전투 HUD(§1 머리 표)

### 1.2 폰트 체계

- **산출물:** 가족 · 굵기 · 역할(본문 · 제목 · 숫자), 타입 스케일(단계 수 · 비율 · 줄 높이 · 굵기), 폴백 정책.
- **정하는 방법:** 후보 3~4개를 HTML 비교판으로 둘로 줄이고, 최종 둘은 Cocos 에디터에서 실제 Label로 넣어 사용자가 고른다(로드맵 §5.4).
- **가장 작은 단계(결정 1A, 2026-10-16):** 번역되는 라벨은 최소 16px이다. 14px는 숫자만 나오는 라벨(HP 숫자 등)에만 쓴다. Cocos Label은 라벨 하나에 글자 크기가 하나라, 번역 라벨에 14를 주면 한국어로 바꿨을 때 한글이 14가 되어 L1-4(한글 16)를 어기기 때문이다. 언어마다 크기를 바꾸는 코드는 두지 않는다.
- **화면 × 단계 표:** 화면 다섯(HUD · 레벨업 카드 · 일시정지 · 결과 · 메뉴)의 글자 요소마다 어느 단계를 쓰는지 적는다. 단계 수는 L1-6 표를 따른다(HUD 3 · 카드 3 · 일시정지 2 · 결과 4 · 메뉴 2). 단계 값과 비율은 폰트를 고른 뒤 비교판에서 정한다 — 미정
- **고르는 기준(결정 6A, 2026-10-16):** 출하 폰트는 한 · 영 글자만 남긴 서브셋으로 넣어 한 굵기 800KB 상한(§1.1)을 지킨다. 한 · 영 · 일 · 중을 다 담은 파일은 한 굵기만 수 MB라 상한을 넘기 때문이다. 대신 후보마다 「일 · 중을 같은 모양의 짝 폰트로 늘릴 수 있나」를 비교 열로 두어, 묶음 3(로드맵 §5.1)을 넣을 때 폰트를 통째로 바꾸지 않아도 되는지를 고를 때 본다. 짝 폰트는 가족 이름이 같은지가 아니라 한 줄 샘플로 비교한다 — 글자 높이 · 기준선 · 굵기 느낌 · 한자 크기 · 숫자 폭(GPT 2차).
- **라이선스 확인 칸:** 이름이 아니라 실제 LICENSE 파일로 넷을 본다 — 상업 게임에 포함, 웹 빌드에 파일 임베드 · 재배포, 서브셋 수정본 생성, 수정본 이름 제한(Reserved Font Name)과 고지 의무. 최종 서브셋 파일 이름을 정할 때 라이선스 문구를 함께 보관한다.
- **고정 폭 숫자:** 이름으로 짐작하지 않는다. 폰트 파일의 `tnum` 기능을 도구로 검사하고, Cocos Label에서 `00:00` · `11:11` · `88:88` 폭이 같은지 본다. 최종 후보에 `tnum`이 없을 때만 타이머 숫자 전용 폰트를 검토한다.
- **비교판 첫 관찰(2026-10-27, `tools/ui/font-board.html`, 브라우저가 받은 웹 폰트 기준):**
  - 숫자 폭 — 기본 숫자가 고정 폭인 것은 Noto Sans KR · Nanum Gothic이다. Pretendard · Noto Serif KR · 마루 부리는 기본 숫자가 비례 폭이라 `11:11`이 `00:00`보다 좁다. `tnum`을 켜면 Pretendard · 마루 부리는 고정 폭이 되고, Noto Serif KR은 웹 판에서 바뀌지 않았다. 웹의 Cocos TTF 라벨은 캔버스에 글자를 그려 `tnum`을 켤 수 없을 가능성이 커서, 그렇다면 Pretendard 타이머는 숫자가 바뀔 때마다 폭이 흔들린다 — Cocos 탐침(§6 다)에서 확인한다. 웹 폰트 파일은 배포 TTF와 기능이 다를 수 있어 최종 판단은 배포 TTF로 한다.
  - 수정본 이름 제한 — LICENSE 머리에 Reserved Font Name이 있는 후보: Pretendard(「Pretendard」), Nanum Gothic(「Nanum」 · 「NanumGothic」 등), Noto Sans KR(「Source」). Noto Serif KR의 LICENSE 머리에는 없다. OFL FAQ 2.6(2026-10-27 확인)은 웹 폰트를 서브셋하는 것을 수정으로 본다. 수정 자체는 허용되지만, 수정본은 보통 Reserved Font Name을 쓸 수 없다. 그래서 Pretendard 서브셋은 폰트 안의 이름을 「Pretendard」가 들어가지 않는 이름으로 바꿔야 한다. Noto Sans KR의 예약 이름은 「Source」라, 이름에 「Source」를 넣지 않으면 된다. 게임 · 앱에 넣는 것은 FAQ 1장이 허용 예로 들고, 폰트만 따로 팔지 않으면 된다. 배포할 때는 저작권 고지와 OFL.txt를 함께 둔다. 이 조항과 확인일은 최종 폰트를 정할 때 ops-licensing에 옮긴다. 마루 부리의 라이선스 파일은 아직 찾지 못했다(확인 필요).
- **비교판 1차 판정(2026-10-27, 사용자):** 본문은 Pretendard · Noto Sans KR 둘로 줄였다(Nanum Gothic은 빠진다). 제목은 세리프 둘을 빼고 「본문 굵게」로 가며, 비교판에서는 Noto Sans KR 800으로 골랐다. 숫자 폭은 기본 상태로 고정 폭인 Noto Sans KR이 통과했다. 짝 폰트 한 줄은 Pretendard ↔ Pretendard JP, Noto Sans KR ↔ Noto Sans JP 둘 다 통과했다. 세리프가 빠졌으므로 아래 「후보」 줄의 원칙대로 한 가족을 기본으로 한다. 최종 하나는 Cocos 에디터의 실제 Label에서 고른다(§6 다). 본문 최종이 Pretendard가 되면 두 가지가 함께 정해져야 한다 — 미정
  - 제목을 Pretendard 800으로 바꿀지(한 가족), Noto Sans KR 800으로 둘지(두 가족)
  - 타이머 숫자 폭: Cocos에서 `tnum`이 켜지면 Pretendard 그대로, 안 켜지면 숫자 라벨만 다른 폰트를 쓸지
- **후보:** 본문 — Pretendard(일본어 짝 Pretendard JP), Noto Sans KR(Noto CJK 가족), Nanum Gothic(1층 최소 글자 판정에 쓴 폰트). 제목 — 세리프 둘(Noto Serif KR · 마루 부리)과 「본문 폰트 굵게」를 비교판에 함께 올려 메뉴 타이틀 · 결과 헤더에서 사용자가 고른다(2026-10-16 사용자 결정). 가족이 둘이면 용량 · 빠진 글자 검사 · 라이선스 · 토큰이 두 배라, 세리프가 무드 L1-1의 「우아한 판타지」를 뚜렷하게 더하지 않으면 한 가족으로 간다. Pretendard JP는 원 저장소(orioncactus/pretendard v1.3.9)의 `dist/web/static/pretendard-jp.min.css`로 함께 배포된다(2026-10-27 확인 — GPT 2차의 「다른 배포 주체일 수 있다」는 해소). 라이선스는 모두 OFL로 알고 있으나 후보를 확정할 때 약관 조항과 확인일을 ops-licensing에 적는다 — 미확인
- **서브셋에 남길 글자(결정 7A, 2026-10-16):** 자주 쓰는 한글 2,350자(KS X 1001) + 영문 · 숫자 + 카탈로그가 쓰는 기호. 플레이어가 글자를 입력하는 자리가 없어 화면 글자는 전부 카탈로그에서 오지만, 카탈로그 글자만 남기면 문구를 고칠 때마다 폰트를 다시 만들어야 해서 2,350자를 택했다. 한 굵기 수백 KB로 800KB 상한 안에 들 것으로 보지만 실측(2b)으로 확인한다. 2,350자는 현대 한국어 음절을 다 담지 않아(귀신 이름 · 고유명사 · 의성어에서 빠질 수 있다) 보증이 아니라 기본 글자 모음이다. 진짜 보증은 「`ko.json` · `en.json`의 모든 글자가 최종 서브셋에 있다」는 자동 검사이고, 이 검사를 출시 전 게이트로 둔다(GPT 2차). 빠진 글자가 나오면 예외 목록에 쌓지 말고 서브셋 입력에 카탈로그를 합친다. 기호 목록은 카탈로그 `message` 값에서 뽑는다(`desc`는 화면에 안 뜬다).
- **없는 글자가 나올 때 Cocos Label의 동작(공식 문서 확인):** 미확인

### 1.3 UI 팔레트 — 의미색 표

- **산출물:** 색마다 이름 · 토큰명 · 역할 · 글자색/배경색 · 값 · 쓰는 화면 · 상태 변형(hover · pressed · disabled) · 색 말고 무엇으로 구분되는지 · 대비비 · 예약색 충돌 검사를 한 줄로 적는 표.
- **분류색도 이 표에서(결정 8A, 2026-10-16):** 분류색 셋(화염 · 얼음 · 번개)과 support 색을 UI 색과 같은 표의 행으로 넣고 한 번에 정한다. 백로그 F141(분류색 다시 정하기)은 이 계획이 닫는다. 따로 정하면 한쪽이 바뀔 때마다 다른 쪽의 충돌 검사를 다시 해야 해서다. F141이 적은 불만(화염이 너무 주황, 번개가 가산으로 겹치면 눈부시고 번개답지 않음, 얼음이 너무 밝고 순해 얼음 느낌이 없음)은 이 표의 입력이다. 상태 이상 색 층(F140)도 같은 색을 쓰므로 이 표의 값을 따른다. **최종 판정 자리(GPT 2차):** 분류색은 UI 비교판에서 후보를 좁히고 실제 가산 블렌딩 이펙트 샘플 위에서 최종 판정한다 — 번개 · 화염은 겹칠수록 흰색 쪽으로 밝아져 평평한 색끼리 잰 거리가 실제 화면을 보장하지 않는다. UI 색 · 글자색은 대표 UI 화면에서 최종 판정한다. 코드 반영은 §4의 코드 슬라이스다.
- **충돌 판정(결정 9A, 2026-10-16):** 가. 같은 화면에 함께 뜨는 두 색은 정상 시야와 1 · 2 · 3형 색각 시뮬레이션(Machado 2009, L1-8과 같은 방식) 모두에서 OKLab 거리 0.15 이상이어야 한다. 나. 이를 못 지키면 위치나 모양이 다른 쌍만 허용한다 — 예: XP 바는 화면 맨 아래 전폭이라 위치로 갈린다. 다. 가와 나를 둘 다 못 지키면 분류색이 아니라 UI 색이 비켜 간다. 전투 중에는 마법을 읽는 일이 먼저라서다. 판정 결과는 표의 마지막 열에 쌍마다 적는다. 0.15는 표준 합격선이 아니라 프로젝트 안의 자동 경고값이고, 1층의 0.22(분류 3색끼리)와 목적이 다르다(GPT 2차).
- **작은 요소(2026-10-16 사용자 결정, GPT 2차 지적):** 글자 · 1~2px 선 · 작은 아이콘은 색 거리 검사를 통과해도 바탕 · 외곽선 · 모양 · 위치 중 하나를 반드시 함께 둔다. 면적이 작으면 같은 거리도 덜 구분되기 때문이고, 1층 겹침 「번개 · XP ↔ 아이보리 글자」가 이 경우다. 2층 색 판정의 통과 조건이다.
- **HP 위험(2026-10-16 사용자 결정):** HP 위험 상태에는 색 말고 깜빡이지 않는 고정 표식(바 무늬 · 아이콘 등)을 3층에서 반드시 둔다. 위험 빨강이 화염과 동시에 터지면 색만으로는 섞이고, HP는 가장 중요한 정보라서다. 2층은 이 조건만 3층에 넘긴다.
- **정해진 규칙:** 강조색은 하나이고 주 행동 버튼 전용이다. 포커스 · 선택은 강조색과 다른 행을 둔다. support 분류색도 이 표에서 정한다.
- **골드의 역할(결정 10A, 2026-10-16):** 샴페인 골드는 주 행동 버튼의 강조색 하나로만 쓴다. 테두리 · 문양 같은 장식은 채도 · 밝기를 낮춘 별도 행(빛바랜 골드)으로 두고, 이 행은 누를 수 있다는 뜻을 싣지 않는다. 그래야 「금빛 = 누른다」가 한 뜻으로 남으면서 무드 L1-1의 금빛 장식도 유지된다. 두 골드가 0.15 이상 떨어지지 않으면 모양(채움 대 선)으로 가른다(충돌 판정 나). 장식은 뜻을 전하지 않으면 대비 기준 대상이 아니지만, 경계 · 조작 요소 역할을 맡는 순간 UI 요소 대비 3:1 대상이 되므로 장식선과 기능선을 나눈다(GPT 2차).
- **상태 행(결정 2A, 2026-10-16):** hover · pressed · disabled에 더해 일곱 상태의 색을 표에 둔다 — 키보드 포커스, 선택된 카드, HP 위험 구간, 쿨다운 진행 중 / 준비 완료, 보상 · 새 항목, 패배 · 경고, 화면 뒤 딤(지금 일시정지의 Backdrop). 2층은 색만 정하고, 그 색을 테두리로 쓸지 채움으로 쓸지와 깜빡임 같은 쓰는 방식은 3층 상태 표와 4층 모션이 정한다. hover는 뜻을 싣지 않는 보조 상태로만 둔다(L1-7).
- **행 목록(결정 11A, 2026-10-16):** 아래 행마다 값 · 상태 변형 · 대비 · 충돌 판정을 채운다. 모두 앞의 결정에서 나온 행이다.

  | 묶음 | 행 |
  |---|---|
  | 바탕 | 화면 뒤 딤 · 패널 · HUD 글자 바탕 |
  | 글자 | 기본 · 보조 · 비활성 — 바탕 둘(패널 · HUD 글자 바탕) 각각에서 대비를 잰다(L1-8). 강조 위 글자 — 버튼 채움 위에서 잰다(2026-10-29 더함, §1.3) |

  | 상태 | 포커스 · 선택 · 위험 · 경고 · 쿨다운 진행 / 준비 · 보상 · 새 항목 |
  | 게임 값 | HP · XP |
  | 결과 | 승리 · 패배 · 티어 셋(전역 · 분류 · 개별) |

- **값 형식(결정 12A, 2026-10-16):** 표에는 hex 하나만 적는다(알파가 필요한 행은 8자리). 코드 슬라이스가 `ui/Theme.ts`에서 그 hex 하나로 Cocos `Color` 객체와 리치 텍스트용 문자열을 둘 다 만들게 하고, `ui/ResultController.ts`의 티어색 `TIER_COLOR`도 Theme.ts로 옮긴다. 같은 색이 코드 두 곳에 따로 있으면 한쪽만 고쳐지기 쉬워서다. 코드 작업 전에 `#RRGGBBAA` 순서와 Cocos 리치 텍스트가 8자리 hex를 받는지 탐침하고, 안 되면 RGB와 알파를 나눈다(GPT 2차).
- **비교판 첫 관찰(2026-10-29, `tools/ui/palette-board.html`):**
  - 분류색 — 넷(화염 · 얼음 · 번개 · support)이 정상과 색각 세 가지 모두에서 서로 0.22 이상이고 패널 위에서 3:1 이상인 조합을 OKLCH 격자에서 찾았다. 번개를 노랑으로 두면 조합이 여럿 나오고, 그중 가장 멀리 떨어진 것이 후보 가(화염 `#e34716` · 얼음 `#66bbe3` · 번개 `#f4ea68` · support 남보라 `#5460ba`, 가장 가까운 쌍 0.24)와 후보 나(support 파랑 `#146db7`, 0.23)다. 번개를 보라 쪽으로 옮기면 넷을 0.22로 떼는 조합이 없었다. support의 남보라 · 파랑은 패널 위 3:1을 겨우 넘는다.
  - 같은 화면에 색이 많을 때 — 레벨업 카드 · 결과처럼 색이 15개 넘게 함께 뜨면, 모든 쌍을 0.15 이상 떼는 것은 색각 이상에서 사실상 불가능하다. 그래서 비교판은 행마다 모양(글자 · 큰 글자 · 채움 · 테두리 · 바 · 표식)을 적고, 모양이 다른 쌍은 충돌 판정 나 항목으로 자동 처리한다. 같은 모양인데 0.15에 못 미치는 쌍만 남긴다. 시작값에서 남은 쌍은 HUD 2 · 레벨업 카드 8 · 결과 7이다.
  - 다섯째 표식 색 — 분류색 넷이 표식으로 함께 뜨는 화면에서는, 경고 · 보상 · 새 항목 같은 다섯째 표식 색이 넷 모두에서 0.15 떨어질 자리가 거의 없다. 후보 16개 중 넷 모두를 통과한 것이 없었다. 이 셋은 색이 아니라 모양이나 글자로 갈라야 한다.
  - 바탕색의 「띠 상한 위 3:1」(L1-8) — 어두운 바탕으로는 지킬 수 없다. 바닥 휘도가 0.08이면 순검정 바탕도 2.6:1이 최대이고, 제안 패널은 2.08:1이다. 보조 글자 4.5:1을 지키려면 바탕이 어두워야 해서 두 규칙을 함께 지킬 수 없다. **결정(2026-10-29, 사용자):** 바탕색은 이 3:1 규칙에서 뺀다. 바탕과 바닥은 테두리선 · 그림자 같은 다른 수단이 가르고, 그 모양 · 두께는 3층이 정한다. 기각: 바탕을 밝게 해 3:1을 지키는 안(글자를 어둡게 해야 해서 밤 무드와 반대), 기준 숫자만 낮추는 안(어두운 바탕끼리의 구분이 나아지지 않는다)
- **비교판 판정(2026-10-29, 사용자):**
  - 분류색은 후보 가로 정했다 — 화염 `#e34716` · 얼음 `#66bbe3` · 번개 `#f4ea68` · support `#5460ba`. 최종 판정은 실제 가산 블렌딩 이펙트 위에서 한다(결정 8A).
  - support의 표시 방식(사용자 방향) — support 마법은 적에게 날아가지 않고 플레이어의 능력을 강화한다. 그래서 효과가 켜져 있다는 것을 플레이어 주변의 오라 같은 것으로 보이고, 오라의 모양과 색은 마법마다 다르다. 전투 중 support는 발사체 셋과 모양 · 위치가 다르므로, 0.22 기준은 L1-8 원래대로 화염 · 얼음 · 번개 셋에만 건다. 비교판이 넷으로 잰 것은 후보를 찾을 때 더한 조건이다. support 분류색은 UI(슬롯 아이콘 · 카드 분류 표식)에만 쓰는 값으로 남보라를 둔다. 오라 색은 이 표가 아니라 support 마법을 만들 때 마법마다 정한다. support 마법은 아직 데이터에 없다. 예외가 하나 있다 — 마법 결투(임시, 기획 magic-system-mage §3.5)는 적 하나에 표식을 붙이므로, 이 마법을 남기면 그 표식은 적 위에서 다른 분류색 · 상태 색 층(F140)과 함께 본다.
  - 충돌 판정 — 남았던 두 쌍(경고 ↔ 번개, 보상 ↔ 번개)은 「나 · 모양이 다르다」로 정했다. 그래서 경고 · 보상 표식은 분류 아이콘과 다른 모양이어야 한다 — 3층에 넘긴다. AI가 제안한 15쌍의 판정은 바꾸지 않았다.
  - 무드 1차 — 패널 테두리(장식)가 너무 어둡고, 버튼 바탕(강조)이 너무 탁하고, 카드 설명 글자(보조 글자)가 너무 어두워 비활성처럼 보였다. 비교판 2판에서 셋의 기본값을 바꿨다 — 장식 `#8a7752` → `#b39b70`(밝기 L 0.58 → 0.70), 강조 `#dcbc7e` → `#ebc874`(채도 C 0.088 → 0.111, 밝은 노랑 쪽으로는 가지 않았다), 보조 글자 `#b3ad9e` → `#d0c9b9`(L 0.75 → 0.84, 패널 위 10.2:1). 보조 글자가 기본 글자와 밝기로 덜 갈리므로(L 차이 0.20 → 0.11), 두 글자의 위계는 크기 · 굵기가 더 맡는다.
  - 무드 2차 — 모달 테두리가 훨씬 밝아 모달이 확 눈에 띄면 좋겠다. 비교판 3판에서 장식을 밝은 샴페인 `#e6d3a3`(L 0.87, C 0.066)으로 바꿨다. 결정 10A는 장식을 「채도 · 밝기를 낮춘」 골드로 적었는데, 밝기는 강조색과 비슷해지고 채도만 낮게 남는다. 두 골드의 거리는 0.15에 못 미치므로 10A의 예비 규칙대로 모양(선 대 채움)이 가른다. 카드 칸 선은 같은 장식색을 45%로 흐리게 그렸다 — 다 밝히면 포커스 · 선택 테두리와 겹쳐 보여서다. 밝아진 장식 테두리는 포커스 고리(아이보리)와도 색이 가까워졌다(가장 가까운 시야에서 0.10). 그래서 둘은 위치(모달 가장자리 대 카드 · 버튼 둘레)와 두께로 가른다 — 3층에 넘긴다.
  - 버튼 글자 — 밝은 채움 위 글자는 어두운 색이 표준이라, 「강조 위 글자」 행을 새로 두고 대비를 강조색 위에서 잰다. 짙은 네이비 `#161d2e`는 10.4:1이고, 아이보리 글자는 1.4:1로 읽히지 않는다. 사용자는 3판을 더 고치지 않고 다음 단계로 넘어갔다 — 3판 값을 HTML 1차 값으로 두고, 최종은 Cocos 대표 화면에서 본다.
  - 모달 모양(2026-10-29 확인) — 모달은 사각형이 아니어도 된다. 위아래가 물결인 모양처럼 그림이나 도형으로 그릴 수 있는 모양이면 Cocos에서 만들 수 있다: 바깥이 투명한 그림을 Sprite에 넣고 안쪽 내용은 자식 노드의 Widget 여백으로 잡는다. 크기가 바뀌면 물결 띠를 Tiled로 따로 깔고, Graphics 곡선으로 그리거나, 내용까지 자를 때는 Mask를 쓴다(Cocos 3.8 매뉴얼). 모양 자체는 3층이 정한다.
  - 이 판정의 자리 — 여기서 고르는 UI 색은 HTML 위의 1차 값이다. UI 색 · 글자색의 최종 판정은 폰트를 고른 뒤 대표 UI 화면(Cocos)에서 한다(§1 진행 순서 · 결정 8A).
- **값:** 분류색 넷은 위 판정. 나머지는 비교판 2판의 시작값이고 무드 2판 판정을 기다린다 — 미정

### 1.4 간격 · 격자 단위

- **산출물:** 여백 배수 단위, 최소 클릭 크기 토큰 값, HUD 모서리 간격 정책.
- **단위(결정 13A, 2026-10-16):** 화면의 모든 여백과 간격은 4px의 배수로만 쓴다. 주로 쓰는 값은 8 · 16 · 24 · 32이고, 4는 작은 라벨 안쪽 여백처럼 아주 좁은 자리에만 쓴다. 지금 토큰 `GAP` 8 · `EDGE_MARGIN` 24가 이미 이 단위 안에 있다. 단위가 없으면 화면마다 여백이 제각각이 되고, 맞추려면 사용자가 에디터에서 노드를 다시 배치해야 한다.
- **누르는 영역:** 보이는 크기 토큰(예: `SKILL_SLOT` 48)과 따로 누르는 영역 토큰을 두고 최소 32×32 논리 px로 한다(L1-7).
- **HUD 모서리 간격:** 값 하나가 아니라 「기본 여백 + 안전 영역」을 더한 값으로 둔다. 안전 영역은 화면이 가려지는 자리(휴대폰 위쪽 카메라 홈 등)만큼 더하는 값이고, v1 PC에서는 0이다. 나중에 모바일을 할 때 그 값만 넣는다.
