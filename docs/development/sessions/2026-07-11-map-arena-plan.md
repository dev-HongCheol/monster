## 1. 배경 — 왜 지금 맵인가

지금 게임에는 공간의 뼈대가 없다. 플레이어는 경계 없이 무한히 걸어가고(`PlayerController._move`에 클램프가 없다), 적은 플레이어 기준 반경 350에 무작위로 스폰되며(`EnemySpawner._spawnEnemy`), 카메라는 팔로우 스크립트가 없어 정적이다. 배경은 placeholder 수준의 `Backdrop` 노드 하나다. 아레나와 카메라는 이후 모든 시스템이 그 안에서 도는 토대라, 늦게 만들수록 "무한 공간을 가정한 코드"에 경계를 소급 이식하는 비용이 커진다. 지금 정해 두면 이후 슬라이스(게임 플로우, 스폰 튜닝 등)가 정해진 아레나 위에 얹힌다.

이 슬라이스는 P0 코어 루프(P0-1~P0-4)가 끝난 뒤 v1의 '넓이'를 채우는 테마 J의 첫 조각이다.

## 2. 확정한 결정 (이 대화에서 사용자와 합의)

- **아레나 모델 = 경계형(bounded).** 유한한 사각 플레이 공간에 외곽 벽을 두고, 플레이어 위치를 그 안으로 클램프한다. (대안이던 자유 스크롤은 뱀서식 무한 필드였으나, 벽의 긴장감·포지셔닝을 살리는 경계형을 택했다.)
- **카메라 = 팔로우 + 벽 클램프.** 카메라가 플레이어를 따라가되, 아레나 벽에서 멈춰 바깥이 보이지 않게 한다.
- **첫 맵 = 서울.** 한강과 두세 개의 대교, 각 구의 유명 건물을 배경과 장애물로 쓴다. **단 이번 슬라이스는 배경(시각 placeholder)까지만** 넣는다. 건물·한강을 실제 충돌 장애물로 만드는 것, 한강을 건널 수 없는 배리어로 만드는 것, 그에 따른 적 경로탐색은 전부 후속 슬라이스로 이월한다.
- **다중 맵은 확정 로드맵이다.** 서울 다음으로 부산·도쿄·오사카 등 여러 맵이 추가되며, 맵마다 구조·크기·장애물의 종류와 위치가 다르다. 이 사실이 아래 아키텍처 결정을 좌우했다.

## 3. 아키텍처 결정 — 데이터 주도 맵 포맷(C)

아레나(경계·크기·배경)를 코드에서 어떻게 표현할지 세 방식을 검토했다.

- **A. 순수 상수 모듈** — 아레나 경계를 순수 모듈 상수로 둔다. 최소·최속에 테스트하기 쉽지만 단일 맵 하드코딩이라, 다중 맵이 오는 순간 결국 데이터로 리팩터해야 한다.
- **B. 씬 노드 기반** — 아레나 경계를 씬 노드의 크기에서 읽고 배경·건물을 에디터에 배치한다. 시각적으로 배치하기 좋지만 로직이 씬에 묶여 단위 테스트가 어렵고 맵 데이터가 씬 파일에 묻힌다.
- **C. 데이터 주도(map JSON)** — 맵 포맷을 한 번 정의하고 맵마다 그 포맷을 JSON으로 채운다. 부산을 추가하려면 `busan.json` 한 장이면 되고 코드는 안 바뀐다.

**택: C.** 다중 맵이 확정 요구사항이고, 맵마다 다른 크기·구조·장애물 위치가 곧 데이터 스키마가 표현하는 바이며, 코드베이스가 이미 데이터 주도(마법·적·카드가 전부 `DataManager` + JSON)라 맵만 예외를 둘 이유가 없다. A는 지금 최소지만 부산이 오는 순간 C의 작업을 다시 하면서 소비처를 상수에서 데이터로 바꾸는 추가 비용이 든다.

**건물·장애물의 데이터화 방식(향후 슬라이스에서 구현):** 좌표를 촘촘히 나열하지 않는다. 건물 하나는 `{ prefab, x, y, rot? }` 한 줄로 적고, 건물의 크기·모양·충돌·아트는 그 프리팹이 자기 안에 들고 있다(맵 JSON은 위치만 지정). 한강처럼 꾸불꾸불한 지형은 굴곡을 맵 고유 프리팹의 폴리곤 콜라이더에 그려 넣어 한 점으로 배치하거나, 외곽선 점 목록으로 데이터에 직접 둔다. 어느 쪽이든 좌표는 손으로 타이핑하지 않고 에디터에서 그려 내보낸다.

## 4. Cocos 3.8 기능 검증 (Context7 공식 문서)

C가 의존하는 기능이 실제로 가능한지 공식 매뉴얼로 확인했다.

- **다각형 콜라이더(`PolygonCollider2D`)** — 임의 다각형 충돌을 지원한다. 다만 내부가 Box2D라 오목하거나 정점이 8개를 넘는 폴리곤은 볼록 조각들로 자동 분할된다. 따라서 꾸불꾸불한 한강을 단일 폴리곤으로 두는 것은 비효율이고, 타일맵이나 여러 조각으로 나누는 편이 낫다(장애물 슬라이스에서 확정).
- **타일맵(`TiledMap`, TMX/Tiled)** — Tiled 에디터의 `.tmx`를 임포트해 레이어별 노드를 자동 생성한다. 공식 예제가 `instantiate(prefab)` + `setPosition` + `addUserNode`로 프리팹을 좌표에 배치하는 것을 그대로 보여준다. "프리팹 + 좌표" 장애물 배치가 문서화된 표준 패턴임을 확인했다.
- **런타임 프리팹 인스턴스화 + 위치 지정** — 위 예제로 확인. JSON 리소스 로드는 이미 마법·적 데이터로 검증된 경로다.
- **카메라 팔로우** — 지원한다. 다만 공식 간단법("Camera를 Player 자식으로 붙이기")은 벽 클램프가 되지 않는다(플레이어를 따라 벽 너머까지 넘어간다). 그래서 경계형은 카메라 위치를 직접 계산해 아레나로 클램프하는 `CameraController` 스크립트가 필요하다. 또한 게임 Canvas의 `Align Canvas With Screen`을 꺼야 카메라가 독립적으로 움직인다(HUD는 별도 UICanvas라 영향 없다).

결론: **C의 전 기능이 Cocos 3.8에서 가능하다.**

## 5. 이번 슬라이스의 맵 데이터 포맷 (최소)

포맷은 최소로 시작해 능력이 붙을 때마다 필드를 늘린다(버전 관리). 지금 필요한 것은 크기와 배경뿐이다.

```json
{ "id": "seoul", "size": [2400, 2400], "backdrop": "maps/seoul/backdrop" }
```

`obstacles`·`regions` 같은 장애물 필드는 이번에 스키마에 넣지 않는다. 필요한 슬라이스에서 추가한다. `size`(2400×2400)와 카메라 줌은 placeholder 값이며 인게임에서 튜닝한다.

## 6. 구현 범위 (이번 슬라이스)

### 신규 파일

- **`logic/ArenaLogic.ts` (순수 로직, cc import 없음)** — 아레나 계산을 순수 함수로 뽑아 TDD 대상으로 삼는다.
  - `clampToArena(x, y, radius, arena)` — 반경을 고려해 위치를 아레나 안으로 클램프한다(엔티티가 벽을 파고들지 않게). 플레이어 이동과 적 스폰이 공유한다.
  - `cameraFollowPosition(playerX, playerY, viewHalfW, viewHalfH, arena)` — 플레이어를 따라가되 뷰 가장자리가 아레나 밖으로 나가지 않도록 클램프한 카메라 위치를 돌려준다.
- **`systems/MapManager.ts` (Cocos)** — 활성 맵 데이터(`seoul.json`)를 읽어 아레나 크기를 노출하고 배경 스프라이트를 구성한다. 아레나 크기의 단일 출처가 되어 카메라·플레이어·스폰이 여기서 읽는다.
- **`components/CameraController.ts` (Cocos)** — 게임 Camera 노드에 붙어, 매 프레임 카메라 위치를 `cameraFollowPosition` 결과로 설정한다. `onLoad`에서 `orthoHeight`를 고정값으로 세팅해 F9(카메라 크로스머신 churn)를 원천 차단한다.
- **`resources/data/maps/seoul.json`** — 위 최소 포맷.

### 수정 파일

- **`components/PlayerController.ts`** — `_move`가 이동 후 최종 위치를 `clampToArena`로 벽 안에 가둔다. (기존 이동 로직·주석은 유지하고 클램프만 덧붙인다.)
- **`systems/EnemySpawner.ts`** — `_spawnEnemy`의 반경 350 스폰 위치를 `clampToArena`로 아레나 안에 가둔다(플레이어가 벽 근처일 때 벽 밖 스폰 방지). 이번 스코프의 유일한 스폰 코드 변경이다.
- **`systems/DataManager.ts`** — 기존 JSON 로드 경로에 맵 데이터 로드를 더한다(마법·적과 동일 패턴). 활성 맵은 당분간 `seoul` 고정.
- **`game/assets/scenes/main.scene`** — 게임 Canvas의 `Align Canvas With Screen` 해제, Camera에 `CameraController` 부착, `MapManager` 노드 추가, `Backdrop`을 아레나 크기에 맞춤, `orthoHeight` 고정. (씬 편집은 7단계 사용자 몫이며, 상세 레시피는 QA 문서에 적는다.)

### 데이터 흐름

`MapManager`가 `seoul.json`을 읽어 아레나 크기와 배경을 구성한다. `CameraController`·`PlayerController`·`EnemySpawner`가 아레나 크기를 `MapManager` 한 곳에서 읽고, 실제 계산은 순수 `ArenaLogic`이 한다.

## 7. 명시적 이월 (이번에 안 함)

- **건물·한강의 실제 충돌 장애물화** — `obstacles` 스키마, 프리팹 배치, `PolygonCollider2D`·`TiledMap` 선택.
- **한강을 건널 수 없는 배리어로** — 대교를 통과 지점(초크포인트)으로.
- **적 경로탐색** — 현재 적은 직선 추적(`_followPlayer`)이라 장애물을 못 피한다. 장애물이 적을 막으려면 회피·경로탐색이 필요하고, 이는 대량 적 성능(G1, v2 이월)과 얽힌다. 장애물 슬라이스에서 "적 관통 vs 경로탐색"을 결정한다.
- **다중 맵 셀렉터** — 지금은 `seoul` 고정. 맵 선택·전환은 부산 등 두 번째 맵이 실제로 생길 때.
- **최종 픽셀 아트** — 서울 배경·건물의 최종 아트는 아트 파이프라인 단계(로드맵 7-9주).
- **카메라 스무딩** — 우선 하드 팔로우로 넣고, lerp·데드존 같은 게임필은 후속.

## 9. TDD 대상과 검증

순수 로직은 테스트를 먼저 쓴다(RED → GREEN).

- **`ArenaLogic.clampToArena`** — 아레나 밖 위치가 반경만큼 안쪽 벽으로 클램프되는지, 안쪽 위치는 그대로인지, 반경이 아레나 절반을 넘는 경계 조건.
- **`ArenaLogic.cameraFollowPosition`** — 플레이어가 중앙일 때 카메라가 플레이어와 일치하는지, 벽 근처일 때 뷰 가장자리가 아레나 가장자리에 맞춰 멈추는지.

카메라·씬·배경 배선은 Cocos 프레임워크에 의존하므로 순수 테스트 대상이 아니며 7단계 수동 QA로 검증한다(플레이어가 벽에서 멈춤, 카메라가 팔로우하다 벽에서 멈춤, 적이 아레나 안에만 스폰, 서울 배경 표시).

## 10. 위험·미결

- **아레나 크기·카메라 줌 값**은 placeholder다. 화면(1280×720) 대비 이동 여유와 체감을 보고 인게임에서 튜닝한다.
- **경계형 전환의 밸런스 영향** — 무한 후퇴가 사라지면서 난이도가 오를 수 있다. 이번엔 구조만 넣고, 벽이 난이도에 주는 영향은 장애물·밸런싱 단계에서 관찰한다.
- **씬 diff** — 카메라 정책을 고정값으로 못박아 F9를 없애되, 첫 커밋에서 기존 `_orthoHeight`(1175.29) 대비 큰 diff가 한 번 난다(의도된 정리).
